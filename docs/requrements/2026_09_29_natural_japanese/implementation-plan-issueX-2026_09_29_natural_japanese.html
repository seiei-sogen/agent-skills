1. 計画の状態

実装済みの計画である。Task 1〜9 はすべて完了し、検証結果は「実装結果と検証結果」に記録した。実装後に ponytail-review によるレビューを2巡行い、重複の削除と矛盾の解消を反映した。計画からの調整と要件側の明確化は同節「計画からの調整」にある。

作業は main 上で完結させ、ブランチと PR は作らない（要件「前置き」）。commit と push は親パイプラインが行い、本計画には PR 作成タスクを置かない。

3.4. 破綻条件と検証項目

要件の失敗例（例外と失敗時の挙動、change_guidance の risk）に加え、計画段階で見つけた破綻条件は次の3件である。いずれも検証項目へ結び付ける。

  1. 規則本文をそのまま移すと output.line-break-each-line の既定が2通りになる。 旧スキルの本文は「指定がなければ needs-confirmation とし」と書いており、D-08 と AC-16 の not-applicable と矛盾する。要件 FR-02 と D-08 にこの1か所の置き換えを明記した。生成スクリプトが置き換えを行い、検証コマンドの grep で旧文言が0件、新文言が1件であることを確認する。

  2. 本文の例示に実在の ID を表の行として書くと AC-01 の48行が崩れる。 要件の ID_RE はファイル全体を数えるため、Phase 6 の形式例や説明で | `sentence.xxx` | の形の行を書いてはならない。形式例は {ID} のプレースホルダーだけを使う。Task 6 の完了判定で AC-01 を再実行する。

  3. 「岩淵ルールで直して」が polish のままだと ID が出ず T-01 が成立しない。 規則や ID を名指しする依頼を diagnostic の要求として扱う判定を「入力と出力モード」節に置く。要件 FR-07 に同じ文を明記した。T-01 のレビューで確認する。

13. 判断から学べること

  1. 安定 ID を持つ表を別ファイルへ移すときは、原本から生成するスクリプトと、移設先を検査するスクリプトを計画に埋め込む。 兆候は、ID の綴りを受け入れ条件で機械照合する要件と、commit 済みの原本（バックアップ）があること。 使える条件は、原本が正規表現で読める形式で、移設先の列追加が機械的に決まること。 使わないほうがよい条件は、移設と同時に本文を大きく書き換える場合で、そのときは手書きと差分レビューのほうが短い。 参照は Task 1、「補助スクリプト」、D-03。検索語は "golden file"、"table migration script"。

  2. 件数を固定する grep の受け入れ条件があるときは、同じパターンの例示を本文に書かない制約を計画に置く。 兆候は、grep -c でファイル全体の件数を固定する AC と、同じ形式を説明する形式例が本文にあること。 使える条件は、形式例をプレースホルダーで書けること。 使わないほうがよい条件は、実例が読者の理解に不可欠な場合で、そのときは AC の正規表現を節の範囲に限定する。 参照は破綻条件 2、Task 6、AC-01。検索語は "count-based acceptance check false positive"。

  3. 任意の要件は、主となる定義が毎回読まれる場所にあり、参照資料が条件付きにしか読まれないなら実施しない。 兆候は、「任意」と書かれた FR と、1000行を超える参照資料への注記。 使える条件は、注記が主表の情報の再掲で、後から別の変更として追加できること。 使わないほうがよい条件は、参照資料が判断の主な材料になっている場合で、そのときは注記が ID の付与を直接助ける。 参照は P-11、D-09、FR-09。検索語は "YAGNI documentation cross-reference"。
