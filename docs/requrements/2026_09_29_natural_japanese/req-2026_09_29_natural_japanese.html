2. 概要

スキル /home/agir_wsl/develop/ghq_repos/github.com/seiei-sogen/agent-skills/skills/natural-japanese/rewrite-japanese-with-iwabuchi-rules/SKILL.md を、 /home/agir_wsl/develop/ghq_repos/github.com/seiei-sogen/agent-skills/skills/natural-japanese/natural-japanese-rewriter/SKILL.md にマージする。

ただし、natural-japanese-rewriter の既存の「項」の概念や、 /home/agir_wsl/develop/ghq_repos/github.com/seiei-sogen/agent-skills/skills/natural-japanese/japanese-kwja-analyze/SKILL.md の KWJA での解析（分かち書き、単語正規化、形態素解析、固有表現認識、言語素性、係り受け、述語項構造、橋渡し照応、共参照、談話関係）などの言語学的概念を上位の概念とし、 rewrite-japanese-with-iwabuchi-rules のルールを、これらの概念で上位に昇華するような形にする。

また、「これは sentence.keep-subject-and-predicate-close だ」のように、 rewrite-japanese-with-iwabuchi-rules の規則をエージェントが作業しやすい形で利用できるようにする。

あくまで natural-japanese-rewriter 単独で、rewrite-japanese-with-iwabuchi-rules のルールがマージされている形にする。 natural-japanese-rewriter 内から rewrite-japanese-with-iwabuchi-rules を呼び出す形にはしない。

3. 背景

現行の natural-japanese-rewriter は、KWJA の解析ファイルから述語項グラフの分析メモを作り、談話・情報構造・語用論・対人関係・文体の制約を固定してから修復箇所を決めて生成する6 Phase 構成である （skills/natural-japanese/natural-japanese-rewriter/SKILL.md:77-209）。

一方の rewrite-japanese-with-iwabuchi-rules は、岩淵「悪文」メモ由来の48規則を文章へ直接照合し、各規則を pass / not-applicable / actionable / needs-confirmation の4状態に分類して、規則 ID 付きで報告する単独スキルである （skills/natural-japanese/rewrite-japanese-with-iwabuchi-rules/SKILL.md:34-60）。 起動条件は「岩淵ルールで直して」など規則を名指しする依頼に限られ、一般的な「校正して」「自然にして」からは除外されている（同 :9-10）。

両者は同じ悪文を別の語彙で扱っている。 たとえば sentence.keep-subject-and-predicate-close は、分析メモではガ格の項と述語の基本句距離として観測でき、sentence.minimize-passive-voice は voice: passive と動作主の復元可能性として観測できる。 規則を文字列照合のチェックリストのまま残すと、同じ判断を二つのスキルが別々に行い、ID による説明責任と KWJA の根拠が結びつかない。

調査で確認した事実（pre-investigation-report-2026_09_29_natural_japanese.json）のうち、要件に影響するものは次のとおりである。

  • 48個の ID は output 1件、sentence 21件、word-choice 16件、honorific 10件で重複がない（スクリプトで検証済み）。

  • 旧スキルは ID を「省略、改名、再利用しない」公開識別子と定めている（rewrite-japanese-with-iwabuchi-rules/SKILL.md:36-37）。元メモは通し番号が原本とずれている可能性を注記しており（docs/sample/iwabuchi-akubun/memo.md:65）、番号は識別子にならない。

  • 追跡ファイルの中で旧スキルを参照するのは旧スキル自身、docs/backups、本要件だけで、README にも他スキルにも参照がない（git grep 0件）。

  • 分析メモの rewrite_targets は analyzer 側では空配列としてしか現れず、要素の形も埋める手順もない（natural-japanese-rewrite-analyzer/SKILL.md:90）。実質的な生産者は親の Phase 3 である（natural-japanese-rewriter/SKILL.md:145）。

  • analyzer の issues[].code は語彙が未定義である。9種の問題コード表はコミット f8f85a4 で削除され、参照文だけが残っている（natural-japanese-rewrite-analyzer/SKILL.md:74）。

  • analyzer は KWJA の解析事実と LLM の判断を区別して記録する（同 :25-27）。

  • references/detailed-rules.md は分割前の保存版で Phase 3 の条件付き読み込みに限られ（natural-japanese-rewriter/SKILL.md:142）、48規則の ID はどこにも現れない。

  • 変更前スナップショット docs/backups/2026_09_29/natural-japanese/ は現行と完全一致し、ID の比較基準とロールバック先になる。

4. 目的

natural-japanese-rewriter を、次の状態にする。

  1. 48規則を、項・付加部・骨格、KWJA の11処理、Phase 2 の5層という既存の上位概念に対応づけて内蔵する。規則は「文字列に照らすチェック項目」ではなく、「分析メモと上位レイヤーのどの観測から判定する規範か」として定義される。

  2. 各規則を安定 ID で参照でき、エージェントが判定、修正理由、要確認、診断出力で ID をそのまま使える。

  3. 旧スキルのトリガー語、出力形式、監査機能を引き継ぎ、natural-japanese-rewriter 単独で完結する。旧スキルは削除し、内部から呼び出さない。

5. 利用者と利用シナリオ

主な利用者は、README、仕様書、技術記事、コードコメント、UI 文言、issue、PR 説明、業務連絡、職務経歴書などの日本語を推敲する Claude Code / Codex の利用者と、その依頼を受けるエージェントである。

代表的な利用シナリオは次のとおりである。

  • 「自然にして」と頼まれ、既定のデストロイモードで書き直す。内部では48規則を照合し、確定できない点だけを ID 付きの 要確認 で返す。

  • 「岩淵ルールで直して」「ルールID付きで推敲して」と頼まれ、diagnostic モードで適用した規則 ID と対象箇所を示す。

  • 「48規則で監査して」と頼まれ、本文を変えずに48行の判定一覧を返す。

  • 「safe で校正して」と頼まれ、原意を保つ範囲で actionable の規則だけを最小修正する。

  • エージェントが分析メモの述語項構造を読み、「これは sentence.state-changed-subject-explicitly だ」と判断して修復理由に ID を残す。

8. 機能要件

8.1. FR-01 トリガー語と起動条件を引き継ぐ

natural-japanese-rewriter の description に、旧スキルのトリガー語を加える。 少なくとも「岩淵ルールで直して」「48規則で悪文をチェックして」「ルールID付きで推敲して」「文の組み立て・用語・敬語を網羅的に点検して」「監査」を含める。 旧スキルの「一般的な校正・自然化依頼には使わない」という除外文は引き継がない。 既存のトリガー語（「自然にして」「翻訳調を直して」「読みやすくして」「LLMっぽさを消して」「リライトして」「校正して」）と、safe 引数の説明は維持する。

description は validator の上限である1024文字以内に収める（現状264文字と239文字）。name は natural-japanese-rewriter のまま変えない。

8.2. FR-02 規則 ID 表を SKILL.md 本体に置く

48規則の ID 表を natural-japanese-rewriter/SKILL.md 本体に置く。 表は既存の形式（| ID | 規則 | の Markdown 表をカテゴリ見出しごとに置き、ID をバッククォートで囲む）を保ちつつ、FR-03 の上位概念と手がかりの出所を列として加える。 規則本文は旧スキルの一文をそのまま移す。 ただし output.line-break-each-line の本文にある「指定がなければ needs-confirmation とし」は、D-08 に合わせて not-applicable に置き換える。置き換えはこの1か所に限る。

新しい参照ファイルは作らない。 references/detailed-rules.md は現状どおり Phase 3 で条件付きにだけ読む。 SKILL.md の行数は400行以下を目安とし、超える場合は表以外の重複記述を削って収める。

8.3. FR-03 規則を上位概念へ対応づける

各規則に、上位概念（用語の10種から1つ）と手がかりの出所（P1 / P2 / P4 / LLM から1つ）を対応づける。 推奨する対応表を次に示す（D-01）。実装者は「主な手がかり」の文言を分析メモの実フィールド名に合わせて調整してよいが、ID、件数、上位概念と出所の語彙は変えない。

LLM を出所とする規則は、KWJA の出力に直接の根拠がないことを意味する。 これらの判定は分析メモの解析事実と混ぜず、diagnostic では LLM の判断であることが分かる形で示す。

8.4. FR-04 Phase 3 で規則の状態を判定する

Phase 3「修復箇所を決める」に、規則の状態判定を加える。

  1. 48規則をすべて内部で照合し、各 ID を4状態のいずれかにする。判定の材料は FR-03 の出所に従い、P1 は分析メモと KWJA 出力、P2 は Phase 2 で固定した制約、LLM は原文と文脈から判断する。P4 の規則（output.line-break-each-line）は、Phase 3 で改行単位の指定の有無から状態を決め、Phase 4 の生成時に適用する。

  2. actionable と needs-confirmation の規則は、分析メモの rewrite_targets の対応する要素に rule_ids として記録する。主となる ID を先頭に、関連 ID を続ける。現行 SKILL.md の Phase 3 は rewrite_target と単数で書いているが、分析メモのキーは rewrite_targets であり、統合後はキー名に合わせる。

  3. rewrite_targets の各要素は、少なくとも decision（repair / keep / confirm）、rule_ids（空配列可）、source（kwja / llm）を持つ。actionable は repair、needs-confirmation は confirm、項を無理に補わない一覧に当たる箇所など意図的に残す箇所は keep とする。keep の箇所に付けた規則の状態は pass とする。規則違反がない自然さ目的の書き直しも decision: repair、rule_ids: [] で記録する。要素は Phase 3 で親スキルが分析メモの rewrite_targets に追記し、LLM 出所の判定は同じ要素の source: llm で記録し、predicates、arguments、entities、issues、ambiguities には KWJA 出力にない根拠を書き込まない。本文を変更しない出力先では repair は修正案の提示を意味し、rule_ids: [] の書き直しは記録しない。規則に対応しない confirm は、判定行では ID 欄を - とし、監査一覧では表の直後に ID なしで添える。既存の修復トリガー（主体の複数候補、係り先の曖昧さなど）による対象には、該当する規則 ID があれば同じ欄に付ける。要素の形は親スキルが定める記録であり、analyzer の出力契約は変えない。

  4. needs-confirmation は decision: confirm とし、Phase 6 の 要確認 に ID 付きで出す。

  5. pass と not-applicable は記録するだけで、監査一覧を除き出力しない。

既存の修復トリガーと非トリガーの一覧（natural-japanese-rewriter/SKILL.md:122-140）は維持する。 規則の判定は、これらの一覧を ID で言い換える位置づけであり、同じ判断を二重に書かない。

Phase 3 の完了条件に「48個の ID すべてに状態が付き、actionable と needs-confirmation が rewrite_targets に rule_ids 付きで記録されている」を加える。

8.5. FR-05 モードごとに規則を扱う

両モードで共通する扱いは次のとおりとする。

  • 48規則をすべて照合する。

  • コード、コマンド、ファイルパス、API 名、設定値、数値、固有名詞、引用、リンク、構造化データを保護し、原文にない事実を作らない。規則を理由に保護範囲を変えず、保護範囲にかかる箇所への規則の判定は not-applicable とする。

  • needs-confirmation は省略せず 要確認 に出す。本文を変更しない出力先では、FR-07 の監査一覧または判定行に含める。

セーフモードでは、旧スキルの最優先原則をそのまま適用する。 actionable は原意・事実・仕様・技術的意味を変えずに修正できる問題に限り、規則を機械的に適用せず、読みやすさや正確さが実際に上がる変更だけを採用する。 規則どうしの判断が衝突した場合は、原意の保持、文脈・係り受け・否定範囲・用語の正確さ、読み手にとっての明確さ、語感・敬語・簡潔さ、行配置の順に優先する。

デストロイモードでは、48規則を自然さの判定基準として使う。 既存の方針どおり文の分割・結合、構成の変更、語の置き換え、冗長な情報の削除を積極的に行い、actionable の判定と修正もデストロイモードが許容する意味の変化の範囲で行う。 needs-confirmation の箇所はもっとも自然な解釈を選んで actionable として扱ってよい。ただし、原文にない主体、対象、動作主、原因、目的、数値、時刻、確実性を確定させる解釈は選ばず（word-choice.match-expression-to-facts、sentence.state-changed-subject-explicitly、sentence.minimize-passive-voice などが該当する）、needs-confirmation のまま 要確認 に残す。 本文を変更しない出力先（レビューだけ、監査だけ）では、needs-confirmation を actionable に倒さず Phase 3 の判定をそのまま出す（D-07）。 規則の優先順位は、既存のデストロイモードの優先順位（自然さ最優先）を上位とし、旧スキルの順序は規則どうしの衝突を解くときだけ使う。

8.6. FR-06 Phase 5 で再照合する

Phase 5「候補文を検査する」に、両モード共通で「候補文に対して48規則を再照合し、新たな actionable を作っていないことを確認する」を加える。 デストロイモードは候補文を再解析しないため LLM 出所で再照合し、セーフモードは意味回帰検査で再解析した分析メモを使う。 新たな actionable が見つかった場合は候補を修正して再照合する。 再照合は意味回帰検査と同じく最大3巡とし、3巡で解消しない actionable は needs-confirmation に変えて Phase 6 の 要確認 に ID 付きで出す。 3巡で needs-confirmation に変えた項目と、再照合で新たに検出して修正した項目は、原文用の分析メモの rewrite_targets に追記し、後者は diagnostic の適用ルールにも載せる。本文を変更しない出力先では Phase 5 を行わない（D-07）。 セーフモードの意味回帰検査（KWJA 再解析、SEMANTIC_DRIFT）は変更しない。

Phase 5 の完了条件に「候補文で actionable の規則が0件」を加える。

8.7. FR-07 出力形式を統合する

「岩淵ルールで直して」「ルールID付きで推敲して」のように規則や ID を名指しする依頼、および適用した規則の提示を求める依頼は、diagnostic の要求として扱う。 この判定は「入力と出力モード」の出力モードの定義に書く。

polish（既定）は現状どおり本文中心とし、要確認 の各項目を規則 ID 付き（- {ID}: {原文だけでは判断できない点}）にする。 規則に対応しない 要確認（KWJA と本文の食い違いなど）は ID なしで出す。 適用した規則の一覧は出さない。

diagnostic は既存の3項目（問題のある述語、不明または競合していた項、修復で明確になった関係）に加えて「適用ルール」を出す。 形式は旧スキルの - {ID}: {対象箇所と修正内容} とし、actionable がなければ「適用ルール: なし」と書く。 LLM を出所とする規則は、KWJA の根拠がない判断であることが分かるように示す。

監査一覧は、ユーザーが監査結果または全規則の判定を求めた場合だけ、規則の定義順で出す。 形式は旧スキルの表（| ID | status | 根拠または対象箇所 |）をそのまま使う。 監査だけを求められた場合はレビューのみと同じく本文を変更せず、監査一覧と解析ファイルのパスだけを出す（ID 付き 要確認 の別掲と診断は出さない）。監査と推敲の両方を求められた場合は diagnostic として扱い、その末尾に加える。ID が複数箇所で異なる状態になる場合は、needs-confirmation、actionable、pass、not-applicable の順で強い状態を1つ書き、3列目に箇所ごとの内訳を書く。

ユーザーが「レビューだけ」「直さないで」と指定した場合は、本文を変更せず、actionable と needs-confirmation の判定を rewrite_targets の要素ごとに1行の ID / 対象箇所 / 問題 / 修正案 の形で出し、解析ファイルのパスを添える。診断の他の項目と 要確認 の別掲は出さず、修正案は Phase 4 の生成方針で作る。needs-confirmation は修正案の代わりに判断に必要な情報を示し、LLM 出所の行は末尾に （LLM 判断） を付ける。 出力モードを増やさず、開始時に確定する出力先（ファイル編集、応答本文、本文を変更しない）で扱う。本文を変更しない出力先では Phase 1〜3 を行い、Phase 4 は「レビューだけ」の修正案を作る生成方針としてだけ使い、Phase 5 は行わない。（LLM 判断） は polish / diagnostic の区別ではなく本項の規定で付け、解析ファイルのパスは原文用だけを示す。

ユーザーが「最終版だけ」と指定した場合は、適用ルール、診断、解析ファイルのパスを省略する。要確認 は省略しない。

ファイルを編集した場合は本文を再掲せず、変更ファイル、変更概要、要確認 を報告する。diagnostic では適用した ID も報告する。

8.8. FR-08 旧スキルを削除する

skills/natural-japanese/rewrite-japanese-with-iwabuchi-rules/ を、SKILL.md と agents/openai.yaml を含めて同じ変更で削除する。 旧スキル名の stub、転送用スキル、alias は作らない。 natural-japanese-rewriter の本文、description、openai.yaml のいずれにも旧スキル名を書かない。

natural-japanese-rewriter/agents/openai.yaml の short_description は、既定がデストロイモードである現状と規則 ID 付きの診断に合わせて更新する。display_name は維持する。default_prompt は追加しなくてよい。

manifest.json は、配布ファイルが変わらない限り変更しない。

8.9. FR-09 detailed-rules.md に規則 ID を注記する（任意）

references/detailed-rules.md の修正観点や典型例のうち、48規則と対応する節に「関連ID: …​」を1行で添えてよい。 規則本文の削除、節の並べ替え、モード方針の追記は行わない。 注記した ID は FR-02 の表に存在するものに限る。 この要件を実施しない場合も受け入れ条件は満たせる。

9. 例外と失敗時の挙動

  • KWJA の実行または解析ファイルの読み取りに失敗した場合は、既存どおりリライトを止めて原因を報告する。規則の判定だけを LLM で続行しない。

  • KWJA は成功したが、ある規則の手がかりとなる素性やタグが出力にない場合（たとえば語種、敬語）は、その規則を LLM 出所として原文から判定し、diagnostic ではその旨を示す。素性がないことを理由に not-applicable としない。

  • 分析メモの ambiguities に該当箇所がある規則は、セーフモードでは旧スキルの順序（一意に復元できる直し、安全な候補すべてに共通する変更、原文保持）で扱い、それでも確定できない箇所（repairability: blocked、recoverability: unknown など）は needs-confirmation とし、actionable にしない。この判定は既存の修復トリガー（文脈で安全に絞れる、など）より優先する。

  • 保護範囲（コード、識別子、URL など）にかかる箇所への規則の判定は not-applicable とし、保護範囲を変更しない。保護範囲の外の箇所には同じ規則を通常どおり適用する。

  • output.line-break-each-line は、改行の単位が指定されていなければ not-applicable とし、現在の行配置を保つ。指定があれば actionable として、表・箇条書き・コード・front matter など行自体に意味がある構造を崩さずに適用する。

  • 監査一覧を求められたが規則の判定を完了できない場合（Phase 3 前の停止など）は、部分的な一覧を出さず、停止理由を報告する。

  • 長い文章で actionable が多数ある場合も、polish の出力は本文と 要確認 だけであり、規則数や文数に比例して増えない。監査一覧は文書単位の48行に固定する。

10. 非機能要件

10.1. ID の安定性

48個の ID の綴りは、変更前スナップショット docs/backups/2026_09_29/natural-japanese/rewrite-japanese-with-iwabuchi-rules/SKILL.md の ID 表と完全一致させる。 ID を省略、改名、再利用しない。 将来規則を追加する場合は新しい ID を付け、廃止した ID を再利用しない。 報告に使う ID は表の定義と完全一致させ、表にない ID を作らない。

10.2. 意味安全性

規則の適用を理由に、原文にない主体、対象、原因、目的、時刻、確実性を追加しない。 技術用語を一般語へ薄めない。word-choice.simplify-overly-formal-literary-or-technical-terms と word-choice.limit-loanwords-and-foreign-words は、固有表現と技術的に必要な語を保護したうえで適用する。

10.3. コンテキスト効率

ID 表は SKILL.md 本体に置き、毎回の起動で参照できるようにする。 references/detailed-rules.md の読み込み条件は変えない。 1〜2文や UI 文言でも48規則の照合は行うが、not-applicable の判定を素早く済ませ、出力を増やさない。

10.4. 保守性

同じ判断を Phase 3 の修復トリガー一覧と規則 ID 表の両方に長く書かない。 規則の状態判定と ID の付与は Phase 3 に集約し、Phase 5 は再照合、Phase 6 は出力だけを担う。 旧スキルの「このスキルは単独で実行する」は引き継がない。

11. 互換性、移行、運用

  • natural-japanese-rewriter の名前、配置、safe 引数、polish / diagnostic の意味、Phase 1〜6 の順序は維持する。mendan-junbi などが名前で参照しているため、改名しない。

  • analyzer と japanese-kwja-analyze の契約は変更しない。rewrite_targets への decision と rule_ids の付与は親スキル側の記録であり、analyzer の出力契約に影響しない。

  • 旧スキルの利用者は、同じ依頼文（「岩淵ルールで直して」など）で natural-japanese-rewriter が起動する。既定がデストロイモードになるため、旧スキルと同じ原意保持の挙動が必要な場合は safe を付ける。この差は description に明記する。

  • 実行コード、永続データ、外部依存を追加しないため、データ移行は不要である。

  • ロールバックは docs/backups/2026_09_29/natural-japanese/ の natural-japanese-rewriter と rewrite-japanese-with-iwabuchi-rules を skills/natural-japanese/ へ戻すことで行える。

  • 利用環境の ~/.claude/skills/ は nix store のスナップショットへの symlink であり、リポジトリで旧ディレクトリを削除しても再ビルドまで旧スキルが残る。再ビルドは利用者の作業とし、本件の完了条件に含めない。

12. 採用した意思決定

各決定は自動壁打ちの推奨案であり、根拠と不確実性を併記する。

12.1. D-01 48規則を10の上位概念と4つの出所に対応づけ、判定を Phase 3 に集約する

規則ごとに「どの層の、どの観測から判定するか」を FR-03 の表で固定する。 上位概念の語彙は KWJA の11処理と Phase 2 の5層、detailed-rules.md の項・付加部・骨格から取り、新しい概念を持ち込まない。48規則が使わない層（情報構造）は語彙に含めない。 判定の位置は既存の修復判断がある Phase 3 に集約し、Phase ごとに判定を分散させない。

根拠は、ユーザーが「項の概念や KWJA の解析を上位概念とする」と明示していること、Phase 3 が実質的に rewrite_targets の生産者であること（natural-japanese-rewriter/SKILL.md:145）である。 不確実性は、KWJA の言語素性に敬語や語種の素性があるかを未確認である点で、該当する規則は LLM 出所へ倒しても要件を満たす形にした。

代替案として「カテゴリ単位（sentence / word-choice / honorific）で層に対応づけ、規則ごとの手がかりは実装者に委ねる」を検討したが、受け入れ条件を検証できず、「これは sentence.keep-subject-and-predicate-close だ」と判断するための手がかりが定義されないため採らない。

12.2. D-02 ID 表は SKILL.md 本体に置き、参照ファイルを増やさない

ID は polish の 要確認 にも使うため、毎回の起動で参照できる必要がある。 条件付きにしか読まれない参照ファイルへ置くと、読んでいない実行で ID を誤って綴る。 SKILL.md は現状209行で、48行の表と Phase 3・5・6 の追記を加えても validator の制限内に収まる。

不確実性は行数の目安（400行）が慣行に基づく値である点で、超えた場合は表以外の重複を削る。 代替案「references/iwabuchi-rules.md を新設し、SKILL.md にはカテゴリ表だけ置く」は、ID の定義が二か所に分かれ、manifest.json の更新も要るため採らない。

12.3. D-03 ID の綴りと件数を変更前スナップショットと一致させる

旧スキルが ID を公開識別子と定義し（rewrite-japanese-with-iwabuchi-rules/SKILL.md:36-37）、リポジトリ内で参照がなくても利用者の過去の出力に ID が残り得る。 綴りを保つコストはゼロで、変更前スナップショットが commit 済みのため機械的に照合できる。

12.4. D-04 規則 ID は親スキルの rewrite_targets と出力に置き、analyzer の issues[].code には載せない

analyzer は KWJA の解析事実と LLM の判断を分けて記録する方針を明記しており（natural-japanese-rewrite-analyzer/SKILL.md:25-27）、規則の状態は判断に属する。 issues[].code は語彙が未定義で、その経緯（コミット f8f85a4）も不明のため、この変更で analyzer の契約に触らない。 rewrite_targets は analyzer が空配列で渡し、親が埋める欄であり、ここに decision と rule_ids を持たせても子スキルの契約は変わらない。

不確実性は、issues[].code の空白が意図的かどうかで、未確定事項に残す。

12.5. D-05 セーフモードは旧スキルの原則、デストロイモードは自然さの基準として規則を使う

旧スキルの最優先原則はセーフモードの制約と一致する。 デストロイモードにそのまま持ち込むと「問題のない文は変更しない」が既定方針（natural-japanese-rewriter/SKILL.md:58）と衝突する。 両モードで共通する保護範囲と事実の非捏造、needs-confirmation の報告は維持し、優先順位だけをモードで切り替える。

12.6. D-06 旧ディレクトリを同じ変更で削除し、stub を残さない

追跡ファイルに旧スキルの参照がなく、トリガー語を description へ移せば起動経路が途切れない。 stub を残すと二つのスキルが同じ依頼に反応し、ユーザーが「呼び出す形にしない」とした意図に反する。 不確実性は利用環境の symlink で、運用上の注意として記載した。

12.7. D-07 出力モードを増やさず、レビューのみと最終版だけを既存の枠で扱う

「レビューだけ」は出力先「本文を変更しない」で actionable と needs-confirmation の判定だけを出す場合、「最終版だけ」は polish で診断と解析ファイルのパスを省く場合として扱う。 旧スキル内で「最終版だけなら推敲後だけを出す」と「どのモードでも needs-confirmation は省略しない」が両立していなかったため（同 :149, :154）、安全側の後者を採る。

12.8. D-08 output.line-break-each-line の既定を not-applicable にする

旧スキルは単位未指定なら needs-confirmation として現状維持としていたが、この解釈では毎回 要確認 が出て polish が騒がしくなる。 現状維持という結果は同じなので、状態だけを not-applicable に変える。 FR-02 で移す規則本文もこの既定に合わせて書き換え、表と例外の記述が食い違わないようにする。 references/detailed-rules.md:214 の「一文ごとに改行する」との整合は未確定事項とし、本件では当該行を変更しない。

12.9. D-09 references/detailed-rules.md への注記は任意にする

修正観点の多くが sentence.* と重なるため注記は有用だが、1422行の参照資料を変更しなくても目的は達成できる。 実施する場合も規則本文の削除と再編は行わない。

13. 判断から学べること

  1. 規則集を既存の解析層へ昇華するときは、規則 ID を安定識別子として残し、規則ごとに「どの観測から判定するか」を表で固定する。 兆候は、チェックリスト型のスキルと解析パイプライン型のスキルが同じ問題を別の語彙で扱っていること。 使える条件は、解析側に観測できるフィールド（項、係り受け、共参照など）が既にあること。 使わないほうがよい条件は、規則が解析結果に対応せず主観的な好みだけで決まる場合で、そのときは LLM 出所として分けて扱う。 参照は D-01、D-04、natural-japanese-rewrite-analyzer/SKILL.md:25-27。 今後調べる概念名と検索語は「rule-to-feature mapping」「predicate-argument structure」「KWJA 言語素性」。

  2. スキルをマージするときは、呼び出し委譲ではなく、トリガー語と出力契約を移して旧スキルを同じ変更で削除する。 兆候は、二つのスキルが同じ依頼に反応し得る状態や、片方が他方を呼ぶだけの薄いスキル。 使える条件は、追跡ファイルに旧スキルの参照がなく、description の上限内でトリガー語を吸収できること。 使わないほうがよい条件は、外部の利用者が旧スキル名に依存している場合で、そのときは期限付きの alias を検討する。 参照は D-06、README.md:98、git grep の結果。 検索語は「migrate callers then delete」「skill description triggers」。

  3. 契約に宙に浮いた参照（列挙されていない語彙を指す文）を見つけても、マージのついでに別スキルの契約を直さず、未確定事項として残す。 兆候は、issues[].code のように値の語彙がなく、参照文だけが残っている状態。 使える条件は、当該契約が今回の変更対象外で、削除の経緯が履歴から読めないこと。 使わないほうがよい条件は、宙に浮いた参照が今回の受け入れ条件を直接壊す場合で、そのときは同じ変更で直す。 参照は D-04、未確定事項、コミット f8f85a4。 検索語は「dangling reference」「schema enum drift」。

16. 品質確認方法

次のコマンドはリポジトリルートで実行する。ID_RE は Markdown 表の ID 行を抽出する正規表現である。

ID_RE='^\| `(output|sentence|word-choice|honorific)\.[a-z0-9-]+` \|'
NEW=skills/natural-japanese/natural-japanese-rewriter/SKILL.md
OLD=docs/backups/2026_09_29/natural-japanese/rewrite-japanese-with-iwabuchi-rules/SKILL.md

# AC-01: 件数と重複
grep -cE "$ID_RE" "$NEW"                                   # 48
grep -oE "$ID_RE" "$NEW" | sort | uniq -d | wc -l          # 0
for c in output sentence word-choice honorific; do
  printf '%s ' "$c"; grep -cE "^\| \`$c\." "$NEW"          # 1 21 16 10
done

# AC-02: 変更前スナップショットと集合が一致
diff <(grep -oE "$ID_RE" "$OLD" | sort) <(grep -oE "$ID_RE" "$NEW" | sort)   # 差分なし

# AC-04, AC-05: 旧ディレクトリと参照の不在
test ! -d skills/natural-japanese/rewrite-japanese-with-iwabuchi-rules && echo removed
git grep -n rewrite-japanese-with-iwabuchi-rules -- skills | wc -l           # 0

# AC-06, AC-07, AC-09（description に限定した AC-06 の確認と AC-03、AC-11 は実装計画の検査スクリプトで行う）
for w in 岩淵ルール 48規則 ルールID 監査; do
  printf '%s ' "$w"; grep -c "$w" "$NEW"                   # それぞれ1以上
done
grep -c 'だけの依頼には使わない' "$NEW"                    # 0
wc -l < "$NEW"                                             # 400以下

# AC-08: validator
python3 <quick_validate.py のパス> skills/natural-japanese/natural-japanese-rewriter

# AC-10: 子スキルの不変
git diff --stat HEAD -- skills/natural-japanese/natural-japanese-rewrite-analyzer \
  skills/natural-japanese/japanese-kwja-analyze                             # 出力なし

AC-03 は、48行それぞれの上位概念列と出所列を目視または短いスクリプトで確認する。 AC-11 は manifest.json の files を読み、各パスの存在とディレクトリ内の未列挙ファイルの有無を確認する。 AC-12 から AC-18 は SKILL.md と openai.yaml を読んでレビューする。 検証シナリオは、スキル指示から期待する判定と失敗時挙動を一意に説明できるかをレビューで確認する。実際に KWJA を実行できる環境では、T-03、T-10、T-12、T-14 を実行して確認する。
