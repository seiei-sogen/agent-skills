2. そもそも何の話？

まず言葉の説明

スキル
Claude Code や Codex などの AI エージェントに渡す「作業の手順書」。SKILL.md というファイルに書きます。エージェントは依頼文を見て、合うスキルを選んで動きます。
natural-japanese-rewriter
日本語を自然で読みやすく書き直すスキル。文章を機械で解析した結果をもとに、Phase 1〜6 の6段階で作業します。
rewrite-japanese-with-iwabuchi-rules（旧スキル）
岩淵「悪文」メモ由来の48規則を文章に照らし、各規則を4状態に分け、規則 ID 付きで報告する単独スキル。「岩淵ルールで直して」のように規則を名指しした依頼でだけ起動し、一般的な「校正して」「自然にして」では起動しませんでした。
KWJA
日本語の文を機械で細かく解析するツール。分かち書き、単語正規化、形態素解析、固有表現認識、言語素性、係り受け、述語項構造、橋渡し照応、共参照、談話関係などの11処理を行います。ざっくり言うと「この語はどの語にかかるか」「誰が何をしたか」を機械が読み取る道具です。
分析メモ
KWJA の結果を analyzer（子スキル）がまとめた YAML。rewrite_targets、predicates、ambiguities などの項目を持ちます。
Phase 1〜6
natural-japanese-rewriter の作業の6段階。Phase 1 で分析メモを作り、Phase 2 で談話・情報構造・語用論・対人関係・文体の制約を固定し、Phase 3 で修復箇所を決め、Phase 4 で制約に沿って生成し、Phase 5 で候補文を検査し、Phase 6 で出力します。
規則 ID
<カテゴリ>.<kebab-case> の形の安定した名前。カテゴリは output、sentence、word-choice、honorific の4種。例: sentence.keep-subject-and-predicate-close。件数は output 1、sentence 21、word-choice 16、honorific 10 の合計48です。
4状態
規則1つの判定結果。pass（適用でき問題なし）、not-applicable（媒体や内容から対象外）、actionable（原意を変えず安全に修正できる問題）、needs-confirmation（原文にない情報や意図が必要）。
セーフモード / デストロイモード
第一引数が safe のときだけ原意を厳密に保つ（セーフモード）。既定はデストロイモードで、自然さを優先して大胆に書き直します。
polish / diagnostic
出力モード。polish は本文中心で内部分析を出さない既定。diagnostic は分析・理由・問題箇所を求められたときだけ診断を追加します。
要確認
原文だけでは判断できない点を、出力の最後にユーザーへ聞き返す欄。

なぜ統合したのか

2つのスキルは、同じ悪文を別々の語彙で扱っていました。

  • たとえば規則 sentence.keep-subject-and-predicate-close（主語と述語を近くに置く）は、分析メモでは「ガ格の項と述語の基本句距離」として観測できます。
  • 規則 sentence.minimize-passive-voice（受身を減らす）は、voice: passive と動作主の復元可能性として観測できます。

つまり、旧スキルの「規則」は、natural-japanese-rewriter が KWJA から得ている「観測」と同じものを見ていました。規則を文字列照合のチェックリストのまま残すと、同じ判断を2つのスキルが別々に行い、ID による説明責任と KWJA の根拠が結びつきません。

目指した状態（目的）

  1. 48規則を、既存の上位概念（項・付加部・骨格、KWJA の11処理、Phase 2 の5層）に対応づけて内蔵する。規則は「文字列に照らすチェック項目」ではなく「分析メモと上位レイヤーのどの観測から判定する規範か」として定義される。
  2. 各規則を安定 ID で参照でき、エージェントが判定、修正理由、要確認、診断出力で ID をそのまま使える。
  3. 旧スキルのトリガー語、出力形式、監査機能を引き継ぎ、natural-japanese-rewriter 単独で完結する。旧スキルは削除し、内部から呼び出さない。

4. 規則はどう仕組みに結びつく？（図2）

ここが今回の中心です。旧スキルの規則は「文章にこの規則を当てはめてチェックせよ」という項目でした。統合後は、規則1つ1つに「何を見て判定するか」を3つの情報で添えました。

ID 表は5列

SKILL.md の中に ## 岩淵48規則の ID 表 という節を新設し、4つのカテゴリ見出し（出力・行配置、文の組み立て、語の選び方、敬語）ごとに、次の5列の Markdown 表を置きました。表本体は67行です。

| ID | 規則 | 上位概念 | 主な手がかり | 出所 |
  • ID: 規則の名前。省略、改名、再利用しない。元メモの通し番号は使わない。表にない ID を作らない。
  • 規則: 旧スキルの一文をそのまま移す。例外は1か所だけ（下の「表はどう作ったか」を参照）。
  • 上位概念: 10種から1つ。
  • 主な手がかり: 分析メモのどの項目を見るか。要件 FR-03 の文言をそのまま使った（平均31字、最長64字）。
  • 出所: 4種から1つ。

上位概念の10種

「規則を判定するとき、どの層の観測を見るか」の名前です。KWJA の11処理と Phase 2 の5層から作られています。

上位概念ざっくり言うと
述語項構造「誰が・何を・どうした」の組み合わせ
係り受け語と語の「かかる／受ける」の関係
節構造・談話関係文の中の区切りと、文どうしのつながり
共参照・照応「それ」「この件」などが何を指すか
形態素・語彙単語の切れ目、品詞、表記
固有表現・保護範囲人名・製品名・コードなど、触ってはいけない範囲
語用論・モダリティ読み手や場面、断定の強さ
対人関係敬語の向きや上下関係
文体です・ます／だ・である、翻訳調など
文書構造行、表、箇条書きなどの並び

Phase 2 の情報構造（topic / focus）に対応する規則は48規則にないため、語彙には含めていません。

5. エージェントは実際にどう使う？（図3）

規則の判定は Phase 3 に集めました。Phase 5 は「もう一度照合する」だけ、Phase 6 は「出す」だけを担当します。

Phase 3: 判定する

  • 48規則をすべて照合し、各 ID を4状態のどれかにします。1〜2文や UI 文言でも照合しますが、not-applicable の判定は素早く済ませて出力を増やしません。
  • 判定の材料は出所に従います。P1 は分析メモと KWJA 出力、P2 は Phase 2 で固定した制約、LLM は原文と文脈。P4 の output.line-break-each-line は、改行の単位が指定されていなければ not-applicable、指定があれば actionable にして Phase 4 で適用します。
  • 分析メモの rewrite_targets の各要素に、少なくとも decision（repair / keep / confirm）と rule_ids（主となる ID を先頭に、関連 ID を続ける。空配列でもよい）を記録します。actionable は repair、needs-confirmation は confirm、「項を無理に補わない」一覧に当たる箇所など意図的に残す箇所は keep です。
  • 既存の修復トリガー一覧（主体の複数候補、係り先の曖昧さなど）は変えません。トリガーに当たる箇所は、該当する規則 ID で言い換えて rule_ids に書きます。同じ判断を二重には書きません。
  • 要素の形は親スキル側の記録です。analyzer の出力契約は変えていません。

困ったときの決まり（例外）

  • 出所が P1 でも、手がかりとなる素性やタグが KWJA 出力にない規則は、LLM 出所として原文から判定し、その旨を記録します。素性がないことを理由に not-applicable にはしません。
  • 分析メモの ambiguities（曖昧な箇所）に当たる規則は、セーフモードでは needs-confirmation にし、actionable にしません。
  • KWJA の実行や解析ファイルの読み取りに失敗したら、既存どおり止めて原因を報告します。規則の判定だけを LLM で続けることはしません。
  • 保護範囲（コード、識別子、URL など）にかかる箇所は、箇所単位で not-applicable にします。保護範囲の外には同じ規則を普通に適用します。

モードで扱いが違う

両モード共通

  • 48規則をすべて照合する。
  • 規則を理由に保護範囲を変えず、原文にない事実を作らない。
  • needs-confirmation は省略せず 要確認 に出す。

セーフモード（safe）

  • actionable は、原意・事実・仕様・技術的意味を変えずに修正できる問題に限る。
  • 規則を機械的に当てず、読みやすさや正確さが実際に上がる変更だけ採用する。
  • 規則どうしが衝突したら、次の順に優先する。
    1. 原意・事実・仕様・技術的意味の保持
    2. 文脈、係り受け、否定範囲、用語の正確さ
    3. 読み手にとっての明確さ
    4. 語感、敬語、簡潔さ
    5. 行配置

デストロイモード（既定）

  • 48規則を「自然さの判定基準」として使う。actionable の判定と修正も、デストロイモードが許容する意味の変化の範囲で行う。
  • needs-confirmation の箇所は、もっとも自然な解釈を選んで actionable として扱ってよい。ただし選んだ解釈を事実として断定せず、事実に関わるもの（word-choice.match-expression-to-facts など）は needs-confirmation のまま 要確認 に残す。
  • 優先順位は、既存のデストロイモードの順位（自然さ最優先）が上。上の5項目の順序は、規則どうしの衝突を解くときだけ使う。
  • word-choice.simplify-overly-formal-literary-or-technical-terms と word-choice.limit-loanwords-and-foreign-words は、固有表現と技術的に必要な語を保護したうえで適用する。

Phase 5: もう一度照合する

  • 両モード共通で、候補文に48規則を再照合し、新たな actionable を作っていないか確かめます。見つかったら候補を直して再照合します。
  • 再照合は最大3巡。3巡で消えない actionable は needs-confirmation に変えて、Phase 6 の 要確認 に ID 付きで出します。
  • デストロイモードは候補文を再解析しないので LLM 出所で再照合します。セーフモードは意味回帰検査で再解析した分析メモを使います。
  • セーフモードの既存の意味回帰検査（KWJA 再解析、SEMANTIC_DRIFT）は変えていません。
  • 完了条件に「候補文で actionable の規則が0件」が加わりました。

Phase 6: 出す

依頼のしかた出るもの
普通の依頼（polish、既定）本文と 要確認 だけ。要確認 の各項目は - `{ID}`: {原文だけでは判断できない点} の形。規則に対応しない 要確認（KWJA と本文の食い違いなど）は ID なし。適用した規則の一覧は出さない。長い文章で actionable が多くても、出力は規則数や文数に比例して増えない
「岩淵ルールで直して」「ルールID付きで推敲して」など規則や ID を名指しした依頼（diagnostic）既存の3項目（問題のある述語、不明または競合していた項、修復で明確になった関係）に加えて「4. 適用ルール」。形式は - `{ID}`: {対象箇所と修正内容}。actionable がなければ「適用ルール: なし」。LLM 出所の判定と、素性がなくて LLM に倒した判定には、行末に （LLM 判断） を付ける（polish では付けない）
「監査して」「全規則の判定を見せて」規則の定義順に48行の表 | ID | status | 根拠または対象箇所 |。監査だけなら本文を変えない。監査と推敲の両方なら diagnostic の末尾に加える。判定を完了できないとき（Phase 3 前の停止など）は部分的な一覧を出さず、停止理由を報告する
「レビューだけ」「直さないで」本文を変えず、actionable と needs-confirmation の判定を ID / 対象箇所 / 問題 / 修正案 の形で出す。needs-confirmation は修正案の代わりに、判断に必要な情報を示す
「最終版だけ」適用ルールと診断を省く。要確認 は省かない
ファイルを編集した場合本文を再掲せず、変更ファイル、変更概要、要確認 を報告する。diagnostic では適用した ID も報告する

出力モードは増やしていません。「レビューだけ」「監査だけ」は、開始時に確定する出力先（ファイル編集、応答本文、本文を変更しない）の枠で扱います。

レビュー2巡でなおしたこと

実装後に ponytail-review によるレビューを2巡行いました（TypeScript / JavaScript を含まないため anti-ai-slop-typescript-general は省略）。重複の削除と矛盾の解消で、SKILL.md は347行から330行になりました。修正後に同じ検証を再実行し、AC-09 の行数以外はすべて同じ結果でした。

要件定義書を先に明確化してから SKILL.md に反映した矛盾は7件です。

  1. デストロイモードの actionable の意味。4状態の定義は「原意を変えず」だが、デストロイモードは細部の意味の変化を許容する。FR-05 に「actionable の判定と修正もデストロイモードが許容する意味の変化の範囲で行う」を追加。
  2. 解消した needs-confirmation の状態。デストロイモードで自然な解釈を選んだ箇所は actionable として扱い、事実に関わるものだけ needs-confirmation のまま残す。
  3. keep の割り当て。「補わない」一覧に当たる箇所など意図的に残す箇所を keep とする。
  4. デストロイモードの Phase 5 再照合の根拠。候補文を再解析しないため LLM 出所で判定する。
  5. 保護範囲の判定単位。規則単位ではなく箇所単位で not-applicable とする。
  6. 「レビューだけ」の出力内容。diagnostic の3項目ではなく、actionable と needs-confirmation の判定を ID / 対象箇所 / 問題 / 修正案 で出す。
  7. Phase 6 の完了条件。監査だけ・レビューだけでは本文を出さないため「出力先に応じてリライト本文、判定、または監査一覧が出力され」とした。

計画から調整した点は3件です。ID 表の冒頭に上位概念と出所の意味を1段落添えたこと、Phase 3 の完了条件を decision の値（repair / keep / confirm）で書いたこと、Task 3 で予定していた ### 48規則の扱い の小見出しを外して既存のモード段落に畳み込んだことです。

あらかじめ警戒した「壊れ方」3つ

  • 規則本文をそのまま移すと output.line-break-each-line の既定が2通りになる。 生成スクリプトが置き換え、grep で旧文言0件・新文言1件を確認（AC-16）。
  • 本文の形式例に実在の ID を表の行として書くと、AC-01 の48行が崩れる。 AC-01 の正規表現はファイル全体を数えるため、形式例は {ID} のプレースホルダーだけを使い、Task 6 の後に AC-01 を再実行。
  • 「岩淵ルールで直して」が polish のままだと ID が出ず、T-01 が成立しない。 規則や ID を名指しする依頼を diagnostic として扱う判定を「入力と出力モード」節に置いた。
