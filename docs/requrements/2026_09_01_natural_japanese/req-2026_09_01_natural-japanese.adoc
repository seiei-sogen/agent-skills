言語学の「項」について教えて。 「項」の概念を応用して、日本語推敲agent skillを強力なものにしたいから、その観点で。

# 「項」とは何か

日本語推敲 agent に使うなら、**「項＝述語が意味を成立させるために用意している参加者スロット」**と捉えるのが最も実用的です。

たとえば、

```text
寝る〈寝る人〉
読む〈読む人、読まれるもの〉
渡す〈渡す人、渡されるもの、受け取る人〉
```

のように、述語ごとに必要となる参加者の型があります。

```text
太郎が    花子に    資料を    渡した。
渡し手    受取手    渡す物    述語
```

自然言語処理でいう述語項構造解析も、概略的には「誰が・何を・誰に・どうした」を復元する処理です。日本語では項が表面に現れないことが多いため、単純な係り受け解析だけでは足りません。([ACLアンスロポロジー][1])

## まず区別したい3つ

実装上は、次の3段階を分けるときれいです。

| 概念    | 内容                  | 例                 |
| ----- | ------------------- | ----------------- |
| 項構造   | 述語の語義が持つ意味的スロット     | `渡す〈渡し手, 物, 受取手〉` |
| 格フレーム | スロットがどの助詞・構文で表現されるか | `Xが Yを Zに 渡す`     |
| 述語項構造 | 実際の文で、各スロットを誰が埋めるか  | `田中さんが資料を顧客に渡した`  |

同じ動詞でも、語義が異なれば格フレームも変わります。

```text
荷物を積む
経験を積む
```

この2つは同じ「積む」でも、項に入る名詞の種類と語義が違います。そのため実用的な格フレームは、単なる動詞見出しではなく、**動詞の語義ごと**に持たせる必要があります。日本語では語順変更、項の省略、格助詞の消失などもあるため、格フレームが重要になります。([ACLアンスロポロジー][2])

# 項と付加詞

次の文を考えます。

```text
昨日、太郎が図書館で本を読んだ。
```

`読む`の項は、おおむね次の2つです。

```text
読む〈読み手＝太郎、読む対象＝本〉
```

一方、

```text
昨日
図書館で
```

は、出来事に時刻や場所を付け加える**付加詞 adjunct**です。

ところが、場所を表す表現が常に付加詞とは限りません。

```text
太郎が札幌に住む。
本を机に置く。
```

`住む`は居住者だけでなく居住場所を選択し、`置く`も置く物だけでなく置き場所を選択します。

```text
住む〈居住者、居住場所〉
置く〈動作主、移動物、到達場所〉
```

したがって、

```text
図書館で読む
```

の場所は付加詞的ですが、

```text
札幌に住む
机に置く
```

の場所は項的です。

ただし、項と付加詞の境界には微妙な例もあります。付加詞とされる要素が、特定の語義ではほとんど必須に見えることもあり、単一のテストで完全に二分するのは危険です。([Ninjal][3])

## 「省略できるから付加詞」は誤り

これは日本語推敲 agent で特に重要です。

```text
もう読んだ。
```

この文には「読む人」も「読むもの」も表面にありません。しかし、`読む`の項構造から消えたわけではありません。

```text
読む〈読み手＝φ、読む対象＝φ〉
```

文脈から、

```text
私は、その資料を、もう読んだ。
```

と復元できるなら問題ありません。

日本語では、このように音形を持たない項が広く許されます。その分析には空代名詞とする立場や項省略とする立場がありますが、推敲 agent では理論的決着をつける必要はなく、**「表面にはないが、述語のスロットとして存在する」**と扱えば十分です。([ことば研究館 | 国立国語研究所][4])

# CGELの観点との接続

ご主人様が関心を持っている *The Cambridge Grammar of the English Language* の用語で近いのは、`complement` と `adjunct` の区別です。

ただし、完全に同じではありません。

* **argument 項**：述語の意味・結合価に属する概念
* **complement 補部**：統語構造上、その主要部によって認可される要素
* **adjunct 付加部**：比較的自由に追加される修飾要素

通常、表面に現れた項は何らかの complement として実現します。しかし日本語のゼロ項は、意味上は項であっても、表面上の complement がありません。

したがって推敲 agent では、少なくとも次の層を混同しないことが重要です。

```text
格助詞：が・を・に・で・から……
統語機能：主語・目的語・斜格補部……
意味役割：動作主・経験者・対象・着点……
談話機能：主題・焦点・既知情報……
```

たとえば、`が`は動作主を表すとは限りません。

```text
太郎が走る。     太郎＝動作主
太郎が驚く。     太郎＝経験者
ドアが開く。     ドア＝変化対象
```

同様に、`は`は主語の印ではありません。

```text
この修正は、本番環境に反映しました。
```

ここでは、

```text
反映する
  動作主：書き手       φ
  反映内容：この修正   は ← 潜在的には「を」
  反映先：本番環境     に
```

と解析できます。

# 強力な推敲 agent の中心原理

項について、単に「ある・ない」と判定するのではなく、次の3軸を別々に持たせるのがよいです。

## 1. 選択性

その要素は、述語の語義によって選ばれているか。

```text
読む → 読み手、読む対象
住む → 居住者、居住場所
置く → 動作主、移動物、置き場所
```

## 2. 実現形式

その項はどう表現されているか。

```text
overt             明示されている
zero              省略されている
topic             は・もで主題化されている
relative-gap      関係節の外側の名詞が項を埋める
nominalized       名詞化の中に隠れている
generic           一般人・不特定主体として解釈される
```

## 3. 復元可能性

省略された項の指示対象が、読み手に分かるか。

```text
clear       一意に分かる
probable    かなり推定できる
ambiguous   複数候補がある
unknown     復元不能
```

この区別により、次のように判断できます。

```text
確認しました。
```

直前にPRの話をしているSlackなら、

```text
確認する
  確認者：書き手      zero / clear
  確認対象：そのPR    zero / clear
```

なので、わざわざ、

```text
私はそのPRを確認しました。
```

と直す必要はありません。

**強い推敲 agent は項を補うだけでなく、補わなくてよい項を見分けます。**

# 日本語で特に検査すべき現象

## 主題化

```text
このPRは確認しました。
```

`このPR`は`確認する`の確認対象です。`は`を常に主語扱いしてはいけません。

## 複数述語による項の共有

```text
担当者が内容を確認し、修正した。
```

通常は、

```text
確認する〈担当者、内容〉
修正する〈担当者、内容〉
```

と、主語と目的語が共有されています。

しかし、

```text
担当者が内容を確認し、顧客に修正を依頼した。
```

では、`修正する`の動作主は顧客になる可能性があります。

複数の述語は意味的に相互作用し、省略項が別の述語の明示項と共有されることがあります。そのため、文中の各述語を個別に処理するより、述語と項を文全体のグラフとして扱うほうが適しています。([ACLアンスロポロジー][1])

## 受け身・使役・可能

```text
田中さんがPRを修正した。
PRが田中さんによって修正された。
部長が田中さんにPRを修正させた。
田中さんはPRが修正できる。
```

意味上の参加者と、`が・を・に`の対応が構文によって変化します。

したがって、先に受け身や使役を正規化し、その後に意味役割を割り当てる必要があります。

## 名詞化

技術文書や業務連絡では、動詞よりもこちらが重要です。

```text
顧客の確認
仕様の確認
本番反映
修正依頼
生成結果の検証
```

特に、

```text
顧客の確認
```

は、少なくとも次の二通りがあります。

```text
顧客が確認する       顧客＝確認者
顧客を確認する       顧客＝確認対象
```

推敲時には必要に応じて、

```text
顧客による確認
顧客情報の確認
```

のように役割を明示します。

## 軽動詞

```text
確認を行う
修正を実施する
共有をする
```

この場合、実質的な項構造は`行う・実施する・する`ではなく、`確認・修正・共有`側が持っています。

```text
確認を行う
  確認者
  確認対象

共有を行う
  共有者
  共有内容
  共有相手
```

`行う`だけを解析しても、有用な情報はほとんど得られません。

## 汎用役割とドメイン役割を分ける

技術文章では、`Agent`や`Theme`だけでは粗すぎます。

```text
developをmainにマージする
```

なら、

```text
汎用役割
  Agent
  Source
  Goal

  operator
  source_branch = develop
  target_branch = main
```

まで持たせたほうが、ブランチ方向の誤りを検査できます。


```text

```

を分けます。

# 推敲処理の流れ

## 1. 述語候補をすべて抽出する

動詞だけでなく、次も対象にします。

```text
形容詞述語      必要だ、可能だ、難しい
サ変名詞        確認する、反映する
出来事名詞      確認、修正、共有、依頼、検証
埋込み述語      ～と判断する、～よう依頼する
```

## 2. 語義と格フレームの候補を出す

一つに即決せず、複数候補を保持します。

```text
確認する
  sense A: 内容を自分で調べる
  sense B: 相手に問い合わせる
  sense C: 相手に了承を求める
```

## 3. 表面の項を対応づける

`が・を・に`だけでなく、`は・も・について・に対して・によって`、無助詞、関係節の空所も扱います。

## 4. ゼロ項を復元する

候補は少なくとも次から探します。

```text
同一節
同一文の別述語
直前文
現在の主題
書き手
読み手
不特定の人
```

日本語の述語項構造解析でも、直接係る項、同一文内に先行詞を持つゼロ項、文外に先行詞を持つゼロ項を分けて扱う方法があります。([ACLアンスロポロジー][1])

## 5. 問題を検出する

推奨する問題コードは次のようなものです。

| コード                        | 意味                    |
| -------------------------- | --------------------- |
| `UNRESOLVED_CORE_ARGUMENT` | 重要な項の指示対象が不明          |
| `AMBIGUOUS_ANTECEDENT`     | ゼロ項の候補が複数ある           |
| `CASE_FRAME_MISMATCH`      | 助詞と述語の語義が合っていない       |
| `SUBJECT_DRIFT`            | 並列述語の途中で動作主が不明瞭に変わる   |
| `ATTACHMENT_AMBIGUITY`     | 一つの句が複数述語の項になり得る      |
| `NOMINAL_ROLE_AMBIGUITY`   | `Nの確認`など、名詞化内部の役割が曖昧  |
| `VAGUE_PREDICATE`          | `する・なる・対応する`が関係を隠している |
| `OVEREXPLICIT_ARGUMENT`    | 明示しすぎて不自然になっている       |
| `SEMANTIC_DRIFT`           | 推敲後に項の対応関係が変化した       |

## 6. 最小限の修正を生成する

優先順位は次のようにします。

```text
助詞の修正
→ 抜けた項の明示
→ 「もの」「こと」の具体化
→ 述語の具体化
→ 文の分割
```

最初から全文を書き換えると、事実関係を変える危険が高くなります。

## 7. 推敲前後の項グラフを比較する

推敲後に、

```text
誰が
何を
誰に
どこへ
何について
```

が変わっていないか検査します。

つまり推敲候補の評価は、おおむね次のようになります。

```text
高評価
  項の復元可能性が上がる
  係り先が一意になる
  元の意味役割を保存する
  文体が用途に合う

減点
  存在しない主体を補う
  原文にない因果関係を加える
  明示しすぎる
  固有名詞や技術用語を変える
  編集距離が大きすぎる
```

# 実例

原文：

```text
ローカルで業務の動作確認をしようとし、
dev環境のデータをCSVに取り込もうとしたところ、
エラーになりました。
```

項を分析すると、

```text
確認する
  確認者：書き手
  確認対象：業務の動作
  実行環境：ローカル

取り込む
  実行者：書き手
  対象：dev環境のデータ
  取り込み先：CSV？
  形式：不明

なる
  何がエラーになったか：曖昧
```

`CSVに`が取り込み先に見えますが、意図は形式でしょう。さらに本来の取り込み先であるローカル環境が、`取り込む`の項としては明示されていません。

修正文：

```text
ローカル環境で対象業務の動作を確認するため、
dev環境のデータをCSV形式でローカル環境に取り込もうとしたところ、
エラーが発生しました。
```

これは単なる言い換えではなく、

```text
CSV形式で          Format
ローカル環境に     Destination
エラーが発生した   発生事象の明示
```

と、項と付加詞の役割を修復しています。

もう一つ、ご主人様が以前書いていたタイプの文です。

```text
件数とエラー内容が別々のワークフローのものだったのを、
最終的に採用したワークフローのものに合わせました。
```

ここでは`もの`が項関係を隠しています。

```text
合わせる
  動作主：書き手
  合わせる対象：件数、エラー内容
  合わせる基準：最終採用ワークフローの結果
```

修正文：

```text
件数とエラー内容が別々のワークフローを参照していたため、
どちらも最終的に採用したワークフローの結果に統一しました。
```

`もの`を減らしたことよりも、

```text
何が何を参照していたか
何を何に統一したか
```

が明示されたことが本質です。

# `SKILL.md`の中核案

```md
# Japanese Argument-Aware Proofreading

## Objective

日本語の文章を、事実関係と文体を維持したまま明確にする。
表面的な言い換えではなく、述語項構造を復元してから推敲する。

## Mandatory internal analysis

1. 文中のすべての述語を抽出する。
   - 動詞
   - 形容詞述語
   - サ変名詞
   - 出来事を表す名詞
   - 埋込み節の述語

2. 各述語について、語義ごとの項構造候補を作る。

3. 次の情報を別々に記録する。
   - 表面の助詞
   - 統語的な関係
   - 意味役割
   - 談話上の役割
   - 明示／省略
   - 指示対象
   - 復元確信度

4. 「は」「も」を自動的に主語とみなさない。

5. 表面にない項も、述語のスロットとして保持する。

6. 同一文および前文からゼロ項の先行詞を探索する。

7. 並列された述語について、項の共有と主体の切替を確認する。

8. 受け身・使役・可能・授受・敬語を正規化してから
   意味役割を決定する。

9. 「NのN」および名詞化について、
   動作主・対象・内容・結果の曖昧性を検査する。

10. 推敲前後の述語項グラフを比較し、
    指示対象や意味役割が変化していないことを確認する。

## Repair triggers

次の場合に限り、項を明示または表現を変更する。

- 誰が行うのか複数の候補がある
- 何を対象としているか不明
- 助詞が誤った意味役割を示している
- 一つの句が複数の述語に係り得る
- 並列中に主体が切り替わっている
- 名詞化によって動作主と対象が区別できない
- 「もの」「こと」「対応する」「なる」が関係を隠している

## Non-triggers

次の場合は、項を無理に補わない。

- 書き手または読み手が一意に復元できる
- 直前の主題が継続している
- 省略しても誤読の可能性が低い
- 明示すると不自然または冗長になる

## Safety constraints

- 原文にない主体・原因・目的・時刻を作らない。
- 不明な指示対象を推測で確定しない。
- URL、コード、識別子、ブランチ名、PR番号、メンションを変更しない。
- 技術用語を一般語へ薄めない。
- 敬語レベルと対人関係を変えない。
- 曖昧性を解消できない場合は、勝手に補完せず指摘する。

## Output modes

### polish

推敲後の文章だけを出力する。

### diagnostic

以下を出力する。

1. 推敲後の文章
2. 問題のある述語
3. 不明または競合している項
4. 修正によって明確になった関係
```

# 五文型より推敲に向いている理由

五文型は、主として表面に現れた要素を一定の配置に分類します。

一方、項構造は、

```text
省略
主題化
受け身
使役
名詞化
関係節
複数述語間の共有
```

を越えて、同じ意味上の参加者を追跡できます。

日本語推敲では、

```text
文が何型か
```

よりも、

```text
各述語について、
誰が何を誰にしたのかが復元できるか
```

のほうがはるかに直接的です。

中心思想を一文でまとめると、

> **日本語推敲を文字列の整形ではなく、述語項グラフの修復として実装する。**

となります。ただし項構造だけですべての推敲問題を解決できるわけではなく、最終的には情報構造、敬語、文体、語用論を別レイヤーとして重ねるのがよい設計です。

[1]: https://aclanthology.org/P15-1093.pdf "Joint Case Argument Identification for Japanese Predicate Argument Structure Analysis"
[2]: https://aclanthology.org/H01-1043.pdf "HLT2001.dvi"
[3]: https://www2.ninjal.ac.jp/past-events/2009_2021/event/specialists/project-meeting/m-2019/20190921/ "www2.ninjal.ac.jp"
[4]: https://kotoba.ninjal.ac.jp/digest/09/d-09-01/ "特集 : 日本語の不思議を科学する 日本語から生成文法理論へ : 統語理論と言語獲得 - ことば研究館 | 国立国語研究所"

具体的には、**「一発で文章を直す」のをやめて、推敲を複数の解析レイヤーに分けます**。

項構造を土台にして、次の順序にするとかなり強いです。

```text
原文
 ↓
① 述語項構造      誰が・何を・誰に・どうした
 ↓
② 指示・談話構造  「これ」「それ」「省略された主語」は何を指すか
 ↓
③ 情報構造        何を既知情報として、何を新情報として伝えるか
 ↓
④ 語用論          この発話で何をしたいのか
 ↓
⑤ 敬語・対人関係  誰が誰に話しているか
 ↓
⑥ 文体            Slack / メール / 報告書など
 ↓
⑦ 表層生成        実際の日本語を書き換える
 ↓
⑧ 意味保存検査
```

この順番が重要です。

## 1. 最初に「項構造」を固定する

たとえば原文が、

> ER図、更新しましたが、シェアポイントにアップロードすると、どうしても解像度が落ちてしまうようです。

なら、まず文章を直さずに内部的にこうします。

```yaml
predicates:
  - predicate: 更新する
    arguments:
      agent: 書き手
      theme: ER図

  - predicate: アップロードする
    arguments:
      agent: 書き手
      theme: ER図
      destination: SharePoint

  - predicate: 落ちる
    arguments:
      theme: ER図の解像度
      condition: SharePointにアップロードした場合
```

ここが**意味の不変条件**になります。

あとで美しい文章を生成しても、

```text
SharePoint自体の解像度が低い
```

のような意味に変わったらNGです。

---

# 2. その上に「談話構造」を載せる

ここでは、

> 今、何について話しているのか

を管理します。

たとえば、

```text
ER図を更新しました。
SharePointにアップロードすると解像度が落ちるようです。
そのため、SVG版をリポジトリにも配置しました。
```

には、

```yaml
discourse:
  current_topic: ER図

entities:
  er_diagram:
    salience: high

  sharepoint:
    salience: medium

  svg_version:
    salience: new
```

くらいの概念を持たせます。

これによって、

```text
こちら
それ
そのファイル
同様に
そのため
```

などが何を指すか検査できます。

### 推敲で見るポイント

たとえば、

```text
こちらを修正しました。
```

だけでは、

```yaml
こちら:
  candidates:
    - PR
    - コード
    - 指摘内容
    - 不具合
```

となるかもしれません。

候補が複数なら、

```text
ご指摘いただいた箇所を修正しました。
```

のように直す。

逆に直前に対象が一つしかなければ、無理に具体化しません。

# 3. 「情報構造」を別レイヤーにする

これは特に重要です。

情報構造とは大雑把に言えば、

```text
何を話題として置くか
何を新しい情報として提示するか
どこを強調するか
```

です。

日本語なら特に、

```text
は
が
も
については
につきましては
```

などと深く関係します。

例えば、

```text
本番環境に修正は反映されています。
```

と

```text
修正は本番環境に反映されています。
```

では、項構造はほぼ同じです。

```text
反映する
  theme = 修正
  destination = 本番環境
```

でも情報構造が違います。

前者は、

> 「本番環境」についてどうなの？

という文脈に向いています。

後者は、

> 「例の修正」ってどうなった？

という文脈に向いています。

つまり agent に、

```yaml
information_structure:
  topic: 修正
  focus: 本番環境への反映完了
```

のような内部表現を持たせる。

そして原則として、

> **原文の topic / focus を不用意に変更しない**

とします。

これはかなり効きます。

---

# 4. 「語用論」は発話行為として解析する

ここからさらに一段上です。

たとえば、

```text
確認してください。
```

は文法だけ見れば命令です。

でもSlackでは、

```text
確認を依頼する
```

という**発話行為 speech act**です。

文章ごとに、

```yaml
speech_act:
  type: request
  requested_action: PRを確認する
  addressee: レビュアー
```

と持たせます。

他には、

```text
報告
質問
依頼
許可要求
謝罪
確認
提案
警告
予定通知
完了通知
```

などがあります。

例えば、

> 17:30ごろmainにマージいたします。何か問題ございましたら、お声がけください。

なら、

```yaml
speech_act:
  primary: schedule_announcement
  secondary: objection_request
```

です。

これを単純な「丁寧な文章にしてください」に渡すと、

> 17:30頃にマージさせていただければと存じます。

などと**許可を求めている文章に変質する**ことがあります。

元は、

```text
私は17:30にやる
問題があれば言って
```

です。

なので、

```text
発話行為を変更禁止
```

は重要な制約になります。

---

# 5. 敬語は「誰から誰へ」をモデル化する

敬語だけ独立して直させると事故りやすいです。

最低でも、

```yaml
participants:
  author:
    role: engineer

  recipient:
    role: client

social_relation:
  direction: author_to_client
  formality: business
  distance: medium
```

のような情報を持たせます。

そして敬語チェックをする。

例えば、

```text
確認いたしました。
```

は、

```text
確認する主体 = 自分
```

なので謙譲的な `いたす` は自然です。

一方、

```text
佐藤様が確認いたしました。
```

は相手側人物ならおかしい可能性がある。

```text
佐藤様がご確認くださいました。
```

などが候補になります。

ここでも項構造が役立ちます。

まず、

```text
確認する.agent = 誰か
```

を確定してから、

```text
その人物と書き手・聞き手の関係
```

を見るわけです。

つまり、

> **敬語判定にも項解析が必要**

なんです。

# 6. 最後に「文体」を適用する

文体はもっと表層に近い。

```yaml
style:
  medium: slack
  register: business-casual
  verbosity: concise
  politeness: polite
  emoji: false
```

メールなら、

```yaml
style:
  medium: email
  register: formal-business
  verbosity: normal
  politeness: high
```

技術文書なら、

```yaml
style:
  medium: technical_document
  register: neutral
  sentence_end: plain
  prefer_explicit_subjects: false
```

という感じです。

大切なのは、

> **文体の都合で意味を変えてはいけない**

という優先順位です。

```text
意味 > 指示関係 > 発話意図 > 情報構造 > 敬語 > 文体
```

くらいで考えるとよいです。

# agent skill にするなら

実際にはLLMに以下のような**内部フェーズ**を強制するとよいと思います。

```text
Phase 1: Semantic analysis

- すべての述語を抽出する。
- 各述語の項を特定する。
- 省略された項を推定する。
- 指示表現の先行詞を特定する。
- 不明なものは UNKNOWN のまま残す。


Phase 2: Discourse analysis

- 現在の主題を特定する。
- 各文の topic / focus を推定する。
- 文間で主体・対象が不用意に切り替わっていないか確認する。


Phase 3: Pragmatic analysis

- 発話行為を特定する。
  request / report / question / proposal / apology /
  announcement / confirmation / warning

- 書き手が相手に何をしてほしいかを特定する。
- 推敲によって発話行為を変更してはならない。


Phase 4: Social analysis

- 書き手、読み手、第三者を区別する。
- 敬語の方向を判定する。
- 尊敬語・謙譲語・丁寧語の主体を検証する。


Phase 5: Style transformation

- 媒体に適した文体へ整える。
- 不要な重複を削る。
- 曖昧な係り受けを修正する。
- 必要な項だけ明示する。


Phase 6: Semantic regression

推敲前後について以下を比較する。

- predicates
- arguments
- referents
- negation
- modality
- tense/aspect
- speech act
- requested action
- certainty

変化していた場合は生成し直す。
```

最後の `Semantic regression` はかなりおすすめです。

## さらに強くするなら「意味グラフ」を一度作る

たとえば、

```text
Node.jsのバージョンが低いことが原因のエラーが
今後多発する可能性があるため、
Azure環境のNode.jsを24 LTSに引き上げたいです。
```

を、

```text
[Node.js version]
       │ low
       ▼
    [errors]
       │ may increase
       ▼
    [future]

[author]
   │ wants
   ▼
[upgrade]
   │ target
   ├── backend
   ├── frontend
   │
   └── version → Node.js 24 LTS
```

くらいにしてしまう。

そして推敲後もこのグラフが保存されていることを確認します。

これなら、

```text
今後エラーが発生するため
```

と直してしまう事故も検出できます。

原文は、

```text
多発する「可能性」がある
```

だけなので、

```yaml
modality:
  possibility: true
```

を失ってはいけないからです。

# 実装上は7レイヤーくらいがちょうどいい

私はこんな構成を勧めます。

```text
┌─────────────────────────┐
│ 7. Surface / Style      │ ← Slackらしい文章にする
├─────────────────────────┤
│ 6. Politeness           │ ← 敬語
├─────────────────────────┤
│ 5. Pragmatics           │ ← 報告・依頼・質問
├─────────────────────────┤
│ 4. Information Structure│ ← は/が、topic/focus
├─────────────────────────┤
│ 3. Discourse            │ ← これ/それ/省略の指示先
├─────────────────────────┤
│ 2. Predicate-Argument   │ ← 誰が何を誰に
├─────────────────────────┤
│ 1. Lexical Semantics    │ ← 「反映する」等の語義
└─────────────────────────┘
```

そして**下から解析し、上から文章生成する**。

```text
解析：
語義
→ 項
→ 談話
→ 情報構造
→ 語用論
→ 敬語
→ 文体

生成：
文体
← 敬語
← 語用論
← 情報構造
← 談話
← 項
← 語義
```

これが推敲 agent の設計としてかなり美しいです。

特にご主人様が作ろうとしている**仕事上の日本語を直す skill**なら、単なる「自然な日本語にしてください」から一段上がって、

> **元文から意味表現をいったん構築し、その意味表現を制約として自然な日本語を再生成する**

という設計にすると強力です。

そして、この中で最重要なのは実は「項」そのものより、**項を中心にして語義・談話・情報構造・語用論を接続できること**です。推敲前後の意味保存までかなり機械的に検証できるようになります。
