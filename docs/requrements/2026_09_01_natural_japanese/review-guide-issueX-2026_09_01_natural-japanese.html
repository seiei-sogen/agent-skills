1. このレビューガイドの使い方

このガイドは、natural-japanese-rewriter と natural-japanese-rewrite-analyzer の変更を、要件、実行時フロー、意味不変条件、検証結果の順に確認するための案内である。

想定読者は、次を判断するレビュアーである。

  • 日本語推敲の基礎を述語項グラフへ置く設計が、原文の意味保持に寄与するか

  • 親スキルと analyzer の責務、入出力契約、縮退動作が整合するか

  • 自然な省略を残しつつ、曖昧な項だけを安全に修復できるか

  • 推敲後の意味回帰と文書構造の破損を検出できるか

レビュー対象は、二つの SKILL.md、要件、実装計画、派生 HTML、実装前バックアップである。 外部 NLP エンジン、辞書、実行時コードの品質は対象外である。

4. 実行時フロー

入力と出力モードを確定
  ├─ 対象不明 → 対象を1件確認して終了
  └─ 対象確定
       ↓
Phase 1: analyzer で述語項グラフを構築
  ├─ analyzer あり → 正規契約を使用
  └─ analyzer なし → 親の同一スキーマで縮退し、最終報告に記録
       ↓
Phase 2: 談話 → 情報構造 → 語用論 → 対人関係 → 文体を固定
       ↓
Phase 3: 修復する / 意図的に残す / 要確認を分類
  ├─ 復元可能な自然な省略 → 残す
  ├─ 安全に直せる曖昧さ・翻訳調・冗長さ → 修復する
  └─ 確定不能 → 原文保持または要確認
       ↓
Phase 4: 意味制約を優先して候補文を生成
       ↓
Phase 5: グラフ、上位レイヤー、保護範囲、文書構造を再比較
  ├─ 一致 → Phase 6
  ├─ 不一致 → SEMANTIC_DRIFT として再生成
  └─ 3巡で未解消 → 該当箇所を原文へ戻し、必要なら要確認
       ↓
Phase 6: polish または diagnostic で出力

このスキル自体は外部サービスへ接続しない。 ファイル入力では、Phase 5 を通過した必要最小限の編集だけを対象ファイルへ反映する。

5. 難しい処理

5.1. 表層と意味を分離する

助詞、語順、態、項の明示・省略が変わっても、意味役割が同じなら許容する。 表層の完全一致を要求すると、主題化や自然な省略を保ったリライトができないためである。

一方、述語の語義、指示対象、項の役割、極性、モダリティ、発話行為、敬語の方向は意味不変条件として保持する。

5.2. 実現形式と談話上の役割を分ける

skills/natural-japanese-rewrite-analyzer/SKILL.md:55 では、realization と discourse_role を別フィールドにしている。

これにより、次を同時に表現できる。

  • このPRは確認しました。 の このPR: overt + topic

  • 次文の 確認しました。 で継続する対象: zero + topic-continuation

topic を実現形式の一種にすると、明示か省略かと主題性が排他的になり、AC-04 を満たせないため採用しなかった。

5.3. 不確実性を消さない

語義や先行詞を一意にできない場合は、候補集合、ambiguous、unknown を保持する。 数値確信度は、根拠のない精密さを与えるため必須にしていない。

安全な候補すべてに共通する修正だけを行い、それ以外は原文保持または 要確認 とする。

5.4. 語義候補ごとの格フレームを分ける

複数の語義候補が異なる格フレームを持つとき、単一の項一覧へ統合すると、どの意味役割がどの語義に属するか分からなくなる。 語義候補、格フレーム、項スロットへそれぞれ ID を付け、各 argument が sense_id、frame_id、slot_id で一つの候補を参照する。 同じ表面の句が複数候補へ対応しても項を候補ごとに分け、互換性のない意味役割を統合しない。

5.5. 正規契約と互換ビューを分ける

skills/natural-japanese-rewrite-analyzer/SKILL.md:104 の schema_version: 2 では、surface と arguments を正規フィールドとする。 旧 verb、args、omitted_args は、正規フィールドから導出する互換ビューとして保持する。 args は mapping、omitted_args は sequence の v1 コンテナ型を維持する。 旧契約の omitted_args は復元できる省略項を表すため、realization: zero だけでなく、recoverability: clear で指示対象が一意という条件も満たす項だけを投影する。 未解決のゼロ項は正規の arguments に残し、旧互換ビューへは出さない。 複数の語義候補が残る場合は、各 legacy_label について全候補の格フレームが同じ指示対象と実現形式に合意するときだけ1回投影し、重複や候補依存の値を作らない。 args と omitted_args は語義別役割を落とす lossy view であり、意味判断は正規グラフで行う。 analyzer 不在時の親スキルも同じ導出規則を使うため、縮退実行だけ互換ビューが空のまま残ることはない。

互換ビューを正規フィールドと独立に編集すると不整合が生じるため、矛盾時は正規フィールドを優先し、矛盾自体を ambiguities に記録する。

5.6. 意味回帰と文書構造を同時に守る

skills/natural-japanese-rewriter/SKILL.md:226 では、候補文へ Phase 1 と Phase 2 を再実行する。 意味グラフだけでなく、原文と候補文の見出し、リスト項目、表の行、コードブロックを対応付け、要素数、順序、階層、入れ子、境界を比較する。

構文上は妥当でも構造要素が脱落または並べ替えられた候補は完成品にできないため、文書構造を原文比較型の回帰ゲートへ含めている。 3巡で不一致を解消できない場合は、文分割・結合や共有指示対象で結び付く編集を原子的修復単位として原文へ戻す。 復元後の候補文全体を同じゲートで再検証し、不一致が0件になるまで出力へ進まない。

8. 重点チェック

レビュアーには、特に次を確認してほしい。

  1. analyzer の正規スキーマと、親の縮退スキーマで、entity、predicate、argument、issue の形と列挙値が一致しているか。

  2. 複数の語義候補で、各 argument が対応する格フレームと項スロットを ID で参照し、役割を混同しないか。

  3. realization と discourse_role の分離で、明示・省略と主題・焦点を独立に表せるか。

  4. 旧 verb、args、omitted_args を互換ビューとして残す判断が、移行コストと契約の明確さのバランスを取れているか。

  5. omitted_args が一意に復元できるゼロ項だけを含み、未解決の項を旧利用者へ復元可能として見せないか。

  6. 複数の語義候補が同じ省略参加者を持つ場合に、旧ビューへ重複せず1回だけ投影し、候補間で競合する項を除外できるか。

  7. analyzer 不在時も、正規フィールドから互換ビューを一貫して導出できるか。

  8. 翻訳調や冗長さを直す経路が、意味グラフの修復トリガーだけに閉じていないか。

  9. Phase 5 が、モダリティ、発話行為、敬語の方向に加え、原文と候補文の文書構造を要素単位で比較しているか。

  10. 原文復帰後に候補文全体を再検証し、分割・結合や指示関係で結び付く編集の回帰を見逃さないか。

  11. polish で内部分析を出しすぎず、diagnostic では判断根拠を確認できるか。

9. 既知の制約と対象外

  • 外部の語義辞書、格フレーム辞書、形態素解析器を使わないため、候補抽出の精度は実行モデルと入力文脈に依存する。

  • 本変更はスキル指示の実装であり、意味グラフを実行コードとして永続化または機械検証しない。

  • Phase 2 の発話行為、requested action、敬語、文体は専用の型付きオブジェクトを追加せず、内部分析と graph_invariants で保持するため、外部から機械監査する場合は格納方法が一定とは限らない。

  • 解消不能な曖昧さを自動で決めず、原文保持または 要確認 にする設計である。

  • references/detailed-rules.md 全体の再編、UI メタデータ、起動条件、外部依存の追加は対象外である。

  • GitHub Enterprise Managed User の制約により、CLI から PR 本文を更新できない。最終本文は生成し、必要に応じて手動反映する。
