== このレビューガイドの使い方

このガイドは、`natural-japanese-rewriter` と `natural-japanese-rewrite-analyzer` の変更を、要件、実行時フロー、意味不変条件、検証結果の順に確認するための案内である。

想定読者は、次を判断するレビュアーである。

* 日本語推敲の基礎を述語項グラフへ置く設計が、原文の意味保持に寄与するか
* 親スキルと analyzer の責務、入出力契約、縮退動作が整合するか
* 自然な省略を残しつつ、曖昧な項だけを安全に修復できるか
* 推敲後の意味回帰と文書構造の破損を検出できるか

レビュー対象は、二つの `SKILL.md`、要件、実装計画、派生 HTML、実装前バックアップである。
外部 NLP エンジン、辞書、実行時コードの品質は対象外である。

== 実行時フロー

[source,text]
----
入力と出力モードを確定
  ├─ 対象不明 → 対象を1件確認して終了
  └─ 対象確定
       ↓
Phase 1: analyzer で述語項グラフを構築
  ├─ analyzer あり → 正規契約を使用
  └─ analyzer なし → 親の同一スキーマで縮退し、最終報告に記録
       ↓
Phase 2: 談話 → 情報構造 → 語用論 → 対人関係 → 文体を固定
       ↓
Phase 3: 修復する / 意図的に残す / 要確認を分類
  ├─ 復元可能な自然な省略 → 残す
  ├─ 安全に直せる曖昧さ・翻訳調・冗長さ → 修復する
  └─ 確定不能 → 原文保持または要確認
       ↓
Phase 4: 意味制約を優先して候補文を生成
       ↓
Phase 5: グラフ、上位レイヤー、保護範囲、文書構造を再比較
  ├─ 一致 → Phase 6
  ├─ 不一致 → SEMANTIC_DRIFT として再生成
  └─ 3巡で未解消 → 該当箇所を原文へ戻し、必要なら要確認
       ↓
Phase 6: polish または diagnostic で出力
----

このスキル自体は外部サービスへ接続しない。
ファイル入力では、Phase 5 を通過した必要最小限の編集だけを対象ファイルへ反映する。

== 難しい処理

=== 表層と意味を分離する

助詞、語順、態、項の明示・省略が変わっても、意味役割が同じなら許容する。
表層の完全一致を要求すると、主題化や自然な省略を保ったリライトができないためである。

一方、述語の語義、指示対象、項の役割、極性、モダリティ、発話行為、敬語の方向は意味不変条件として保持する。

=== 実現形式と談話上の役割を分ける

`skills/natural-japanese-rewrite-analyzer/SKILL.md:54` では、`realization` と `discourse_role` を別フィールドにしている。

これにより、次を同時に表現できる。

* `このPRは確認しました。` の `このPR`: `overt + topic`
* 次文の `確認しました。` で継続する対象: `zero + topic-continuation`

`topic` を実現形式の一種にすると、明示か省略かと主題性が排他的になり、AC-04 を満たせないため採用しなかった。

=== 不確実性を消さない

語義や先行詞を一意にできない場合は、候補集合、`ambiguous`、`unknown` を保持する。
数値確信度は、根拠のない精密さを与えるため必須にしていない。

安全な候補すべてに共通する修正だけを行い、それ以外は原文保持または `要確認` とする。

=== 正規契約と互換ビューを分ける

`skills/natural-japanese-rewrite-analyzer/SKILL.md:101` の `schema_version: 2` では、`surface` と `arguments` を正規フィールドとする。
旧 `verb`、`args`、`omitted_args` は、正規フィールドから導出する互換ビューとして保持する。

互換ビューを正規フィールドと独立に編集すると不整合が生じるため、矛盾時は正規フィールドを優先し、矛盾自体を `ambiguities` に記録する。

=== 意味回帰と文書構造を同時に守る

`skills/natural-japanese-rewriter/SKILL.md:200` では、候補文へ Phase 1 と Phase 2 を再実行する。
意味グラフだけでなく、見出し階層、リストの入れ子、表、コードブロックの妥当性も確認する。

意味が同じでも Markdown や AsciiDoc が壊れた候補は完成品にできないため、文書構造を回帰ゲートへ含めている。

== 重点チェック

レビュアーには、特に次を確認してほしい。

. analyzer の正規スキーマと、親の縮退スキーマで、entity、predicate、argument、issue の形と列挙値が一致しているか。
. `realization` と `discourse_role` の分離で、明示・省略と主題・焦点を独立に表せるか。
. 旧 `verb`、`args`、`omitted_args` を互換ビューとして残す判断が、移行コストと契約の明確さのバランスを取れているか。
. 翻訳調や冗長さを直す経路が、意味グラフの修復トリガーだけに閉じていないか。
. Phase 5 が、モダリティ、発話行為、敬語の方向、文書構造を漏れなく比較しているか。
. `polish` で内部分析を出しすぎず、`diagnostic` では判断根拠を確認できるか。

== 既知の制約と対象外

* 外部の語義辞書、格フレーム辞書、形態素解析器を使わないため、候補抽出の精度は実行モデルと入力文脈に依存する。
* 本変更はスキル指示の実装であり、意味グラフを実行コードとして永続化または機械検証しない。
* 解消不能な曖昧さを自動で決めず、原文保持または `要確認` にする設計である。
* `references/detailed-rules.md` 全体の再編、UI メタデータ、起動条件、外部依存の追加は対象外である。
* GitHub Enterprise Managed User の制約により、CLI から PR 本文を更新できない。最終本文は生成し、必要に応じて手動反映する。
