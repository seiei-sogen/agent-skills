# 日本語リライトのパイプライン

日本語テキストを、原意・事実・仕様・技術的意味を保ったまま、分析、リライト、検証、出力の順で自然で読みやすい日本語へ仕上げる親スキルである。
対象は README、仕様書、技術記事、Zenn 記事、コードコメント、docstring、エラーメッセージ、UI 文言、issue、PR 説明文、職務経歴書など。

## 子スキルと優先順位

開始時に `natural-japanese-rewrite-analyzer` を利用できるか確認し、Phase 1 を実行する段階でその `SKILL.md` を最後まで読む。
見つからない場合はパイプラインを止めず、Phase 1 の分析メモ形式に沿って同等の分析を自前で行い、代替した事実を Phase 4 の報告に含める。

指示が衝突する場合は、現在のユーザー指示、この親スキルの Phase 固有の指示、子スキルの通常指示の順に優先する。

## 入力と成果物を確定する

入力は、リライト対象の日本語テキスト、またはファイルパスとする。
複数ファイルは1件ずつ独立したパイプラインとして扱う。
日本語リライト対象を特定できない入力では Phase 1 を始めず、対象を1つだけ確認する。

開始時に次を確定する。

- リライト対象範囲: 本文、見出し、箇条書き、コメント、UI 文言、エラーメッセージなど
- 出力先: ファイル編集か、応答本文か
- 文体: です・ます調、である調、UI 向けの短い文など、周囲の主な文体に合わせる基準

成果物は次の3つとする。

- 分析メモ: Phase 1 の内部成果物。原則としてユーザーへ出力しない
- リライト本文: ファイル編集の反映、または応答本文
- 要確認リスト: 原文だけでは判断できなかった点。0件なら省略する

1〜2文の短文や UI 文言でも Phase の順序と成果物は変えない。
分析メモと検証を内部で簡潔に済ませ、出力を本文中心に絞る。

## 最優先ルール

- 原意を変えない。
- 事実を変えない。
- 仕様を変えない。
- 技術的意味を変えない。
- 原文から判断できない情報を補わない。
- コード、コマンド、ファイルパス、API 名、設定値、数値、固有名詞、引用、リンク先、構造化データは、明確な誤りがない限り保護範囲として保持する。
- 問題のない文はそのまま残す。

自然さより意味保持を優先する。
判断材料が不足する場合は、次の順で安全側に倒す。

1. 文脈から一意に復元できる直しだけ行う。
2. 一意に決まらない箇所は、原文の表現を保持する。
3. 保持すると読みにくい場合は、意味を足さない範囲でぼかす。
4. それでも読み手が誤解しうる場合だけ、本文へ混ぜずに `要確認` として短く分ける。

## Phase 1: 分析

`natural-japanese-rewrite-analyzer` の分析手順で、リライト対象の保護範囲、述語、項、付加部、骨格、曖昧さを分析し、次の形式で分析メモを作る。

```yaml
protected_ranges:
  - 変更してはいけない語句、コード、数値、仕様、固有名詞、引用
rewrite_targets:
  - 不自然さ、翻訳調、冗長さ、係り受け、助詞、文分割の問題
predicates:
  - 述語と対応する項
adjuncts:
  - 条件、理由、目的、時点、範囲などの付加部
ambiguities:
  - 原文だけでは判断できない箇所
rewrite_policy:
  - 分割、語順変更、助詞調整、省略維持、明示化の方針
```

完了条件: リライト対象の全文が分析メモに反映され、各述語の項が「明示・復元可・複数候補・復元不能」のどれかに分類され、保護範囲と曖昧さが列挙されている。
満たしたら Phase 2 へ進む。

## Phase 2: リライト

分析メモの `rewrite_policy` に沿って、文ごとに「そのまま残す」か「直す」かを決めて処理する。
長文、技術的な曖昧さが多い文、判断に迷う文、既存の詳細ルールとの照合が必要な場合は、先に `references/detailed-rules.md` を読む。

### 語順

日本語では、述語の近くに重要な項を置くと読みやすくなる。
長い条件、理由、目的、補足説明が文の骨格を圧迫している場合は、文を分ける。
ただし、文を分けることで対比、因果、条件が失われる場合は分けない。

### 助詞

助詞は意味関係を変えない範囲で自然に整える。
`は` と `が`、`を` と `に`、`で` と `により` などを入れ替える場合は、主題、焦点、対象、手段、場所、原因が変わらないか確認する。

### 冗長表現

LLM らしい定型句、翻訳調の直訳、過度に硬い名詞句は簡潔にする。
ただし、仕様書、契約文、職務経歴書などで必要な厳密さは残す。

### 文分割

一文に複数の条件、理由、例外、結果が詰まっている場合は分割する。
Markdown の箇条書き、表、コードブロック、JSON / YAML / TOML、コマンド例は構造を壊さない。

### 省略と補完

省略された主語や目的語は、文脈から一意に復元できる場合だけ補う。
補うとかえって不自然な項は、日本語として自然な省略のまま残す。

完了条件: 分析メモの `rewrite_targets` すべてが「直した」か「意図的に残した」に分類され、`protected_ranges` に変更がない。
満たしたら Phase 3 へ進む。

## Phase 3: 意味保持の検証

原文と修正後を文単位で突き合わせ、次の逸脱を確認する。

- 原意、事実、仕様、技術的意味
- 否定、条件、例外、因果、時系列、範囲
- 主体、対象、能動と受け身
- 可能性、義務、許可、推量、断定の強さ
- 保護範囲の原文との一致
- Markdown などの文書構造

逸脱を見つけたら修正し、同じ検証を再実行する。
最大3巡で逸脱が0件になったら Phase 4 へ進む。
3巡で解消しない文は原文の表現へ戻し、`要確認` に加える。

## Phase 4: 出力

ファイルが対象なら、必要最小限の変更だけを編集に反映し、変更概要と `要確認` を短く報告する。
応答本文が対象なら、修正後の本文を先に出し、必要な場合だけ主な修正点と `要確認` を短く続ける。
分析メモ全体、内部手順の説明、過剰な解説は出さない。

Phase 3 の逸脱が0件（`要確認` への退避済みを含む）で、リライト本文が出力され、`要確認` がすべて報告済み（0件なら省略）になったときだけパイプライン完了とする。
