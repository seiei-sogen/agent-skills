# 要件から設計文書を作る

要件定義書の EARS 規則と Gherkin 例を参照し、アーキテクチャ、データモデル、インターフェース、状態遷移を設計する。実装タスクは作らない。コードの実装、commit、push、PR 操作は行わない。

## 入力と出力

入力は同じ対象の `req-<topic>.adoc` と `pre-investigation-report-<topic>.json`。必要なら設計文書の保存先も受け取る。[成果物の契約](../pipe-requirements-to-pr/references/artifact-contracts.md) に従い、既定では要件定義書と同じディレクトリに `design-<issue-token>-<topic>.adoc` を作る。同名ファイルが別対象なら上書きせず停止する。

開始時に入力、関連コード、既存設計・ADR、未コミット変更を確認する。調査レポートが無効、要件と別対象、または変更すべきファイルに保持できない既存変更がある場合は停止して報告する。既存の同対象設計文書は草稿として更新し、確認済みの判断と検証結果を失わない。

## 自動壁打ち

工程に入る前に `poteto-mode-start`、`grilling-matt-p`、`quality-gated-review-improve` の `SKILL.md` を読む。poteto-mode が有効なら再起動しない。スキルが見つからなければ代替せず停止する。この工程に限り `grilling-matt-p` の質問待ちを、根拠を調べて推奨回答を自動採用する手順に置き換える。

1. 要件の EARS ID、Gherkin シナリオ、調査済みの制約、既存パターンを整理する。確認できない事実は推奨回答で補わない。
2. コンポーネント境界、データの所有と保存、インターフェースの事前・事後条件、状態・失敗・並行性、移行と運用の論点を依存順に洗い出す。
3. 各論点について現行方式と有力な代替を比較し、採用案、根拠、影響、不確実性を記録する。安全な既定値を置ける設計判断は推奨案を採用して進む。セキュリティ、データ損失、外部契約などで安全な案を置けなければ停止する。
4. [成果物の契約の設計文書](../pipe-requirements-to-pr/references/artifact-contracts.md#設計文書) を満たす AsciiDoc を保存する。EARS と Gherkin は参照 ID とシナリオ名で結び、設計文書を両者の形式で書き直さない。

## 状態・並行性の核を Quint で確かめる

並行する操作、再試行、タイムアウト、複数段階の状態遷移などが要件の成否を左右する場合は両スキルの `SKILL.md` を読み、`quint-modeling` の「from requirements」と `quint-lang` を使う。対象の操作と不変条件だけを `.qnt` に切り出し、設計文書からファイルと対応する EARS ID・Gherkin シナリオを参照する。逐次的な CRUD や配置・技術選定だけなら Quint を追加せず、理由を設計文書に書く。

Quint の対象範囲、操作の粒度、時間や障害の前提も、要件・調査・関連コードから自律的に決めて記録する。`quint-modeling` の確認待ちはこの工程では設計判断の自動採用に置き換える。モデルの意味が変わる未確認の事実に安全な前提を置けない場合だけ停止する。

EARS の常時・状態規則を不変条件、イベント・異常規則をガード付き action、Gherkin の代表例を実行トレースへ対応付ける。状態の形と操作の前後条件をモデル化し、並行性が重要なら競合する操作の介在を表す。UI、HTTP、DB インデックスなどモデルの性質に無関係な詳細は AsciiDoc の設計に置く。Quint の構文と CLI は `quint-lang` を正とし、例示コードを未検証のまま転記しない。

モデルは小さな単位で `quint typecheck`、`quint test`、`quint run` を実行し、対応するトレースと不変条件を確認する。並行性の安全性が設計の中心で有限の検査範囲を定められる場合は `quint verify` による有界検査も行う。反例が出たら設計または根拠ある要件を修正して再実行する。検査した範囲、使用したコマンド、結果、未検査の条件を設計文書に残す。サンプル実行や有界検査を無制限の正しさの証明として扱わない。必要な CLI や検査環境が使えない場合は制約と再実行手順を記録し、検証完了とせず次工程へ進まない。

## 品質ゲートと引き渡し

`quality-gated-review-improve` で設計文書を採点・修正する。要件定義書は採点し直さず、[成果物の契約の文書間の品質ゲート](../pipe-requirements-to-pr/references/artifact-contracts.md#文書間の品質ゲート) に従って整合だけを確認する。EARS 規則とシナリオから設計上の責務・操作・検証へ追えるか、設計に要件外の振る舞いがないか、Quint の抽象化と結果が正しく説明されているかを確認する。モデルで判明した要件の欠落が重大な指摘に当たる場合だけ、根拠を確認して要件を修正する。設計文書が原則90点以上で重大な不整合が0件なら完了する。モデルの必須不変条件に未解決の反例がある場合は次工程へ進めない。

更新した要件定義書、設計文書、Quint ファイル、品質点、Quint の実行結果と残課題を報告する。
