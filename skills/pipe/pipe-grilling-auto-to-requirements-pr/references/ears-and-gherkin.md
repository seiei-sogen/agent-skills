# 要件の規則と受け入れ例

要件定義書では、適用範囲のある規則を EARS、具体的な受け入れ例を Gherkin で書く。EARS が正本であり、Gherkin はその規則を代表的な入力・状態で確かめる。1つの規則に必要なら複数の例を対応させる。例だけから未記載の規則を推測させない。

- 判定可能な機能要件、利用者に見える失敗時の結果、性能・安全性などの制約は、必要な条件と結果を EARS で記す。無条件は「システムは〜しなければならない」、状態は `While`、イベントは `When`、異常条件は `If … then`、機能の有無は `Where` を使う。閾値や時間など規則を決める値は EARS に残す。UI 操作や特定ユーザー名は規則の意味に必要な場合だけ入れる。
- Gherkin の代表例は、判断の境界がある規則にだけ `Given` / `When` / `Then` で書く。判断の境界とは、対象の選び方、閾値、一致判定、結果の分岐のように、入力や状態の違いで結果が分かれる箇所をいう。境界ごとに、結果が分かれることを示す最小限の例を置く。`Given` は前提、`When` は操作・事象、`Then` は公開インターフェースから観測できる結果にする。境界のない規則や、性能などシナリオにしにくい規則は EARS と測定方法で十分とする。内部の失敗や並行操作の割り込みへの対処は、設計文書と実装計画のテストで確かめる。
- 規則に安定した ID を付け、各シナリオに対応する ID を `@REQ-001` のようなタグで付ける。シナリオが規則にない振る舞いを示したら、根拠を確認して規則を補うか、シナリオを直す。既存の要件 ID や見出し体系があればそれを使う。
- AsciiDoc では EARS を通常の本文、Gherkin を `[source,gherkin]` のコードブロックに置く。文書の既存構成を保ち、関連する規則と例を近くに配置する。Gherkin 記法はテストツールの導入を意味しない。

例。規則の閾値と解除条件は EARS に置き、Gherkin で境界を確かめる。

```text
REQ-001: When 同一アカウントのパスワード認証が5回連続で失敗したとき、システムはそのアカウントを15分間ロックしなければならない。
REQ-002: While アカウントがロックされている間、システムは正しいパスワードでもログインを拒否しなければならない。
REQ-003: When ロック開始から15分経過したとき、システムはアカウントのロックを解除し、正しいパスワードによるログインを許可しなければならない。

[source,gherkin]
----
@REQ-001
Scenario: 5回目の失敗でロックされる
  Given アカウント "alice" は4回連続で認証に失敗している
  When "alice" が誤ったパスワードでログインする
  Then アカウント "alice" はロックされる

@REQ-002
Scenario: ロック中は正しいパスワードでも拒否される
  Given アカウント "alice" は14分前にロックされた
  When "alice" が正しいパスワードでログインする
  Then ログインは拒否される

@REQ-003
Scenario: 15分経過するとログインできる
  Given アカウント "alice" は15分前にロックされた
  When "alice" が正しいパスワードでログインする
  Then ログインは成功する
----
```

この例で「成功を挟むと連続失敗回数をリセットする」ことも求めるなら、その規則を別の EARS 要件として追加してから受け入れ例を書く。
