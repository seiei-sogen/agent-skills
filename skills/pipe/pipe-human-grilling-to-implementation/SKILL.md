# 人間との壁打ちで要件・設計・実装を進める

`pipe-requirements-to-pr` から、事前調査、要件定義、design、実装計画、実装と検証を切り出した親スキルである。
事前調査は要件定義の前に自動で行い、壁打ちの判断には人間の回答を使う。
実装・検証と文書の HTML 生成までを対象とする。commit、push、PR 操作、PR 用の差分レビューとレビューガイド生成は対象に含めない。

## 子スキルと実行モード

開始時に次のスキルを利用できることを確認し、それぞれを実行する段階で `SKILL.md` を最後まで読む。

- `poteto-mode-start`
- `pre-investigation-report`
- `grilling-matt-p-anti-kajo`
- `pipe-grilling-auto-to-requirements-pr`
- `pipe-auto-grilling-design`
- `pipe-generate-quality-gated-implementation-plan`
- `quality-gated-review-improve-anti-kajo`
- `tdd-matt-p`
- `asciidoc-to-colorful-html`
- `easy-to-understand`

issue 入力では `git-suggest-branch-name`、Quint が必要な設計では `quint-modeling` と `quint-lang`、そのモデルに沿う実装では `quint-execute-spec` も読む。
必要なスキルが見つからなければ同等手順で代替せず、名前と停止した工程を報告する。

指示の優先順位は、現在のユーザー指示、この親スキルの段階固有の指示、子スキルの通常指示の順とする。
名前に `auto` を含む子スキルにも、以下の人間との壁打ち、実行範囲、完了条件を明示して渡す。
子スキルの推奨回答の自動採用、commit・push・PR 操作、および remote や PR を必須とする完了条件は、このスキルでは適用しない。

全工程を始める前に `poteto-mode-start` を使い、このスキルへの依頼全体を対象タスクとして渡す。
poteto-mode が有効なら再起動せず、その状態を引き継ぐ。
調査、文書作成、実装、検証は poteto-mode で進め、壁打ちの回答待ちはこの親スキルに従う。

## 入力と成果物を確定する

入力は既存の `req-<topic>.adoc` 1件、または GitHub issue URL 1件とする。
入力がない場合は、対象のパスまたは URL だけを確認する。複数の入力は独立したパイプラインとして扱う。

[成果物の契約](../pipe-requirements-to-pr/references/artifact-contracts.md) を読み、識別子と保存先を決める。
要件定義書と同じディレクトリに、調査レポート、設計文書と必要な図・Quint モデル、実装計画、3文書の HTML、実装計画の解説 HTML を保存する。
ユーザーが保存先を指定した場合はその指定を優先する。同名の別対象ファイルは上書きしない。

Git リポジトリ、現在のブランチ、作業ツリー、適用される指示を確認し、開始時の変更一覧を記録する。
既存変更を保持できない箇所は作業前に報告する。既存変更を巻き戻したり、パイプラインの成果物として扱ったりしない。
既存の要件ドラフトを入力にして統合先ブランチ上にいる場合は、事前調査の前に対象の作業ブランチを用意する。
親が確定したブランチと worktree を全工程で使い、子スキル側で作り直さない。

issue 入力では [issue の初期化手順](../pipe-requirements-to-pr/references/github-issue-bootstrap.md) の取得、リポジトリ照合、ブランチ命名、worktree の準備までを先に行う。
ここでは要件定義書を生成せず、取得した issue 本文とコメントを調査入力にする。
`<branch-tail>` から `<topic>` と要件定義書の予定パスを確定し、その worktree を以後の作業ルートにする。
既存の要件ドラフトを入力にした場合も、事前調査が完了するまでその文書を更新しない。

## 人間との壁打ちの共通ルール

要件定義、設計、実装計画では `grilling-matt-p-anti-kajo` の通常モードを使う。
子スキルにある質問待ちの省略や推奨回答の自動採用は行わない。

1. 調査済みの事実と、これから人間が決める判断を分ける。コードや設定で調べられる事実は自動で確認する。
2. デザインツリーと依存関係を整理する。前提が確定した質問を、番号、選択肢、推奨回答、根拠と影響を付けて一つのラウンドで提示する。
3. ユーザーの回答を待つ。推奨案、無回答、時間の経過を回答として扱わない。別の未回答質問に依存する問いは次のラウンドへ送る。
4. 回答から派生した論点を反映し、残るフロンティアを聞く。部分回答の場合は未回答を残し、それに依存する判断を進めない。
5. フロンティアが空になったら、この段階の決定、対象外、残る制約を要約し、共通理解に達したことをユーザーに確認する。確認を得るまで、その判断に基づく次工程へ進まない。

各段階の文書に、質問、実際の回答、採用理由、根拠、未回答事項、共通理解の確認を記録する。
推奨案と実際の回答を区別し、回答のない項目を合意済みにしない。
対象外や未確定に置く判断にもユーザーの回答を使う。確認できない事実は、確認方法とともに未確定事項へ残す。

品質ゲート、Quint 検査、実装中の発見で、合意した挙動・対象範囲・制約・設計方式を変える必要が出た場合は、影響する判断の壁打ちへ戻る。
点数を上げるために人間の決定を自動で変更しない。
意味を変えない文章修正、既存パターンに従う実装、事実の追加調査、テストのシーム選びは、元の方針どおり自動で進める。

## Phase 0: 事前調査を自動実行する

要件定義の壁打ちや文書作成を始める前に、入力を調査対象として `pre-investigation-report` を実行する。
保存先は `pre-investigation-report-<topic>.json` とする。調査開始についてユーザーの確認を挟まない。
既存ドラフトまたは取得した issue を、達成したい結果、守るべき制約、提案された実現方法に分けて読む。
要件に関係する責務、処理の流れ、制約、既存パターン、判断の根拠、未解決の問いを調査する。
推奨案は候補として記録し、人間の決定として採用しない。

生成した JSON をパースし、子スキルのキーと型、根拠パス、`open_questions`、同じ対象の調査であることを確認する。
この工程で変更するのは調査レポートだけとする。要件定義書の編集やコードの実装を先行させない。
有効で現在のコード・入力・対象範囲に合うレポートがあれば再利用し、不足分を同じ JSON に追加する。
未確認の事実が後続判断を左右する場合は追加調査し、確認できないまま確定事項にしない。
この検証が完了したら、ユーザーに調査結果を示して Phase 1 へ進む。

## Phase 1: 要件定義を人間との壁打ちで確定する

issue 入力の場合は、Phase 0 のレポートを確認した後に、初期化手順の要件定義書作成だけを行う。
issue から読み取れる事項を草稿にし、未決事項は壁打ちに残す。

`pipe-grilling-auto-to-requirements-pr` には、要件定義書と検証済み調査レポートを渡し、Phase 2 の要件確定と Phase 3 の品質ゲートだけを委譲する。
次を段階固有の指示として渡す。

- 事前調査は親の Phase 0 で完了している。必要な追加調査だけを同じレポートへ反映する。
- `grilling-matt-p-anti-kajo` は人間との壁打ちの共通ルールに従い、通常の回答待ちを行う。
- [要件定義書の契約](../pipe-requirements-to-pr/references/artifact-contracts.md#要件定義書) と [EARS/Gherkin の記法](../pipe-grilling-auto-to-requirements-pr/references/ears-and-gherkin.md) に従う。
- 採用した判断、代替案、判断から学べる内容は、人間の回答と調査根拠から書く。自動で安全側へ倒して対象外にする手順も、人間への質問に置き換える。
- 要件の品質改善は `quality-gated-review-improve-anti-kajo` で行い、[共通の改善ループ上限](../pipe-requirements-to-pr/references/artifact-contracts.md#文書間の品質ゲート) を子スキルにも引き継ぐ。判断を変える改善は人間へ戻す。
- 子スキルの Phase 4・5 の公開処理は実行しない。

完了には、同じパスの要件定義書に実際の回答と共通理解の確認が反映され、調査 JSON が有効で、要件の品質点が80点以上であることを確認する。
90点以上を目標とし、品質ゲートの最終点、終了理由、未確定事項を記録する。

## Phase 2: design を人間との壁打ちで確定する

更新済み要件定義書、調査レポート、設計文書の指定パスを `pipe-auto-grilling-design` に渡す。
自動採用の手順を共通ルールに置き換え、責務の境界、データの所有と保存、公開インターフェース、状態遷移、失敗・並行時の扱い、移行と運用を人間と詰める。
設計文書の内容、図、EARS ID と Gherkin から設計要素への対応、品質ゲートは元の子スキルどおりとする。

Quint が必要になる条件と検査方法も子スキルどおりとする。
モデルの意味を左右する設計判断は、根拠と推奨案を示して人間に決めてもらう。モデル作成スキルの確認待ちを自動採用へ置き換えない。
検証環境がない場合や必須不変条件に未解決の反例がある場合は、制約を報告し、設計を検証済みとして次工程へ進めない。
反例の解消に要件や設計の判断変更が必要なら、該当段階の人間との壁打ちへ戻る。

設計文書と共通理解の確認を実物で確認し、品質点が原則90点以上で、要件との重大な不整合が0件なら完了とする。

## Phase 3: 実装計画を人間との壁打ちで確定する

更新済み要件定義書、設計文書、調査レポート、実装計画の指定パスを `pipe-generate-quality-gated-implementation-plan` に渡す。
同スキルの自動壁打ちを共通ルールに置き換え、変更境界、依存順、方式の比較、テスト戦略、移行、ロールバック、運用上の判断を人間と詰める。
方式比較と学びの整理の適用条件、文書の内容、品質ゲートは元の子スキルを引き継ぐ。

テスト戦略には `tdd-matt-p` を使い、[テスト方針](../pipe-requirements-to-pr/references/artifact-contracts.md#テスト方針) に従う。
シームは事実と公開インターフェースから自動で選び、理由を計画へ記録する。合意済みのテスト戦略を変える必要がある場合だけ壁打ちへ戻る。
各タスクは EARS ID を `Satisfies`、設計文書と Quint の対応を `Design`、Gherkin または測定・確認条件を `Done when` に結び付ける。
最小の正常系を端から端まで通してから、状態依存・異常系へ進む縦切りの計画にする。

実装計画の共通理解の確認を得て、品質点が原則90点以上、文書間の重大な不整合が0件になったら完了とする。
子スキルの例外終了条件を使う場合も、人間が決める判断を未回答のまま進めず、残課題が実装を危険にしないことと終了理由を記録する。
確定した要件・設計・計画と検証順序をチェックポイントとして共有し、公開処理を挟まず Phase 4 へ進む。

## Phase 4: 実装と検証

合意と品質ゲートを通過した設計文書・実装計画に従い、タスクを上から実行する。
Quint モデルがある対象は `quint-execute-spec` で操作・不変条件と実装の対応を検証する。
テストを生成・変更する前に `tdd-matt-p` を使い、元のテスト方針を各サイクルの前と途中で適用する。

1. 必要なコードと周辺文脈を読み、公開インターフェースと検証する振る舞いを確認する。
2. テストを追加するタスクは、正常系・境界条件・失敗系を1件ずつ扱う。意図した理由で失敗することを確認し、最小実装で通してから次へ進む。テスト追加が不要なタスクは計画どおり実装する。
3. 対象を絞った検証から、変更全体に必要な lint、型チェック、テスト、ビルド、実アプリの確認へ広げる。
4. 今回の変更が原因の失敗を修正して再検証し、実施結果と完了したタスクを計画へ反映する。

`Satisfies` を満たし、`Done when` を実際に確認した結果を各タスクに残す。
計画外の変更が必要な場合は、影響する要件・設計・モデル・計画を見直す。判断が変わる場合は人間との壁打ちと該当の品質ゲートを通し直してから実装する。
Quint の不変条件を通すためだけにモデルを弱めない。対象外の既存問題は記録に留める。

## Phase 5: HTML と最終確認

最新の要件定義書、設計文書、実装計画から `asciidoc-to-colorful-html` でそれぞれ同名の HTML を生成する。
`easy-to-understand` で `easy-implementation-plan-<issue-token>-<topic>.html` も生成する。
元の [HTML の契約](../pipe-requirements-to-pr/references/artifact-contracts.md#html-派生成果物) に従い、図、CSS、ローカル画像を埋め込み、単体で表示できることを確認する。
修正した AsciiDoc と派生 HTML が一致することを確認する。HTML だけで要件や判断を変更しない。

## 再開と完了報告

再開時は調査の根拠、要件・設計・計画の内容、実際の回答と共通理解の確認、品質点、実装進捗、検証結果を照合する。
ファイルがあるだけで完了としない。同じ対象・根拠・判断で完了している工程は再利用し、済んだ壁打ちを繰り返さない。
回答待ちは回答待ちとして再開し、未回答や合意を捏造しない。上流の判断が変わった場合は、影響する下流の合意と検証を確認し直す。

すべての判断が確認され、品質ゲートと計画タスクの検証を通り、成果物が最新の状態になった場合だけ完了とする。
未実施の検証や回答待ちが残る場合は、完了した工程、残る問い、停止理由、再開に必要なことを報告する。
最終回答には、成果物のパス、主な人間の判断、各品質点と終了理由、実装・検証結果、現在のブランチ、残課題を簡潔に書く。
