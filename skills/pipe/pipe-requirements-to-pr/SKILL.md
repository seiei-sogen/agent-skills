# 要件から PR までのパイプライン

既存の `req-*.adoc`、または GitHub issue から生成した `req-*.adoc` を実装可能な要件へ仕上げ、計画どおりに実装し、レビュー可能な PR まで進める親スキルである。
要件定義、設計、実装計画はそれぞれ子パイプラインへ委譲し、この親スキルは入力の確定、工程の接続、実装以降を受け持つ。
単にパイプラインの相談や設計をしているだけなら実行しない。全工程の実行、またはこのスキルの明示呼び出しを確認してから開始する。

## 子スキルと優先順位

開始時に次のスキルを利用できることを確認し、それぞれの `SKILL.md` を実行する段階で最後まで読む。

- `poteto-mode-start`
- `pipe-grilling-auto-to-requirements-pr`
- `pipe-auto-grilling-design`
- `pipe-generate-quality-gated-implementation-plan`
- `tdd-matt-p`
- `commit-push`
- `ponytail:ponytail-review`
- `review-guide`
- `asciidoc-to-colorful-html`
- `easy-to-understand`
- `pr-update-gh`

差分に TypeScript または JavaScript が含まれる場合だけ、`anti-ai-slop-typescript-general` も利用できることを確認し、Phase 6 を始める前にその `SKILL.md` を最後まで読む。

GitHub issue URL を入力にする場合だけ、`git-suggest-branch-name` も利用できることを確認し、issue 初期化を始める前にその `SKILL.md` を最後まで読む。
Quint モデルがある対象を実装する場合は、`quint-execute-spec` を利用できることを確認し、Phase 5 の前にその `SKILL.md` を読む。

指示が衝突する場合は、現在のユーザー指示、この親スキルの段階固有の指示、子スキルの通常指示の順に優先する。子スキルが見つからなければ、その工程を同等手順で代替せず、見つからないスキル名を報告して停止する。

## poteto-mode で全工程を進める

パイプラインを始める前に `poteto-mode-start` を使う。
このスキルへの依頼全体を対象タスクとして渡し、以後の調査レポート作成、要件定義、設計、実装計画、実装、検証、レビュー、commit、push、PR 作成と更新を poteto-mode が有効な状態で進める。
poteto-mode がすでに有効な場合は再度呼び出さず、その状態を引き継ぐ。

## 入力と成果物を確定する

入力は、既存の AsciiDoc 要件定義書 `req-<topic>.adoc` 1件、または `https://github.com/<owner>/<repo>/issues/<number>` 形式の GitHub issue URL 1件とする。複数指定された場合は1件ずつ独立したパイプラインとして扱う。

- 既存の `req-*.adoc` が入力なら、そのファイルを後続工程の要件定義書として今までどおり処理する。
- GitHub issue URL が入力なら、[GitHub issue から要件定義書を初期化する](references/github-issue-bootstrap.md) を読み、ブランチ、worktree、要件定義書を作成する。生成した `req-*.adoc` を後続工程の入力に設定し、その worktree 内で既存の流れへ合流する。
- どちらにも該当しない入力では後続工程を始めず、必要なパスまたは URL を1つだけ確認する。

開始時に [成果物の契約](references/artifact-contracts.md) を読み、次を確定する。

- 調査レポート: `pre-investigation-report-<topic>.json`
- 設計文書: `design-<issue-token>-<topic>.adoc`
- 実装計画: `implementation-plan-<issue-token>-<topic>.adoc`
- 実装計画の解説 HTML: `easy-implementation-plan-<issue-token>-<topic>.html`
- 要件定義書 HTML: `req-<topic>.html`
- 設計文書 HTML: `design-<issue-token>-<topic>.html`
- 実装計画 HTML: `implementation-plan-<issue-token>-<topic>.html`
- レビューガイド: `review-guide-<issue-token>-<topic>.adoc`
- レビューガイド図: `review-guide-<issue-token>-<topic>-<symbol-or-flow>.svg`
- レビューガイド HTML: `review-guide-<issue-token>-<topic>.html`

調査レポートと確定した要件定義書は Phase 1、設計文書と必要な Quint モデルは Phase 2、実装計画は Phase 3 の子パイプラインが生成する。HTML は実装とレビュー修正を終えた Phase 7 でまとめて生成する。残りもこの親スキルが生成する。

成果物は要件定義書と同じディレクトリへ置く。ユーザーが保存先を指定した場合はその指定を優先する。

Git リポジトリ、`develop`、現在のブランチ、作業ツリー、適用される指示を確認する。開始時点の変更一覧を記録し、既存変更をパイプラインの変更と混ぜない。同じファイルの同じ箇所に既存変更があり、安全に保持できない場合は停止して対象を報告する。

## 自律実行の境界

このスキルによる全工程の実行依頼は、GitHub issue URL 入力時のブランチと worktree の作成、対象要件の作成・更新、設計文書・実装計画・レビューガイドの作成、実装、検証、対象変更の commit / push、PR の作成・更新を進める根拠になる。環境が個別承認を要求する操作は、その場で承認を求める。

推奨回答の自動採用は設計上の意思決定に限る。事実はコード、設定、文書、issue から確認する。確認できない事実を作らない。判断材料が不足する場合は、次の順で処理する。

1. 既存パターンと明示要件に沿う。
2. 後から変更しやすく、影響範囲が狭い安全側の推奨案を採用する。
3. 推奨案、根拠、不確実性を要件定義書に残す。
4. セキュリティ、法令、データ損失、外部契約に関わり、安全な既定値を置けない場合だけ停止する。

## Phase 1: 要件定義（子パイプラインへ委譲）

要件定義書のパスを入力に `pipe-grilling-auto-to-requirements-pr` を使う。事前調査、自動壁打ちによる要件確定、要件の品質ゲート、要件成果物の commit と push、初回 PR の作成と本文更新までを子パイプラインへ委譲する。

委譲時に次を段階固有の指示として明示し、子スキルの既定より優先させる。

- PR の base は `develop` とする。
- 作業ブランチは親が確定したものを使い、子スキル側で新しいブランチを作らない。現在のブランチが `develop` なら、委譲前に変更内容へ合う作業ブランチを作る。
- 調査レポートの保存先は [成果物の契約](references/artifact-contracts.md) で確定した名前に従う。
- 開始時に記録した既存変更は stage も commit もしない。

完了報告から次を確認する。満たさない場合は Phase 2 へ進まず、停止理由と残課題を報告する。

- 調査レポートが有効な JSON で、必須フィールド、根拠パス、`open_questions` を含む
- 要件定義書が自動壁打ちと品質ゲートを通過した最終版で、品質点が80点以上である
- 対象成果物だけの commit が remote にあり、現在のブランチのオープンな PR を再取得して確認できている

この PR を以後の唯一の PR として扱い、後続 Phase で新しい PR を重ねて作らない。

## Phase 2: 設計文書（子パイプラインへ委譲）

更新済み要件定義書、調査レポート、設計文書の指定パスを入力に `pipe-auto-grilling-design` を使う。設計判断の自動壁打ち、設計文書と必要な Quint モデルの作成、要件との品質ゲートを委譲する。子スキルが更新した要件定義書と設計文書を後続工程の入力にする。

完了報告だけでなく成果物を確認する。設計文書がアーキテクチャ、データ、インターフェース、状態遷移を扱い、EARS ID と Gherkin シナリオから設計要素へ追えることを確かめる。Quint が必要な場合は `.qnt`、検査結果、未解決の反例がないことを確認する。設計文書の品質点が原則90点以上で重大な不整合が0件でなければ Phase 3 へ進まず、停止理由と残った指摘を報告する。

## Phase 3: 実装計画（子パイプラインへ委譲）

更新済み要件定義書、設計文書、調査レポート、実装計画の指定パスを入力に `pipe-generate-quality-gated-implementation-plan` を使う。
実装計画の自動壁打ちと生成、要件・設計との文書品質ゲートを子パイプラインへ委譲する。
子スキルが更新した要件定義書、設計文書、実装計画を、以後の最終版として扱う。

完了報告と成果物から、実装計画の最終点が原則90点以上で、文書間の重大な不整合が0件であることを確認する。
子スキルの例外終了条件に該当した場合は、残課題が実装を危険にしないことを確認する。

## Phase 4: 実装計画の commit、push

要件・設計・計画が品質ゲートを通過した時点で、実装へ進む前のチェックポイントを共有する。開始時に記録した既存変更が作業ツリーに残っていないこと、および現在の未コミット変更がすべてこのパイプラインの対象であることを確認する。`commit-push` は未コミット変更をすべて commit するため、対象外の変更を分離できない場合は実行せず、該当ファイルを報告して停止する。

`commit-push` を実行し、設計文書と図、Quint モデル、実装計画、更新した要件定義書を含む現在の対象変更を1つのコミットとして現在のブランチへ push する。子スキルの完了報告から、作成された commit と upstream の追跡参照が一致することを確認する。PR 本文の更新は Phase 8 でまとめて行う。

## Phase 5: 実装と検証

品質ゲートを通過した設計文書と実装計画に従い、タスクを上から実行する。Quint モデルがある対象は `quint-execute-spec` を使い、設計文書に記録した操作・不変条件と実装の対応を検証する。
テストを生成・変更する前に `tdd-matt-p` を使い、[成果物の契約のテスト方針](references/artifact-contracts.md#テスト方針) に従う。シームはユーザーに確認せず自律的に選び、実装計画へ記録する。「良いテストとは何か」と「アンチパターン」は各サイクルの前と途中で適用する。

1. 各タスクに必要なコードと周辺文脈を読み、検証する振る舞いと公開インターフェースを確認する。
2. テストを追加する場合は、計画した正常系、境界条件、失敗系を1件ずつ扱う。失敗するテストを実行して意図した理由で失敗することを確認し、既存パターンに従う最小実装で通してから次のテストへ進む。テスト追加が不要なタスクは計画どおり実装する。
3. 対象を絞った検証から始め、変更全体に必要な lint、型チェック、テスト、ビルドへ広げる。
4. 今回の変更が原因の失敗を修正し、同じ検証を再実行する。
5. 完了した計画タスクと実際の検証結果を実装計画へ反映する。

タスクの完了時は、`Satisfies` の EARS 規則を満たし、`Done when` の Gherkin シナリオまたは測定・確認条件を実際に検証した結果を記録する。

計画外の変更が必要になったら、要件・設計文書・Quint モデル・計画の整合を確認して更新してから実装する。Quint の不変条件を通すためだけにモデルを弱めず、要件の根拠と検査結果を確認する。対象外の既存問題は修正せず記録に留める。

## Phase 6: develop 比較レビュー

[レビューと PR](references/review-and-pr.md) を読み、差分をレビューする。対象は `develop` と現在のブランチの差分、および未コミットの対象変更である。Claude Code や Codex のホスト固有レビュー機能は使わない。

`ponytail:ponytail-review` で過剰設計を洗い出す。差分に TypeScript または JavaScript が含まれる場合は `anti-ai-slop-typescript-general` も使い、防御的な過剰実装、見せかけの型安全、不要なヘルパー、冗長な実行時チェックを洗い出す。含まれない場合は省略し、省略した理由を最終報告に残す。

`anti-ai-slop-typescript-general` のレビューと修正が終わった後に、`tdd-matt-p` で生成・変更したテストをレビューする。TypeScript / JavaScript がなく前者を省略した場合も、テストがあれば実行する。[レビューと PR](references/review-and-pr.md) の基準に従い、AI slop的なテストやアンチパターンに該当するテストを削除または修正し、必要な振る舞いの検証を残して再実行する。

各スキルの所見に加えて、正しさ、回帰、エラー処理、セキュリティ、データ損失、契約、境界条件、テスト、保守性を確認する。根拠のある指摘は修正して検証を再実行する。単純化の指摘であっても、要件定義書、設計文書、実装計画で決めた挙動、公開 API、永続化形式、セキュリティ検査、外部入力に対する正当な防御的チェックは変えない。最大3巡で、重大または高重要度の未解決指摘が0件になったら完了する。安全に直せない重大指摘が残る場合は Phase 8 の最終更新へ進まず停止し、既存 PR の URL と未解決指摘を報告する。

## Phase 7: レビューガイド

レビューガイドの生成直前に、Phase 6 の修正と再検証を終えた要件定義書、設計文書、実装計画から、次の HTML を生成する。

- `asciidoc-to-colorful-html` で要件定義書を `req-<topic>.html` へ変換する。
- `asciidoc-to-colorful-html` で設計文書を `design-<issue-token>-<topic>.html` へ変換する。
- `asciidoc-to-colorful-html` で実装計画を `implementation-plan-<issue-token>-<topic>.html` へ変換する。
- `easy-to-understand` で実装計画の解説 HTML を `easy-implementation-plan-<issue-token>-<topic>.html` に生成する。

成果物契約と各スキルの出力契約を満たし、HTML が変換元の最新内容と一致し、設計文書の図が埋め込まれていることを確認する。変換警告から include、画像、xref などの文書不備が判明した場合は AsciiDoc を修正し、設計に影響すれば Phase 2、要件・設計・計画の整合には Phase 3 の品質ゲートを再実行してから対応する HTML を再生成する。文書修正が実装に影響する場合は Phase 5〜6 も再実行する。すべての HTML が最終文書と一致したら、レビューガイドを生成する。

`review-guide`を使い、Phase 6の修正と再検証を終えた最終実装からレビューガイドを生成する。対象として`develop`と現在のブランチの差分、未コミットの対象変更、要件定義書、設計文書、Quint モデル、実装計画書、検証結果を渡し、出力先に`review-guide-<issue-token>-<topic>.adoc`を指定する。

子スキルが生成したAsciiDoc、難しい処理に対するSVG図、`review-guide-<issue-token>-<topic>.html`を最終検証の対象に含める。成果物が現在の最終差分と一致しない場合、図示すべき処理が図示されていない場合、または生成したSVGがHTMLへ埋め込まれていない場合はPhase 8へ進まない。

## Phase 8: commit、push、PR 更新

[レビューと PR](references/review-and-pr.md) の PR 手順に従う。HTML 生成後に要件定義書、設計文書、Quint モデル、実装計画を更新していた場合は、設計・モデルへの影響を Phase 2、文書間の整合を Phase 3 の品質ゲートで再確認し、Phase 7 の手順で実装計画の解説 HTML を再生成する。要件定義書、設計文書、実装計画、レビューガイド、またはSVG図を更新していた場合は、対応する HTML を `asciidoc-to-colorful-html` で再生成し、変換元の最新内容と一致することを確認する。設計文書の HTML と図、実装計画の解説 HTML、レビューガイド、参照するSVG図、そのHTML、Quint モデルまで含む対象変更だけが未コミットであることを確認してから、`commit-push` を実行する。

Phase 1 で作成した PR をそのまま使い、draft 状態を維持する。オープンな PR が見つからない場合だけ `gh pr create --draft --assignee @me` で `develop` 向け draft PR を作成する。assignee はこの環境で `gh` が認証している GitHub ユーザーとする。その後 `pr-update-gh` を実行し、設計文書・Quint モデル・レビューガイドへの導線、実施した検証、確認してほしい点を含む本文へ更新して、再取得した本文、URL、isDraft、assignees を確認する。ユーザーが明示的に指示しない限り draft を解除しない。

## 再開と完了報告

各 Phase の開始時に既存成果物と Git / PR の状態を検証する。完了条件を満たす Phase は再利用し、途中または不整合な Phase から再開する。ファイルの存在だけで完了扱いにしない。子パイプラインへ委譲した Phase は、この親スキルの段階固有の指示を反映した子スキルの完了条件で再開可否を判断する。Phase 1〜6 の再開時は HTML の未生成や未更新を不整合とみなさず、Phase 7 で最新文書との一致を確認する。

最後に次を簡潔に報告する。

- 更新・生成した要件定義書、調査レポート、設計文書と図、Quint モデル、実装計画、実装計画の解説 HTML、レビューガイド、SVG図、および4文書の HTML
- 各子パイプラインの品質ゲートの最終点と終了理由
- 実装概要と検証結果
- レビューで使ったスキル、指摘、修正結果
- 要件定義のチェックポイント commit、実装計画のチェックポイント commit、最終 commit、ブランチ、PR の URL
- 残課題。なければ「なし」

PR の作成または更新と再取得確認が完了し、重大な未解決事項がなく、上記成果物が現在の実装と一致したときだけパイプライン完了とする。
