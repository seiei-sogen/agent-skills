# レビューと PR

このファイルは `pipe-requirements-to-pr` の Phase 4、Phase 6、Phase 8 で参照する。

## 共通のレビュー対象

`develop` が存在し、現在の作業ブランチが意図した変更を含むことを確認する。レビュー対象は次の和集合とする。

- `develop...HEAD` の commit 済み差分
- index の差分
- working tree の差分
- 対象となる untracked ファイル

レビュー開始時と修正後に対象一覧を取り直す。生成物、依存ファイル、既存のユーザー変更を区別する。

## レビューの進め方

ホストやプラットフォーム固有のレビュー機能は使わない。次の順序で差分をレビューする。

- `ponytail:ponytail-review` を使い、過剰設計を洗い出す。削除できるコード、再実装された標準機能、不要な依存、投機的な抽象が対象である。
- 差分に TypeScript または JavaScript が含まれる場合は `anti-ai-slop-typescript-general` を使い、防御的な過剰実装、見せかけの型安全、不要なヘルパー、冗長な実行時チェック、抽象のノイズを洗い出す。含まれない場合は省略し、省略した理由を最終報告に残す。
- 上記のレビューと修正が終わった後に `tdd-matt-p` を使い、生成・変更したテストを「良いテストとは何か」と「アンチパターン」でレビューする。言語を問わず実施し、対象テストがない場合だけ省略する。シームの選定には [成果物の契約のテスト方針](artifact-contracts.md#テスト方針) を適用し、ユーザーへの確認は求めない。

テストレビューでは、内部実装への依存、同語反復的な期待値、内部モック、振る舞いを検証しない形だけのアサーションや重複を洗い出す。AI slop的なテストやアンチパターンに該当するテストは、検証価値がなければ削除し、必要な受け入れ条件や回帰を唯一検証している場合は公開インターフェースを通すテストへ修正する。削除・修正の理由を記録し、必要な振る舞いの検証が残っていることを確認して関連テストを再実行する。

各スキルの所見に加えて、正しさ、回帰、エラー処理、セキュリティ、データ損失、契約、境界条件、テスト、保守性を自分で確認する。

`anti-ai-slop-typescript-general` が保持を求める防御的チェックと振る舞い保持の制約を守る。要件定義書、設計文書、実装計画で決めた挙動、公開 API、永続化形式、セキュリティ検査を、単純化を理由に変えない。

所見は重大度順に、`パス:行番号`、問題、影響、根拠、修正案を示す。所見がなければ、確認した範囲と残存リスクを記録する。スタイル上の好みだけの所見は修正対象にしない。

## 修正ループ

1. 差分全体をレビューする。
2. 今回の要件に関係し、根拠が明確な所見を修正する。
3. 関係するテストと静的検査を再実行する。
4. 最新差分を再レビューする。

最大3巡とする。重大または高重要度の所見が残る場合は、回数だけを理由に Phase 8 の最終更新へ進まない。仕様判断を要するが安全側の推奨案を採れる場合は、要件・設計・計画を更新して反映する。

## commit、push、PR 前の状態確認

初回 PR は Phase 1 の要件定義パイプラインが作成する。実装、レビューガイド、最終検証が完了した Phase 8 では、新しい PR を重ねて作らず、同じ PR に最終差分を追加して本文を更新する。

### Phase 4 のチェックポイント

親スキルで `commit-push` の完了を確認した後、`develop...HEAD` の差分と commit 履歴を再確認する。現在のブランチを head に持つ PR が Phase 1 で作成した1件だけであることを検索して確かめる。見つからない場合だけ後述の手順で作成する。

### Phase 8 の最終更新

1. `git status` と差分を再確認する。
2. パイプライン対象のファイルだけを stage する。
3. リポジトリ規約に沿う commit メッセージで commit する。
4. 「レビューの進め方」の順序で最終差分を再レビューする。修正した場合は検証、commit、同じ再レビューを繰り返す。
5. `develop...HEAD` の差分と commit 履歴を再確認する。
6. 現在のブランチを upstream へ push する。

現在のブランチが `develop` の場合は、要件が不具合修正なら `fix/`、それ以外は `feat/` を先頭にし、`<issue-token>-<topic>` をリポジトリの命名規則に合わせて正規化したブランチを作る。既存の同名ブランチを推測で再利用しない。

既存のユーザー変更は stage しない。同じファイルに対象変更と既存変更が混在し、安全に部分 stage できない場合は停止する。

## PR の作成と更新

現在のブランチを head に持つオープンな PR を正確に検索する。

- 存在しない場合: `develop` を base に `gh pr create --draft --assignee @me` で draft PR を作成する。
- 1件存在する場合: draft 状態を維持してその PR を使う。
- 複数件または状態不明の場合: 推測で選ばず停止する。

assignee はこの環境で `gh` が認証している GitHub ユーザーとし、`gh api user --jq .login` で確認する。既存 PR には `pr-update-gh` で認証ユーザーを追加し、既存の assignee は削除しない。ユーザーが明示的に指示しない限り、実装・検証の完了を理由に `gh pr ready` などで draft を解除しない。

初回 PR のタイトルと本文は、Phase 1 の子パイプラインが要件定義書と品質ゲートの結果から作る。実装以降の工程が未完了であることも明記する。Phase 8 では設計文書、Quint モデル、最終差分、検証結果、レビューガイドを反映し、`pr-update-gh` を使って本文を整える。

本文には少なくとも次を含める。

- 変更の対象と、利用者またはシステムから見た変化
- 要件定義書、設計文書、実装計画の位置と、作成した場合は Quint モデルの位置
- 要件定義書、設計文書、実装計画を閲覧できる HTML の位置
- レビューガイドへのリンクまたはリポジトリ相対パス
- 実行した検証と結果
- レビュアーに確認してほしい点
- 既知の制約、移行、互換性、手動作業。該当する場合のみ

`pr-update-gh` の更新後に PR を再取得し、head、base、state、URL、本文が意図どおりであることを確認する。isDraft と assignees も取得し、新規 PR は draft、既存 PR は更新前と同じ draft 状態であり、認証ユーザーが assignee に含まれることを確認する。外部操作が失敗したら対象を変えて再試行せず、原因と再開点を報告する。
