# 成果物の契約

このファイルは `pipe-requirements-to-pr` の開始時、要件更新時、設計・実装計画作成時、レビューガイド作成時に参照する。
子パイプラインの `pipe-grilling-auto-to-requirements-pr`、`pipe-auto-grilling-design`、`pipe-generate-quality-gated-implementation-plan` も、成果物の名前と内容はこの契約に従う。

## 識別子と配置

入力 `req-<topic>.adoc` の `<topic>` は、先頭の `req-` と末尾の `.adoc` を除いた文字列とする。空文字、パス区切り、`..` を含む入力は受け付けない。

`<issue-token>` は次の順に、事実として確認できる値を使う。

1. ユーザーが明示した issue 番号
2. 要件定義書に記載された GitHub issue 番号
3. 現在のブランチ名に含まれる issue 番号
4. 現在のブランチに紐づく PR が参照する issue 番号

番号を得られた場合は `issue<number>` とする。得られない場合は、事実を捏造せず `issueX` を使う。

ユーザー指定がない場合は、入力と同じディレクトリへ次の名前で保存する。

```text
req-<topic>.adoc
pre-investigation-report-<topic>.json
design-<issue-token>-<topic>.adoc
design-<issue-token>-<topic>.html
implementation-plan-<issue-token>-<topic>.adoc
easy-implementation-plan-<issue-token>-<topic>.html
req-<topic>.html
implementation-plan-<issue-token>-<topic>.html
review-guide-<issue-token>-<topic>.adoc
review-guide-<issue-token>-<topic>-<symbol-or-flow>.svg
review-guide-<issue-token>-<topic>.html
```

既存ファイルがある場合は内容と現在の対象が一致するか確認する。同名の別用途ファイルは上書きせず停止する。

## 要件定義書

要件定義書には、システムが何をするかを、利用者・操作者・外部システムから観測できる結果で書く。既存の文書構造と記法を優先し、少なくとも次の情報を一意に読み取れる状態にする。該当しない項目は無理に空見出しを追加しない。

- 背景、目的、利用者または利用シナリオ
- 対象範囲と対象外
- 機能要件と観測可能な受け入れ条件
- 非機能要件と測定・確認方法
- 判断に効いた前提、制約、既存システムとの契約
- 正常系、境界条件、利用者に見える失敗時の結果
- 採用した意思決定、代替案、採用理由
- データ移行、互換性、セキュリティ、運用への影響
- 未確定事項と、そのまま実装可能かどうか
- 安全面でgrillingで対象外としたこと

どう実現するかは設計文書に書く。ロックの順序、transaction の境界、再試行や例外処理の仕組み、内部の競合への対処、クラス名やメソッド名は設計文書に置く。要件には「確定までに対象が変わっていたら結果を保存しない」のような、観測できる結果だけを残す。

前提には、規則や判断を左右した事実だけを根拠パスとともに書く。それ以外の調査結果は調査レポートを参照させる。

[EARS と Gherkin による要件と受け入れ例](../../pipe-grilling-auto-to-requirements-pr/references/ears-and-gherkin.md) に従い、適用範囲のある規則を EARS、判断の境界がある規則の代表例を Gherkin で書く。規則と例は要件 ID で結び付ける。例にだけ現れる振る舞いは規則へ反映するか、例を修正する。

自動壁打ちで採用した決定には、推奨案であること、根拠、不確実性を残す。

自動壁打ちで安全側に倒し、対象外または未確定に置いた論点は、「安全面でgrillingで対象外としたこと」という見出しの節に書く。対象外は今回作らないこと、未確定は要件では決めず、設計と実装が他の規則に反しない範囲で決めることを表す。各項目に、論点、対象外と未確定のどちらに置いたか、見送った理由、後から足す条件を書く。issue や下書きが示した対象外は「対象範囲と対象外」、調べても確認できなかった事実は「未確定事項」に書き、この節には自動壁打ちで見送った論点だけを置く。

## 設計文書

`design-<issue-token>-<topic>.adoc` に、要件の EARS ID と Gherkin シナリオを参照しながら、次を記す。設計文書は自由記述と必要な図で構成し、要件や実装タスクを写し直さない。

- 目的、対象範囲、既存構成と採用した方式・根拠
- コンポーネントの責務と依存、データの形・所有・永続化
- 公開インターフェース、操作の前提・結果、失敗時の振る舞い
- 状態遷移、並行性、時間、再試行に関する前提と不変条件
- 要件が観測できる結果だけを定めた失敗時・並行時の挙動を実現する方式（transaction の境界、ロック、例外処理）
- 要件 ID・シナリオと設計要素の対応、未確認事項、検証結果と制約

`pipe-auto-grilling-design` の条件で Quint が必要と判断した場合は、対象だけの Quint モデルを要件定義書と同じディレクトリに `.qnt` として保存し、設計文書からパス、対応する EARS ID・シナリオ・不変条件、検査コマンドと結果を参照する。同名の別対象モデルは上書きしない。モデルの抽象化と検査範囲を明記する。該当しない場合は Quint を省略した理由を記す。モデルを用いる実装では `quint-execute-spec` を参照し、設計とコードの対応を確認する。

説明に図が必要なら設計文書と同じディレクトリへ SVG を置き、AsciiDoc から参照する。HTML 生成時に図が埋め込まれたことを確認する。

## 実装計画

AsciiDoc として、少なくとも次を含める。

1. 要件サマリと対象外
2. 技術方針と既存パターン
3. 変更対象一覧
4. 依存順に並んだ実装タスク
5. テスト・検証計画
6. 移行、互換性、ロールバック、運用上の作業
7. リスクと軽減策
8. 完了条件

設計文書の決定を実装タスクに落とし込み、要件の EARS と Gherkin は参照先として使う。各タスクは、満たす規則を EARS 要件 ID で示し、対応する Gherkin シナリオを完了条件に結び付ける。依存関係が許す範囲でシナリオ単位の縦切りにし、最小の正常系から状態依存・異常系へ進める。

各実装タスクには次を記載する。

- `Satisfies`: 対応する EARS 要件 ID。共通基盤のタスクは、それが支える要件 ID と後続タスクを示す
- `Design`: 対応する設計文書の節。Quint モデルがあれば、対応する action・不変条件と検査ゲート
- 対象パスと主要シンボル。未確定なら探索起点
- 変更前後の責務または振る舞い
- 依存タスク
- 追加・更新するテスト
- `Done when`: 対応する Gherkin シナリオ名と検証方法。シナリオがない規則と、設計文書で決めた失敗時・並行時の扱いは、テストで確かめる振る舞い、測定値、検査結果など観測できる完了判定

たとえば、要件定義書の `REQ-001` と「5回目の失敗でロックされる」に対応するタスクは次のように書く。

```asciidoc
=== T3: 連続失敗をロックする
* Satisfies: REQ-001
* Design: 認証状態の更新
* Depends on: T1
* Done when: 「5回目の失敗でロックされる」をログイン経由で確認できる
```

シナリオ名は要件定義書の記載と一致させ、テストツールを導入しない場合も実行・確認方法を明記する。

チェックボックスは実際の進捗と一致させる。実装後に計画から逸脱した箇所があれば、理由と最終的な実装を反映する。

### テスト方針

テストの計画、生成、レビューには [tdd-matt-p](../../../matt/engineering/tdd-matt-p/SKILL.md) を使い、「良いテストとは何か」と「アンチパターン」、[tests.md](../../../matt/engineering/tdd-matt-p/tests.md)、[mocking.md](../../../matt/engineering/tdd-matt-p/mocking.md) に従う。

このパイプラインでは「事前に合意されたシームでのみテストしてください」のユーザー確認手順を置き換える。要件、既存設計、公開インターフェースを調べ、重要な経路や複雑なロジックを観測できる最適なシームを自律的に選ぶ。テストを書く前に、選んだシーム、選定理由、検証する振る舞いを実装計画に記録し、確認待ちで停止しない。実装中に選び直す場合も、根拠と計画を更新して進める。

- 公開インターフェースから利用者や呼び出し元に見える振る舞いを検証し、内部リファクタリングで壊れないテストを計画・生成する。
- 期待値は仕様や既知の正しい具体例から独立に定める。実装と同じ計算による期待値、定数の自己比較、内部の呼び出し回数・順序、プライベートメソッド、インターフェースを迂回したDB照会による検証を避ける。
- モックは必要なシステム境界に限り、内部モジュールや協力者をモックしない。
- テストを追加する実装タスクは、1つのシームで1つの失敗するテストを確認し、最小実装で通す赤→緑の垂直スライスにする。全テストを先に書く水平スライシングを計画・実行しない。

## 文書間の品質ゲート

各 Phase の品質ゲートは、その Phase が作った成果物だけを採点する。上流の文書は採点し直さず、次の不整合だけを確認する。

- 要件にある受け入れ条件へ対応する計画タスクまたは検証がない
- 設計の判断・状態遷移・Quint の不変条件に対応する実装タスクや検証がない
- 実装計画が設計文書と異なる方式・インターフェース・データの所有を前提にしている
- EARS 要件 ID または Gherkin シナリオ名から担当タスクと完了判定を追えない
- Gherkin の例が EARS の規則にない振る舞いを要求する、または規則と例の要件 ID が対応しない
- 計画が要件にない挙動を追加する
- 同じ用語が異なる意味で使われる
- 要件の対象外を計画が変更対象に含める
- 要件にある失敗時の結果、互換性、移行、セキュリティの扱いが、設計文書または計画にない
- 計画の完了条件を満たしても要件の成否を判定できない

重大な指摘は、実装者が異なる挙動を選び得る、受け入れ判定が不能になる、またはデータ損失やセキュリティ上の欠陥につながる指摘を指す。上流の文書は重大な指摘を解消するときだけ修正し、修正箇所がその指摘を解消したことだけを確認する。

文書間の確認と修正は最大2巡とする。重大でない指摘は、規則、シナリオ、設計要素を増やさずに直せる場合だけ直し、それ以外はその Phase の成果物の残課題に記録する。2巡目の修正後も重大な指摘が残る場合は次の Phase へ進まず、残った指摘を報告して停止する。

## HTML 派生成果物

`req-<topic>.html`、`design-<issue-token>-<topic>.html`、`implementation-plan-<issue-token>-<topic>.html`、`review-guide-<issue-token>-<topic>.html` は、検証を通過した同名の AsciiDoc から `asciidoc-to-colorful-html` で生成する。

`easy-implementation-plan-<issue-token>-<topic>.html` は、品質ゲートを通過した実装計画から `easy-to-understand` で生成する解説 HTML とする。

- CSS とローカル画像を埋め込み、単一ファイルで表示できる状態にする。
- HTML の内容変更は変換元の AsciiDoc へ反映し、HTML を再生成する。
- この親パイプラインでは Phase 1〜6 の HTML 生成・更新を保留し、Phase 7 のレビューガイド生成直前に要件定義書、設計文書、実装計画の HTML、および実装計画の解説 HTML を生成する。それ以降に変換元の AsciiDoc が変わった場合は、対応する HTML を再生成して最新内容との一致を確認する。
- 既存 HTML を上書きする場合は、同じ変換元から作られた派生成果物であることを確認する。同名の別用途ファイルなら停止する。

## レビューガイド

内容、SVG図、検証の契約は`review-guide`スキルを正本とする。パイプラインは最終差分と関連成果物を入力にし、このファイルで確定した`review-guide-<issue-token>-<topic>.adoc`を出力先として指定する。

SVG図は`review-guide-<issue-token>-<topic>-<symbol-or-flow>.svg`としてレビューガイドと同じディレクトリへ置き、HTMLへdata URIとして埋め込む。
