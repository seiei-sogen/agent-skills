# 確定済みの計画から実装、実証、レビュー、PR 更新まで進める

`pipe-requirements-to-pr` の Phase 5〜9 を、引数で指定した実証スキルと証跡ディレクトリで実行するラッパーである。
工程の中身は親スキルとその子スキルに従い、このスキルは引数の確定、再開位置、実証スキルと証跡の指定だけを受け持つ。

## 引数

空白区切りのパスを順不同で受け取り、形で種類を判別する。

- `.adoc` で終わるパス 1 件。要件定義書 `req-<topic>.adoc`
- 最後の要素が `verify-` で始まるパス 1 件以上。実証スキルのフォルダ。要件定義書と別の checkout にあってよい
- 残りのパス 1 件。証跡ディレクトリ。なければ作る

種類ごとの件数が合わない場合は後続を始めず、不足しているパスを 1 つだけ確認する。

## 子スキル

- `pipe-requirements-to-pr`。開始時に `SKILL.md` と、同スキルが Phase 5〜9 で読む参照ファイル、子スキルを同スキルの規則どおり読む

子スキルが見つからない場合は同等手順で代替せず、見つからないスキル名を報告して停止する。
指示が衝突する場合は、現在のユーザー指示、このスキルの段階固有の指示、親スキルと子スキルの通常指示の順に優先する。

## 進め方

1. 要件定義書のあるリポジトリの checkout（`git -C <要件定義書のディレクトリ> rev-parse --show-toplevel`）を作業ディレクトリとし、以後の工程をすべてそこで行う。
2. `pipe-requirements-to-pr` を再開として実行する。同スキルの「再開と完了報告」の規則で、Phase 1〜4 の完了を既存成果物と Git / PR の状態から確認する。Phase 1〜3 の成果物が欠けている、または完了条件を満たさない場合は、その Phase をやり直さず停止して理由を報告する。Phase 4 だけ未完なら親スキルの規則で commit と push を行う。
3. Phase 5 から Phase 9 までを順に実行する。次を段階固有の指示として、親スキルと子スキルの既定より優先する。

### 実証スキル

- 実証スキルは引数のものを使う。`pipe-implement-and-verify` の表の「場所」を引数のパスに読み替え、実証は手順 1 の checkout のルートで実行する。
- 引数の実証スキルが受け持たない側の実証が要件に必要な場合は、`pipe-implement-and-verify` の規則で選ぶ。

### 証跡

- Phase 5〜7 で生成する証跡と確認用出力は、すべて証跡ディレクトリ配下に置く。実証スキルの証跡、`agent-browser` のスクリーンショットと snapshot、`user-story-review` の出力ディレクトリを含む。
- 実証スキルが証跡の場所を変数や引数で決める場合は、それを証跡ディレクトリ配下の実行ごとのフォルダに向ける。`verify-auto-reserve` は `AR_VERIFY_EVIDENCE` で決める。変えられない実証スキルは、既定の場所に残した証跡を実証の完了後に証跡ディレクトリへコピーする。
- 実装計画に記録する証拠の場所は、証跡ディレクトリ配下のパスにする。
- 証跡ディレクトリは commit に含めない。手順 1 の checkout 内にあるときは、`commit-push` が拾わないよう `git rev-parse --git-path info/exclude` が示すファイルへ追記する。実証スキルの Evidence 規則（JWT、cookie、実ユーザーの個人情報を含めない）は証跡ディレクトリでも守る。

## 完了報告

親スキルの完了報告に加えて、証跡ディレクトリのパスと、実証した EARS 規則・Gherkin シナリオごとの証跡の場所を報告する。
