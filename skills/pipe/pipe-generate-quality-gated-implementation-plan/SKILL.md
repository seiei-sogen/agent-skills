# 品質ゲート済みの実装計画を生成する

更新済みの要件定義書、設計文書、事前調査レポートから、実装可能な計画を作る。
コードの実装、commit、push、PR 作成は行わない。

方式を選ぶ理由と、その判断を別の案件でも使える条件を実装計画に残す。以下の方式比較と学びの整理は、設計判断、未知の技術、障害原因の検討がある場合に行う。単純な文言修正や既存手順で決まる変更では省略し、理由を最終報告に一言添える。

## 子スキル

各工程を始める前に、対応する `SKILL.md` を最後まで読む。

- `poteto-mode-start`
- `grilling-matt-p`
- `tdd-matt-p`
- `quality-gated-review-improve`

子スキルが見つからない場合は同等手順で代替せず、見つからないスキル名を報告して停止する。
指示が衝突する場合は、現在のユーザー指示、このスキルの工程固有の指示、子スキルの通常指示の順に優先する。

## 入力と成果物

入力は次の3件とする。

- 更新済みの `req-<topic>.adoc` 1件
- 同じ対象の `design-<issue-token>-<topic>.adoc` 1件。設計文書が参照する Quint モデルも読む
- その要件を調査した有効な JSON レポート 1件

[成果物の契約](../pipe-requirements-to-pr/references/artifact-contracts.md) を読み、実装計画の保存先を確定する。
ユーザーが保存先を指定していない場合は、要件定義書と同じディレクトリへ次の名前で保存する。

```text
implementation-plan-<issue-token>-<topic>.adoc
```

入力が不足している場合は、必要なパスを確認してから始める。
調査レポートを JSON として読めない場合、または設計文書と調査レポートが同じ要件の成果物だと確認できない場合は停止する。
既存の成果物が同じ対象のものか確認できない場合は上書きせず停止する。

## poteto-mode で実装計画を進める

入力と成果物を確定した後、実装計画の生成を始める前に `poteto-mode-start` を使う。
このスキルへの依頼全体を対象タスクとして渡し、以後の自動壁打ち、実装計画の生成、品質ゲートを poteto-mode が有効な状態で進める。

## 実装計画を生成する

要件定義書、設計文書、調査レポートを入力に `grilling-matt-p` を使う。
この工程では、同スキルの「1問ずつユーザー回答を待つ」を次の自動モードへ置き換える。

1. 事実で解消できる論点は、調査レポートと必要最小限の追加調査で解消する。
2. 実装方式、変更境界、依存順、テスト戦略、移行、ロールバック、運用上の論点を依存順に整理する。
3. 意思決定ごとに質問、選択肢、推奨回答、根拠、影響、不確実性を整理する。
4. 推奨回答をユーザー回答として採用し、主要論点と派生論点が尽きるまで続ける。

テスト戦略を決める前に `tdd-matt-p` を使い、「良いテストとは何か」と「アンチパターン」に従ってテストを計画する。[成果物の契約のテスト方針](../pipe-requirements-to-pr/references/artifact-contracts.md#テスト方針) に従い、シームはユーザーへの確認なしに自律的に選ぶ。この段階ではテストコードを生成せず、観測する振る舞い、期待値の根拠、赤→緑で進める順序を計画に残す。

要件定義書の EARS 要件 ID と Gherkin シナリオ名を確認し、[成果物の契約の実装計画](../pipe-requirements-to-pr/references/artifact-contracts.md#実装計画) に従って各タスクの `Satisfies` と `Done when` に結び付ける。`Design` には設計文書の節と、該当する Quint action・不変条件があればその検査ゲートを記す。設計文書の構成・データ・インターフェース・状態遷移を実装と検証の順序へ落とし込む。計画自体を EARS や Gherkin で書き直さない。

依存関係が許す範囲で、まず端から端まで通る正常系のシナリオを1本選び、状態依存、異常系、任意機能を追加する。DB・API・UI などの層をまとめて先に作る計画ではなく、シナリオごとに観測可能な進捗が出るタスクへ分ける。シナリオを持たない横断要件や非機能要件には、対応する EARS ID と測定・確認方法を完了条件にする。Gherkin を参照することだけを理由に BDD ツールを追加しない。

### 設計に沿って実装方式を確認する

実装方式を採用する前に、要件の「達成したい結果」「守るべき制約」「提案された実現方法」を確認する。必須の指定は維持し、提案として残された方法は比較対象にする。要件にある失敗例と判断を引き継ぎ、新たに見つけた破綻条件があれば、具体的な操作や条件と起きる問題を示す。重要な状況を最大3件に絞り、計画の検証項目に結び付ける。

設計文書で比較済みの方式を基準にし、計画時に新たな破綻条件が見つかった場合だけ有力な代替案を最大2案比較する。採用方式が変わる場合は設計文書と Quint モデルを更新・再検証してから計画へ反映する。有力な案がなければ理由を記し、比較のためだけの案は作らない。必須制約を満たさない案を採用するために要件を書き換えない。

比較表には各案の次の情報を含める。

- 設計上の概念と仕組み、成立する前提
- 今回の失敗例に対して解決できる問題と解決できない問題
- 実装・移行・運用コスト
- 採用または不採用の理由、判断が変わる条件
- 根拠の参照先、未確認事項、今後調べるための検索語

たとえば同時更新なら、競合する操作を待たせる、更新時に競合を検出する、処理順を制御する、といった仕組みの違いを比較する。製品名やライブラリ名だけの比較にしない。新しい概念や技術は、素朴な実装の失敗例、失敗を防ぐ仕組み、防げないこと、今回導入する価値の順に説明する。

判断を左右する不確かな仕様やライブラリ機能は、公式ドキュメントまたは本番データに触れない小さな検証で確認し、参照先または検証結果を計画に残す。確認できない場合は未確認と明記し、その機能がある前提で採用を確定しない。確認方法と結果に応じた代替案を計画へ残す。

### 判断を次の案件でも使える形にする

実装計画の「判断から学べること」に、再利用できる知識を最大3件残す。各件に、思い出す兆候、使える条件、使わないほうがよい条件、比較した判断・根拠への参照、概念名と検索語を含める。要件側の学びは参照し、計画で増えた判断や適用条件を中心に書く。ユーザーが既知と明示した内容の解説は繰り返さず、採否の理由は残す。

計画段階で得た知識と、実装後に検証が必要な仮説を区別する。仮説の検証は既存のテスト・運用確認タスクに組み込み、このスキル内で実装や実装後の振り返りを実施したことにしない。

### 計画を保存する

方式比較と学びの整理を省略した場合も、採用した回答を統合し、実装計画を有効な AsciiDoc として保存する。
[成果物の契約](../pipe-requirements-to-pr/references/artifact-contracts.md) にある実装計画の内容契約を満たす。
同じ対象の実装計画がある場合は草稿として再利用し、実装済みの進捗と検証結果を失わない。

## 文書の品質ゲートを通す

`quality-gated-review-improve` を使い、実装計画を採点・修正する。
要件定義書と設計文書は採点し直さず、[成果物の契約の文書間の品質ゲート](../pipe-requirements-to-pr/references/artifact-contracts.md#文書間の品質ゲート) に従って実装計画との不整合だけを確認する。設計文書を修正した場合は参照する Quint モデルと検証結果の整合も確認する。
各 EARS 要件と Gherkin シナリオから計画上の担当タスクと完了判定を追えることを確認する。タスクの完了条件に、対応する規則にはない振る舞いや、実行方法のないシナリオがあれば修正する。
テスト計画も `tdd-matt-p` の基準でレビューし、内部実装への依存、同語反復的な期待値、全テストを先に書く水平スライシングがあれば、品質ゲートの合格前に修正する。

方式比較と学びの整理を行った場合は、比較の前提が要件と整合し、失敗例から方式の採否・検証項目を追えること、未確認事項と再利用の限界が明確なことも採点する。既存方式の採用も同じ基準で評価し、案の数や技術の新しさを加点理由にしない。

要件定義書を正とする。設計側に重大な欠陥を見つけた場合は設計文書と Quint モデルを直し、検査結果を更新してから実装計画へ反映する。
Quint モデルを直すときは `quint-modeling` と `quint-lang` を読み、設計スキルと同じ検査を再実行する。
要件側に重大な欠陥を見つけた場合は要件を直し、設計文書、Quint モデル、実装計画へ反映する。
実装計画が原則90点以上で、文書間の重大な不整合が0件になったら合格とする。
子スキルの例外終了条件に該当した場合は、残課題が実装を危険にしないことを確認する。

## 完了報告

次を簡潔に報告する。

- 更新した要件定義書と設計文書、必要な Quint モデル
- 生成した実装計画
- 品質ゲートの最終点と終了理由
- 残課題。なければ「なし」
