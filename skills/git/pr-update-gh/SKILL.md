# 現在のブランチの PR 本文を更新する

現在のブランチに紐づくオープンな PR の本文を、変更の対象と内容が前提知識なしでも分かり、レビュアーが1分で読める文章へ更新する。
ユーザーがタイトルの更新も明示しない限り、PR のタイトルは変更しない。
draft PR も更新対象とする。更新前の draft 状態を維持し、ユーザーが明示的に指示しない限り `gh pr ready` などで draft を解除しない。
assignee には、この環境で `gh` が認証している GitHub ユーザー（`@me`）を追加する。リポジトリの所有者や既存 PR の作者から推測せず、既存の assignee は削除しない。

## PR を特定する

1. Git リポジトリ内であることと、現在のブランチ名を確認する。
2. `gh pr view --json number,url,title,body,baseRefName,headRefName,state,isDraft,assignees,additions,deletions` を使い、現在のブランチに紐づく PR と追加・削除行数を取得する。`gh api user --jq .login` で認証ユーザーも確認する。
3. 取得した PR が現在のブランチを head に持つオープンな PR であることを確認する。

ブランチが取得できない、PR が見つからない、または PR がオープンでない場合は更新しない。
別のブランチや PR を推測で選ばず、判明した状態をユーザーへ伝える。

## 変更内容を調べる

PR のタイトル、既存本文、base ブランチ、コミット履歴、変更ファイル一覧、差分を確認する。
PR 上の実際の差分は `gh pr diff` を優先し、差分が大きい場合は変更ファイル一覧と重要な差分を絞って読む。

調査結果から、次を分けて整理する。

- 対象：変更される機能、画面、処理、利用者、文書など
- 内容：対象が以前の状態からどのように変わるか
- 理由：issue、既存本文、コミット、差分から根拠を確認できる変更目的
- 確認事項：レビュアーが確認できる具体的な動作や成果物

ファイルパスや実装手段は、変更を理解するために必要な場合だけ使う。
「ファイルを修正した」ではなく、その修正で何が変わるのかを書く。

既存本文からは、チケットリンク、関連 PR、注意事項、手動作業、チェックリストの状態、スクリーンショットなどの事実だけを新しい本文へ移す。文章は引き継がず、新しい構成で書き直す。
差分から古くなったと断定できない事実は残す。

## 本文の構成を決める

`git rev-parse --show-toplevel` で得たリポジトリのルートで、GitHub が参照する次の PR テンプレートを大文字小文字を区別せずに探す。

- `.github/pull_request_template.md`
- `docs/pull_request_template.md`
- `pull_request_template.md`
- `.github/PULL_REQUEST_TEMPLATE/` 配下の `.md`

テンプレートが見つかったら、それを本文の構成にする。

- 見出しと並び順をテンプレートのまま使い、背景、やったこと、確認方法などの各セクションを埋める。
- 必須の3項目は、同じ意味の欄があればそこへ書く。なければ末尾に見出しを追加する。それ以外の見出しはテンプレートのものだけを使う。
- 書く内容がないセクションも見出しを残し、「なし」と書く。
- 記入例や説明用の HTML コメントは、書いた内容に置き換える。
- チェックボックスは、実際に実行・確認したものだけにチェックを入れる。
- `.github/PULL_REQUEST_TEMPLATE/` に複数ある場合は、変更内容に合うものを1つ選ぶ。合うものを判断できなければ、既定構成を使う。
- テンプレートに変更内容を書く場所がない場合は、概要や背景にあたるセクションへ1〜2文で含める。

テンプレートが見つからない場合は、次の既定構成を使う。

```markdown
## 修正対象

- 変更・追加する機能やページを具体的に書く

## このPRで行うこと

- 対象がどのように変わるかを書く
```

テンプレートの有無にかかわらず、次の3項目を本文に必ず含める。TODO とレビューアーへの確認事項がなければ「なし」と書く。

- **修正対象**：変更・追加する機能と、対応するフロントや管理画面のページを書く。ページだけの変更ならそのページ、画面変更がなければ実際に変更する機能・処理・文書を書く。確認済みの URL があれば併記し、なければ判明したパスだけを書く。ホスト名を推測しない。
- **TODO**：別 PR に回したこと、別対応が必要なことを書く。
- **レビューアーに確認してほしいこと**：こちらで決めた仕様や、判断・確認を求める点を書く。

テンプレートがない場合は、既定構成の「修正対象」欄を使い、TODO とレビューアーへの確認事項の見出しを末尾に追加する。理由が読者の理解に役立ち、根拠もある場合だけ、`変更する理由` などの短いセクションを追加する。

## 本文を書く

本文は、レビュアーが1分で読める報告にする。読者の判断に必要なことだけを書き、詳細は差分とコミットメッセージに任せる。

内容は次のように整理する。

- 1つの事実は1つのセクションにだけ書く。背景で述べた原因や、変更点で述べた判断を、他のセクションで繰り返さない。
- 変更点は、読者が気づく変化ごとに1項目にまとめる。例：「`Top.tsx` に state を追加」ではなく「横カードと一覧が同じ並び順になる」。ファイル名は、その変化を探す場所として必要なときだけ項目の末尾に添える。
- 設計上の判断は、レビュアーが差分を見て疑問に思うものだけを、判断と根拠を1文ずつで書く。
- 確認したことは、実行した内容と結果を1項目1行で書く。例：「`bun run test` 33件成功」。未実施の確認は、何をどの環境で確認するかを1行で書く。
- 確認してほしい点は重要なものから簡潔に書き、判断してほしい内容を1項目1文で書く。
- 箇条書きは1段だけにし、入れ子にしない。1つの箇条書きは5項目までにする。超える場合は関連する項目をまとめ、重要な順に並べる。

テンプレートでも既定構成でも、各セクションの文章を [i-have-adhd](https://github.com/ayghri/i-have-adhd) の規則で簡潔にする。
このプラグインは `disable-model-invocation: true` のためスキルから呼び出せない。PR 本文に効く規則を次に移してある。

- 各セクションの先頭に結論を書き、内容を書き終えたらそこで終える。前置き、全体のまとめ直し、結びの挨拶は入れない。
- 再現や手動確認の手順が必要な場合だけ番号付きで書き、1項目につき1つの操作にする。
- 一文には一つの要点だけを書き、箇条書きの文末の形をそろえる。
- 「改善」「対応」「最適化」で済ませず、変更後にできるようになったことを確認できる形で書く。例：「`/login` でメールリンクのログインができる」。
- 時間や規模は、数値と単位で書く。
- 比喩や慣用句ではなく、行った操作をそのまま書く。
- 情報を足さないぼかし（「〜かもしれない」「〜など」）は削る。根拠のある不確かさは残す。
- 専門用語や略語が必要なら、最初に短く意味を補う。
- 内部整理だけで利用者から見える動作が変わらない場合は、そのことを明記する。

`additions + deletions` を差分行数とし、本文全体の文字数上限を次で決める。差分行数が 0 の場合も最小区分を使う。

| 差分行数 | 本文の上限 |
| --- | ---: |
| 0〜99行 | 1,000文字 |
| 100〜499行 | 1,600文字 |
| 500〜1,999行 | 2,400文字 |
| 2,000行以上 | 3,600文字 |

本文ファイルを `LC_ALL=C.UTF-8 wc -m <本文ファイル>` で測る。上限を超えた場合は次の順に削る。

1. ファイル単位の変更の列挙と実装手段
2. レビュアーの判断に関わらない設計の説明
3. 確認の手順。結果は残す
4. 複数のセクションで重なる説明

削るときも、必須の3項目、テンプレートの固定文、利用者から見える動作の変更、互換性への影響、手動作業、関連チケット、未実施のテスト、既存本文から移した事実は残す。これらを簡潔に書いても上限を超える場合は、情報を削らず超過を許容する。
目的、影響、互換性、テスト結果は、根拠を確認できたものだけを書く。実行していないテストは未実行と書く。

## PR を更新して確認する

完成した本文を安全な一時 Markdown ファイルへ保存し、適用上限と文字数、必須の3項目を確認してから、PR 番号を明示して次の形式で更新する。

```bash
gh pr edit <PR番号> --body-file <本文ファイル> --add-assignee @me
```

更新後は `gh pr view <PR番号> --json url,body,isDraft,assignees` で再取得し、意図した本文、更新前と同じ draft 状態、認証ユーザーの assignee への追加を確認する。
更新に失敗した場合は別の PR へ切り替えたり、同じ操作を無制限に繰り返したりせず、エラーを報告する。

最後に、更新した PR の番号と URL、使ったテンプレートのファイル名（なければ「テンプレートなし」）、本文の文字数と適用上限、上限超過時はその理由、および本文に書いた「対象」と「内容」を簡潔に報告する。
