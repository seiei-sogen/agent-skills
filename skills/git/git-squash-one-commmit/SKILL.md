# git-squash-one-commmit

現在のブランチで、基点ブランチから分岐した後に積んだコミットを 1 つにまとめる。
`git reset --soft <分岐点>` で HEAD を分岐点へ戻し、ブランチ全体の差分を 1 回でコミットし直す。
途中で基点ブランチを merge していても、分岐点は最新の merge-base になるため、基点ブランチ側の変更は新しいコミットに入らない。

## 子スキルと優先順位

コミットメッセージは `commit-message-generator` で作る。手順 3 に入る時点で、その `SKILL.md` を最後まで読む。
見つからない場合は、同等の手順で代替せず、スキル名を報告して停止する。
指示が衝突する場合は、現在のユーザー指示、このスキルの指示、`commit-message-generator` の指示の順に優先する。

## 入力と成果物

- 入力: 現在チェックアウトしているブランチ。ユーザーが基点ブランチを指定した場合は、その指定も使う。
- 成果物: 分岐点を親に持ち、スカッシュ前の HEAD と同じツリーを持つコミット 1 つ。
- 元 HEAD: スカッシュ前の HEAD のコミット ID。失敗時の復元に使うため、履歴を書き換える前に控える。

push は依頼に含まれる場合だけ行う。

## 1. 対象ブランチと状態を確認する

1. `git rev-parse --show-toplevel` で Git リポジトリ内にいることを確認する。
2. `git branch --show-current` でブランチ名を確認する。detached HEAD、または `develop`、`main`、`master`、ユーザー指定の基点ブランチそのものなら、共有ブランチの履歴を守るため停止して報告する。
3. `git status` で、rebase、merge、cherry-pick などが進行中でないことを確認する。進行中なら停止して報告する。
4. `git diff --quiet` と `git diff --cached --quiet` がどちらも終了コード 0 になることを確認する。追跡ファイルに未コミット変更がある場合は、スカッシュ後のコミットに混ざるため停止し、扱いをユーザーに確認する。未追跡ファイルはコミットに入らないため、そのまま進めてよい。
5. `git fetch origin` を実行する。失敗した場合は停止する。古い参照で分岐点を決めると、基点ブランチ側の変更がコミットに混ざる。
6. リモートに同名ブランチ `origin/<ブランチ名>` がある場合は、`git rev-list --count HEAD..origin/<ブランチ名>` が 0 であることを確認する。1 以上なら、リモートにだけあるコミットをスカッシュで失うため停止し、そのコミット一覧を報告する。

完了条件: ブランチ名が確定し、進行中の操作、追跡ファイルの未コミット変更、リモートにだけあるコミットがどれもない。

## 2. 基点ブランチと分岐点を決める

ユーザーが基点ブランチを指定した場合は `origin/<指定ブランチ>` を使う。リモートになければローカルの同名ブランチを使う。
指定がない場合は、`origin/develop`、`origin/main`、`origin/master` のうち存在するものを候補にし、候補ごとに次を求める。

```sh
git merge-base HEAD <候補>
git rev-list --count <merge-base>..HEAD
```

コミット数が最小の候補を基点ブランチとし、その merge-base を分岐点とする。
最小の候補が複数あって merge-base が異なる場合や、候補が 1 つもない場合は、候補とコミット数を示して基点ブランチをユーザーに確認する。

`git log --oneline <分岐点>..HEAD` で対象コミットを一覧する。

- 0 件なら、スカッシュ対象がないと報告して終了する。
- 1 件なら、すでに 1 コミットであると報告して終了する。
- 2 件以上なら、`git rev-parse HEAD` で元 HEAD を控えて手順 3 へ進む。

完了条件: 基点ブランチ、分岐点のコミット ID、対象コミット一覧、元 HEAD が確定している。

## 3. 1 つのコミットにまとめる

1. `git reset --soft <分岐点>` を実行する。作業ツリーは変わらず、ブランチ全体の差分がステージされる。
2. `commit-message-generator` の手順で、ステージ済みの差分とブランチ名からコミットメッセージを作る。`git log --format=%B <分岐点>..<元 HEAD>` で元のコミットメッセージも読み、差分だけでは分からない目的や経緯を本文に反映する。
3. `git log --format='%an <%ae>' <分岐点>..<元 HEAD> | sort -u` で作者を確認する。`git config user.name` と `git config user.email` の本人以外がいれば、メッセージ末尾に空行を置き、1 人 1 行で `Co-authored-by: <名前> <メール>` を追加する。
4. メッセージを一時ファイルに書き、`git commit -F <一時ファイル>` で 1 回コミットする。
5. commit hook や署名が失敗した場合は、検証を無効化せずに `git reset --soft <元 HEAD>` でブランチを元に戻し、エラーを報告して終了する。

完了条件: 分岐点の上にコミットが 1 つ作成されている。失敗した場合は、ブランチが元 HEAD に戻っている。

## 4. スカッシュ結果を検証する

次をすべて確認する。

- `git rev-list --count <分岐点>..HEAD` が `1` である。
- `git rev-parse HEAD^` が分岐点のコミット ID と一致する。
- `git diff --quiet <元 HEAD> HEAD` が終了コード 0 になり、ツリーが変わっていない。
- `git status --short` で、追跡ファイルに変更が残っていない。

1 つでも満たさない場合は完了とせず、元 HEAD と満たさなかった項目を報告する。

完了条件: 4 項目すべてを満たしている。

## 5. push する（依頼がある場合だけ）

スカッシュは履歴を書き換えるため、元のコミットがすでにリモートにあれば通常の push は拒否される。

- `origin/<ブランチ名>` がない場合は、`git push --set-upstream origin <ブランチ名>` を実行する。
- `origin/<ブランチ名>` がある場合は、手順 1 で fetch したその先端 `git rev-parse origin/<ブランチ名>` を期待値にし、`git push --force-with-lease=<ブランチ名>:<期待値> origin <ブランチ名>` を 1 回実行する。
- 拒否された場合は、その時点のリモートの状態を `git fetch origin` で確認し、エラーとあわせて報告して終了する。`--force` への切り替えや再試行はしない。

完了条件: `git rev-parse HEAD` と `git rev-parse origin/<ブランチ名>` が一致する。

## 6. 報告する

次を簡潔に報告する。

- 基点ブランチと分岐点のコミット ID
- まとめたコミットの件数と件名一覧
- 新しいコミットの hash と件名
- 元 HEAD のコミット ID と、復元コマンド `git reset --soft <元 HEAD>`
- push の有無と push 先
- 実行した検証
