# 要件から PR までのパイプライン

`req-*.adoc` を実装可能な要件へ仕上げ、計画どおりに実装し、レビュー可能な PR まで進める親スキルである。
単にパイプラインの相談や設計をしているだけなら実行しない。全工程の実行、またはこのスキルの明示呼び出しを確認してから開始する。

## 子スキルと優先順位

開始時に次のスキルを利用できることを確認し、それぞれの `SKILL.md` を実行する段階で最後まで読む。

- `pre-investigation-report`
- `grilling-jp`
- `quality-gated-review-improve`
- `asciidoc-to-colorful-html`
- `pr-update-gh`

指示が衝突する場合は、現在のユーザー指示、この親スキルの段階固有の指示、子スキルの通常指示の順に優先する。子スキルが見つからなければ、その工程を同等手順で代替せず、見つからないスキル名を報告して停止する。

## 入力と成果物を確定する

入力は既存の AsciiDoc 要件定義書 `req-<topic>.adoc` 1件とする。複数指定された場合は1件ずつ独立したパイプラインとして扱う。

開始時に [成果物の契約](references/artifact-contracts.md) を読み、次を確定する。

- 調査レポート: `<topic>.json`
- 実装計画: `implementation-plan-<issue-token>-<topic>.adoc`
- 要件定義書 HTML: `req-<topic>.html`
- 実装計画 HTML: `implementation-plan-<issue-token>-<topic>.html`
- レビューガイド: `review-guide-<issue-token>-<topic>.adoc`

成果物は要件定義書と同じディレクトリへ置く。ユーザーが保存先を指定した場合はその指定を優先する。

Git リポジトリ、`main`、現在のブランチ、作業ツリー、適用される指示を確認する。開始時点の変更一覧を記録し、既存変更をパイプラインの変更と混ぜない。同じファイルの同じ箇所に既存変更があり、安全に保持できない場合は停止して対象を報告する。

## 自律実行の境界

このスキルによる全工程の実行依頼は、対象要件の更新、計画とレビューガイドの作成、実装、検証、対象変更の commit / push、PR の作成・更新を進める根拠になる。環境が個別承認を要求する操作は、その場で承認を求める。

推奨回答の自動採用は設計上の意思決定に限る。事実はコード、設定、文書、issue から確認する。確認できない事実を作らない。判断材料が不足する場合は、次の順で処理する。

1. 既存パターンと明示要件に沿う。
2. 後から変更しやすく、影響範囲が狭い安全側の推奨案を採用する。
3. 推奨案、根拠、不確実性を要件定義書に残す。
4. セキュリティ、法令、データ損失、外部契約に関わり、安全な既定値を置けない場合だけ停止する。

## Phase 1: 事前調査

`pre-investigation-report` を使い、要件定義書を調査入力、`<topic>.json` を保存先として指定する。子スキルの読み取り専用制約を守り、この段階では JSON 以外を変更しない。

JSON が妥当で、必須フィールドと根拠パスを持つことを確認する。調査だけでは確定できない事項を `open_questions` に残した状態で Phase 2 へ渡す。

## Phase 2: 自動壁打ちと要件更新

要件定義書と調査レポートを入力に `grilling-jp` の論点抽出と依存順の検討を行う。Phase 2 と Phase 3 に限り、同スキルの「1問ずつユーザー回答を待つ」を次の自動モードへ置き換える。

1. 事実で解消できる論点は調査レポートと必要最小限の追加調査で解消する。
2. 意思決定ごとに質問、選択肢、推奨回答、根拠、影響、不確実性を内部で整理する。
3. 推奨回答をユーザー回答として自動採用し、依存する次の論点へ進む。
4. 主要論点と派生論点が尽きるまで続ける。

壁打ち結果を要件定義書へ反映する。元の意図と確定済み事実を保持し、採用した判断、受け入れ条件、対象外、例外・失敗時の挙動、未確定事項が実装者に追える状態にする。更新後の要件定義書が成果物契約を満たしたら完了とする。

## Phase 3: 実装計画の自動壁打ちと生成

更新済み要件定義書と調査レポートを入力に `grilling-jp` を再実行する。この Phase では、実装方式、変更境界、依存順、テスト戦略、移行、ロールバック、運用上の論点を依存順に検討する。各論点の推奨回答を Phase 2 と同じ自動モードで採用し、採用理由と影響を整理する。

実装上の主要論点と派生論点が尽きたら、採用した推奨回答を統合して実装計画を生成し、指定パスへ有効な AsciiDoc として保存する。タスクごとに要件との対応、対象ファイルまたは探索起点、変更内容、依存順、テスト、完了条件を記載する。未確定のファイル名やシンボルを推測で断定せず、探索タスクとして明記する。

## Phase 4: 文書の品質ゲート

`quality-gated-review-improve` を使い、要件定義書と実装計画を同じ変更の文書ペアとしてレビュー・更新する。各文書の品質に加えて、要件と計画の矛盾、漏れ、過剰実装、検証可能性を採点対象に含める。

要件定義書を正としつつ、要件側の欠陥が見つかった場合は要件を直して計画へ再反映する。原則90点以上、かつ文書間の重大な不整合が0件になったら Phase 5 へ進む。子スキルの例外終了条件に該当した場合は、残課題が実装を危険にしないことを確認する。

## Phase 5: AsciiDoc の HTML 化

`asciidoc-to-colorful-html` を使い、品質ゲートを通過した要件定義書と実装計画をそれぞれ単体 HTML へ変換する。既定の出力名を使い、`req-<topic>.html` と `implementation-plan-<issue-token>-<topic>.html` を生成する。

両方の HTML が成果物契約と子スキルの出力契約を満たし、変換元の最新内容と一致することを確認する。変換警告から include、画像、xref などの文書不備が判明した場合は Phase 4 に戻って AsciiDoc を修正・再評価し、その後に両方の HTML を再生成する。

## Phase 6: 実装と検証

品質ゲートを通過した実装計画を上から実行する。

1. 各タスクに必要なコードと周辺文脈を読み、リポジトリの既存パターンに従って実装する。
2. 正常系、境界条件、失敗系を計画に沿ってテストする。
3. 対象を絞った検証から始め、変更全体に必要な lint、型チェック、テスト、ビルドへ広げる。
4. 今回の変更が原因の失敗を修正し、同じ検証を再実行する。
5. 完了した計画タスクと実際の検証結果を実装計画へ反映する。

計画外の変更が必要になったら、まず要件と計画を更新し、両文書の整合を確認してから実装する。対象外の既存問題は修正せず記録に留める。

## Phase 7: main 比較レビュー

[プラットフォーム別レビューと PR](references/platform-review-and-pr.md) を読み、実行環境に応じたレビューを行う。対象は `main` と現在のブランチの差分、および未コミットの対象変更である。

正しさ、回帰、エラー処理、セキュリティ、データ損失、契約、境界条件、テスト、保守性の順で確認する。根拠のある指摘は修正して検証を再実行する。最大3巡で、重大または高重要度の未解決指摘が0件になったら完了する。安全に直せない重大指摘が残る場合は PR を作成せず停止する。

## Phase 8: レビューガイド

最終差分をもとにレビューガイドを作成する。最初に読むべき root、推奨する読解順、変更の実行時フロー、難しい処理の不変条件と失敗時挙動、重要コードの解説、テストとの対応、重点チェック項目を記載する。

パス、シンボル、必要な行番号を実在確認し、コードを大量に複製しない。レビューガイド自体を最終検証の対象へ含める。

## Phase 9: commit、push、PR

[プラットフォーム別レビューと PR](references/platform-review-and-pr.md) の PR 手順に従う。Phase 5 より後に要件定義書または実装計画を更新していた場合は、対応する HTML を `asciidoc-to-colorful-html` で再生成し、変換元の最新内容と一致することを確認する。レビューガイドまで含む対象変更だけを commit し、現在のブランチを push する。現在のブランチが `main` なら、変更内容に合う作業ブランチを作ってから進める。

現在のブランチにオープンな PR がなければ `main` 向け PR を作成する。PR が存在する場合はその PR を使う。その後 `pr-update-gh` を実行し、レビューガイドへの導線、実施した検証、確認してほしい点を含む本文へ更新して、再取得した本文と URL を確認する。

## 再開と完了報告

各 Phase の開始時に既存成果物と Git / PR の状態を検証する。完了条件を満たす Phase は再利用し、途中または不整合な Phase から再開する。ファイルの存在だけで完了扱いにしない。

最後に次を簡潔に報告する。

- 更新・生成した要件定義書、調査レポート、実装計画、両文書の HTML、レビューガイド
- 品質ゲートの最終点と終了理由
- 実装概要と検証結果
- プラットフォームレビューの方式、指摘、修正結果
- commit、ブランチ、PR の URL
- 残課題。なければ「なし」

PR の作成または更新と再取得確認が完了し、重大な未解決事項がなく、上記成果物が現在の実装と一致したときだけパイプライン完了とする。
