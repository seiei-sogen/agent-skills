# 成果物の契約

このファイルは `pipe-requirements-to-pr` の開始時、要件更新時、実装計画作成時、レビューガイド作成時に参照する。

## 識別子と配置

入力 `req-<topic>.adoc` の `<topic>` は、先頭の `req-` と末尾の `.adoc` を除いた文字列とする。空文字、パス区切り、`..` を含む入力は受け付けない。

`<issue-token>` は次の順に、事実として確認できる値を使う。

1. ユーザーが明示した issue 番号
2. 要件定義書に記載された GitHub issue 番号
3. 現在のブランチ名に含まれる issue 番号
4. 現在のブランチに紐づく PR が参照する issue 番号

番号を得られた場合は `issue<number>` とする。得られない場合は、事実を捏造せず `issueX` を使う。

ユーザー指定がない場合は、入力と同じディレクトリへ次の名前で保存する。

```text
req-<topic>.adoc
<topic>.json
implementation-plan-<issue-token>-<topic>.adoc
req-<topic>.html
implementation-plan-<issue-token>-<topic>.html
review-guide-<issue-token>-<topic>.adoc
review-guide-<issue-token>-<topic>.html
```

既存ファイルがある場合は内容と現在の対象が一致するか確認する。同名の別用途ファイルは上書きせず停止する。

## 要件定義書

既存の文書構造と記法を優先する。少なくとも、次の情報を一意に読み取れる状態にする。該当しない項目は無理に空見出しを追加しない。

- 背景、目的、利用者または利用シナリオ
- 対象範囲と対象外
- 機能要件と観測可能な受け入れ条件
- 非機能要件と測定・確認方法
- 前提、制約、既存システムとの契約
- 正常系、境界条件、例外・失敗時の挙動
- 採用した意思決定、代替案、採用理由
- データ移行、互換性、セキュリティ、運用への影響
- 未確定事項と、そのまま実装可能かどうか

自動壁打ちで採用した決定には、推奨案であること、根拠、不確実性を残す。調査レポート由来の事実には、必要に応じて根拠パスを添える。

## 実装計画

AsciiDoc として、少なくとも次を含める。

1. 要件サマリと対象外
2. 技術方針と既存パターン
3. 変更対象一覧
4. 依存順に並んだ実装タスク
5. テスト・検証計画
6. 移行、互換性、ロールバック、運用上の作業
7. リスクと軽減策
8. 完了条件

各実装タスクには次を記載する。

- 対応する要件の見出しまたは受け入れ条件
- 対象パスと主要シンボル。未確定なら探索起点
- 変更前後の責務または振る舞い
- 依存タスク
- 追加・更新するテスト
- タスク固有の完了判定

チェックボックスは実際の進捗と一致させる。実装後に計画から逸脱した箇所があれば、理由と最終的な実装を反映する。

## 文書ペアの品質ゲート

個別採点に加えて、次の不整合を確認する。

- 要件にある受け入れ条件へ対応する計画タスクまたは検証がない
- 計画が要件にない挙動を追加する
- 同じ用語が異なる意味で使われる
- 要件の対象外を計画が変更対象に含める
- 失敗時挙動、互換性、移行、セキュリティの扱いが片方にしかない
- 計画の完了条件を満たしても要件の成否を判定できない

重大な不整合は、実装者が異なる挙動を選び得る、または受け入れ判定が不能になる不整合を指す。

## HTML 派生成果物

`req-<topic>.html`、`implementation-plan-<issue-token>-<topic>.html`、`review-guide-<issue-token>-<topic>.html` は、検証を通過した同名の AsciiDoc から `asciidoc-to-colorful-html` で生成する。

- CSS とローカル画像を埋め込み、単一ファイルで表示できる状態にする。
- HTML の内容変更は変換元の AsciiDoc へ反映し、HTML を再生成する。
- 変換元の AsciiDoc が変わった場合は、対応する HTML を再生成して最新内容との一致を確認する。
- 既存 HTML を上書きする場合は、同じ変換元から作られた派生成果物であることを確認する。同名の別用途ファイルなら停止する。

## レビューガイド

AsciiDoc として、最終差分に基づく次の順序を基本にする。

1. `このレビューガイドの使い方`: 想定読者、対象、非対象
2. `最初に読む root`: 入口となるファイルとシンボル、その理由
3. `推奨する読解順`: ファイル・シンボルごとの確認目的
4. `実行時フロー`: 入力から出力、早期終了、失敗、外部 I/O
5. `難しい処理`: 不変条件、設計理由、代替案を採らなかった理由
6. `重要コードの解説`: パス、シンボル、責務、入力、出力、副作用、失敗時挙動
7. `テストとの対応`: 要件・実装・テストの対応と実行結果
8. `重点チェック`: レビュアーに判断してほしい具体的な点
9. `既知の制約と対象外`

root は変更全体の理解を最短で始められる入口であり、単なるリポジトリルートではない。複数の入口がある場合は主 root と補助 root を区別する。

コード解説はコードの逐語訳ではなく、なぜその処理が必要か、何を守るか、どこで壊れ得るかを説明する。行番号を記載する場合は最終 commit 直前に再確認する。
