# 共通処理の変更がほかの利用箇所に与える影響を確認する

変更した共通処理の利用箇所をたどり、要件で意図していない影響があれば修正する。共通化を維持するために、今回の修正対象以外の挙動を変えない。

## 1. 差分と意図した変更を確認する

比較先ブランチは呼び出し元またはユーザーの指定を引き継ぐ。指定がなければリポジトリの規約から特定し、一意に決められない場合だけ確認する。

`git diff <比較先ブランチ>...HEAD`、index、working tree、対象となる未追跡ファイルを確認する。既存のユーザー変更は区別し、今回の修正に無関係な変更を巻き戻さない。

要件、設計、関連する既存テストから、意図して変える挙動と、維持すべき挙動を整理する。文書がない場合はコードからの推定と明記する。

変更した共通関数、共有コンポーネント、共通の型・設定を抽出する。共通処理の変更がなければ、その根拠を報告して終了する。

## 2. 修正対象以外への影響をたどる

各共通処理について、呼び出し箇所や参照箇所をリポジトリ全体で検索する。再エクスポート、ラッパー、コールバック、設定経由の利用もたどり、今回の修正対象以外の画面・機能まで確認する。

利用箇所ごとに、変更前後の入力、出力、副作用、エラー処理や契約の差を確認する。調査結果は同じ挙動の利用箇所をまとめ、次の表に記録する。

| 変更した共通処理 | 利用箇所と経路 | 維持すべき挙動・意図した変更 | 影響と根拠 | 検証方法・結果 |
| --- | --- | --- | --- | --- |

根拠にはファイル・シンボル、要件やテストを示す。既存テストが通ることだけで、今回の修正対象以外への影響がないと判断しない。必要な利用経路を実行または検証する。

動的な参照やリポジトリ外の利用者など、追跡・実行できない範囲は「未確認」と記録する。検索で見つからないことを、利用者がいない根拠にしない。

## 3. 意図しない影響を修正する

要件に含まれない挙動の変化があれば、影響を受ける利用経路と原因を特定して修正する。共通処理を一律に変えることが原因なら、今回だけ必要な処理を対象の呼び出し元へ移す、または処理を切り分ける。

要件が共通の挙動変更を求めている場合は、関係する利用箇所も要件に従って更新する。影響があるという理由だけで、意図した変更を戻したり、処理の分離や共通化を強制したりしない。

修正では、公開 API、永続化形式、入力検証、セキュリティ検査、必要なエラー処理を保つ。検証を通すために、修正対象以外の期待値を書き換えない。

今回の修正対象で期待する挙動と、修正対象以外で維持する挙動の両方を検証する。意図しない影響を再現するテストがなければ、利用者から見える挙動を確認する最小の回帰テストを追加する。

修正後の差分から利用経路を再確認し、表と検証結果を更新する。

## 4. 結果を報告する

次を簡潔に報告する。

- 影響を調べた共通処理、利用箇所と根拠。
- 見つかった意図しない影響と修正内容。なければその根拠。
- 実施した検証と結果。
- 未解決の影響、未確認の範囲と理由。

呼び出し元には、修正ファイルと関連する要件 ID・シナリオも返す。今回の要件 ID がない既存利用箇所も、表の利用経路、維持すべき挙動、検証方法と結果を返し、再検証の対象から漏らさない。未解決・未確認を残したまま「影響なし」「検証済み」と報告しない。
