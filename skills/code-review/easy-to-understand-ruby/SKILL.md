# Easy To Understand (Ruby / Rails)

対象の Ruby / Rails コードを、TypeScript エンジニアだが Ruby と Rails にブランクがある読者が、予備知識なしで「何をしているか」と「なぜそう書いてあるか」を理解できる HTML にする。
手本の品質を毎回出すために、下の Phase を順に進め、各 Phase の完了条件を満たしてから次へ進む。

## 参照資料と優先順位

開始時に次を読む。

- 手本: `sanko/easy-closed-place-check-model.html` を最後まで読む。節の順、図の使い方、文の長さ、TypeScript への言い換え方をこれに合わせる。差分や複数ファイルの依頼でもこの手本に倣う。`sanko/easy-2026-10-08-14-15-branch-diff.html` は旧版で検査を通らないため、手本にしない。
- 骨組み: `references/html-template.html`。CSS はこのまま使い、`{{ }}` を埋める。
- Ruby: `references/ruby-4.md`。対象に出てくる構文を 2 章と 3 章の表で引き、Ruby 4.0 固有の挙動は 1 章で裏を取る。
- Rails: `references/rails-guide-81/index.md` で該当章を選び、その章の該当節だけ読む。
- 検査: `scripts/check_easy_html.py`。

指示が衝突したら、ユーザーの指示、この SKILL.md、手本の順に優先する。

## 入力と成果物を確定する

入力は次のいずれか 1 つ。複数あれば 1 つずつ別の HTML にする。

- ファイルパス、クラス名、メソッド名
- ブランチ名、コミット範囲、PR 番号、`git diff` の対象
- 指定がなければ直前のやりとりで扱ったコード

成果物は `easy-<対象名>.html` 1 件。`<対象名>` はファイルなら拡張子を除いたファイル名をケバブケースにしたもの（`closed_place_check.rb` なら `easy-closed-place-check.html`）、差分なら `<ブランチ名>-diff`（ブランチ名の `/` と `_` は `-` に置き換える）。保存先はユーザーの指定、なければ現在のディレクトリ。
読者はユーザーが変えたときだけ変える。

### 差分モード

入力がブランチ、コミット範囲、PR のときは次の読み替えで同じ Phase を進める。

- 対象は `git diff --stat <base>...<head>` に出る Ruby、ERB、Haml、YAML のファイル。SHA は `git rev-parse --short <head>`。
- セグメントはファイル 1 つにつき 1 つ。順は DB、モデル、サービス、バッチ、コントローラとビュー、テスト。ファイルが 9 つを超えるときは、この層ごとに 1 セグメントにまとめる。
- 2 節は「変更ファイルの地図」（パス、役割、追加と削除の行数の表）にし、各ファイルの節で変更箇所を行番号 `.ln` つき、セグメント見出し `.mk` つきで引用する。
- `.lead` には、パスの代わりに `<base>...<head>` と変更ファイル数、行数の代わりに追加と削除の行数を書く。
- Phase 3 の「対象の全行」は、変更箇所の全行と読む。

## 最優先ルール

- 説明に書く事実は実行して確かめる。`bin/rails runner`、`bin/rails console` の `to_sql`、`ruby -e`、spec の実行結果。アプリなしで gem だけで確かめたときは、その gem の版を添える。
- Rails ガイドに書かれた挙動は、章と節を添えれば実行なしで書いてよい。SQL 文字列や enum の数値などの具体値は実行結果だけを載せ、確かめられないものは「未確認」と明記して推測で断定しない。
- 説明するのは対象のコードに出てくるものだけ。一般論の講義を足さない。
- 本文と表に書く行番号は、対象ファイルの実際の行番号と一致させる。
- 「です・ます」で書く。1 段落は 4 文まで。長くなるなら箇条書きか表に割る。
- 色は CSS 変数だけで指定する。文字と背景が同系色になる指定をしない。
- `<`、`>`、`&` はコード内でも `&lt;` `&gt;` `&amp;` に変える。

## やさしく書くルール

読者は仕組みより先に「何のためか」を知りたい。文章が硬くなるのは、専門用語と漢語を重ね、仕組みから書き始めるときなので、次を守る。

- 節の冒頭に `.plain`（「ひとことで言うと」）を置く。コードも専門用語も使わず、業務の言葉で 1〜2 文。全体像、コード全文、文法表、各セグメント、「書いていないこと」の節すべてに付ける。
- `.oneline` に、日常のもの（付箋、台帳、名簿、受付、など）へのたとえを 1 つ入れる。たとえは 1 つだけ。増やすと混ざる。
- `.oneline` の直後に `.goals`（「読み終わるとわかること」）を 3 つ書く。
- コードを除いた 1 文は 60 字以内。超えたら読点で 2 文に割る。
- 専門用語は初出で 2 通りに言い換える。TypeScript の対応物と、ふだんの言葉（「サブクエリ（SQL の中に入れ子にした別の検索）」「LEFT JOIN（相手がなくても左側の行は残す結合）」）。
- 漢語の動詞はやまと言葉にする。取得する→取ってくる、実行される→動く、参照する→見る、保持する→持っておく、生成する→作る、結合する→くっつける、抽出する→選び出す、〜に関して→〜について、〜において→〜で。受け身（〜される）は主語を書いて能動にする。
- SQL や実行結果を載せたら、直後に `.ja`（「日本語にすると」）で話し言葉の 1 文に訳す。「〜なものだけ」「〜を横にくっつける」の形。
- 段落の 1 文目は「何のためか」。仕組みは 2 文目から。
- 「つまずきやすい点」は Q&A にする。Q は読者が口にしそうな言葉（「なんで import がないの？」）、A は 2 文以内で、最後にセグメントの記号。
- 見出しに専門用語だけを置かない。「遅延評価」ではなく「この時点では、まだ DB に問い合わせていない」。

## Phase 1: 対象と周辺を読む

1. 対象を読み、`wc -l` で行数、`git log -1 --format=%h -- <path>` でコミット SHA を取る（差分は「差分モード」の読み替え）。対象が別リポジトリからの複製なら、元のパスも `.lead` に書く。
2. 対象が参照するものを辿る: schema（`db/schema.rb` または annotate コメント）、関連先モデル、呼び出し元（`grep -rn <クラス名/メソッド名> app lib spec`）、spec、i18n の yml、対象アプリの `.claude/rules` や `CLAUDE.md` の規約、要件定義書や設計文書。呼び出し元ごとに、呼び出している行を 3〜5 行そのまま控える。spec は example 名（`it "..."`）を控える。存在しないものは「なし」と控える。
3. 対象に出てくる Ruby 構文と Rails の機能を列挙し、`references/ruby-4.md` と Rails ガイドの該当節を引いて意味を確認する。

完了条件: 呼び出し元ごとの引用行、spec の example 名、引いた Rails ガイドの章と節の名前、構文と機能の一覧が作業メモに揃っている。

## Phase 2: 事実を実行で確かめる

対象のリポジトリで `bin/rails runner 'puts Rails.env'` を試す。通らなければ `docker compose exec <app> bin/rails runner 'puts Rails.env'`、次に `RAILS_ENV=test bin/rails runner 'puts Rails.env'` を試す。どれかが通ったら、その方法で次を実行して結果を控える。

- scope、クラスメソッド、関連の SQL。メソッドチェーンは 1 段ずつ `to_sql` を取り、前段との差分の SQL 断片を控える（`bin/rails runner 'puts Model.a.to_sql; puts Model.a.b.to_sql'`）。
- enum が作るメソッド名（`Model.instance_methods.grep(/^result_/)`）、関連の解決先（`p Model.reflect_on_association(:name).klass`）、`squish` などの文字列処理の結果
- `::` の有無による定数の解決先。対象と同じ囲いの中で `name` を出して比べる（`bin/rails runner 'module GoogleMap; puts Restaurant.name; end; class GoogleMap::ClosedPlaceCheck; puts Restaurant.name; end'`）。`const_get` は祖先も辿るので、この確認には使わない。
- validation の有無（`Model.new.valid?` と `errors.full_messages`）
- spec の該当例の実行結果

3 つとも通らない場合は、その旨を HTML の冒頭 `.lead` に 1 文書き、確かめられなかった事実に「未確認」を付ける。

完了条件: HTML に載せる SQL、メソッド名、解決先のクラス名が、すべて実行結果か「未確認」のどちらかに分類されている。

## Phase 3: 骨組みを決める

HTML を書く前に、次を作業メモとして返答に箇条書きで書く。

1. 1 文の要約、日常のものへのたとえ 1 つ、TypeScript の対応物（Prisma のモデル、NestJS のサービス、cron ジョブ、など）、「読み終わるとわかること」3 つ
2. コード全文を A〜 のセグメントに分ける。各セグメントに「ひとことで言うと」の 1〜2 文を添える。セグメントは 4〜9 個。各セグメントが後半の 1 節になり、対象の全行がどれかのセグメントに入る。空行は直前のセグメント、先頭のコメントは次のセグメントに付ける（差分は「差分モード」の読み替え）。
3. 全体像: 登場する表や処理が何のためにあるかを 2 段落で書き、続けて対象が関わる表、クラス、処理の関係の図を描く。主役を `f-amber` で目立たせ、figcaption でどの箱が主役かを言う。
4. 文法表に載せる行: Phase 1 で列挙した構文すべて。各行に「このファイルでの例（行番号）」を付ける。
5. 追加の図: 処理の流れ（じょうご、ステップ）、名前解決、ライフサイクル、呼び出し元の関係のうち、文章だけでは分かりにくいものを 1〜3 つ。流れと名前解決の図はそのセグメントの節に、ライフサイクルの図は「書いていないこと」の節に置く。
6. 「書いていないこと」: 保存処理、validation、関連コードの置き場所。
7. つまずきやすい点: `references/ruby-4.md` 4 章と、Phase 2 で確かめた Rails の挙動のうち、対象に出ているものだけ。数合わせで足さない。読者の疑問の形（Q）で書き、各項目に対応するセグメントの記号を添える。

完了条件: 7 項目が埋まり、セグメントごとに「ひとことで言うと」があり、セグメントと節の対応が 1 対 1 で、対象の全行がセグメントに割り当てられている。

## Phase 4: HTML を書く

`references/html-template.html` を複製し、`{{ }}` を Phase 3 の内容で埋める。

節の順は手本と同じにする。

1. `.oneline`（要約、たとえ、TypeScript の対応物）と `.goals`
2. 全体像（`.plain`、2 段落の前置き、図）
3. コード全文（`.plain`、行番号 `.ln`、セグメント見出し `.mk`、コメントは `.cm`。差分は「差分モード」の地図と引用）
4. 文法表と「いちばん大事な違い」の note
5. セグメントごとに 1 節
6. 「書いていないこと」「つまずきやすい点（`.qa`）」「ことば早見表」。早見表は本文を書き終えてから、本文で使った用語を拾って作る。

セグメントの節の書き方。

- 見出しの直後に `.plain` を置く。
- `.cmp` で Ruby と TypeScript を並べる。TypeScript 側は読者が実際に書く形（Prisma、TypeORM、NestJS、Knex、`as const`、デコレーター）にし、Ruby の直訳にしない。ラベルは「TypeScript のイメージ」、ライブラリで言い換えるときは「Prisma のイメージ」のようにその名前。
- 起きることを番号付きで書き、理由（なぜこの書き方か）を書く。理由には根拠の出どころを 1 つ添える: spec の example 名、規約ファイルのパス、要件定義書の節名、コード内コメントの行番号。
- 呼び出し元は Phase 1 で控えた行をそのまま引用する。
- schema や annotate コメントのセグメントは、TypeScript の `type` に書き直して載せる。
- enum と定数の値は、名前・画面の表示（i18n の yml）・意味（要件定義書やコード内コメント）の 3 列の表にする。
- 処理の流れは `.step` で 1 段ずつ、Ruby の 1 行と Phase 2 で得た SQL 断片や結果を並べ、直後に `.ja` で日本語に訳す。

SVG の書き方。`viewBox` と `aria-label` を付け、色は `f-*` クラスだけで指定する。文字は日本語で書き、識別子だけ `mono` クラスにする。文字は 14px 以下。文字幅の目安は日本語 1 文字がフォントサイズ、英数字がその 0.6 倍で、箱はその幅に左右 8px を足して描く。矢印は `<marker>` を使う。

完了条件: `python3 scripts/check_easy_html.py <出力ファイル>` が OK。検査は骨組み、SVG のはみ出し、段落と 1 文の長さ、やさしさの部品（`.plain` `.goals` `.ja` `.qa`）を見る。

## Phase 5: 手本と見比べて直す

1. 手本と並べて次を読み直し、満たさない箇所を直す。
   - 各セグメントの節に、「ひとことで言うと」、Ruby と TypeScript の対比、起きること、根拠つきの理由の 4 つがある。
   - `.cmp` の TypeScript 側が、読者が実際に書く形になっている。
   - 文法表の行がコードの構文を漏らしていない。
   - 「未確認」が付いていない事実は Phase 2 の結果で裏が取れている。
   - 専門用語に初出の言い換え（TypeScript の対応物とふだんの言葉）がある。
   - 「やさしく書くルール」の漢語を、やまと言葉に置き換えてある。
2. 直したら `python3 scripts/check_easy_html.py <出力ファイル>` を再実行する。

手順 1 と 2 を NG が 0 になるまで繰り返す。3 回で収まらなければ、残る NG を最終報告に書く。

完了条件: 検査が OK で、手順 1 の 6 項目を満たす。

## 完了報告

- 出力ファイルのパス
- 実行して確かめた事実と、未確認にした事実
- 参照した Rails ガイドの章と `ruby-4.md` の節
- 検査の結果と、残った NG
