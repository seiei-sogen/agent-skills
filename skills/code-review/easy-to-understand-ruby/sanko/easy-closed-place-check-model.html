5B：class GoogleMap::ClosedPlaceCheck < ApplicationRecord

ひとことで言うとこの 1 行で、「DB の表を Ruby のクラスとして扱う」準備が全部終わります。import も、表の名前の指定も、列の定義もいりません。
Ruby
class GoogleMap::ClosedPlaceCheck < ApplicationRecord
  ...
end
TypeScript のイメージ
export class ClosedPlaceCheck extends ApplicationRecord {
  ...
}

この1行で起きていることは3つです。

  1. 継承するだけで DB 操作が全部使える。ApplicationRecord の親は Rails の ActiveRecord::Base です。これを継承すると find（ID で1件取る）、where（条件で探す）、update!（保存）などが最初から使えます。
  2. import 文がいらない。Rails（Zeitwerk という仕組み）は「ファイルの場所」と「クラス名」を対応させて、使われた瞬間に自動で読み込みます。
    app/models/google_map/closed_place_check.rb ⇔ GoogleMap::ClosedPlaceCheck
  3. 表の名前も自動で決まる。クラス名 ClosedPlaceCheck から closed_place_checks（複数形・スネークケース）を作り、GoogleMap モジュールが決めている接頭辞 google_map_ を付けて、google_map_closed_place_checks になります（app/models/google_map.rb の table_name_prefix）。

Rails の基本方針は「名前を決まりどおりにすれば、設定は書かなくてよい」です。英語では Convention over Configuration と呼びます。

6C：audited only: :dismissed_at, on: :update

ひとことで言うと「対応不要にした」という操作だけ、いつ誰がやったかを別の表に残しておきます。
Ruby
audited only: :dismissed_at, on: :update
TypeScript のイメージ
@Audited({ only: ['dismissed_at'], on: ['update'] })
class ClosedPlaceCheck { ... }

audited は「いつ・誰が・どの値をどう変えたか」を audits という別の表に自動で残す gem です。

  • only: :dismissed_at：dismissed_at 列が変わったときだけ記録する。
  • on: :update：更新のときだけ記録する。新しく行を作ったときは記録しない。

なぜ dismissed_at だけか：この表で人が手で変えるのは「対応不要にする」（dismissed_at に時刻を入れる）だけです。result などはバッチが毎回上書きするので、履歴に残しても役に立ちません。また、紐付けの付け替えの履歴は、紐付け行（RestaurantWebSystem）側の audited が URL の変更として残します。

ひとことで言うと「この記録は、どのお店のものか」をつなぐ線です。:: は「同じ名前の別のクラスと間違えないように」という印です。

「この記録は1つのお店に属する」という宣言です。これだけで次のものが使えるようになります。

  • check.restaurant = r：restaurant_id に r.id を入れる。

class_name: "::Restaurant" の :: がないとどうなるか

Rails は、関連の名前 :restaurant からクラス名 Restaurant を推測します。ただし探すときは、今いる名前空間の内側から順に探します。GoogleMap の中には GoogleMap::Restaurant（Google の情報の控えの表）があるので、そちらが先に見つかってしまいます。

TypeScript でいえば、import { Restaurant } from './restaurant'（同じフォルダの別物）と import { Restaurant } from '@/models/restaurant'（ルートからの絶対パス）の違いです。

書き方何が起きるか
check.result文字列 "no_match" が返る（DB の中身は 2）

「G の条件に当てはまる紐付け行を集めて、その記録の id を持つ行だけ返して」

記録がまだない組では、サブクエリ（SQL の中に入れ子にした別の検索）の id が NULL になります。SQL では NULL はどの値とも一致しないので、一覧に出るのは「記録がある組」だけです。

なぜ result 列で絞らないのか（28・50行目のコメント）

紐付け行は、ほかの画面やバッチでも書き換えられます。記録の result は「最後に調べたときの結果」でしかありません。だから「今も対応が必要か」は、毎回いまの紐付けを見て決めます。spec にある2つの例がこれを示しています。

  • 「別の画面で紐付けを直した店舗は一覧から消える」：result が no_match のままでも、紐付けが閉業ページを指さなくなったので消える。
  • 「付け替えた後で閉業 place に戻された組は、すぐに一覧へ戻る」：result が付け替え済みでも、紐付けがまた閉業ページを指したので出る。

10G：target_web_systems：再チェックの対象を探す、このファイルの心臓部

ひとことで言うと「いま調べ直す必要があるお店はどれか」を選び出す、いちばん長い検索条件です。1 行ずつ条件を足して、対象を絞り込んでいきます。

def self. なのでクラスメソッド（TS の static）です。メソッドを1つずつつなげて（メソッドチェーン）、検索条件を少しずつ足していきます。行の先頭の . は「前の行の続き」という意味です。

「お店が公開中で、テスト用でなく、AR 側では閉業にしていないものだけ」

  • merge：別のモデル（ここでは Restaurant）の検索条件を、今の検索に合体させる。
  • published：Restaurant の enum が作った scope。公開中のお店。
  • where.not(...)：「〜ではない」。:permanently_closed は Rails が enum の数字 2 に置き換える。
  • AR 側でも閉業になっているお店は、今回の対象外と決めています（要件定義書の「対象外」）。
  • ::Restaurant の ::：このファイルの書き方（class GoogleMap::ClosedPlaceCheck）では、:: がなくても AR のお店になります（コンソールで確認済み）。ただし module GoogleMap で囲む書き方のファイル（closed_place_pair.rb など）では、Restaurant は GoogleMap::Restaurant を指します。:: を付けると、どちらの書き方でも意味が変わりません。

4Google の情報と結合する

.joins("INNER JOIN google_map_restaurants ON google_map_restaurants.google_place_id = restaurant_web_systems.source_id")

「Google から取ってきた情報の行も、横にくっつける」

紐付け行と google_map_restaurants の間には Rails の関連（belongs_to など）がありません。そのため名前では書けず、SQL を文字列でそのまま書いています。紐付け行の source_id（place ID）で、Google の情報の行を見つけます。

5Google 側で閉業のものだけ

.where("google_map_restaurants.data->>'open_status' = 'permanently_closed'")

「Google 側で閉業になっているものだけ」

data は jsonb 列（JSON をそのまま入れられる PostgreSQL の列）です。->> は PostgreSQL の演算子で、JSON のキーの値を文字列で取り出します。TS でいえば data.open_status === 'permanently_closed' です。この PR では、この条件に合う行だけを集めた索引（index_google_map_restaurants_on_permanently_closed）も追加しています。

6記録を「あれば」くっつける（LEFT JOIN）

.joins(<<~SQL.squish)
  LEFT JOIN google_map_closed_place_checks
    ON google_map_closed_place_checks.restaurant_id = restaurant_web_systems.restaurant_id
   AND google_map_closed_place_checks.closed_google_place_id = restaurant_web_systems.source_id
SQL

「この組の記録があれば横にくっつける。なくても行は残す」

  • <<~SQL から SQL までが1つの文字列です（ヒアドキュメント）。~ は行頭の字下げを取り除く印です。SQL という語はただの終わりの目印で、END でもかまいません。
  • .squish：Rails が足した文字列のメソッドで、改行や連続した空白を1つの空白にまとめる。実際に試すと "LEFT JOIN a ON b = c" のように1行になる。
  • INNER ではなく LEFT にする理由：LEFT JOIN は「相手がなくても、左側の行は残す」結合です。まだ一度も調べていない組には記録がありません。INNER JOIN だと、そういう組が消えてしまいます。LEFT JOIN なら、記録がない組も残り、記録の列はすべて NULL になります。

7「対応不要」にした組を外す

.where(google_map_closed_place_checks: { dismissed_at: nil })
AND google_map_closed_place_checks.dismissed_at IS NULL

「『対応不要』の時刻が入っていないものだけ」

  • ハッシュのキーに表の名前を書くと、別の表の列を条件にできる。
  • nil を渡すと、Rails は = NULL ではなく IS NULL にしてくれる（SQL の = NULL は常に成り立たない）。
  • 記録がない組は、LEFT JOIN で dismissed_at も NULL なので、ここを通る。つまり未チェックの組も対象に入る。

返ってくるのは「記録」ではなく「紐付け行」

このメソッドは ClosedPlaceCheck クラスにありますが、返すのは RestaurantWebSystem の検索条件です（コンソールで見ると型は RestaurantWebSystem::ActiveRecord_Relation）。55行目の @return もそう書いています。

この時点では、まだ DB に問い合わせていない

このメソッドが返すのは「検索条件のかたまり」（Relation）で、まだ DB には問い合わせていません。count や each などを呼んだときに、初めて SQL が実行されます。TS の Knex や Kysely のクエリビルダーが、await するまで実行されないのと同じです。

rel = GoogleMap::ClosedPlaceCheck.target_web_systems  # まだ何も起きない
rel.count                                              # ここで SELECT COUNT(*) ... が走る
rel.exists?(id: 123)                                   # ここで「1件でもあるか」の SQL が走る

なぜこのクラスに置くのか：3か所が同じ条件を使うから

53行目のコメントのとおり、同じ条件を3か所で使います。条件を1か所にまとめておけば、「バッチは対象と判断したのに、一覧には出ない」といったずれが起きません。

11このクラスに「書いていない」こと

ひとことで言うとこのクラスにあるのは「表の形」と「探し方」だけです。書き込みや入力チェックは、別の場所にあるか、DB に任せています。

保存の処理は別のクラスにある

記録を書き込むのは app/services/google_map/closed_place_pair.rb の record! です。

ClosedPlaceCheck.find_or_initialize_by(restaurant_id:, closed_google_place_id:).update!(attributes)
  • restaurant_id: は restaurant_id: restaurant_id の省略形です（Ruby 3.1 から）。TS の { restaurant_id } と同じです。
  • find_or_initialize_by：条件に合う行があれば読み込み、なければ「まだ保存していない新しい行」を作る。
  • update!：値を入れて保存する。! 付きなので、失敗したら例外を投げる（throw）。! なしの update は false を返すだけ。
  • この2つで「あれば上書き、なければ作る」になり、「組ごとに1行、毎回上書き」が実現します。

入力チェック（validates）がない

モデルでの入力チェックは、belongs_to が自動で付ける「お店が必須」だけです。ほかの「空はだめ」（not null）や「同じ組は1行」（UNIQUE）は DB が守っています。違反すると、保存のときに DB がエラーを返します。

列の定義がどこにもないのに、なぜ check.checked_at が使えるの？

Rails が起動時に DB の表を見て、列ごとの読み書きメソッドを作るからです（A）。

import がないのに、なぜ ApplicationRecord や RestaurantWebSystem が見つかるの？

ファイルの場所とクラス名を合わせておくと、使われた瞬間に自動で読み込まれるからです（B）。

クラスの中の audited や enum は、宣言？ それとも処理？

処理です。クラスを読み込むときに 1 回だけ動く、ただのメソッド呼び出しです。デコレーターと同じ役目です（C・D・E）。

Restaurant と書いたら、どの Restaurant になるの？

今いる名前空間の内側から順に探すので、別物を指すことがあります。迷ったら :: を付けてください（D・G の 3）。

check.result は数字が返るの？

文字列 "no_match" が返ります。DB に入っているのは数字ですが、Ruby では名前で扱います（E）。

target_web_systems を呼んだら、すぐ SQL が走るの？

走りません。count や each を呼んだときに初めて走ります（G）。

where(dismissed_at: nil) は = NULL になって、何も当たらないのでは？

Rails が IS NULL に直してくれるので、ちゃんと当たります（G の 7）。
