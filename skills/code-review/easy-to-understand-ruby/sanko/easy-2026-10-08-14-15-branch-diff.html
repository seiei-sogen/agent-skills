1まず全体像

何が困っていたのか

AutoReserve（以下 AR）の店舗は、Google マップ上のお店と紐付いています。Google マップ上のお店 1 件を、コードでは place と呼びます。

ところが、テナントが入れ替わったりリニューアルしたりすると、AR の店舗が閉業した旧テナントの place に紐付いたまま取り残されることがあります。place そのものが消えればクロールが失敗するので気づけます。しかし、place が残ったまま「閉業」と表示されているだけだと、誰も気づけません。issue を起票した時点で、Google マップ上は閉業になっている店舗が 274 件ありました。

今までAR の店舗「海鮮居酒屋 湊」の紐付け先は、閉業した旧テナントの place のまま。営業中の新しい place が別にあるのに、誰も気づかない。
このブランチ毎日バッチが閉業 place に紐付いた店舗を見つけ、Google マップを検索し直す。同じ店だと確実に言える候補が 1 件だけなら自動で付け替える。それ以外は管理画面に並べて、人が決める。

作ったものは 4 つ

  1. 日次バッチ：Google マップ側で閉業になった紐付けを 1 日最大 50 組選び、1 組ずつ再チェックする（RecheckClosedGoogleMapLinksBatch）。
  2. 判定と付け替え：検索で見つかった候補を、電話番号・店名・距離・営業中かどうかで AR の店舗と比べる。自動で付け替えてよいときだけ付け替える（GoogleMap::ClosedPlaceRecheckService ほか）。
  3. 再チェック記録のテーブル：(店舗, 閉業 place) の組ごとに、最新の結果を 1 行だけ残す（google_map_closed_place_checks）。
  4. 管理画面：自動で付け替えられなかった組を一覧にする。運用担当は候補を選んで手で付け替えるか、「対応不要」にする（admin の「Google Map 閉業の紐付け確認」）。

なぜ「毎日のバッチ」で拾うのか

既存のクロールは place の営業状況を DB に保存しています。バッチはその値を読むだけなので、クロール本体を変えずに済みます。クロールの途中に処理を足す案もありましたが、それだと既にある 274 件を拾えません。クロールの遅延や失敗にも波及します（要件定義書「採用した判断」）。

4-1. import が 1 行もない理由

このブランチのどのファイルにも import や require がありません。Rails（Zeitwerk というオートローダー）がファイルの場所とクラス名を対応させ、初めて使われたときに自動で読み込むからです。app/ 直下のフォルダ名（models、services など）は名前に入らず、その下のフォルダが名前空間になります。

このブランチで一番まぎらわしいのがここです。Restaurant という名前のクラスが 2 つあります。

  • ::Restaurant：AR 店舗（restaurants テーブル）

6モデル

Rails のモデルは、テーブル 1 つに対応するクラスです（ActiveRecord）。TypeORM や Prisma のエンティティに近いものですが、クエリを組み立てるメソッドもモデル自身が持つ点が違います。

6-1. GoogleMap::Restaurant に open_status を足した

前半はコメント（annotate）の更新です。後半で、place の営業状況を読むメソッドを足しました。

  • data は jsonb の列なので、Ruby では文字列をキーにした Hash になります。例：{ "open_status" => "permanently_closed", "coordinates" => {...} }。
  • data&.dig("open_status") は、data が nil なら nil、そうでなければ "open_status" の値を返します。dig は入れ子の Hash を安全にたどるメソッドです。
  • メソッドの最後の式がそのまま戻り値になるので、return は書きません。

Ruby 文法メモ：YARD コメント

# @return [String, nil] は YARD という書式のドキュメントコメントです。JSDoc の @returns {string | null} と同じ役割です。

なぜメソッドにしたのか

place の営業状況は、候補の判定（§6-3）、閉業 place が営業に戻ったかの確認（§7-2）、手動の付け替えの確認（§7-3）で読みます。毎回 data["open_status"] と書かずに、名前で読めるようにしました。

論点採用した案採らなかった案と理由
きっかけクロールが保存した営業状況を読む日次バッチ。処理の直前に閉業 place を取り直すクロールの途中に処理を足す。既にある 274 件を拾えず、クロールの遅延や失敗に波及する
AR 側も閉業の店舗初回は対象外含める。本当に閉業したのか、誤った紐付けで閉業にされたのかを区別する根拠がまだない
自動で付け替える条件4 条件すべてが一致する候補がちょうど 1 件。紛らわしい候補が無く、候補をすべて取得でき、ほかの行が指していない検索結果が 1 件なら付け替える。検索は網羅的でなく、近くの別の店や同じ店の別の掲載を取り違える
付け替えのやり方紐付け行の url を書き換える消して作り直す（既存の画面のやり方）。データの優先順位の判定が変わる。古い行を archived にして新しく作る。status を見ない URL の逆引きが、古い place を店舗に結び付けたままにする
付け替えたときの店舗情報変えない付け替えた後に店舗情報の更新処理を呼ぶ。契約店舗の営業状況まで書き換わり、「営業状況の反映は後で扱う」という issue の方針と食い違う

Q1. バッチが自動で付け替えるのは、どんなときですか。

完全一致（営業中・300 m 以内・電話番号が一致・店名が一致）の候補がちょうど 1 件で、部分一致の候補が無く、候補をすべて取得でき、付け替え先をほかの紐付け行が指していないときだけです（§6-3、§7-2）。

Q2. module GoogleMap の中で Restaurant と書くと、何を指しますか。

place（GoogleMap::Restaurant、google_map_restaurants テーブル）です。AR 店舗を指すには ::Restaurant と書きます（§4-2）。

Q3. 管理画面の一覧に出る組は、何で決まりますか。

記録の result ではなく、今の紐付けで決まります。紐付け行がまだ閉業 place を指していて、店舗が公開中で AR 側が閉業でなく、対応不要にしていない組です（target_web_systems、§6-2）。

Q4. バッチが検索している間に、運用担当が別の画面で紐付けを直しました。バッチはどうしますか。

書く直前に紐付け行をロックして読み直し、組がもう対象でないので何も書きません（skipped）。運用担当の変更は上書きされません（§7-3、図 4）。

Q5. Google マップへのアクセスを、DB のロックの中で行わないのはなぜですか。

1 組で数秒かかるからです。その間ロックとトランザクションを持ち続けると、同じ行を更新したい別の処理を待たせ、DB の接続も占有します（§7-2）。

Q6. 「対応不要」にした組は、その後どうなりますか。

dismissed_at に日時が入り、再チェックの対象からも一覧からも外れます。誰が操作したかは audited の変更履歴に残ります（§7-3、§10-5）。

Q7. 付け替えで、紐付け行の url だけを書き換えれば足りるのはなぜですか。

紐付け行の before_validation :set_source_from_url が保存の直前に URL を解析し、source と source_id を自動で更新するからです（§2）。
