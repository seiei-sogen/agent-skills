# SQL レビュー

変更差分や指定されたクエリに含まれる SQL を、データ量が増えたときに遅くなる書き方や、インデックスが効かない書き方がないかの観点で確認し、根拠と修正案を付けて報告する。
性能が対象で、業務ロジックの正しさやセキュリティは別のレビューに任せる。

## 入力と成果物

対象は、比較先ブランチとの差分、またはユーザーが指定したファイル、クエリ、EXPLAIN 出力である。
差分の場合は `git diff <比較先>...HEAD`、index、working tree、対象となる未追跡ファイルを含める。
比較先は呼び出し元またはユーザーの指定を引き継ぎ、指定がなければリポジトリの規約から特定し、一意に決められない場合だけ確認する。

成果物は、指摘ごとの位置、観点、問題、根拠、修正案、重大度をまとめた指摘表である。
修正の範囲は次のとおりである。

- 入力が差分で、差分で入った SQL の指摘が重大度 高なら、自動で修正する
- 差分の中以下の指摘と、指定されたクエリへの指摘は、ユーザーが求めた場合だけ修正する
- 差分外の既存 SQL の指摘は、重大度にかかわらず修正せず報告する

確認できなかった事柄は、指摘の根拠の欄か報告に「ラベル: 対象」の書式で書く。ラベルは 2 種類を使い分ける。

- 要確認: 指摘の前提、修正案の効果、実行計画などを確かめられなかった（例: 要確認: 修正後の計画）
- 規模未確認: テーブル規模や実行頻度が分からない（例: 規模未確認: orders）

判定基準と修正例は参照資料 [references/sql-patterns.md](references/sql-patterns.md) にまとめ、手順 2 の観点表に各観点の節番号を載せている。

## 接続と実行の制約

接続先と呼ぶのは、ユーザーが指定した DB と、プロジェクトのローカル開発用・テスト用 DB である。
ローカル開発用・テスト用と判定するのは、ホストが localhost や docker compose のサービスで、フレームワークの環境設定（`database.yml` の `development`、`test` など）がそう示す DB に限る。判定できなければ接続せず、停止している DB を自分で起動しない。

接続先では次だけを行う。

- `EXPLAIN`
- 統計ビューとシステムカタログの参照（参照資料 10 節）
- `EXPLAIN ANALYZE`。実際にクエリを実行するので、ロック句、副作用のある関数、データ変更を含む CTE、`SELECT INTO` を含まない `SELECT` に限る。ローカル開発用・テスト用以外の接続先では、ユーザーが許可した場合に限る
- ローカル開発用・テスト用 DB に限り、発行 SQL を確かめるためのアプリのコンソールやテストの実行、修正の検証のための読み取り専用の比較クエリとテストの実行

統計更新、`VACUUM`、`REINDEX`、インデックスの作成や削除は、ユーザーの許可なしに実行しない。テストフレームワークがテスト DB を作り直す操作はこの禁止に含めない。

## 1. 対象の SQL と前提を集める

入力が差分なら、差分から次を抽出する。
入力がユーザーの指定したクエリ文字列や EXPLAIN 出力なら、それをそのまま対象にし、利用箇所の追跡は省く。指定がファイルなら、そこで定義したクエリやスコープの利用箇所は追う。

- `.sql` ファイル、マイグレーション、スキーマや DDL の変更
- 文字列として埋め込まれた生 SQL
- ORM やクエリビルダの呼び出しのうち、発行される SQL が変わる箇所
- 関連の参照（`user.posts` のような遅延ロード）と、ループの中でクエリを発行しているコード
- 差分で変えたクエリ、スコープ、関連定義の利用箇所。view、serializer、ジョブなど差分の外にあるループまで追う。事前読み込み（`includes` など）を外した場合は、利用箇所がループ内でその関連を参照しているかを確認する

ORM の呼び出しは、`to_sql`（Rails）や `str(queryset.query)`（Django）、クエリログで実際の SQL を確かめる。確かめられない場合は、推定した SQL を書き「要確認: 発行 SQL」と記録する。
差分に SQL に当たる変更がなければ、その根拠を報告して終了する。

次に、判断の前提になる情報を集める。

- DBMS の種類とバージョン。参照資料は PostgreSQL の構文で書いてある。同等機能がない手法は提案せず、その DBMS の代替手段を書くか、代替がなければ修正案を「なし」とし理由を書く。DBMS が不明なら PostgreSQL の構文で書き「要確認: DBMS」を付ける
- 対象テーブルの定義と既存インデックス。スキーマファイル、過去のマイグレーション、DDL から読む
- テーブルの想定規模とクエリの実行頻度。要件、設計、既存のコメント、ユーザーの説明から読む。接続先があれば統計ビューから、ユーザーが貼った本番相当の計画があればその実測行数からも読み、どの環境の値かを根拠に書く。分からなければ「規模未確認: テーブル名」と記録する
- 実行計画。接続先があれば `EXPLAIN` を取り、制約を満たす `SELECT` は `EXPLAIN (ANALYZE, BUFFERS)` で実測も取る。ユーザーが貼った EXPLAIN 出力も同様に扱い、取得環境が分からなければ「要確認: 計画の取得環境」と記録する
- 実行計画の代表性。計画を取った環境の行数が想定規模と桁で違う場合や、想定規模が未確認の場合は、計画はインデックスを使える形かどうかの確認にだけ使い、Seq Scan などのノード種別では判定しない。判定は条件・結合・並び替えの列と既存インデックスの対応（参照資料 2、3 節）と想定規模で行い、根拠に「計画の取得環境の行数 n」を書く。差分のスキーマ変更が接続先に未適用なら「要確認: 変更後の計画」とする

既存インデックスが分からないまま「インデックスがない」と断定しない。

## 2. 観点ごとに点検する

各クエリを次の観点で確認する。判定基準と修正例は、参照資料の対応する節を読む。

| 観点 | 見る箇所 | 典型的な問題 | 参照する節 |
| --- | --- | --- | --- |
| 実行計画 | `EXPLAIN` 出力、ヒント句、プランナー設定 | 大きいテーブルの Seq Scan、見積もりと実測の乖離、外側の行数が多く内側をインデックスで引けない Nested Loop、パーティションキーで絞れず全パーティションを読む、ヒント句や設定で計画を固定している | 1 |
| インデックス利用 | `WHERE`、`JOIN`、`ORDER BY` の列と既存インデックス | 条件・結合・並び替えの列の組み合わせに合うインデックスがない、列への関数適用、暗黙の型変換、前方ワイルドカードの `LIKE`、`OR` 条件、複合インデックスの列順不一致 | 2、3 |
| 取得量とページネーション | `SELECT` 句、`LIMIT`、`OFFSET`、`COUNT` | 大きい列を含む多数行の全列取得、大きい `OFFSET`、全件 `COUNT(*)` | 4 |
| JOIN とサブクエリ | `FROM`、`JOIN`、サブクエリ、CTE | `SELECT` 句の相関サブクエリや `NOT IN` が外側の行ごとに実行される、`LIMIT` 付きサブクエリや実体化される CTE の外側に条件がある | 5 |
| N+1 | ループ内のクエリ、関連の参照、ORM の遅延ロード | 親の件数ぶんクエリが発行される | 6 |
| 集約 | `GROUP BY`、`HAVING` | 絞り込み列とグループ化列を含むインデックスがない、行の条件を `HAVING` に置いている、繰り返し計算される重い集約 | 7 |
| 書き込み | `INSERT`、`UPDATE`、`DELETE` | ループ内の 1 件ずつの書き込み、一括化できる更新 | 8 |
| スキーマとマイグレーション | DDL、インデックス定義、メンテナンスコマンド | 書き込みや読み取りを止めるインデックス作成・削除や DDL、重複インデックス、削除・変更する対象に依存する既存クエリや制約、結合相手と合わない列の型 | 9 |

観点ごとの判断は、テーブル規模と実行頻度に照らして行う。
数十行のマスタテーブルへの Seq Scan や、管理画面で月に数回動くクエリの `OFFSET` を、同じ重みで指摘しない。
ORM が既定で発行する全列取得（`SELECT users.*`）は、大きい列を含む多数行の取得か、カバリングインデックスで Index Only Scan を狙える場合にだけ指摘する。

## 3. 指摘を整理する

指摘は次の表にまとめる。

| 位置 | 観点 | 問題 | 根拠 | 修正案 | 重大度 |
| --- | --- | --- | --- | --- | --- |

- 位置: ファイルと行、ORM 呼び出しのメソッド名、または指定されたクエリの識別子
- 根拠: 実行計画、既存インデックス、テーブル規模、該当する参照資料の節。推測で断定せず、確認できなかった前提は「要確認: 対象」または「規模未確認: テーブル名」と書く
- 修正案: 対象の DBMS の構文で書く。インデックス追加なら、書き込みが遅くなるコストと、同じインデックスで賄える既存クエリを併記し、作成方法は参照資料 9 節に従う。結果や API の仕様、コールバックやトランザクションの単位が変わる修正案（カーソル方式のページネーション、概算件数、マテリアライズドビュー、書き込みの一括化など）は、重大度が中以上の指摘に限って出し「仕様変更が必要」と明記する。低の指摘で仕様変更を伴う手段しかなければ、修正案を「なし」とし理由を書く
- 重大度: 次の基準で決める

| 重大度 | 基準 |
| --- | --- |
| 高 | 想定規模で明らかに遅くなる、またはロックや大量 I/O で他の処理に影響する。参照資料 9 節で書き込みや読み取りを止めるとした操作（`CONCURRENTLY` なしのインデックス作成・削除や `REINDEX`、全行の書き換え・検証、`VACUUM FULL`）は、規模未確認でもここに置き「規模未確認: テーブル名」を併記する |
| 中 | 今は問題にならないが、テーブルの成長や実行頻度の増加で問題になる。それ以外の規模未確認もここに置き、問題になる規模の条件を書く |
| 低 | 規模も成長も小さく実害はないが、書き方として直したほうがよい |

今回の差分で変更していない既存の SQL に問題を見つけた場合は、同じ形式と重大度基準で別の表に記録する。手順 1 で読んだ範囲で目に入ったものだけを記録し、網羅的には探さない。重大度 高でも手順 4 の修正対象には含めず、報告で目立つ位置に置く。

## 4. 修正する

差分で入った重大度 高の指摘は、ユーザーの依頼を待たずに修正する。差分の中以下の指摘と、指定されたクエリへの指摘は、ユーザーが求めた場合だけ修正する。
修正は、結果集合、`ORDER BY` で指定された並び順、NULL の扱い、アプリケーション側のトランザクション境界を変えない範囲で行う。
変更前後で同じ結果になることを、既存テストか比較クエリで確認する。
「仕様変更が必要」と記した修正案は、重大度 高でも自動では修正せず、修正の依頼だけでも承認とみなさず、ユーザーが仕様変更を認めた場合にだけ行う。認められていなければ実施せず、指摘表に残す。実施した場合は、認めた変更どおりに結果が変わり、それ以外は変わらないことを確認する。

- インデックスは、同じ列を含む既存インデックスで賄えないかを先に確認する
- インデックス作成は参照資料 9 節の書き込みを止めない方法で行い、マイグレーションのフレームワークがトランザクションで包む場合はその解除（Rails の `disable_ddl_transaction!` など）も含める
- インデックスの削除は、参照資料 9 節の削除の条件をすべて満たす場合に限る
- 接続先があれば、修正前後の `EXPLAIN` で改善を確認する。接続先がない場合や、許可なしにインデックスを作れず修正後の計画を取れない場合は「要確認: 修正後の計画」と報告に書く

修正を通すために、既存テストの期待値を書き換えない。ユーザーが認めた仕様変更の範囲のテストは除く。

## 5. 結果を報告する

次を簡潔に報告する。

- レビューした SQL と、前提にした DBMS、テーブル規模、既存インデックス
- 指摘表。指摘がなければ、確認した観点と根拠
- 差分外の既存 SQL に見つけた問題（指摘表とは分けて）
- 自動で修正した差分の重大度 高の指摘と、求められて修正した指摘。それぞれ変更内容と検証結果
- 修正していない重大度 高の指摘。差分外の既存 SQL のもの、仕様変更が必要で承認待ちのもの、検証できず見送ったもの
- 確認できなかった範囲と理由。実行計画が取れない、規模が分からない、既存インデックスが読めないなど

確認できなかった範囲を残したまま、無条件の「問題なし」とは書かない。指摘がない場合は「指摘なし（要確認: 実行計画 / 規模未確認: orders）」のように範囲を併記する。

## 完了条件

- 差分または指定されたクエリから SQL を抽出し、差分の場合は変更したクエリやスコープの利用箇所も抽出している
- DBMS、テーブル定義、既存インデックス、想定規模を確認している、または「要確認」「規模未確認」と記録している
- 各クエリを手順 2 の観点で点検し、指摘が位置、根拠、修正案（または「なし」と理由）、重大度を備えている
- 推測で断定した指摘がなく、確認できなかった前提は「要確認: 対象」または「規模未確認: テーブル名」の書式で記録されている
- 差分で入った重大度 高の指摘は、修正済みか、仕様変更が必要・検証不能で未修正と報告されている
- 差分外の既存 SQL は修正されておらず、重大度 高のものが報告されている
- 修正した場合、結果集合が変わらないこと（仕様変更を認めた修正では認めた変更以外が変わらないこと）と性能の改善を確認しているか、確認できなかったことを報告している
- 確認できなかった範囲と理由が報告されている
- 差分に SQL がない場合は、その根拠を報告している
