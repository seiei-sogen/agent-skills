# SQL レビュー

変更差分や指定されたクエリに含まれる SQL を、データ量が増えたときに遅くなる書き方や、インデックスが効かない書き方がないかの観点で確認し、根拠と修正案を付けて報告する。
性能が対象で、業務ロジックの正しさやセキュリティは別のレビューに任せる。

## 入力と成果物

対象は、比較先ブランチとの差分、またはユーザーが指定したファイル、クエリ、EXPLAIN 出力である。
比較先は呼び出し元またはユーザーの指定を引き継ぎ、指定がなければリポジトリの規約から特定し、一意に決められない場合だけ確認する。

成果物は、指摘ごとの位置、観点、問題、根拠、修正案、重大度をまとめた指摘表である。
修正はユーザーが求めた場合だけ行い、求められていなければ指摘表と報告で終える。

パターンの判定基準と修正例は [references/sql-patterns.md](references/sql-patterns.md) にある。手順 2 の観点表に対応する節を示す。

## 接続と実行の制約

データベースへの接続は、ユーザーが接続先を指定した場合に限り、次だけを行う。

- `EXPLAIN`
- 統計ビューの参照（参照資料 10 節）
- `EXPLAIN ANALYZE`。実際にクエリを実行するので、対象が `SELECT` で、`FOR UPDATE` などのロック句や `nextval` のような副作用のある関数を含まず、接続先がローカルかテスト用の場合に限る。それ以外の接続先では、ユーザーが許可した場合に限る

`ANALYZE <table>` による統計更新、`VACUUM`、`REINDEX`、インデックスの作成や削除は、ユーザーの許可なしに実行しない。
プロジェクトのローカル開発用・テスト用 DB では、接続先の指定がなくても、`to_sql` やテスト実行による SQL の確認と `EXPLAIN` を行ってよい。

確認できなかった事柄のラベルは 2 種類を使い分ける。

- 要確認: 指摘の前提、修正案の効果、実行計画などを確かめられなかった
- 規模未確認: テーブル規模や実行頻度が分からない

## 1. 対象の SQL と前提を集める

入力が差分なら、差分から次を抽出する。
入力がユーザーの指定したクエリやファイルなら、それをそのまま対象にし、利用箇所の追跡は省く。

- `.sql` ファイル、マイグレーション、スキーマや DDL の変更
- 文字列として埋め込まれた生 SQL
- ORM やクエリビルダの呼び出し。`where`、`joins`、`includes`、`order`、`group` など、発行される SQL が変わる箇所
- 関連の参照（`user.posts` のような遅延ロード）と、ループや繰り返し処理の中でクエリを発行しているコード
- 差分で変えたクエリ、スコープ、関連定義の利用箇所。view、serializer、ジョブなど差分の外にあるループまで追う。差分で事前読み込み（`includes` など）を外した場合、利用箇所がループ内でその関連を参照していれば N+1 になるので、参照箇所を確認して判定する

ORM の呼び出しは、`to_sql` やクエリログで実際の SQL を確かめる。確かめられない場合は、推定した SQL を書き、推定であると記録する。

差分に SQL に当たる変更がなければ、その根拠を報告して終了する。

次に、判断の前提になる情報を集める。

- DBMS の種類とバージョン。構文、インデックス種別、`EXPLAIN` の出力形式はこれに依存する
- PostgreSQL 以外の場合の読み替え。参照資料は PostgreSQL の構文で書いてある。同等機能がない手法（部分インデックス、`INCLUDE`、`CONCURRENTLY`、`pg_stat_*` など）は提案せず、その DBMS の代替手段か「要確認」を書く
- 対象テーブルの定義と既存インデックス。スキーマファイル、過去のマイグレーション、DDL から読む
- テーブルの想定規模とクエリの実行頻度。要件、設計、既存のコメント、ユーザーの説明から読む。接続先があれば統計ビュー（`pg_class.reltuples`、`pg_stat_statements.calls` など）からも読み、どの環境の値かを根拠に書く。分からなければ「規模未確認」と記録する
- 接続先が指定されていれば、`EXPLAIN` の出力。制約を満たす `SELECT` は `EXPLAIN (ANALYZE, BUFFERS)` で実測も取る。差分がスキーマやインデックスの変更を含み、接続先に適用されていない場合は、変更前の計画だけを取り、変更後は「要確認」とする
- ユーザーが EXPLAIN 出力を貼った場合は、接続先から取った計画と同じに扱う。取得した環境と行数が出力やユーザーの説明から分からなければ「要確認: 計画の取得環境」と記録し、`ANALYZE` なしの出力なら見積もりだけで判断する
- 計画を取った環境の行数が想定規模と違う場合（ローカルやテスト用 DB など）、プランナーは小さいテーブルに Seq Scan や Nested Loop を選ぶので、計画は参考値として扱う。根拠には「接続先の行数 n、想定規模と異なる」と書き、想定規模での判断は書き方と既存インデックスから行う

既存インデックスが分からないまま「インデックスがない」と断定しない。

## 2. 観点ごとに点検する

各クエリを次の観点で確認する。判定基準と修正例は、参照資料の対応する節を読む。

| 観点 | 見る箇所 | 典型的な問題 | 参照する節 |
| --- | --- | --- | --- |
| 実行計画 | `EXPLAIN` 出力、ヒント句、プランナー設定 | 大きいテーブルの Seq Scan、行数見積もりと実測の乖離、外側の行数が多く内側をインデックスで引けない Nested Loop、ヒント句やセッション設定で計画を固定している | 1 |
| インデックス利用 | `WHERE`、`JOIN`、`ORDER BY` の列と、手順 1 で集めた既存インデックス | 条件・結合・並び替えの列を先頭に持つインデックスがない、列への関数適用、暗黙の型変換、前方ワイルドカードの `LIKE`、`OR` 条件、複合インデックスの列順不一致 | 2、3 |
| 取得量 | `SELECT` 句、`LIMIT`、`COUNT` | 大きい列（text、jsonb、blob）を含む多数行の全列取得、大きい `OFFSET`、全件 `COUNT(*)` | 4 |
| JOIN とサブクエリ | `FROM`、`JOIN`、サブクエリ、CTE | 行ごとに実行される相関サブクエリ、プランナーが押し下げられない絞り込み条件 | 5 |
| N+1 | ループ内のクエリ、関連の参照、ORM の遅延ロード | 親の件数ぶんクエリが発行される | 6 |
| 集約 | `GROUP BY`、`HAVING` | 絞り込み列とグループ化列を含むインデックスがない、繰り返し計算される重い集約 | 7 |
| 書き込み | `INSERT`、`UPDATE`、`DELETE` | ループ内の 1 件ずつの書き込み、一括化できる更新 | 8 |
| スキーマとマイグレーション | DDL、インデックス定義、メンテナンスコマンド | 書き込みを遅くするだけの重複・未使用インデックス、大きいテーブルをロックするインデックス作成、全行の書き換えや検証を伴う DDL、テーブルをロックする `VACUUM FULL` や `REINDEX`、用途に合わないデータ型、範囲で絞る巨大テーブル | 9 |

観点ごとの判断は、テーブル規模と実行頻度に照らして行う。
数十行のマスタテーブルへの Seq Scan や、管理画面で月に数回動くクエリの `OFFSET` を、同じ重みで指摘しない。
ORM が既定で発行する全列取得（`SELECT users.*`）は、大きい列を含む多数行の取得か、カバリングインデックスで Index Only Scan を狙える場合にだけ指摘する。

修正案のうち、カーソル方式のページネーション、概算件数、マテリアライズドビュー、ORM の一括操作への置き換えのように結果や API の仕様、コールバックやトランザクションの単位が変わるものは、指摘として出してよいが「仕様変更が必要」と明記する。

## 3. 指摘を整理する

指摘は次の表にまとめる。

| 位置 | 観点 | 問題 | 根拠 | 修正案 | 重大度 |
| --- | --- | --- | --- | --- | --- |

- 位置: ファイルと行、または ORM 呼び出しのメソッド名
- 根拠: 実行計画、既存インデックス、テーブル規模、該当する参照資料の節。推測で断定せず、確認できなかった前提は「要確認」と書く
- 修正案: 対象の DBMS の構文で書く。DBMS が不明なら PostgreSQL の構文で書き「要確認: DBMS」を付ける。代替手段がない場合は「なし」と理由を書く。インデックス追加を提案する場合は、書き込みが遅くなるコストと、同じインデックスで賄える既存クエリを併記し、ロックを避ける作成方法は参照資料 9 節に従う
- 重大度: 次の基準で決める

| 重大度 | 基準 |
| --- | --- |
| 高 | 想定規模で明らかに遅くなる、またはロックや大量 I/O で他の処理に影響する。テーブルをロックするインデックス作成や全行の書き換えは、規模未確認でもここに置き、「規模未確認」を併記する |
| 中 | 今は問題にならないが、テーブルの成長や実行頻度の増加で問題になる。それ以外の規模未確認もここに置き、問題になる規模の条件を書く |
| 低 | 規模も成長も小さく実害はないが、書き方として直したほうがよい |

今回の差分で変更していない既存の SQL に問題を見つけた場合は、差分の指摘と分けて記録する。手順 1 で読んだ範囲で目に入ったものだけを記録し、網羅的には探さない。

## 4. 修正する（求められた場合）

修正は、結果集合、並び順、NULL の扱い、トランザクション境界を変えない範囲で行う。
「仕様変更が必要」と記した修正案は、ユーザーが仕様変更を認めた場合にだけ行う。
変更前後で同じ結果になることを、既存テストか比較クエリで確認する。

- インデックスは、同じ列を含む既存インデックスで賄えないかを先に確認する
- 大きいテーブルへのインデックス作成は、DBMS がロックを避ける手段（PostgreSQL の `CREATE INDEX CONCURRENTLY` など）を持つなら、それを使う。マイグレーションのフレームワークがトランザクションで包む場合は、その解除（Rails の `disable_ddl_transaction!` など）も修正に含める
- インデックスの削除は、次をすべて満たす場合に限る
  - 主キー、一意制約、排他制約、外部キーを支えるインデックスではない
  - プライマリとすべてのレプリカの統計ビューで未使用である
  - 統計の観測期間（`stats_reset` 以降）に、月次バッチなど低頻度の処理が含まれている
- 接続先があれば、修正前後の `EXPLAIN` で改善を確認する。接続先がない場合や、許可なしにインデックスを作れず修正後の計画を取れない場合は「要確認: 修正後の計画」と報告に書く

修正を通すために、既存テストの期待値を書き換えない。

## 5. 結果を報告する

次を簡潔に報告する。

- レビューした SQL と、前提にした DBMS、テーブル規模、既存インデックス
- 指摘表。指摘がなければ、確認した観点と根拠
- 修正した場合は、変更内容と検証結果
- 差分外の既存 SQL に見つけた問題（指摘表とは分けて）
- 確認できなかった範囲と理由。実行計画が取れない、規模が分からない、既存インデックスが読めないなど

確認できなかった範囲を残したまま、無条件の「問題なし」とは書かない。指摘がない場合は「指摘なし（要確認: 実行計画 / 規模未確認: orders）」のように範囲を併記する。

## 完了条件

- 差分または指定されたクエリから SQL を抽出し、差分の場合は変更したクエリやスコープの利用箇所も抽出している
- DBMS、テーブル定義、既存インデックス、想定規模を確認している、または「要確認」「規模未確認」と記録している
- 各クエリを手順 2 の観点で点検し、指摘が位置、根拠、修正案、重大度を備えている
- 推測で断定した指摘がなく、確認できなかった前提は「要確認」または「規模未確認」になっている
- 修正した場合、結果集合が変わらないことと性能の改善を確認しているか、確認できなかったことを報告している
- 確認できなかった範囲と理由が報告されている
