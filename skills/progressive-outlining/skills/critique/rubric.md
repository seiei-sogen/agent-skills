# 批評ルーブリック

自分の設計原則に合わせて編集する。項目は増減してよいが、各項目は「判定できる問い」の形にしておく。
各項目を OK / 要検討 / NG で判定し、根拠と修正案を添える。

## A. 要件

- A1. 各要件は EARS 形式で書かれ、検証可能か（テスト名に翻訳できるか）
- A2. 非スコープが明示され、要件と矛盾していないか
- A3. 「制約」に書かれたものは本当に制約か（設計判断の先取りになっていないか）

## B. 構造

- B1. ディレクトリ構成が責務を表しているか。1ファイルに複数の責務、または責務が薄すぎるファイルがないか
- B2. 依存の向きが一方向か。外側（I/O・フレームワーク）が内側（ドメイン）に依存し、逆はないか
- B3. モジュール境界を跨ぐ型が最小か。フレームワーク固有の型が内側に漏れていないか

## C. 表現

- C1. 関数ベースで素直に書けるか。クラスや継承が必要に見える箇所は、本当に必要か
- C2. 状態の置き場所が明確か。頻繁に変わる状態を広域の仕組み（React Context 等）に置いていないか
- C3. エラーが型に現れているか（例外任せになっていないか）

## D. 検証可能性

- D1. 自作コードをモックせずにテストできる境界になっているか
- D2. テスト名が仕様を言い切っているか（「〜のテスト」ではなく「〜のとき〜する」）
- D3. 型検査が通れば防げる誤りを、テストで防ごうとしていないか

## E. 手戻りリスク

- E1. 実装に入ってから初めて判明しそうな未知（外部 API の挙動、既存コードの前提）が列挙されているか
- E2. 未決事項が「決めなくても進める」ものと「今決めないと後で壊れる」ものに分けられているか
