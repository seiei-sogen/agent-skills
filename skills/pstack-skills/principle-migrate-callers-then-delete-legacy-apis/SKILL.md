# Migrate Callers Then Delete Legacy APIs

新しい API が正しい設計だと決めたら、互換レイヤーを残すのではなく、同じリファクタの波の中で呼び出し側を移行し、古い API を取り除く。

**規則:**
- 内部の呼び出し側がまだ存在するというだけの理由で、レガシー API の経路を残さない
- 呼び出し側を棚卸しし、移行し、古い API をただちに削除する
- 一時的なアダプタは既定のアーキテクチャではなく、例外的で期限付きのものとして扱う
- テストは新しい契約を検証するように更新し、リファクタ前の実装詳細だけを守るテストは削除する

**適用するとき:**
- 後方互換性に依存する外部ユーザーがいない
- プロジェクトが協調した破壊的変更を吸収できる
- 新しい API が単純化またはリファクタの取り組みの一部である

古い API と新しい API の両方を残すと、二重経路の複雑さが生まれ、掃除が遅れ、コードベースが追記専用のように感じられる。
