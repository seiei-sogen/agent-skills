# 根拠説明テンプレート

型スケッチと併せて出荷する文章。1 ページ。見出しは文頭のみ大文字（sentence case）、ボイラープレートなし。斜体の注記を実際の内容に置き換える。

## 問題

*1 段落。何をしようとしているのか、そして既存システムや制約のどこが形を自明でなくしているのか。[フェーズ A](../SKILL.md#phase-a-ground-the-problem) が設計の守るべき制約（相互運用すべき既存の型、壊せない呼び出し側、境界を越えてきた不変条件）を明らかにしたなら、読者が自分と同じ制約を見られるようにここで挙げる。*

## 使い方（呼び出し側の視点）

*型スケッチより先に、これを最初に書く。利用者が読む README やクイックスタートと、利用者自身のコードにおける現実的な呼び出し箇所を 2、3 個示す。何をインポートし、何を呼び、何が返ってくるか。[形](#shape) の型スケッチはここから導出する。両者は一致しなければならない。食い違ったときは、スケッチを使い方に合わせて調整する。逆ではない。呼び出し側の体験が仕様である。型はそれに従う。*

## 形

*推奨アーキテクチャ。データ構造を先に。次に、データがシグネチャをどう流れるか。要となる決定を挙げる。どの不変条件が型に符号化されているか、バリデーションはどこにあるか、システムが意図的に何をしないかを述べる。インターフェースの深さを明示的に判断する。公開サーフェスがどの複雑さを隠し、何が呼び出し側に露出したままで、なぜインターフェースが必要以上に大きくないのかを述べる。各決定の背後にある原則を引用する（例: `per boundary-discipline`）。原則の内容を再述しない。*

## 統合の決定

*[arena](../../arena/SKILL.md) が埋める。どの候補がベースになりその理由は何か、他の各候補から何を取り入れたか、何を却下しその理由は何かを記録する。*

## 受け入れたトレードオフ

*選んだ形が行うトレードオフごとに 1 項目。形式は「Y と引き換えに X を受け入れる」。将来の読者が見落としと誤解しかねないものをすべて挙げる。早すぎる最適化や早すぎる単純化に見えるものを含む。*

## 検討した代替案

*必須。具体的な代替の形を少なくとも 1 つ挙げ、なぜ負けたのかを 1 行で添える。各代替案は実装の単純さだけでなくインターフェースの深さで判断する。呼び出し側に露出する複雑さと隠す複雑さを挙げる。設計空間に本当の対抗馬があったなら、2 つか 3 つの代替案がここに入る。制約が答えを強いた場合は 1 つでよく、結論は「これが唯一成立する形だった。なぜなら...」と表現する。同じ形のバリエーションを並べない。このセクションは、選んだ形が検討して却下した設計上の代替案を扱う。他のランナーの候補ではない。*

## 未解決の疑問とリスク

*スケッチ中に気づいた、人間の判断が必要な事柄と、実装開始前に指摘しておく価値のあるリスク。断定ではなく質問として表現し、人間の答えがコメントではなく解決になるようにする。*
