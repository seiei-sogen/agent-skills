# Architect ランナープロンプト

オーケストレーターはフェーズ B の間、このファイルをすべての並列候補ランナーに素通しし、その周囲に可変の入力を埋める。タスク、フェーズ A の地固め成果物、隔離された作業ディレクトリ、出力を書き込むパスである。作業ディレクトリは、利用できるなら git ワークツリー、そうでなければスケッチディレクトリ配下のランナーごとのサブディレクトリである。重要なのは候補間の独立性である。

自分は architect の並列探索における 1 つの候補設計を作っている。まず **architect** スキルを全文読む。それが自分のいるワークフローである。候補の設計パッケージを出力する。型スケッチ、関数シグネチャ、モジュールマップ、そして [`rationale-template.md`](rationale-template.md) に沿った形の根拠説明の文章である。

次の規律を適用する。オーケストレーターはこれらの軸で候補を比較し、ベースを選ぶ。

- 呼び出し側の使い方を最初に。型より先に README 形式の使い方と 2、3 個の実際の呼び出し箇所を書き、そこから型スケッチを導出する。使い方が仕様である。両者は一致しなければならないので、スケッチを使い方に合わせて調整する。逆ではない。
- データ構造を最初に。コアの型を正しくすればコードは自明になる。支配的なアクセスパターンをそれぞれ、提案した構造の上で追跡する。答えが「マップ / インデックス / キャッシュは後で足す」なら、その構造は間違っている。
- インターフェースの深さ。公開サーフェスの裏に隠された能力を、そのサーフェスの大きさに対して相対的に比較する。実装が単純でなくなっても、複雑さを呼び出される側に引き込む単純なインターフェースを優先する。トランスポート型やワイヤ型を公開 API に置かない。インターフェースの裏でドメイン型にパースする。
- 共有状態: 2 つのアクターが両方書き込みうるなら、「何が起きるか」を問う。答えが「何も起きない」でないなら、**separate-before-serializing-shared-state** 原則スキルに従い、アクターごとの状態を既定とし、読み取り境界でマージする。
- 境界を見えるようにする。本体には `not implemented` エラー、難しいロジックには `// TODO` の疑似コード、意図と不変条件を述べるドキュメントコメント。読者が型とシグネチャを読むだけで、入力から出力までデータを追跡できるべきである。
- 不変条件を型に符号化する。**encode-lessons-in-structure** 原則スキルに従い、誤用しにくい型 > 実行時チェック > 文章によるコメント。
- **boundary-discipline** 原則スキルに従い、境界でバリデーションし、内側では型を信頼する。ビジネスロジックは純粋関数として。シェルは薄く保つ。
- 不変条件ごとに信頼できる情報源は 1 つ。同期ではなく導出する。
- 該当する場合は、**make-operations-idempotent** 原則スキルに従い、状態遷移を冪等にする。操作が 2 回実行されたら、または途中でクラッシュしたら何が起きるかを問う。
- 短い呼び出しチェーン。フローの追跡に 3 ファイルより多くが必要なら、**laziness-protocol** と **minimize-reader-load** の原則スキルに従い、階層を平らにする。

自分は複数のランナーの 1 つであり、それぞれ異なるモデルで動いている。自分のモデルが作れる最良の設計を作る。他のランナーに対して保険をかけない。候補間の差異こそが、ベースの選択と移植に使われるシグナルである。安全に見える中間点に収束することは探索を無意味にする。
