# Type System Discipline

型チェッカーは証明支援系である。それを使って、ありえない状態、食い違ったプリミティブ、未処理のバリアントをコンパイル時に排除する。型が無視を許すケースは、コンパイラが止められたはずの実行時エラーになる。ハンドラーを増殖させるより、エラーや特殊ケースを定義によって存在しなくすることを優先する。表現不可能な状態、全域関数、インターフェースの再設計（以下のパターン）がその道具である。

型付きの言語ならどれにも当てはまる。`typescript-best-practices` のようなスキルが、具体的な構文にこれを根付かせる。

**パターン:**

- **不正な状態を表現不可能にする。** バリアントを直和型としてモデル化する。TypeScript の判別可能ユニオン、Rust/Swift/Kotlin のペイロード付き enum、Scala の sealed class、Haskell/OCaml の ADT である。矛盾する組み合わせがコンパイルを通るような、任意フィールドの寄せ集めとして状態をモデル化しない。見落としやすいアンチパターン: `{ completed: boolean; completedAt?: Date }` は `completed: true; completedAt: undefined` を許容するが、これは無意味である。`completedAt !== null` のような単一の源からブール値を導出するか、`{ kind: 'open' } | { kind: 'done'; at: Date }` のようにバリアントを明示的にモデル化する。バグのせいで「待て、この組み合わせは本当に起きうるのか」という問いが出るなら、型は緩すぎる。
- **型は制限ではなく構築である。** 緩い型からチェックで削り出すのではなく、欲しい値から型を組み上げる。リファインメント型が必要に見える不変条件は、たいてい構築 1 つで済む。空でないリストは先頭と残りであり、長さチェック付きのリストではない。有効な時間範囲は開始と長さであり、順序を保ち続けなければならない 2 つのタイムスタンプではない。特権的な表現は存在しない。ペアのリストは、そう解釈すれば偶数長のリストなのだから、不正な値を構築できない形を選び、その上に呼び出し側が必要とするインターフェースを公開する。
- **意味を持つプリミティブにブランドを付ける。** `UserId` と `OrderId` は内部的には文字列だが、交換可能であってはならない。Rust の newtype、Swift の opaque type、Kotlin の value class、Haskell の phantom type、TypeScript のブランド付き交差型である。生成時に一度バリデーションし、下流では型を信頼する。
- **外部データはパースされるまで型なしである。** RPC ペイロード、JSON、IPC メッセージ、CLI 引数、設定ファイル、環境変数、データベースの行。すべての境界に、非構造化の入力を型付きモデルへ変えるパース関数を置く。バリデーションの置き場所は **boundary-discipline** 原則スキルを参照する。
- **型システムに嘘をつかない。** キャスト、安全でない強制変換、コンパイラを迂回するアサーション関数は、潜在的な実行時クラッシュである。コンパイラが事実を証明できないなら、自分で証明する（バリデーションする、絞り込む、モデルを精緻化する）か、そのキャストが危険であることを受け入れる。
- **網羅的なマッチはコンパイラの仕事である。** 直和型に対してマッチするとき、新しいバリアントが処理されずに追加されたら、コンパイラがコンパイルを失敗させなければならない。言語が提供するイディオムを使う。TypeScript の `never` 型の束縛、Rust の注釈なしの `match`、Haskell の `-Wincomplete-patterns`、Kotlin の sealed class のマッチ網羅性である。
- **権威あるスキーマから型を導出する。** protocol buffer、OpenAPI 仕様、GraphQL スキーマ、データベースのマイグレーション、デザインシステムのトークンファイルが形を定義しているなら、並行する型を手で書くのではなく、そこから導出する。**encode-lessons-in-structure** 原則スキルを参照する。
- **型を強化するのは部分性が現れた場所だけにする。** 実行時アサーション、null チェック、「ここには決して到達しないはず」という throw は、型が弱すぎる場所の印である。そのチェックを型へ押し上げる。そこで止める。型システムの仕事は、各使用箇所が処理しなければならないケースを追跡することであり、データをできるかぎり精密に記述することではない。全域関数を優先する。空のリストの `sum` は 0 なので、普通のリストを受け取る。空のリストの `head` には答えがないので、空でないリストを要求する。

**テスト:**

- 「このフィールドの組み合わせがいつ有効かを説明するコメントを書けるか」。書けるなら、型は緩すぎる。直和型に分割する。
- 「関数の引数のうち 2 つが同じプリミティブ型を共有しているのに、意味は異なるか」。ブランドを付ける。
- 「この `any`、この `as`、この `assertNotNull` はどこから来たか」。境界まで辿り、代わりにそこでバリデーションする。
- 「来月新しいバリアントが追加されたら、コンパイラは次のエージェントにケースを追加すべき場所を教えるか」。教えないなら、マッチは網羅的でない。
- 「この型は別のファイルが所有する形を複製しているか」。代わりに導出する。
- 「この型を強化しているのは操作を全域に保つためか、それとも単により精密にするためか」。そうしなくても何もパニックしないなら、普通の型のままにする。
