# Model the Domain

実際のドメインを、条件分岐に散らばらせるのではなく、データ構造に符号化する。

**理由:** 散在するブール値、繰り返される形の前提、複数ファイルにまたがる分岐は偶発的な複雑さである。ドメインに一致する構造は、不正な状態を表現不可能にし、分岐を削除する。書く時点でそれを選ぶのは安い。後から取り戻そうとするとリファクタリングに見え、先送りされる。

**次のような構造を選ぶ:**

- 散在するブール値、フェーズ、ライフサイクルのチェックの代わりに、ステートマシン。
- 緩いパラメータや繰り返される形の前提の代わりに、型付きのオブジェクトやモデル。
- 複数ファイルにまたがる分岐の代わりに、マップ、レジストリ、ルックアップテーブル、または判別可能ユニオン。
- その場しのぎの状態変更の代わりに、reducer またはコマンド／イベントモデル。
- load、validate、transform、save のような一連の手順ではなく、1 つのドメイン知識のまとまりを中心に構成されたモジュール。実行順序は所有権ではない。
- 繰り返される振る舞い、所有権、または不変条件を集める小さなモジュール境界。
- データアクセスのパターンが求める場合には、キュー、キャッシュ、インデックス、グラフ／ツリー、または正規化されたコレクション。
- その他、当てはまる構造なら何でも。どれも当てはまらないときは、コードが決して許してはならないことと、データがどう読まれるかを見極め、まさにそれを符号化する構造を探す。

抽象を無理に押し込まない。現在の形がすでに明確で、局所的で、育つ見込みが低いなら、退屈なコードを優先する。分岐、重複したルール、不正な状態、ライフサイクルのリスクを取り除かずに間接参照だけを増やす抽象は疑う。

この原則を飛ばした兆候は、新機能が既存の if/else の連鎖を分岐 1 つぶん伸ばすこと、または 1 つ目と同期を保たなければならない 2 つ目のブール値が生まれることである。時間軸による分解も兆候の 1 つだ。フェーズ名を付けたモジュールは、同じドメインルールをステップごとに繰り返す。
