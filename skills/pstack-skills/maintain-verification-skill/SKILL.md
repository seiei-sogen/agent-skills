# 検証スキルを保守する

機能マップはアプリが変わった瞬間に腐る。このスキルは、`/create-verification-skill` が生成したスキル（または機能マップを持つ任意のプロジェクトローカルな検証スキル）のための保守ループである。厳密さの単位は機能であり、すべての文ではない。すべての機能ファイルをソースからカバーし、すべての機能をライブで実行するが、すべての箇条書きを端末で試すことはしない。

**プラットフォームに関する注記。** Codex や他の非 Claude ランタイムでは、以下の機能ごとに並列なソース読み取り役は `spawn_agent` のファンアウトに対応し、プロジェクトローカルなスキルは `.claude/skills/` ではなくランタイムのスキル置き場所にある。[`codex-tools.md`](../poteto-mode/references/codex-tools.md) を参照する。

## 結果

1 つを選び、どれかを明言する。

- **clean**。すべての機能がソースとライブのカバレッジを得た。出荷する価値のあるものはない。ブランチも PR も作らない。
- **changed**。証明済みのドキュメント、ハーネス、マップの修正を 1 つの PR で出荷する。
- **blocked**。カバレッジを完了できなかった、または証明済みの修正を安全に出荷できなかった。何が妨げたかを正確に述べる。

## 編集範囲

検証スキル自身のディレクトリ（その SKILL.md、features/、それが所有するハーネススクリプト）だけを編集する。実行中に製品コードを決して編集しない。マップが記述している動作をアプリがもうしないなら、それはドキュメントのドリフト（マップを直す）か、製品のリグレッション（報告する。ドキュメントで覆い隠さない）のどちらかである。

## パス

0. **対象を特定する。** 保守する検証スキルを見つける。本文に launch/drive のセクションと機能マップを持つプロジェクトローカルなスキル（通常は `.claude/skills/verify-*/`）である。候補が複数ある → どれかを尋ねる。1 つもない → 停止し、対象をでっち上げる代わりに `/create-verification-skill` を示す。

1. **インデックスの衛生。** 機能マップの README を読み、その兄弟ファイルを glob する。欠落、余分、重複、リンク切れのエントリを直す。軽量に済ませる。生成されたインベントリは作らない。

2. **ソースの波。** 機能ファイルごとに読み取り専用のサブエージェントを 1 つ、同時に起動する。各サブエージェントは「このユーザー向け機能はどう動くか」をソースから説明し、ありそうなドキュメントのドリフトを引用付きで指摘し、簡潔なライブ検証レシピを 1 つ返す。子はアプリを決して操作せず、ファイルを決して編集しない。返す形は、機能の要約 / ソースの入口 / ありそうなドリフトまたはなし / レシピ 1 つ。

3. **照合する。** すべての機能ファイルに返された要約がある。重なるレシピを、現実的な範囲でできるだけ少ないアプリ状態にマージする。引用されたドリフトを抜き取り検査する。クリーンだという主張を再証明はしない。最近の変更を一通り調べ、マップにないユーザー向けサーフェスを探す。欠けていると呼ぶ前に、具体的なソースパスを必須とする。

4. **ライブパス。** ソースがクリーンに見えても必須。すべての操作はコーディネーターが担い、検証スキル自身の起動モデルに従う。サーバーと UI では長寿命のインスタンス 1 つを直列に操作し、短命な CLI では操作ごとに新しい分離されたセッションを使う（決めるのはそのスキルの Launch セクションであり、このスキルではない）。すべての機能を少なくとも 1 回実行し、どんな失敗が起きても、パスの間ずっと 3 つの不変条件を保つ。(1) 最後に想定外の挙動をしてから健全性を確認していないインスタンスを決して操作しない。最初の操作の前に doctor を実行し、セッションが単位である場合は新しいセッションごとに doctor を実行し、失敗した操作の後に再び doctor を実行する。doctor が失敗を見られない場合（健全なプロセス上で UI 状態が固まっている）は、うまくいくことを願うのではなく、既知の状態にリセットするか再起動する。(2) それまでに取得した証拠はすべてのクリーンアップを生き残る。これは名指しした場所で確認するもので、仮定してはならない。(3) 操作が起動したものは、その操作の有用性を超えて生き残らない。失敗した反復の残留物は、セッションが固まっていても、終了していても、共有されていても片付ける（共有インスタンスでは、インスタンスではなく残留物を片付ける）。スキルのドリフトが原因の doctor の失敗はドリフトである。パスを `blocked` と呼ぶ前に、編集範囲の中で直し、1 回だけ再試行する（修正が無効にしたものだけを再起動し、それ以上はしない）。到達できない機能は、具体的な前提（認証、エンタイトルメント、OS、外部状態）と試した経路がある場合に限り `verified-unreachable` とする。マップがその前提を省いているなら、それはドリフトである。トリアージによるハーネスの修正はすべて、出荷前にライブで再操作する。最終的なティアダウンは、それらの再証明を含む実行の最後の操作の後に行い、実行を超えて生き残るものがないようにする（スキルの定めにより、証拠は残す）。

5. **トリアージ。** ユーザー視点の説明が間違っているか欠けている → ドキュメントのドリフト。直す。動作しているのにハーネスが操作できない → ハーネスの不足。直す。ハーネスの修正は生成時と同じヘルパーの規則に従う（スクリプトは実行可能で、呼び出し方をスキル本文に記載する）。アプリの動作が実際に壊れている → 製品の不足。ユーザーのために記録し、この PR には入れない。

6. **出荷するか止める。** changed の場合、証明済みの修正を 1 つの PR にし、変更したすべてのファイルを先に読み直す。clean または blocked の場合、PR は作らず、結果とカバレッジを正直に報告する。

簡潔な実行メモ（カバーした機能、到達できない前提、確認したドリフト、結果）をスクラッチの場所に残す。コミットはしない。
