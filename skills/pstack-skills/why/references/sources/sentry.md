# Sentry エラー履歴

## このソースに含まれるもの

Sentry は、うまくいかなかったことのアーカイブである。防御的なコード、修正のコード、エラー処理のコードについては、直接の動機がここにあることが多い。誰かにチェック、キャッチ、リトライ、フォールバックを追加させるに至った、具体的な例外、スタックトレース、発生頻度である。

- **issue。** 件数、初回・最終発生のタイムスタンプ、影響を受けたリリース、コメントを持つ、グループ化されたエラー
- **イベント。** issue 内の個々のエラー発生（スタックトレース、タグ、ユーザーコンテキスト）
- **リリース。** 関連する issue を持つデプロイ記録（「どのバージョンがこれを修正したか」に有用）
- **リプレイ。** ユーザーに見えるエラーのセッション録画（有効な場合）
- **プロファイル。** パフォーマンスプロファイリングのデータ（「なぜ」にはあまり有用でなく、「どれだけ遅いか」に向く）
- **issue のコメントと担当割り当て。** 根本原因についてのエンジニアのメモが含まれていることがある

Sentry が提供する最も価値のあるものは**時間的な相関**である。「issue X は 2024-01-02 に作成され、1 日 500 イベントでピークに達し、2024-01-15 のリリース v2.14.0 以降は現れなくなった。そのリリースが防御的なチェックを出荷したものだ」というものである。

## 検索方法

Sentry MCP を使う。

1. **位置を把握する。** プロジェクトのスラッグと組織が分からない場合:

   ```
   find_organizations
   find_projects
   ```

2. **対象に関連する issue を検索する。**

   ```
   search_issues (natural language, e.g., "errors in PaymentService timeout", "unhandled exceptions in uploadFile")
   ```

   良いクエリの構成要素: 対象が処理する例外クラス名、対象の関数名やクラス名、対象がチェックしているエラーメッセージ文字列、対象のファイルパス。

3. **リリースと時間枠で絞り込む。**

   ```
   search_issue_events (filter by release, time, environment, trace ID, tags)
   get_issue_tag_values (for an issue, see distribution across versions, users, environments)
   ```

   疑わしい issue について、次を確認する:
   - **初回発生。** エラーはいつ現れ始めたか。
   - **最終発生。** いつ止まったか。対象の出荷日と一致するか。
   - **影響を受けたリリース。** どのバージョンで発生したか。どれが修正だったか。
   - **頻度の推移。** 急増した後、解消されたか。

4. **文脈のためにイベント全体を取得する。**

   ```
   get_sentry_resource (pass a Sentry URL or type+ID)
   ```

   スタックトレースは対象コードを通過しているか。タグとブレッドクラムは、対象が防御している条件と一致するか。

5. **対象の前後に出荷されたリリースを確認する。**

   ```
   find_releases (around the commit date of the target)
   ```

   リリースバージョンを PR のマージ日と照合する。

6. **Seer は控えめに使う。**

   ```
   analyze_issue_with_seer
   ```

   Seer は AI による根本原因分析を生成する。仮説の生成役としては有用だが、権威ある情報ではなく推論として扱う。実際のイベントとスタックトレースが一次証拠である。Seer の説明は二次的なものである。

## ここで良い証拠とはどのようなものか

- **初回発生**が対象の PR の少し前で、**最終発生**がその少し後である issue。対象がこのエラーに対処したことを示唆する
- 対象の関数を通過する、または対象の関数で終わるスタックトレース。防御対象となっている正確な失敗モードを示す
- 修正を説明する、PR 作成者による issue へのコメント
- Sentry の issue URL や ID を参照している、対象の PR 説明やコミットメッセージ
- イベント数が多く、対象を含むリリースの後に止まった issue

## よくある落とし穴

- **グループ化のずれ。** Sentry はエラーをフィンガープリントでグループ化する。リファクタリングやリネームによって、「同じ」エラーが新しい issue ID で追跡されることがある。issue が突然終わっている場合、エラーは単に再グループ化されただけかもしれない。直後に新しい issue がないか確認する。
- **リリースとの相関はノイズが多い。** 1 つのリリースには多数のコミットが含まれる。issue が v2.14.0 で止まったことは、対象がそれを修正したことを証明しない。同じリリース内の別の変更が修正したのかもしれない。対象の正確なコミットと照合する。
- **気付かれない修正。** 防御的なコードのためではなく、上流が変わったためにエラーが止まることがある。相関は修正を示唆する。何が修正したのかは証明しない。
- **resolved は fixed と同じではない。** issue はコード変更なしに手動で「resolved」に設定できる。`resolved` はコードが修正した証拠ではなく、人間が付けた印として扱う。
- **Seer のハルシネーション。** Seer は、自信ありげに聞こえるが正しくない説明を生成することがある。主張をするときは、実際のイベント、スタックトレース、タイムスタンプに立ち戻る。
- **サンプリング。** 一部のプロジェクトはイベントを積極的にサンプリングしている。イベント数が少ないのは、稀なエラーだからではなく、サンプリング率が高いだけかもしれない。疑わしい場合は、空白として記録する。

## 返すもの

関連する各 issue について:
- issue ID とタイトル
- プロジェクトと組織
- 初回発生・最終発生のタイムスタンプ
- イベント数（分かればサンプリング率も）
- 影響を受けたリリース
- 対象との関連を示す代表的なスタックトレースの抜粋（要約ではなく、そのままの抜粋）
- 対象の出荷日との初回・最終発生の相関
- issue へのリンク
- 作成者のコメントや解決メモがあればそれら
