# インシデントとポストモーテムのコンテキスト

独立したソースではなく、**横断的な観点**である。インシデントは防御的コードの動機になることが多い（「X の障害の後にこのチェックを追加した」）。そのため、対象が防御的に見える場合（null チェック、リトライロジック、タイムアウト処理、レートリミット、フィーチャーフラグ）は、利用できるすべてのソースを横断して、インシデントの履歴を重点的に探す。

- **Notion**: 対象のファイル、機能、エラー文字列に言及しているポストモーテムを検索する
- **Linear**: `incident`、`sev-*`、`postmortem-action-item`、`reliability` のラベルが付いたチケットを探す
- **Slack**: 対象コードが追加された日付の前後で、`#sev-*` と `#incident-*` チャンネルを検索する
- **Git**: 「fix for incident」「add defensive check」のようなメッセージのコミット、および「revert」の後に「re-apply with...」が続くコミットは強いシグナルである
- **Datadog**: タイムラインを持つ正式なインシデント記録、ポストモーテムのアクションアイテムとして作成されたダッシュボードやモニターを `search_datadog_incidents` で探す
- **Sentry**: 初回観測/最終観測の窓が対象の PR の出荷日と一致する issue、対象を通るスタックトレース
- **Databricks**: エラー条件を分類するプロダクト分析イベント（クライアントから報告された失敗、ユーザーに見えるリトライのイベントなど）は、インシデントの窓で急増することが多い。対象の PR の出荷後にそのイベント数が減少していれば、Datadog や Sentry のシグナルにノイズが多い場合でも、対象コードがユーザーに見える症状を解消したことの状況的な裏付けになる。

インシデントへのリンクを見つけたら、ポストモーテムの全文を取得する。ポストモーテムには通常、コード変更に直接結び付く「Action Items」セクションがある。複数のソースが裏付け合うとき（Datadog のインシデント ID が Linear のチケットに現れ、それが Notion のポストモーテムに現れ、それが対象の PR にリンクする Slack のスレッドに現れ、さらに Databricks のエラーイベント数が修正後に減少している）、証拠は特に強い。

コードの防御的な性質からインシデント起因の由来がもっともらしいときは、時間を割く価値がある。防御的に見えないコードについてはスキップする。
