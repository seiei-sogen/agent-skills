# Linear チケット

## このソースに含まれるもの

- 機能、バグ、その動機を記述した issue
- issue に添付されたプロジェクト文書（多くは PRD や仕様書）
- 親 issue とサブ issue の関係（より広いイニシアチブ → 個別のチケット）
- issue へのコメント（明確化、スコープ変更、「なぜこれをやるのか」という根拠説明）
- 動機の種類を示すラベル（例: `compliance`、`customer-request`、`perf`）
- スコープ変更を説明するステータス更新
- 添付ファイルとリンクされた GitHub PR

Linear は、製品やビジネスの文脈がしばしば置かれている場所である。「顧客 X が求めたからこれをやる」や「これは Q3 のコンプライアンスイニシアチブのためだ」という層がここにある。

## 検索方法

Linear MCP を使う。

1. **リンクされたチケットから始める。** シードとなるコミットや PR がチケット ID（例: `ENG-1234`、`[BUG-567]`）を参照しているなら、まずそれらを `get_issue` で取得する。コメントを含めて issue 全体を読む。
2. **キーワードで関連 issue を列挙する。** `list_issues` のテキスト検索で、機能名、主要なシンボル、ビジネス用語を検索する。複数の言い回しを試す。
3. **issue ツリーをたどる。** サブ issue にたどり着いたら、その親を取得する。サブ issue は戦術的なものである。親が「なぜ」を持っていることが多い。
4. **プロジェクト文書を読む。** issue がプロジェクトに属しているなら、`get_project` を使って添付文書を確認する。プロジェクトレベルの文書は、仕様と根拠説明が最もよく記録されている場所である。
5. **ラベルとマイルストーンを確認する。** ラベルは動機のカテゴリ（customer-request、incident-followup、compliance）を示唆する。マイルストーンは作業を締め切りに結び付けており、締め切りが動機を明かすことが多い。

## ここで良い証拠とはどのようなものか

- ビジネス上の問題を述べた issue の説明: 「顧客 Acme は SOC2 監査のために X を必要としている」
- 決定を記録したコメント: 「アプローチ A は請求サービスに手を入れる必要があるため、アプローチ B にすることにした」
- イニシアチブのようなタイトルの親 issue: 「Q3 Enterprise Readiness」や「Reduce Payment Failures」
- 添付された PRD や仕様書
- `customer:acme`、`incident-followup`、`compliance`、`perf-regression` のようなラベル

## よくある落とし穴

- **スコープのずれ。** PR が参照するチケットは、クローズされた後に別のスコープで再オープンされている場合がある。履歴全体を読む。
- **機械的なテンプレート。** 「Why」セクションを必須にしながら、定型文で埋めているチームがある。汎用的な文言（「ユーザー体験を改善する」）は、おそらく本当の答えではない。
- **古いチケット。** 古いチケットは、その後変更された計画のある時点の版を反映していることが多い。日付を確認し、コードの出荷日と照合する。
- **重複クローズの連鎖。** duplicate-of の関係をたどって、正規のチケットまで戻る。
- **非公開ワークスペースの内容。** issue にアクセスできない場合は、推測せずに空白として記録する。

## 返すもの

関連する各チケットについて:
- チケット ID とタイトル
- 説明またはコメントから引用した問題や動機（言い換えない。シンセサイザー（統合役）が引用するために正確な文言を必要とする）
- ラベル、親 issue、プロジェクト
- 作成者、作成日、クローズ日
- 利用可能ならチケットへのリンク
