# Databricks の分析データとシステムテーブル

## このソースに含まれるもの

Databricks はプロダクト分析、データパイプライン、ウェアハウスのテレメトリを担う層である。Datadog を補完する。Datadog が*インフラ/ランタイム*の視点であるのに対し、Databricks は*プロダクト/データ*の視点である（ユーザーが何をしたか、どの実験が走ったか、機能の利用がどう変化したか、しきい値の定数がどこから来たか）。

- **プロダクト分析イベント。** `your_warehouse.events.analytics_track_event`（生データ）と、`<your_analytics_db>.<schema>.<table>` にある、型付きで重複排除された、イベントごとの dbt モデル。ユーザーの行動: 機能の呼び出し、クリック、承認/拒否、送信、クライアントから報告されたエラー。
- **利用量と課金のイベント。** `your_warehouse.events.usage_event` / `<your_analytics_db>.<schema>.stg_usage_events`、`your_warehouse.events.raw_model_event` / `<your_analytics_db>.<schema>.stg_raw_model_events`。コストや量に基づく決定のために使う。
- **実験 / フィーチャーフラグのデータ。** 露出（exposure）と結果のテーブル。**スキーマは会社ごとに異なる。** 名前を仮定する前に `SHOW TABLES` で探る。
- **システムテーブル。** `system.query.history`、`system.compute.warehouses`、`system.billing.*`、`system.access.audit`。「このクエリは高コストだったか」「誰かがこれを実行した頻度はどれくらいか」「ウェアハウスの負荷はいつ急増したか」に答える。
- **dbt のリネージ。** `<your_analytics_db>.<schema>` のモデルは、どのパイプラインがあるテーブルやフィールドに依存しているかを明らかにする。上流の変更が、消費側コードの変更の動機になることは多い。
- **Databricks ノートブック。** エンジニアがコード変更の前に書いた探索的な分析。**SQL MCP からはクエリできない。** 根拠説明がノートブックにあると疑われる場合は、ギャップとして明示する。

## 検索の仕方

Databricks SQL MCP を使う。主要なツールは `execute_sql_read_only`。`statement_id` が返ってきたら、再実行するのではなく `poll_sql_result` でポーリングする。

**クエリの前に全体像を把握する。** スキーマは会社ごとに異なる。テーブル名を信用する前に探る。

```sql
SHOW TABLES IN <your_analytics_db>.<schema> LIKE '*<keyword>*';
DESCRIBE TABLE <your_analytics_db>.<schema>.stg_<event>;
```

**すべてのクエリに時間の制約を付ける。** これらのテーブルは巨大で、制約のないスキャンはタイムアウトする。`_timestamp`（イベント）または `start_time`（`system.query.history`）でフィルタし、出荷日を挟む窓を使う。通常は前後 30 日程度で、それより広げるのは強い理由があるときだけにする。

**生テーブルより型付き dbt モデルを優先する。** `<your_analytics_db>.<schema>.<table>` は重複排除され、型付けされ、リキッドクラスタリングされている。`your_warehouse.events.analytics_track_event` には重複があり、`properties_json` は型付けされていない。モデル名のパターンは `stg_<source>_<event_name_with_underscores>` で、`<source>` は `app`、`backend`、`website`、`cli` のいずれか。パターンだけで特定できないときは、`SHOW TABLES` で正確なモデル名を確認する。完全な対応表は `databricks-use-dbt-models` スキルを参照。生テーブルに降りるのは、dbt モデルがまだ存在しない場合か、dbt の更新遅延の中にあるイベントが必要な場合だけにする。

**型付き dbt モデルの列の規約**（これを知っていれば `DESCRIBE` の往復を省ける）:

- `_timestamp`、`_id`、`_auth_id`、`_request_id`、`event_name`。すべてのモデルに標準で存在する
- `properties_<name>`。型付きでアンダースコア区切りのイベントプロパティ（`properties_entrypoint`、`properties_size_bytes` など）
- `context_team_id`、`context_client_version`、`context_country`、`context_client_os`。事前に抽出されたクライアントのコンテキスト

### 成果につながりやすい調査パターン

対象に合うテーブルと列の組み合わせを選ぶ。

1. **イベント利用の推移。** PR マージの前後 ±30 日の窓で、該当する `stg_*` モデルの日次カウントを取る。マージから 1、2 日以内にゼロから安定した量へ階段状に立ち上がっていれば、その PR が機能を立ち上げたことの強い状況証拠になる。ゼロへ減衰していれば、非推奨化か削除を示唆する。
2. **ガードレール / 防御的チェックの由来。** PR の*前* 14 日間における、該当する `properties_<name>` 列の分布（中央値 / p99 / 最大値）。p99 が対象のしきい値定数と一致していれば、その数値はデータから選ばれたことを示唆する。
3. **実験 / フィーチャーフラグの照会。** `SHOW TABLES ... LIKE '*experiment*'` で露出テーブルを見つけ、PR の日付付近で、該当するフラグキーの露出数をバリアント別に取得する。
4. **マイグレーション、バックフィル、性能改善の書き換えに対するクエリ履歴の証拠。** `system.query.history` を `statement_text ILIKE '%<table_or_symbol>%'` でフィルタし、`start_time` の窓を狭く取ると、変更の動機になったと思われる高コストなクエリが浮かび上がる（`total_duration_ms` でソートするか、`SUM(read_bytes)`、`COUNT(*)` で集計する）。
5. **dbt のリネージ。** 対象が `<your_analytics_db>.<schema>` のモデルを読み書きしている場合、そのモデル自身の git 履歴（このリポジトリ内）に根拠説明があることが多い。自分で追うのではなく、その手がかりを git 調査役に戻す。

## ここでの良い証拠とはどのようなものか

上のパターンの形に加えて:

- エラーを分類するイベントのカウントが、防御的コードの PR の後の数日でほぼゼロまで落ちる。その PR がそのエラーの種類を解消したことを示唆する
- 露出テーブルの行が、対象のフィーチャーフラグのキーを、PR の出荷日付近の「shipped」/「concluded」の決定とともに示している

## よくある落とし穴

- **計装されている ≠ 原因である。** イベントの存在は、誰かがログを取るほど気にかけていたことを意味するだけで、対象コードがそれ*ゆえに*存在することを意味しない。因果を主張する前に、git 調査役からの PR やコミットの引用と組み合わせる。
- **気づかれにくい計装の変更。** イベント量の階段状の変化は、新しいイベントのログ記録が始まっただけで、ユーザーの行動が変わったわけではないかもしれない。立ち上がりを機能立ち上げのシグナルと読む前に、同じ窓に計装の PR がないか確認する。
- **スキーマドリフト。** イベントプロパティは進化する。今日の型付き dbt モデルにある列は、対象が書かれた時点には存在しなかったかもしれない。古いデータでは、そのプロパティが生の `properties_json` の中にしかないことがある。
- **dbt の更新遅延。** `<your_analytics_db>.<schema>.*` はスケジュールに従って再構築される（多くは毎時または毎日）。直近数時間のイベントについては、代わりに `your_warehouse.events.*` を使い、`_id` で重複排除する。
- **会社ごとに異なるテーブル。** 実験、フィーチャーフラグ、課金、利用量のテーブルはまちまちである。存在を一度も確認していないテーブルの結果を報告するのは、典型的な失敗パターンだ。まず `SHOW TABLES` / `DESCRIBE TABLE` で探る。
- **保持期間の崖。** 該当する窓がテーブルの保持期間や dbt モデルの作成日より前なら、それは null の結果ではなく*ギャップ*である。シンセサイザー（統合役）が「結果なし」を「活動なし」と読まないように、ギャップであることを明示する。
- **ノートブックはクエリできない。** SQL MCP は Databricks ノートブックを見られない。根拠説明がノートブックにあると疑われる場合は、ギャップを返す。

## 返すもの

関連する指摘ごとに:
- 種類（プロダクトイベント / 実験の露出 / 利用量または課金イベント / システムテーブルの行 / dbt モデル）
- 完全修飾のテーブル名と、実行した正確なクエリ
- クエリした時間の窓
- コンパクトな数値の要約（カウント、パーセンタイル、最初と最後に観測されたタイムスタンプ）。**生の行をダンプしない。**
- 対象の出荷日との時間的な相関（例: 「最初の行は 2024-08-15、PR #49074 のマージは 2024-08-14」）
- 関連性と強さ: 直接的 / 状況的 / 弱い
