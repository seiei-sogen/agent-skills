# Slack の会話

## このソースに含まれるもの

- 問題と決定についてのリアルタイムの議論
- 火消しの決定が下されたインシデントチャンネル
- トレードオフが議論された設計ディスカッションのスレッド
- シニアエンジニアが答えたが文書には残らなかった質問
- なぜ何かが見直されたのかを説明する、マージ後の議論
- DM（通常は検索できないので、それに応じてスコープを決める）

Slack は、*本当の*決定が下された場所であることが多い。特に、文書を書くほどではない小さな変更ではそうである。同時に、最も消えやすいソースでもある。スレッドは削除され、チャンネルはアーカイブされ、検索品質は時間とともに劣化する。

## 検索方法

Slack MCP のツールはさまざまである。どの Slack MCP が利用可能かを確認し、まずそのツールスキーマを調べる。`mcp_auth` が必要な場合がある。認証に失敗したら、停止してその空白を報告する。

1. **作成者で限定した検索。** PR のマージ日前後の、PR 作成者によるメッセージ。スコープを劇的に絞り込め、当たりを引くことが多い。
2. **機能名と主要なシンボルのキーワード検索。** スペルミスやくだけた言い回しも含める。
3. **PR URL の検索。** Slack では、PR がレビューや議論されるときにリンクが貼られることが多い。PR の URL（または `/pull/<number>` だけ）を検索する。
4. **エラー文字列の検索。** コードが特定のエラーを処理しているなら、そのエラー文字列を検索する。インシデントのスレッドが浮かび上がることが多い。
5. **チャンネルを限定した検索。** ありそうなチャンネルに絞る:
   - `#eng-*`。エンジニアリングの議論
   - `#proj-*`。プロジェクトのチャンネル
   - `#incident-*` / `#sev-*`。インシデントのチャンネル
   - 所有チームのチーム固有チャンネル
   - 設計レビューのチャンネル
6. **スレッドの走査。** 関連するメッセージを見つけたら、スレッド全体を取得する。決定は返信の中にあることが多い。

## ここで良い証拠とはどのようなものか

- トレードオフが明示的に議論されたスレッド（「A を使うつもりだったが、…だから B のほうが良い」）
- コードが防いでいるバグを説明するインシデントチャンネルのメッセージ
- レビュアーからの質問と、作成者やリードからの権威ある回答
- 決定が下された会議への言及
- 顧客の要望を説明する、プロダクトマネージャーや顧客対応エンジニアからのメッセージ

## よくある落とし穴

- **チャンネル考古学の限界。** 非常に古いメッセージは、保持ポリシーによって消えていることがある。ある日付より前に何も見つからない場合は、その保持期限の境目を記録する。
- **検索されない DM。** 多くの決定は検索できない DM で行われる。それらは見逃すことになる。これは既知の制限である。
- **「決定」としての思いつきの冗談。** Slack はくだけた場である。「笑、とりあえずやっちゃえ」は、コミットの前にあったとしても決定ではない。熟考された議論を探す。
- **単一メッセージでの文脈の崩壊。** スレッドなしでは、単一のメッセージは文脈の中とは違う意味に読めることが多い。常にスレッドを取得する。
- **認証の失敗。** MCP が認証されていなければ、停止する。指摘をでっち上げない。Slack が検索できなかったと報告する。

## 返すもの

関連する各スレッドについて:
- チャンネル名
- パーマリンクまたはスレッド ID
- 参加者
- 議論の日付範囲
- 主要な引用（そのまま）と発言者
- 文脈: どのスレッド、インシデント、議論の一部だったか
