# Notion 文書

## このソースに含まれるもの

- PRD（製品要求文書）
- 技術仕様書と RFC
- アーキテクチャ決定記録（ADR）
- 設計レビューの議事録
- ドメインの文脈を持つチームページ
- インシデントのポストモーテム
- 防御的なコードを説明しているかもしれないランブック
- 優先順位を定める戦略文書

Notion は、「なぜ」がコードになる前に長文の形で置かれていることが多い場所である。重要な機能には通常、文書がある。

## 検索方法

Notion MCP を使う。

1. **`notion-search` によるキーワード検索。** 次を試す:
   - 機能名
   - 対象コードの主要なシンボルやクラス名
   - 作成者のハンドル（設計文書はコードが取り込まれる前に書かれていることが多い）
   - エラー文字列やユーザーに見える用語
   - コードの出荷時期が分かっているなら、期間を限定したクエリ
2. **`notion-fetch` で候補ページを取得する。** プレビューではなく全文を読む。根拠説明は文書の中ほどに埋もれていることが多い。
3. **バックリンクと子ページをたどる。** 設計文書には、検討した代替案、付録、実装メモのサブページがあることが多い。
4. **関連するデータベースを確認する。** `notion-query-data-sources` と `notion-query-meeting-notes` は、その決定を議論した議事録を浮かび上がらせることがある。
5. **作成者固有のスペースを検索する。** PR 作成者が個人ノートブックを持っている場合（一部の企業では一般的）、コードに先立つ探索的な思考がそこにあるかもしれない。

## ここで良い証拠とはどのようなものか

- 対象コードの目的と一致する「Problem statement」や「Motivation」セクションを持つ PRD
- 「Alternatives considered」や「Rejected approaches」のセクション
- 対象コードを特定のインシデントに対する修正として名指ししているポストモーテム
- 「Y だから X に決めた」と記録し、PR と同じ作成者や日付範囲に結び付く議事録
- 形式的でなく記入された ADR テンプレート（ステータス、文脈、決定、影響）

## よくある落とし穴

- **古くなった文書。** 仕様書は実装前に書かれ、更新されないことが多い。文書は、その後変更された計画を記述しているかもしれない。実際の PR と照合する。
- **文書と現実のずれ。** 仕様書が「X をやる」と言っていても、コードは実際には Y をやっているかもしれない。その食い違いを指摘する。シンセサイザー（統合役）がその矛盾を表に出す。
- **定型テンプレート。** 「Why」セクションを必須にし、そこが中身のない文で埋められている組織がある。具体性を探す。
- **リンクされていない文書。** 最も関連の深い文書がどこからもリンクされていないことがある。広いキーワード検索が役立つ。
- **複数のドラフト。** あるトピックに複数の文書がある場合、確定したもの、または最後に更新されたものを見つける。日付を確認する。
- **アクセス制限されたページ。** ページにアクセスできない場合は、空白として記録する。

## 返すもの

関連する各文書について:
- タイトルと URL
- 作成者と最終更新日
- 動機の文言（そのままの引用）と、ページやセクションの位置
- 関連するリンク先ページ（シンセサイザーが引用できるように）
- 文書が確定版かドラフトか
