# Datadog のテレメトリ

## このソースに含まれるもの

Datadog はランタイムの記録、つまり計画や議論されたことではなく、本番で実際に何が起きたかを保持している。

- **メトリクス。** チームが計装したカウンター、ゲージ、ヒストグラム。メトリクスの*存在*それ自体が証拠である。誰かがこの数値を監視する価値があると考えたのだ。
- **モニターとアラート。** 誰かを叩き起こすに値するとチームが判断した条件。`rate_limit_hit > 10/min` で発火するモニターは、チームがそのしきい値を心配していたことの直接的な証拠である。
- **ダッシュボード。** 整理されたビュー。チャートは、チームがそのサブシステムで何を重要と考えているかを教えてくれる。
- **APM のトレースとスパン。** リクエスト単位のランタイムデータ。「なぜこれは遅いのか」「なぜここにタイムアウトがあるのか」という問いに役立つ。
- **ログ。** 大量のイベント記録。防御的コードの動機となったエラー条件を含んでいることが多い。
- **インシデント。** タイムラインとリンクされたポストモーテムを持つ正式なインシデント記録。
- **ノートブック。** 探索的な調査。仮説と分析を含んでいることが多い。

Datadog は「このコードが書かれた当時、本番の実態はどうだったか」に答え、それがコードの形を説明することが多い。

## 検索の仕方

Datadog MCP を使う。広く始めて、次に絞り込む。

1. **対象を所有するサービスを特定する。**

   ```
   search_datadog_services (名前またはチームでフィルタ)
   search_datadog_service_dependencies (上流/下流を見る)
   ```

2. **まずダッシュボードとモニター。チームが何を気にかけているかを教えてくれる。**

   ```
   search_datadog_dashboards (query: 機能名、サービス名、シンボル)
   search_datadog_monitors   (同じクエリ)
   ```

   ダッシュボードやモニターが対象をカバーしているなら、そのクエリと監視しているしきい値を記録する。そのしきい値が「なぜこれは N でクランプされているのか」の答えであることは多い。

3. **対象の周辺のメトリクス。**

   ```
   search_datadog_metrics (名前のパターンで。例: 機能やシンボル)
   get_datadog_metric_context (メタデータ: 説明、単位、タグ)
   get_datadog_metric (時系列。「PR の日付付近にスパイクはあったか」)
   ```

   メトリクスの推移を対象の追加/変更日と相関させることは、強い補強証拠になる。「`payment_timeout` メトリクスは 2023-11-03 にスパイクし、リトライロジックは 2023-11-06 にマージされた」。

4. **ログ。絞り込む、ダンプしない。**

   ```
   search_datadog_logs (対象付近の生ログのパターン。use_log_patterns=true を設定する)
   analyze_datadog_logs (SQL 風の集計。カウントが必要なときだけ)
   ```

   シンボル、エラー文字列、機能名で検索する。**時間の制約を付けたクエリを強く優先する**（例: 変更の前後 30 日）。ログの量は膨大である。制約のない検索は時間を浪費し、タイムアウトすることもある。

5. **APM のスパンとトレース。**

   ```
   aggregate_spans    (統計: 「このエンドポイントはどのくらいの頻度で失敗するか」)
   search_datadog_spans (個々のスパンを調べる)
   get_datadog_trace  (特定のトレース ID)
   ```

   タイムアウト、リトライ、遅いパス、サービスをまたぐ振る舞いに役立つ。

6. **インシデント。**

   ```
   search_datadog_incidents (タイトル、チーム、日付範囲で)
   get_datadog_incident     (特定のインシデントの全詳細)
   ```

   対象が防御的に見えるなら、それが追加された時期の前後のインシデントを検索する。タイムラインに「X の防御的チェックを追加」と含まれるインシデントは、直接的な証拠に近い。

## ここでの良い証拠とはどのようなものか

- クエリとしきい値が、コードが強制する制約と一致しているモニター（コードは 100 でクランプし、モニターはリクエストが 100/min を超えるとアラートする）
- 対象の作者が作成したダッシュボードで、コードが計測または防御している対象に対応するウィジェットを持つもの
- コードがマージされる直前に本番のスパイクを示し、その後は安定した値を示しているメトリクス
- 対象コード、同じシンボル、または同じエラー文字列を参照しているインシデント記録
- 防御的コードが防ぐはずの特定のエラーパターンを示し、変更前の窓のタイムスタンプを持つログ

## よくある落とし穴

- **相関は因果ではない。** PR の前のスパイクと、その後の安定化は示唆的であって、決定的ではない。同じ窓で他の変更が取り込まれたかもしれない。近隣の PR を確認する。
- **見つけたチャートへの過剰適合。** Datadog の可視化は人間が*作った*もので、その人間の枠組みを反映している。「retry success rate」という名前のチャートは、チームがリトライの成功を気にかけていたことの証拠であって、それが特定のコード行が存在する理由であることの証拠ではない。
- **消えたテレメトリ。** メトリクスはリネームや削除されることがあり、保持期間が短いこともある。該当する窓のデータが見つからないなら、それは null の結果ではなくギャップである。
- **大規模でのノイズ。** よくある文字列でログを検索すると数千件の一致が返る。サービス、タグ、時間で積極的に絞り込む。生ログをダンプするのではなく、`analyze_datadog_logs` で集計する。
- **計装されている != 原因である。** メトリクスの存在は、誰かが何かを計測するほど気にかけていたことを教えてくれるだけで、コードがそれ*ゆえに*追加されたことを教えてくれるわけではない。コミットや PR の日付と照合する。

## 返すもの

関連する項目ごとに:
- 種類（ダッシュボード / モニター / メトリクス / ログパターン / トレース / インシデント / ノートブック）
- タイトルまたは名前
- リンクまたは識別子（ダッシュボード ID、モニター ID、メトリクス名、インシデント ID）
- 所有者/作者と、作成日/更新日
- 問いに関係する特定の条件、クエリ、または引用（可能な限り原文どおりに）
- 関連性: これが対象コードについて何を示唆するか、そしてそのつながりはどれくらい強いか
