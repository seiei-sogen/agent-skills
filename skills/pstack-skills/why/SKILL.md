# Why

コードの背後にある動機と意図を調査する。

`how` スキルの対となるスキル。`how` はコードが何をし、どう動くかに答える。`why` はどのような力がその形を導いたかに答える。

**ディスパッチ契約。** 設定済みのすべてのロールを [`provider-dispatch.md`](../poteto-mode/references/provider-dispatch.md) を通じて解決する。調査役は親のライブな MCP サーフェスを必要とするため、既定かつサポートされるポータブルなルートは `inherit-parent`（またはその別名 `auto`）である。コードアンカーはパスで渡す。Codex では、残りの Claude ツール名を [`codex-tools.md`](../poteto-mode/references/codex-tools.md) を通じて解決する。

## 運用姿勢

**注意深く、慎重で、精密な調査役**として動く。知っていることと推測していることを正直に区別する。確信度の枠組み全体と言い回しガイドについては `references/epistemics.md` を読む。シンセサイザー（統合役）はそれに従わなければならない。

## ステップ 1. 対象と問いを理解する

ユーザーが何を尋ねているかを解析する。**対象**は通常、コードのひとかたまり、パターン、機能、または名前の付いた設計判断である。**問い**は通常、設計の根拠説明、トレードオフ、動機となったエッジケース、外部制約、デッドコード、または広範な履歴の調査である。

対象が曖昧な場合（明確な指示対象のない「なぜこうしているのか」など）、会話のコンテキスト（開いているファイル、最近の編集、カーソル位置、直前に話していたこと）から最善の推測をする。外れていればユーザーが軌道修正できるように、解釈を簡潔に述べてから進める。

## ステップ 2. コードアンカーを確立する

調査役を起動する前に、調査を具体的なコードに固定する。必要なもの:

- 関連するファイルパスと行範囲
- 主要なシンボル（関数名、クラス名、定数）
- 初期コミット一覧。対象に触れた直近の数コミット。
- マージコミットから得た PR 番号（件名の `(#1234)` パターン）

これはインラインで組み立てる。

```bash
# Blame target lines for last-touch commits
git blame -L <start>,<end> <file>

# Full file history, with patches, through renames
git log --follow -p -- <file>

# Last N commits touching the file, PR numbers visible
git log --oneline -20 -- <file>

# Extract PR numbers from a commit message
git log -1 --format=%B <commit>
```

実質的な内容のあるコミットについては、`gh` で PR 本文と議論を取得する:

```bash
gh pr view <number> --json title,body,author,createdAt,mergedAt,labels,closingIssuesReferences,comments,reviews
```

これをシードコンテキスト（ファイルパス、シンボル、コミット、PR 番号、リンクされたチケット ID）として記録する。調査役に渡す。

## ステップ 3. 並列の調査役を起動する（既定の姿勢）

**既定では完全な並列調査を行う。**

### 発見

調査役を起動する前に、Claude Code 環境で利用可能な MCP を列挙する。システムプロンプト先頭のツール一覧を使う（すべての MCP は `mcp__<server>__<name>` という接頭辞付きのツールとして現れる）。それができなければ、プラグインまたはプロジェクトの `.mcp.json` を読むか、`claude mcp list` を実行する。

利用可能な各 MCP を 1 つの証拠カテゴリに対応付ける:

1. ソース管理の履歴
2. issue / チケットトラッカー
3. 長文ドキュメント
4. リアルタイムのチームチャット
5. インフラ可観測性
6. エラー / 例外トラッキング
7. プロダクト分析ウェアハウス

ソース管理は git と `gh` を通じて常に利用できる。残りの 6 つについては、MCP 名、サーバー指示、ツール名、リソースのディスクリプタを使って分類する。ある MCP が複数のカテゴリに当てはまりうる場合は、その主要な証拠に合うカテゴリを選ぶ。曖昧なケースはカバレッジマップに記録する。

最小限ではなく、完全な**カバレッジマップ**を目指す。検索を飛ばすのではなく、結果が空だったことを記録する。

一致する調査役をすべて 1 回のファンアウトフェーズで起動し、並行して実行させる。1 つのエージェントに複数の MCP を担当させない。それぞれを、割り当てた MCP を利用可能にしたうえで、設定済みの why-investigators ディスクリプタ（既定 `inherit-parent`）を通じてルーティングする。調査役はそれでもファイルを書かない。MCP を使える実行モードが機械的には読み取り専用でない場合でも、それは姿勢として守る。

各調査役が受け取るもの:
1. `references/investigator-prompt.md` のベースプロンプト
2. 選択した MCP 向けのカテゴリプレイブック `references/sources/<source>.md`。`references/source-playbook.md` の例から適応させたもの
3. **対象コードが防御的に見える場合**（null チェック、リトライロジック、タイムアウト処理、レート制限、フィーチャーフラグ、egress ガード、OOM ハンドラ）は、横断的な `references/sources/incident-postmortem.md`
4. ステップ 2 のコードアンカー（ファイルパス、シンボル、コミットハッシュ、PR 番号、チケット ID）
5. ユーザーの元の問い

### 調査役の一覧。利用可能な証拠カテゴリごとに 1 人

一致する MCP があるカテゴリごとに調査役を 1 人起動する。各調査役はちょうど 1 つのツールまたは MCP を担当する。

各項目は、カテゴリと、そのカテゴリが固有に浮かび上がらせる「なぜ」の種類を示す。何が返ってくるかを予測し、カテゴリが空を返したときにギャップをどう名指しするかを知り、（証明可能に無関係なまれな場合に限り）スキップを正当化するために使う。

1. **ソース管理調査役**。Git 履歴、PR のための `gh`、コードコメント、テスト。常に起動する。唯一保証されたソース。*レビュー中に記録された実装時の根拠説明*を浮かび上がらせるのが最も得意。

2. **issue / チケットトラッカー調査役**（例: Linear、Jira、GitHub Issues、Plane、Shortcut の MCP）。*プロダクトまたはビジネス上の強制力*を浮かび上がらせるのが最も得意。「なぜ」がエンジニアリングの外にあるときに最も強い。

3. **長文ドキュメント調査役**（例: Notion、Confluence、Google Docs、Coda の MCP）。*長文の設計の根拠説明*を浮かび上がらせるのが最も得意。「なぜ」がコードになる前に書き出されている場所。

4. **リアルタイムのチームチャット調査役**（例: Slack、Discord、Microsoft Teams、Mattermost の MCP）。*ドキュメントに到達しなかったリアルタイムの議論*を浮かび上がらせるのが最も得意。ソース管理、チケット、ドキュメントの記録が薄いときに特に重要。

5. **インフラ可観測性調査役**（例: Datadog、New Relic、Honeycomb、Grafana、Splunk の MCP）。インフラ / 実行時の視点。*コードの動機となったインフラと実行時の現実*を浮かび上がらせるのが最も得意。対象がインフラのシグナル（タイムアウト、リトライ、レート制限、サーキットブレーカー）に反応するときに最も強い。

6. **エラー / 例外トラッキング調査役**（例: Sentry、Rollbar、Bugsnag、Airbrake の MCP）。*防御的または是正的なコードの動機となった特定の例外とエラーの軌跡*を浮かび上がらせるのが最も得意。catch ブロック、null ガード、型チェック、リトライ、その他の防御に最も強い。

7. **プロダクト分析ウェアハウス調査役**（例: Databricks、Snowflake、BigQuery、ClickHouse、dbt、Redshift の MCP）。プロダクト / データの視点。*コードの形を決めたプロダクトとデータの現実*を浮かび上がらせるのが最も得意。フラグで制御されたコード、実験駆動の出荷、データマイグレーション、「この数字はどこから来たのか」という問いに最も強い。

### 調査役をスキップするとき

最終的な「Sources Consulted」セクションに載せる**明示的で書面化された正当化**がある場合にのみスキップする。有効な理由は 2 つ:

- この環境に**そのカテゴリ向けの MCP が利用できない**。これは選択ではなくギャップとしてフラグを立てる。例:「リアルタイムのチームチャットをスキップ。一致する MCP が利用できないため、会話の記録は検索できなかった。」
- 「おそらく無関係」ではなく、**ソースが証明可能に無関係である**。高いハードル。例:「エラー / 例外トラッキングをスキップ。対象はビルド時スクリプトで、実行時のコードパスがない。」

スコープ評価から、PR の説明にすでに完全な答えが含まれる単一コミットの些細な対象だと示唆される場合は、利用可能な 7 カテゴリすべての検索が冗長になると確認した**後に限り**、インラインで答えてよい。その旨を明示的に述べる。これはまれであるべきだ。

## ステップ 4. 統合する

設定済みの why-synthesizer ディスクリプタ（既定 `inherit-parent`）を通じてシンセサイザーを 1 つディスパッチする。シンセサイザーの品質チェックは引用を抜き取り検証するため、関連する MCP アクセスを維持する。シンセサイザーはファイルを書かない。

シンセサイザーが受け取るもの:
1. 調査役の指摘。空だった結果と、正当化付きでスキップされたカテゴリを含む
2. ステップ 2 のコードアンカー（ファイルパス、シンボル、コミットハッシュ、PR 番号、チケット ID）
3. ユーザーの元の問い
4. `references/epistemics.md` の認識論の枠組み
5. `references/synthesizer-prompt.md` のシンセサイザープロンプトテンプレート

## ステップ 5. 提示する

シンセサイザーの出力を受け取り、ユーザーに提示する。明確さのために軽く編集したり会話からコンテキストを加えたりしてもよいが、**確信度の言い回しは書き換えない**。

## 出力形式

出力構造は `references/synthesizer-prompt.md` のもの: The Question、The Code in Question、What We Found、What We Can Reasonably Infer、Competing Hypotheses、What We Don't Know、Sources Consulted、Confidence Summary。必要に応じて適応させるが、確信度の区分は崩さず、Sources Consulted は調査役ごとに 1 行を保つ。何も返さなかった調査役やスキップした調査役も、理由とともに含める。

Sources Consulted ブロックの後、ユーザーの `why` の問いが実際にこのコードを変更する前段であるなら、系譜の指摘を、変更の計画に適した Preserve / Change / Avoid / Risk の制約セットに変換する。

## 避けるべきよくある失敗パターン

- **新近性バイアス**。最新のコミットが権威的だと仮定すること。現在の形は多くの以前の決定が積み重なったものであることが多い。さかのぼって追跡する。

## リファレンスファイル

- `references/epistemics.md`。確信度の階層と言い回しガイド。シンセサイザーはこれに従わなければならない。
- `references/investigator-prompt.md`。調査役サブエージェント向けのベースプロンプトテンプレート。
- `references/source-playbook.md`。下記のカテゴリプレイブックを指す索引。
- `references/sources/*.md`。カテゴリごとに自己完結した例のプレイブックが 1 つずつあり、加えて横断的な `incident-postmortem.md`。調査役にはそのカテゴリに一致する 1 ファイルだけを与え、利用可能な MCP に適応させる。
- `references/synthesizer-prompt.md`。シンセサイザーサブエージェント向けのプロンプトテンプレート。出力形式を含む。
