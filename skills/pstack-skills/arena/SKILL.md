# Arena

同じタスクに対して N 個の並列試行をファンアウトする。すべての候補を最初から最後まで読む。最も強いものをベースとして選ぶ。他の候補の最良のアイデアをそこへ移植する。統合結果を検証する。

**ディスパッチ契約。** ファンアウトの前に [`provider-dispatch.md`](../poteto-mode/references/provider-dispatch.md) を読む。設定済みの値はプロバイダ修飾付きのディスクリプタであり、ホストネイティブのモデルスラグではない。親がネイティブレーンと外部レーンを直接開始する。子が自らルーティングすることはない。Codex 上では、残りの Claude ツール名を [`codex-tools.md`](../poteto-mode/references/codex-tools.md) で解決する。

## 開始

何かを起動する前に、フェーズごとに 1 項目ずつ持つ TODO リストを開く。

1. 枠組み
2. ファンアウト
3. 相互ジャッジ
4. 選択
5. 移植
6. 検証

## フェーズ A: 枠組み

N 個の候補は同じプロンプトを受け取るので、プロンプトが契約である。

1. 各候補が作る成果物を述べる。
2. ルーブリックを導出する。*この* タスクにおける成功とは何かを述べ、それを 3 から 6 個の具体的で採点可能な基準に変える。ルーブリックはフェーズ D で選ぶ側が使う道具である。候補にはタスクしか見せない。
3. ランナーを選ぶ。現在のハーネスの pstack モデルシートに `arena runners` があればそれを使う。なければ既定として `claude:fable@max`、`codex:gpt-5.6-sol@max`、`grok:grok-4.6@xhigh`、`claude:opus@xhigh` にそれぞれ 1 つずつ。アリーナが複数の設計方向を扱うときは、さらに多く生成する。作業が判断に敏感ではなく生成量に律速されるなら、同じディスクリプタを N 回使う。
4. 出力パスを割り当てる。**separate-before-serializing-shared-state** 原則スキルに従い、各候補は自分専用の場所（可能なら git ワークツリー、そうでなければ `/tmp/arena-<slug>/candidate-<n>/`）に書き込む。

## フェーズ B: ファンアウト

プロバイダディスパッチ契約を通して、N 個のレーンすべてを 1 回のファンアウトフェーズで開始する。ネイティブレーンはバックグラウンドのサブエージェントである。外部レーンは、タスク / セッションのハンドルを保持した直接のバックグラウンドランチャープロセスであり、決してフォアグラウンド呼び出しではなく、決してサブプロセスを監督するサブエージェントでもない。すべてのレーンに、タスク、共有の地固めへのパス、自分専用の出力パス、そして成果物と短い根拠説明の両方を作るという指示を与える。

各根拠説明は、その候補が検討した代替案と却下したものを挙げる。

外部レーンは、レシートが `complete` を示し、かつ一致する `provider-report` か Codex の正確な `pinned-argv` の証拠のいずれかを伴うときだけカウントする。ネイティブレーンは、そのツールトランスクリプトが割り当てられたモデルの結果を返したときにカウントする。候補が失敗したら、N-1 で進め、正確な脱落を統合記録に記す。黙って別のプロバイダで置き換えることは決してしない。

## フェーズ C: 相互ジャッジ

フェーズ B の候補がすべて完了した後、現在のハーネスの pstack モデルシートに `arena cross-judge pool` があればそこから、なければ上のランナー既定からジャッジのディスクリプタを選ぶ。親およびベースになりそうな候補とは異なるプロバイダを優先する。プロバイダ契約を通して読み取り専用のジャッジを 1 つディスパッチする。ジャッジはルーブリックと完了した候補をパスラベルで見て、各基準を採点し、根拠説明付きでベースを推薦する。ジャッジはフェーズ D で親が候補を読むのと並行して実行するのであり、候補そのものと並行するのではない。候補がまだ書いている間にジャッジをディスパッチしない。

## フェーズ D: ベースを選ぶ

選ぶ前にすべての候補を最初から最後まで読む。

各候補をルーブリックに照らして基準ごとに採点する。全体的な印象で採点しない。相互ジャッジと比較する。ベースについて一致すれば選択は確認される。不一致なら、どちらかが偏っているか、ルーブリックが曖昧だったということである。決める前に両方の根拠説明を読む。

将来のメンテナが不変条件を壊さずに最も容易に拡張できる候補を基準にベースを選ぶ。2 つが同点に感じられるときは、Laziness Protocol に従い、より綺麗な境界かより小さな API を優先する。

選択とその理由を、ベースの成果物と並べた短い統合ノートに記録する。相互ジャッジの判定も含める。

## フェーズ E: 移植

敗れた各候補をもう一度通して読み、ベースへ移植する価値のあるものを特定する。シグナルは通常、候補ごとに 1 つか 2 つであり、その大部分ではない。

**redesign-from-first-principles** 原則スキルに従い、各移植を手作業で織り込む。機械的に貼り付けない。結果は 1 つのメンタルモデルの下で一貫していなければならない。

何を、どの候補から移植したか、そして何を却下しその理由は何かを記録する。

N 個の候補が同じ形に収束したなら、それは強い合意のシグナルである。収束を記録に記し、合意された形を出荷する。移植は不要である。N 個の候補が大きく発散したなら、フェーズ A の指定が不足していた。発散を平均するのではなく、枠組みをやり直して再実行する。

## フェーズ F: 検証

**prove-it-works** 原則スキルに従い、統合された成果物は他のあらゆる出力と同じ精査に耐えなければならない。

検証がアリーナの捕まえられなかった問題を明らかにしたなら、フェーズ A が間違っていた（枠組みをやり直して再実行する）か、ある候補がそれを捕まえていたのに移植を見逃した（フェーズ E に戻る）かのどちらかである。ごまかして覆い隠さない。

## 出力

統合された成果物 1 つ。それと並べて短い統合ノート 1 つ。ベース、移植（元の候補付き）、却下したもの、あれば脱落、そして検証結果を挙げる。
