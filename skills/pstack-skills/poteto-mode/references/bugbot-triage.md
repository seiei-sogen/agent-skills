# Bugbot トリアージ

Babysit プレイブック（`../playbooks/babysit.md`）が Bugbot やレビュー自動化のコメントを扱うときに、このリファレンスを使う。目的は Bugbot を既定で無視することではない。目的は、すべてのコメントを必須のコード変更として扱うのをやめることである。

## 判定ルーブリック

行動する前に各 Bugbot スレッドを分類する:

- `fix`: コメントが、正当性、セキュリティ、プライバシー、データ損失、認証、課金、マイグレーション、冪等性、競合、または出荷される挙動に関するもっともらしい問題を特定している。最も下位の所有 PR で修正し、コミット SHA を付けて返信してスレッドを解決する。
- `dismiss`: コメントが文書化された低リスクのノイズパターンに一致し、現在のコードや文脈から、その懸念にコード変更が不要だと証明できる。短い理由を付けて返信し、スレッドを解決する。
- `ask`: コメントが新規、高深刻度、セキュリティ／プライバシー／データ関連、または曖昧である。推測せずユーザーに尋ねる。

迷ったら尋ねる。ノイズの多いコード品質のコメントを飛ばすのは安いが、本物のデータやセキュリティのバグを飛ばすのは安くない。

## 学習したパターンの形式

今後のパターンはこの形で追加する:

```markdown
### <短いパターン名>

- 確信度: candidate | recurring | strong
- 飛ばす条件: <真でなければならない条件>
- 飛ばしてはならない条件: <リスクの境界>
- シグナルの例: <パターンを識別する言い回しやコードの文脈>
- 出所: <PR やコメントの URL、または短い経緯のメモ>
```

例が 1 つか 2 つなら `candidate` を使う。実際の却下が複数回あった後に `recurring` を使う。パターンが狭く、繰り返し検証され、低リスクである場合だけ `strong` を使う。

## 繰り返し現れるスキップ候補

### 意図的な UI やデザインシステムの見た目の変更

- 確信度: candidate
- 飛ばす条件: PR 説明文、スクリーンショット、デザインレビュー、または近くのコードが見た目の変更を明示しており、Bugbot のコメントは共有の見た目の既定値が変わったことを述べ直しているだけである。
- 飛ばしてはならない条件: コメントが、アクセシビリティ、フォーカスの可視性、キーボード操作、色のコントラスト、または PR が意図して変えていないコンポーネント API の契約を指している。
- シグナルの例: フォーカスのアウトライン、ボタンのサイズ、余白、共有コンポーネントの見た目の既定値に関するコメントで、所有者が「意図的」や「意図どおり」と返信しているもの。

### Bugbot には見えない上位スタックやスタック内での使用

- 確信度: candidate
- 飛ばす条件: Bugbot がエクスポート、コンポーネント、ヘルパー、ファイルを未使用としてフラグしているが、使用中のフォージ（forge）の PR 一覧と差分、上位スタックの差分、または PR の文脈から、スタック内の後続の PR で使われていることが分かる。
- 飛ばしてはならない条件: 現在の PR がスタックの一部ではない、そのシンボルが公開 API である、または上位スタックでの使用とされるものが検証できない。
- シグナルの例: 「エクスポートされたコンポーネントが一度も使われていない」に、「上位スタックで使っている」のような人間の返信が付いているもの。

### 並行実装中の一時的な重複

- 確信度: candidate
- 飛ばす条件: 削除、置換、または実証の途中にある古いパスと並行させて新しいパスを保つために、PR が少量のコードを意図的に重複させている。
- 飛ばしてはならない条件: 重複したコードがセキュリティ、課金、データアクセス、API の挙動を変える、または長寿命の共有抽象化のほうが明らかにリスクを減らす。
- シグナルの例: 「著しい重複」や「バリデーションロジックの重複」で、所有者が古いパスは削除される、または重複ロジックは意図的にローカルにしていると説明しているもの。

### 既存のフレームワークやコンポーネントの不変条件が警告をカバーしている

- 確信度: candidate
- 飛ばす条件: その懸念が、現在の差分や近くのコードから見える共有コンポーネント、フレームワークの契約、型の不変条件、または単一の情報源によってすでに保証されている。
- 飛ばしてはならない条件: 不変条件が仮定されているだけで強制されていない、タイミングに依存する、または値が食い違いうる非同期／状態の境界をまたぐ。
- シグナルの例: 共有のポップオーバーがビューポートの範囲を強制しているのに内側のポップオーバーに max-height がないというコメント、またはローカルで確認した値と渡した値が同じ情報源を共有している nullable な値についてのコメント。

### 所有者が宣言したフォローアップや先送りしたクリーンアップ

- 確信度: candidate
- 飛ばす条件: PR 所有者がその問題は既知のフォローアップだと明示的に言っており、現在の PR で挙動が悪化しておらず、コメントが高リスク領域に関するものではない。
- 飛ばしてはならない条件: エージェントが所有者の入力なしに動いている、問題が中／高深刻度のプロダクト挙動である、または先送りすると新しいリグレッションがマージされる。
- シグナルの例: 「それは後で心配する」や「いずれこれは削除する」。

### 自ら撤回された、または明示的に偽陽性とされた規則コメント

- 確信度: recurring
- 飛ばす条件: コメント本文または後続の Bugbot の返信が、その指摘は撤回された、準拠している、または偽陽性だと明示しており、エージェントが該当の規則をローカルで検証できる。
- 飛ばしてはならない条件: 唯一の証拠が、高リスクの問題に対して人間が説明なしに「偽陽性」と言っていることだけである。
- シグナルの例: 本文にそのファイルはすでに準拠していると書かれたファイル命名規則のコメント。

## 既定では尋ねる

以前の PR で似たものが却下されていても、これらのカテゴリは自動でスキップしない:

- セキュリティ、プライバシー、認証、課金、データ保持、学習データ、権限境界の指摘。
- 高深刻度の指摘。
- マイグレーション、スキーマ、冪等性、並行性、システム横断の挙動の指摘。
- 提案された修正が小さく、プロダクトの意図を変えずに明らかにリスクを減らすコメント。

過去のデータでは、人間がセキュリティやデータフローのコメントを却下することが時々あった。それらは所有者の判断であって、チーム全体のスキップ規則ではないと扱う。

## 最近の面倒見からの候補となる学び

チームに有用そうだがまだ成熟していない新しい候補の学びは、面倒を見ている間またはその後にここへ追記する。複数の PR がパターンを確認したら、繰り返し現れる候補を上のセクションへ昇格させることを優先する。

### ブラウザのネイティブ挙動の手動での再実装

- 確信度: candidate
- 飛ばす条件: 実質的に決してない。差分がブラウザのネイティブ挙動を手動の同等物で置き換えている場合（ネイティブの sticky → JS で位置決めしたクローン、ネイティブのスクロール対象決定 → 転送した wheel/touch イベント、描画順による遮蔽 → mask/clip-path）、そのコードに対する Bugbot のロジックバグの指摘は一貫して正当だった。
- 飛ばしてはならない条件: 指摘が、そうしたコードにおけるイベント転送の抜け（wheel の deltaMode、タッチのパン、端でのスクロール連鎖、タップの遊び）、mask/clip のヒットテストの食い違い、または observer と React の状態のタイミング競合に関するもの。既定は修正。
- シグナルの例: 「mask はヒットテストに影響しない」「オーバーレイが wheel スクロールを塞ぐ」「deltaMode を無視している」「React が状態を適用する前に IntersectionObserver のコールバックの中で動く」。
- 出所: sticky 遮蔽の PR 1 件。Bugbot のパス 6 回、指摘およそ 18 件、そのすべてが却下ではなく修正された。

### 契約テストのずれの主張は安く検証できる。まずテストを実行する

- 確信度: candidate
- 飛ばす条件: 検証そのものは決して飛ばさない。コマンド 1 つで済む。PR がプロトコルやドキュメントの文章を固定する契約テスト（SKILL.md に対する正規表現、ドキュメント文言のスナップショット）を含み、Bugbot が「テストがもうドキュメントと一致しない」（またはその逆）と主張しているなら、分類する前に PR の先端でそのテストを実行する。赤なら主張が経験的に確認され、緑なら却下の返信に使える具体的な反証になる。
- 飛ばしてはならない条件: 該当なし。これは検証の近道であって、却下パターンではない。なお、パスの繰り返しで却下寄りに傾くヒューリスティックはここでは誤作動する。文章を固定するテストがずれるのは、まさに以前の修正ラウンドがその文章を編集するからである。
- シグナルの例: 以前の修正コミットで固定対象の一節を書き換えた PR に対する「契約テストが修正前の待機を省いている」。先端でのテスト実行は、まさに引用されたアサーションで失敗した。
- 出所: 文章を固定する PR 1 件、Bugbot のパス 8 回。以前のすべてのパスが修正・解決済みだったにもかかわらず、パス 7 で主張は本物だった。

### 同じ PR の後半ですでに修正済みの、古くなったセキュリティレビューの指摘

- 確信度: candidate
- 飛ばす条件: エージェント型セキュリティレビュー（または類似のもの）が認可やバリデーションの呼び出しが欠けていると主張しているが、現在の PR の先端にはまさにそのゲートが（テスト付きで）明確に含まれている。典型的には、レビュー実行後の後続の強化コミットで追加されたもの。
- 飛ばしてはならない条件: 引用されたヘルパーが対象のプリンシパルに対して何もしない、チェックがそれが守るべき副作用の後に動く、または主張されたプリンシパルに対するカバレッジが欠けている。
- シグナルの例: 先端ではまさにそのガードが副作用の前にすでに呼ばれているのに、HIGH の「認可チェックの欠落」の指摘。
- 出所: 強化コミットがレビュー実行より後になった webhook エンドポイントの PR 1 件。

### 意図的に狭くしたエラー条件を広げると本当のエラーが隠れる

- 確信度: candidate
- 飛ばす条件: 指摘が狭いエラー条件（特定の `errno`、エラーコード、ステータスの種別）を包括的なものへ広げるよう求めており、その狭さが実質的な区別をエンコードしている。典型的な形は `ENOENT` で制御された依存関係のフォールバックである。「バイナリがインストールされていない」は「コマンドは実行されたが失敗した」とは別の状況である。非ゼロ終了すべてでリトライすると、正当な失敗（見つからない、認証の期限切れ、ネットワーク）をフォールバックに対して再実行し、その後フォールバックのエラーを報告して本当のエラーを隠してしまう。
- 飛ばしてはならない条件: 狭い条件が同じカテゴリのケースを取り逃している（`EACCES` のような別の「バイナリが使えない」errno、別のトランスポート層の失敗）、未処理のパスがデータを失うか部分的な状態を残す、またはリトライが冪等でかつ元のエラーがなお表面化する。
- シグナルの例: 「X が ENOENT で失敗したときだけリトライする … 動く Y があってもフォールバックを決して試さない」が、失敗した操作ではなく依存関係の欠落のためにフォールバックが存在するコードを指している。
- 出所: 失敗したコマンドではなく欠落したバイナリのためにフォールバックが存在した CLI リネームの PR 1 件。
