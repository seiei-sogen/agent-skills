# プロバイダディスパッチ

pstack のモデル選択はプロバイダ修飾付きのディスクリプタである:

```text
<provider>:<model>@<effort>
```

## モデル行列

| ファミリー | 上流 pstack の選択 | プロバイダ | モデル | 既定エフォート | 選択可能なエフォート | Claude ネイティブのエージェント語幹 |
|---|---|---|---|---|---|---|
| fable | fable | claude | fable | max | low medium high xhigh max | fable |
| sol | gpt-5.6-sol-max | codex | gpt-5.6-sol | max | low medium high xhigh max | - |
| grok | grok-4.6-fast-xhigh | grok | grok-4.6 | xhigh | low medium high xhigh max | - |
| opus | opus | claude | opus | xhigh | low medium high xhigh max | opus |

許容されるエフォートの全体は厳密に `low`、`medium`、`high`、`xhigh`、`max` である。初回実行時の要求エフォートは各行の「既定エフォート」セルである。Claude ネイティブのエージェント語幹が `-` のファミリーには Claude ネイティブのエージェントがない。それ以外では、同梱のエージェント名は `pstack-<stem>-<effort>` である。

`fable` と `opus` は Claude Code のローリングエイリアスである。Claude は各エイリアスを利用可能な最新のファミリーリビジョンに解決する。ランナーのレシートは要求したエイリアスを `model` に、プロバイダが報告した具体的なリビジョンを `reportedModel` に保持する。検証は、一致するファミリーの数値付き `claude-fable-*` または `claude-opus-*` リビジョンだけを受け入れる。

## 読み取り時の正規化

設定済みディスクリプタは、行列に照合したりルートを選んだりする前に正規化する。プロバイダ修飾付きの Claude モデルが `claude-fable-` または `claude-opus-` で始まり、残りのリビジョンが数字とハイフンだけなら、そのモデル要素をメモリ上で `fable` または `opus` に置き換える。プロバイダ、エフォート、ロール、レーンの順序は保つ。ネイティブディスパッチやランナーの argv には正規化済みのディスクリプタだけを使う。バージョン付きの旧版を Claude に渡してはならない。

この読み取り時の規則により、古いインストール済みシートでもユーザーのファイルを書き換えることなく直ちに最新のファミリーリビジョンを使える。親の実行ごとに 1 回、永続化されたシートが古いこと、および `/setup-pstack` が通常のプローブと確認の後にそれを書き直すことを報告する。未知のバージョン付き Claude モデルは引き続き無効である。外部ランナーは、見逃された Fable や Opus のバージョン固定を黙って実行するのではなく拒否する。

`fast` は Cursor の Grok セレクタの一部であり、Grok Build CLI のモデルやエフォートのフラグではない。移植可能な Grok ルートは現在の CLI モデル `grok-4.6` に固定する。初回実行時の Grok のエフォートは `xhigh` である。

## ルートは親が所有する

最上位のハーネスがルートを一度だけ解決する。子は割り当てられたプロバイダ、モデル、エフォート、アクセスモード、プロンプト、作業ディレクトリ、出力パスを受け取る。子がハーネスを検出したり、プロバイダを選んだり、別のモデルを起動したりすることは決してない。環境マーカーはファンアウトの前に最上位のハーネスを裏付けるのに使ってよいが、入れ子のプロセスは親のマーカーを継承するので、それをルーティングに使ってはならない。

| 親 | `claude:*` | `codex:*` | `grok:*` |
|---|---|---|---|
| Claude Code | ネイティブの `Agent` | 外部ランナー | 外部ランナー |
| Codex | 外部ランナー | ネイティブの `spawn_agent` | 外部ランナー |

`inherit-parent` と `auto` は引き続きエイリアスである。親の現在のモデルとエフォートを、親のネイティブなサブエージェントプリミティブを通して使う。パネルではやはり 1 レーンを消費するが、プロバイダの多様性を減らす。統合の記録にそのことを書く。

## ネイティブレーン

ネイティブディスパッチは 2 つ目の CLI 起動とその基本コンテキストを避けられる。

- Claude Code: ディスクリプタの `(provider, model)` をモデル行列の 1 行に照合し、その行の Claude ネイティブのエージェント語幹とディスクリプタのエフォートを使って `pstack-<stem>-<effort>` を通してディスパッチする。それらの定義がローリングのモデルエイリアス、要求エフォート、`background: true` を選ぶ。`pstack-fable-max` と `pstack-opus-xhigh` はその集合に引き続き含まれる。完全なタスク、根拠となるパス、アクセスモード、固有の出力場所を `Agent` のプロンプトで渡す。タスクハンドルを保持し、ファンアウトの後にだけ回収する。
- Codex: ディスクリプタのモデルと `reasoning_effort`、完全なタスク、根拠となるパス、アクセスモード、固有の出力場所を付けて `spawn_agent` を呼ぶ。書き込み側には分離されたワークツリーを使う。Codex のサブエージェントはすでに並行して動く。

同一プロバイダのディスクリプタを外部ランナーに送ってはならない。ネイティブルートのほうが安く、すでに利用できるため、ランナーはその呼び出しを拒否する。

## 外部レーン

ランチャーはインストール済みプラグイン配下の `skills/poteto-mode/scripts/runner/pstack-runner` にある。親は完全な候補プロンプトを固有のファイルに書き、固有の出力ディレクトリまたはワークツリーを作り、ランチャーを直接呼び出す。その前に別のエージェントを置いてはならない。

```text
pstack-runner \
  --parent <claude|codex> \
  --provider <claude|codex|grok> \
  --model <real CLI model> \
  --effort <low|medium|high|xhigh|max> \
  --mode <read-only|isolated-write> \
  --prompt <unique prompt file> \
  --cwd <repository or dedicated worktree> \
  --output <unique final-response file> \
  --receipt <unique receipt file> \
  [--timeout <seconds>]
```

引数は argv 配列として渡すか、すべてのパスを引用符で囲む。プロンプトの文章をシェルコマンドに埋め込んではならない。ランチャーは割り当てられた CLI と認証を事前確認し、モデルをちょうど 1 回だけ呼び出し、CLI が対応していれば再帰的なエージェントと周囲のスキルディスパッチを無効にし、組み込みツールのサーフェスを制限し、正確なプロバイダ／モデル／エフォートのフラグを記録する。外部レーンは親の MCP サーフェスを受け取らない。MCP に依存する Why と Reflect のロールは `inherit-parent` か `auto` に留める。ランチャーは決してフォールバックしない。

Grok の認証事前確認には上限付きのリトライが 1 回ある。最初の `grok models` の結果が未認証と分類されるなら、ランナーは 5 秒待って同じ事前確認をもう 1 回試す。2 回目の失敗は終端である。この遅延と 2 回目の試行はランナーの絶対期限とキャンセルのラッチを共有し、レシートは両方の試行の証拠を保持する。モデルの実行は決してリトライされない。

購読済みの子 CLI が自分の資格情報とネットワークに到達できるかどうかは、依然として親のツールサンドボックスが決める。セットアップのライブプローブは実際の親プロファイルから実行する。ブロックされた外部 CLI は目立つドロップアウトであり、権限を引き上げたりモデルを黙って差し替えたりする理由にはならない。

親の呼び出しはそれ自体が再開可能なバックグラウンド作業でなければならない:

- Claude Code: `run_in_background: true` を付けた Bash ツール呼び出しでランチャーを呼び、そのタスク ID を保持する。フォアグラウンドの Bash ツール呼び出しには、ランナー自身のタイムアウトがもっと長くても自動的に 10 分の上限がかかる。`&` でシェルに投げてタスクハンドルを失うのは同等ではない。
- Codex: セッション ID を返す永続的な exec セッションでランチャーを実行し、そのハンドルを待つかポーリングする。モデルの実行時間全体にわたって 1 つのフォアグラウンドのツール呼び出しを開いたままにしない。

バックグラウンドプロセスを開始し、他のレーンの起動を続け、その後それらのハンドルを回収する。ネイティブレーンと外部レーンは同じファンアウトフェーズに属する。

ランナーとその事前確認には暗黙のタイムアウトがない。ロール、モード、都合のよい丸い数字から所要時間をでっち上げてはならない。実際の実装レーンは 90 分、あるいはそれよりはるかに長く動くことがある。`--timeout` は、ユーザー、外部サービスの期限、または測定されたタスク契約が実際の上限を与えるときだけ渡す。その値はモジュール読み込みと引数解析より前のラッパー開始時点から起算され、セットアップ、事前確認、モデル実行、出力取得を通じて 1 つの絶対期限のままである。子ごとに新しい持ち時間になることは決してなく、長い待機は与えられた期限を短縮せずにランタイムで安全な塊に分けて設定される。それ以外の場合は、保持したバックグラウンドのタスク／セッションのハンドルを通して生存を監視し、実行が死んでいる証拠があるときだけ手動でキャンセルする。その保持したハンドルを通してキャンセルすることで、ランナーは SIGINT または SIGTERM を受け取り、動作中の子が残っていればそれに送り、継承した出力パイプの待機をやめ、空の出力の予約を削除し、`cancelled` のレシートを書く。そのレシートは保存する。リトライは新しい固有の出力パスとレシートパスを持つ新しい試行である。変化のない実行中の状態はドロップアウトではなく、Claude の 10 分のフォアグラウンド上限は健全なレーンを終了させる理由には決してならない。

読み取り専用モードは、プロジェクト限定の設定と明示的なツール一覧を持つ Claude のプランモード、Codex の読み取り専用サンドボックス、および Grok のプランモードに `read-only` サンドボックスと読み取り向けのツール一覧を加えたものに対応する。Grok の組み込み読み取り専用プロファイルは、自身の状態ディレクトリとシステムの一時ディレクトリを意図的に書き込み可能なままにしているので、読み取り専用の Grok レーンは `/tmp`、`/var/tmp`、ホストの一時ディレクトリ配下のワークツリーではなく実際のチェックアウトに向ける。`isolated-write` は、プロジェクト限定の設定を持つ Claude の `acceptEdits`、Codex の `workspace-write`、および Grok の `acceptEdits` に `workspace` サンドボックスと書き込み可能なツール一覧を加えたものに対応する。すべての書き込み側には専用のワークツリーか出力ディレクトリだけを与える。書き込み側を主チェックアウトにルーティングしてはならない。

並行するすべての外部レーンには、別々のプロンプト、出力、レシートのパスが必要である。ランチャーは出力とレシートのパスを排他的に予約し、それらの上書きを拒否する。

## 完了とドロップアウト

成功には次のすべてが必要である:

1. 終了ステータス `0`。
2. レシートのステータス `complete`。
3. `modelVerified: true` かつ `modelEvidence: "provider-report"` であるか、または `reportedModel: null`、`modelVerified: false`、`modelEvidence: "pinned-argv"` の Codex レシートであること。Claude の `fable` と `opus` のエイリアスでは、プロバイダの具体的な報告が要求したファミリーに属していなければならない。Codex 0.149.0 は厳密な `--model` 引数を受け付けるが、提供したモデルを JSONL ストリームで報告しない。
4. 空でない出力ファイル。

レシートはさらに、経過時間、CLI が公開している場合のトークン使用量、利用できる場合のコストを持つ。親ハーネス間の比較が証拠に基づくものになるよう、arena やレビューの成果物と一緒に保管する。

CLI の欠落、ログイン失敗、モデルの利用不可、明示的なタイムアウト、キャンセル、予約後に捕捉可能なランチャーの失敗、子の非ゼロ終了、不正な形式の結果、モデルの不一致はいずれも、レシートを伴うドロップアウトである。それを記録し、呼び出し元スキルの既存のドロップアウト方針を適用する。`cancelled` のレシートはランナーがシグナルを受け取ったことを証明する。その `signal` フィールドは、ランナーがまだ動作中の直接の CLI 子プロセスにそのシグナルを送ったときだけ非 null になり、キャンセルが終了後のパイプ回収を止めただけのときは null のままである。その直接の子の下で起動されるプロセスはプロバイダ CLI が所有し、レシートはプロセスツリーの kill を主張しない。レシートを削除したり上書きしたりしない。親モデルで代替したり、別のプロバイダでリトライしたり、外部ディスクリプタをネイティブのモデルスラッグとして再解釈したりしてはならない。

ネイティブレーンと外部レーンを同じファンアウトフェーズで開始し、判定の前にそれらすべてを待つ。ジャッジは、所有者がまだ書き込んでいる間に候補のパスを読んではならない。
