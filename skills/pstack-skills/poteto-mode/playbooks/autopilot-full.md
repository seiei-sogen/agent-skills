### Autopilot-full

**判定の責任は自分にあり、PR の責任は決して負わない。各 PR はビルドからマージまで 1 人のオーナーが運び、自分のクリーンな swarm 判定なしには何もマージされない。** 「このキューを autopilot して」「フル autopilot」、および PR ごとに 1 オーナーのプログラムに使う。Orchestrate は、コーディネーターが検証済みの作業を自ら取り込み、ワーカーは決してマージしない常設プログラムを運用する。ここでは各 PR のオーナーがマージまでのライフサイクル全体を運び、ルートは検証、副署（countersign）、監査だけを保持する。

1. **オペレーターの項目に印を付け、述べてから待つ（state-then-wait）を守る。** オペレーターが名指しした項目はオペレーターのものにとどまる。オペレーターがレビューし、オペレーターがクリックし、どのオーナーもそれをマージしない。プロトコルや計画を述べるよう求められたら、その説明を提示して止まる。実行はオペレーターの明示的な実行許可（go）があってから始める。その許可が出たら、プログラム目標の全文を常設指示に書き込み、自分の TODO リストにも言い直す。Claude Code には `/goal` コマンドがないからだ。その目標はキューが終わるまでターンをまたいで有効である。
2. **PR ごとに 1 人のオーナーを、ライフサイクル全体と早期の記録付きで起動する。** プログラムにつき 1 回、フォージ（forge）を解決する。GitHub CLI（`gh`）が既定である。`command -v origin` が成功し、Origin がリポジトリを解決できるなら、PR の作成、編集、表示、監視の操作には `origin pr ...` を使う。オーナーのマージは引き続き Shipping のステップ 5 の expected-head 規則に従う。そうでなければ `gh` にとどまり、フォールバックしたことを記録する。フォージが報告したベースリポジトリを `<base-repo>` として記録し、すべての GitHub PR コマンドに `--repo "$base_repo"` を渡す。`<head-remote>`、`<head-url>`、`<base-remote>` は Shipping のステップ 1 に従って個別に解決してバリデーションする。これらのいずれかが `origin` という名前であるとか、ベースとヘッドのリポジトリが同じであるとは決して仮定しない。Graphite（`gt`）を決して必須にしない。PR ごとに 1 つのバックグラウンドサブエージェントが、自身のワークツリーで、ビルド、最初の push、Opening a PR の準備完了規則に従って早期に開く PR、実際の成果物での自己証明（**prove-it-works** 原則スキル）、`../references/bugbot-triage.md` に従った懐疑的なレビューボットのトリアージ、スロップ除去（**deslop** スキル、`/deslop`）、`/no-comments`（**no-comments** スキル）を担う。babysit の前に、自己完結した PR またはプライベートスタックのルートは、`<base-remote>` 経由で取得した現在のトランクへ rebase する。プライベートスタックの子は、代わりに `<head-url>` 経由で親の正確な先端を取得し、その先端へ rebase する。選んだ正確なコミットを `<target-tip>` として記録する。どちらの rebase やその他の書き換えの前にも、オーナーは自分の PR とプライベートスタックの子孫すべてに Shipping のステップ 4 の解除して確認する規則を適用し、フォージがすべてのリクエストが解除済みであると確認できなければ止まる。ブランチの公開済み SHA を `git ls-remote -- "$head_url" "refs/heads/$branch"` で `<captured-sha>` として記録し、ローカルの rebase 前の先端と等しいことを要求する。ブランチの現在のパッチベースを `<current-base-sha>` として記録し、`git merge-base --is-ancestor "$current_base_sha" "refs/heads/$branch"` が通ることを要求し、ターゲットが変わったときは `git rebase --onto "$target_tip" "$current_base_sha" -- "$branch"` を使う。rebase の後、`git push --force-with-lease="refs/heads/$branch:$captured_sha" -- "$head_url" "HEAD:refs/heads/$branch"` で公開する。その後、グリーンになるまで babysit ループ（`playbooks/babysit.md`）を実行し、マージも自ら担う。約 15 分以内に、すべてのオーナーは `decisions.tsv` の記録を開始し、最初のブランチスナップショットを push し、自己証明の前に PR を開く。これにより URL、決定、チェックが永続的な記録を形成する。Opening a PR の準備完了規則に従う。リポジトリの指示により、必要な証拠が記録されるまで早期の PR をドラフトのままにしてもよい。`decisions.tsv` はコミットせずに保ち、レポートと一緒に返す。必須の rebase は常に babysit に先立ち、ドリフトや競合を待つことは決してない。マージは、オーナーが単独で行ってはならない唯一のステップである。ステップ 4 がそれをゲートする。
3. **オーナーを真に並列で走らせ、決してスタックしない。** PR が自己完結しているなら多数のオーナーを同時に走らせる。ブランチごとに 1 人の書き手、互いに重ならないファイル、PR 間のドリフトは rebase で吸収する。本当に重なる作業だけを直列化する。自己完結した PR は main から直接ブランチを切り、順序のある作業はマージしてからブランチを切る。例外は 1 つ。本当に依存関係のある変更を分割しなければならないオーナーは、短いプライベートスタックを持ってよい。そのスタックは Autopilot-stack の同一リポジトリ規則とフォークベース規則に従い、すべての子は親の正確な先端をパッチベースとして記録する。
4. **マージ可能なヘッドはすべて、マージ前に swarm 検証する。** オーナーのマージ可能なヘッド SHA で、**swarm** スキルに従って並列の独立した検証器をファンアウトし、1 つの判定に集約する。レーンは次の通り。その SHA でゲートを再実行する。変更が触れる実際のサーフェスで、要となる振る舞いをライブで証明する（変更の要求に応じて、CLI と TUI には `run` スキル、UI には `verify`）。PR 本文を信用せずにレシートと差分を監査する。**トランクに対するリグレッションレーン。** 同じ要となるシナリオを現在のトランクで実行する。トランクにその機能がないなら、その事実を記録し、トランクが生成できるふりをするのではなく、差分が追加する振る舞いとユーザーが待つ最終状態をゲートする。ライブレーンは最低ラインであり、それを欠く判定はクリーンではない。ルートのクリーンな判定なしにマージはない。指摘は前進修正のためにオーナーへ戻し、新しいヘッドには新たな swarm と新たな判定を行う。
5. **クリーンな判定が出たらオーナーがマージし、次の項目を取る。** オーナーは、トランクへ新たに rebase したヘッドからのみマージする。プライベートスタックの子は、親がマージされた後に Shipping のステップ 4 を経てその状態に達する。マージ可能レポートには判定 SHA と現在の landing SHA を記録する。マージ前にトランクが再び動いたら、`playbooks/shipping.md` のパッチ ID 規則が再検証を左右する。変更されたパッチには新しい判定が必要である。変更されていないパッチは判定を保持するが、Shipping のステップ 3 に従い、現在の CI とマージ可能性が通った後で新しい `<landing-sha>` を記録する。オーナーは、`<landing-sha>` に結び付けた Shipping のステップ 5 のサーバー強制の expected-head フローを通じてのみ自分の PR を取り込む。PR 番号だけのマージや、ガードのない自動マージは決して使わない。その後オーナーはキューから次の自己完結した項目を取る。オペレーターの完全自律の付与とルートのクリーンな判定の組み合わせが、babysit だけでは決して得られないマージ権限である。オペレーターが名指しした項目はマージ可能で止まり、オペレーターのクリックを待つ。
6. **ルート層を運用する。** 固定されたゲートや予算値（CI が厳しくする方向にしか変更を許さない上限）の本当に新しい引き上げには、自分の新たな副署が必要であり、検証器の証明の後にのみ与える。すでに main に取り込まれた値を吸収することはドリフトであり、引き上げではない。全オーナーに対する監査ティックをおよそ 30 分ごとに実行する。ティックは観測の周期であり、決してリース、締め切り、キャンセルのしきい値ではない。各ティックはダイナミックモードの本物の `/loop` としてアームし、sleep でブロックするのではなく自分自身のウェイクアップをスケジュールさせる。周期を記憶や失われやすい完了通知に任せることは決してしない。各ティックで、このプレイブックをディスクから再読し（インストール済みプラグイン配下の `skills/poteto-mode/playbooks/autopilot-full.md`）、次に常設目標を再読する。その両方に対して運用を監査する。そのティック中にドリフトを修正し、緊急として扱う。保持しているハンドルを通じて各オーナーを汎用的な生存確認またはステータス確認で調べ、決定の記録を収集する。コミット、push、PR やチェックの差分、保存されたレポート、生きている保持プロセスを証拠として数える。経過時間や新しい副作用がないことだけでは、レーンが停止していることの証明にはならない。実装の実行は 90 分あるいはそれ以上健全に続くことがある。レーンを停止させるのは、死んだプロセス、失敗したハンドル、明示的なエラー、呼び出し側が与えた外部の締め切りといった、失敗の肯定的な証拠がある場合だけである。代替をディスパッチする前に、保持しているハンドルを通じてキャンセルする。マージがまとまって発生したら、レトロパスとマージ後のボットコメントのスイープを実行する。
7. **オペレーターの停止には即座に待機する。** オペレーターの保留や停止は、書き込みゼロの命令としてすべてのオーナーに即座に届く。オーナーは、オペレーターが解放するまで各自のブリーフ（指示書）を保持する。

**返答:** 各 PR のオーナー、状態、ヘッド SHA を含むキュー。各判定とそれを生成した swarm。何がマージされ、各オーナーが次に何を取ったか。与えた副署とその理由。開いているオペレーターのゲート。収集した決定の記録の所在。
