### Autopilot-stack

**スタックの責任は自分にあり、取り込みの責任は決して負わない。完全な自律でキューをビルドして検証し、その後オペレーターに 1 本の線形スタックを渡す。オペレーターはそれを自らレビューして取り込む。** **Autopilot-full** の姉妹プレイブック。

1. **オーナーループを変更せずに実行する。** プログラムにつき 1 回、フォージ（forge）を解決する。GitHub CLI（`gh`）が既定である。`command -v origin` が成功し、Origin がリポジトリを解決できるなら、PR の作成、編集、表示、監視の操作には `origin pr ...` を使う。このプレイブックは決してマージしない。そうでなければ `gh` にとどまり、フォールバックしたことを記録する。フォージが報告したベースリポジトリを `<base-repo>` として記録し、すべての `gh pr` コマンドに `--repo "$base_repo"` を渡す。`<head-remote>`、`<head-url>`、`<base-remote>` は Shipping のステップ 1 に従って個別に解決してバリデーションする。これらのいずれかが `origin` という名前であるとか、ベースとヘッドのリポジトリが同じであるとは決して仮定しない。ヘッドリポジトリがフォークのときは、その同一性をバリデーションし、オーナー名とリポジトリ名を `<fork-owner>` と `<head-name>` として記録する。Graphite（`gt`）を決して必須にしない。PR ごとに 1 つのバックグラウンドサブエージェントが、自身のワークツリーで、その変更を端から端まで担う。ビルド、最初の push、Opening a PR の準備完了規則に従って早期に開く PR、自己証明（ゲート、CI、レシート）、`../references/bugbot-triage.md` に従った懐疑的なレビューボットのトリアージ、スロップ除去（**deslop** スキル、`/deslop`）、`/no-comments`（**no-comments** スキル）、`playbooks/babysit.md` に従ってグリーンになるまで面倒を見ること。作業が自己完結しているならオーナーは並列化する。約 15 分以内に、すべてのオーナーは **show-me-your-work** スキルに従って `decisions.tsv` の記録を開始し、最初のブランチスナップショットを push し、自己証明の前に PR を開く。リポジトリの指示により、必要な証拠が記録されるまで早期の PR をドラフトのままにしてもよい。記録はコミットせずに保ち、レポートに含めて返す。
2. **ウェイクチェーンで監査する。** ルートはおよそ 30 分ごとに監査ティックを実行する。ティックは観測の周期であり、決してリース、締め切り、キャンセルのしきい値ではない。各ティックはダイナミックモードの本物の `/loop` としてアームし、sleep でブロックするのではなく自分自身のウェイクアップをスケジュールさせる。周期を記憶や失われやすい完了通知に任せることは決してしない。各ティックで、このプレイブックをディスクから再読し（インストール済みプラグイン配下の `skills/poteto-mode/playbooks/autopilot-stack.md`）、次に常設目標を再読する。その両方に対して運用を監査する。そのティック中にドリフトを修正し、緊急として扱う。保持しているハンドルを通じて各オーナーを汎用的な生存確認またはステータス確認で調べる。コミット、push、PR やチェックの差分、保存されたレポート、生きている保持プロセスを証拠として数える。経過時間や新しい副作用がないことだけでは、レーンが停止していることの証明にはならない。実装の実行は 90 分あるいはそれ以上健全に続くことがある。レーンを停止させるのは、死んだプロセス、失敗したハンドル、明示的なエラー、呼び出し側が与えた外部の締め切りといった、失敗の肯定的な証拠がある場合だけである。代替をディスパッチする前に、保持しているハンドルを通じてキャンセルする。
3. **オペレーターのゲートを守る。** 述べてから待つ（state-then-wait）ので、計画を述べる要求は実行許可（go）ではない。オペレーターの明示的な実行許可が出たら、プログラム目標の全文を常設指示に書き込み、自分の TODO リストにも言い直す。Claude Code には `/goal` コマンドがないからだ。その目標はチェーンが終わるまでターンをまたいで有効である。オペレーターの停止で、すべてのオーナーは即座に書き込みゼロの待機に入る。
4. **STACK-READY で検証する。** オーナーは正確なヘッド SHA とともに STACK-READY を報告する。ルートはその SHA を swarm 検証する。**swarm** スキルに従ったファンアウトで、その SHA でゲートを再実行する並列の独立した検証器、要となる振る舞いに対するライブ実行時の最低ライン、PR 本文を信用しないレシートと差分の監査を行う。swarm は 1 つの判定に集約する。指摘はオーナーへ戻し、未検証のものは何もスタックに入らない。
5. **クリーンな判定で追加し、決して出荷しない。** どのオーナーもマージ、自動マージのアーム、クローズをしない。クリーンな判定が出たら、その PR を 1 つの凍結された下から上へのリストに、検証順またはオペレーターが指定した順序で追加する。同一リポジトリのヘッドについては、フォージのベースブランチのチェーンもその順序を記録する。フォークのヘッドについては、すべての PR がトランクを対象にするので、それらの等しいベースブランチからスタックの順序を決して推測しない。
6. **トポロジーの書き手は 1 人、ビルドの書き手は並列。** オーナーは自分のブランチだけを push し、先端、現在のパッチベース、意図する親を報告する。ルートが唯一のトポロジーの書き手である。既存の PR を rebase、force-push、またはリターゲットする前に、ルートはその PR とすべての子孫に Shipping のステップ 4 の解除して確認する規則を適用し、フォージがすべてのリクエストが解除済みであると確認できなければ止まる。トランクは `<base-remote>` 経由で取得する。別のスタックブランチは `<head-url>` 経由で直接取得する。`<head-remote>` は fetch URL がベースリポジトリで push URL がフォークである可能性があるからだ。選んだリポジトリの同一性をアクティブなフォージを通じてバリデーションし、取得したターゲットを `<parent-tip>` として記録する。rebase の前に、子ブランチの公開済み SHA を `git ls-remote -- "$head_url" "refs/heads/$branch"` で `<captured-sha>` として記録し、ローカルの rebase 前の先端と等しいことを要求する。`git merge-base --is-ancestor "$current_base_sha" "refs/heads/$branch"` が通ることを要求する。親が変わったときは、`git rebase --onto "$parent_tip" "$current_base_sha" -- "$branch"` で子のコミットだけを移動し、次に `<parent-tip>` を子の新しいパッチベースとして記録する。`git push --force-with-lease="refs/heads/$branch:$captured_sha" -- "$head_url" "HEAD:refs/heads/$branch"` で公開する。ヘッドとベースのリポジトリが同じときは、親ブランチをベースにして子 PR を作成またはリターゲットする。解決したフォージと操作に応じて、`origin pr create --status open --base "$parent_branch"`、`gh pr create --base "$parent_branch" --repo "$base_repo"`、`origin pr edit "$pr" --base "$parent_branch"`、または `gh pr edit "$pr" --base "$parent_branch" --repo "$base_repo"` を使う。ヘッドリポジトリがフォークのときは、ローカルの子ブランチは親の正確な先端へ rebase した状態を保ちつつ、すべての PR はベースリポジトリの `<trunk>` に対して作成またはリターゲットする。GitHub では、承認済みの PR タイトルと本文を `<title>` と `<body>` として取得し、`gh api --method POST "repos/$base_repo/pulls" -f "title=$title" -f "body=$body" -f "head=$fork_owner:$branch" -f "head_repo=$head_name" -f "base=$trunk" --jq .html_url` で作成する。`-F draft=true` は Opening a PR の準備完了規則がドラフトを要求するときだけ付ける。そうでなければ解決した Origin の同等コマンドを使う。リターゲットは `gh pr edit "$pr" --base "$trunk" --repo "$base_repo"` または解決した Origin の同等コマンドで行う。フォージはフォークにしかない親ブランチを PR のベースとして使えない。チェーンを `gt` 経由で submit や登録することは決してしない。
7. **ドリフトはルートで吸収し、動いたものを再検証する。** ルートは `<base-remote>` 経由で現在のトランクを取得し、ステップ 6 の明示的な旧ベースと新しい親のフローでチェーンを下から上へ rebase する。rebase でオーナーのファイルに競合が出たら、そのオーナーが自分の担当部分を修正し、ルートがステップ 6 の取得済み SHA によるリースのフローで結果を push する。rebase はその上にあるすべての SHA を書き換え、旧 SHA での判定を無効にする。各 PR について、判定 SHA で記録したパッチベースからヘッドまでの差分の安定な `git patch-id` と、新しいパッチベースからヘッドまでの差分のものを比較する。パッチ ID が変わっていなければコードの判定を保持する。変わったパッチは、納品前にステップ 4 をやり直す。パッチ ID が変わっていなくても、書き換えた push のたびにマージ可能性と CI を再実行する。副署の規則は Autopilot-full から変わらない。本当に新しい固定値の引き上げは、ルートの新たな副署のための停止を発生させる。取り込まれた値のドリフトを吸収することは引き上げではない。
8. **チェーンを納品する。** 納品物は、検証済み PR の凍結された下から上への 1 つのリストであり、解決したフォージでレビューでき、各リンクは検証器の判定を PR 本文またはコメントに持つ。同一リポジトリのヘッドはベースブランチのチェーンを使う。フォークのヘッドはローカルの親の系譜を保持しつつ、すべての PR はトランクを対象にする。オペレーターは現在の最下段の PR だけを Shipping に送り、1 つずつ進める。merge-when-ready の要求は、Shipping がすべての子孫を解除して確認した後の、その最下段にだけ適用される。チェーン全体や子孫に対して merge-when-ready を提案したりアームしたりすることは決してしない。

**autopilot の選び方。** PR が独立しており取り込み権限が与えられているなら Autopilot-full。オペレーターが取り込み前にレビューを望む、作業が順序付きまたは結合している、あるいはマージ権限が与えられていないなら Autopilot-stack。

**返答:** スタックのルートと先端へのリンク、リンクごとの 1 行の判定要約、保留または除外したものとその理由。
