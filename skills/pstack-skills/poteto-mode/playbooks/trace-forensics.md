### Trace forensics

**成果物からの診断の責任は自分にある。読み込み、形を整え、原因へ絞り込み、ソースに帰属させる。**

生きているプロセスを計装する **Runtime forensics** とは別物である。ここでは取得済みのデータがすでに存在する。成果物は固定されたデータセットであり、読むものであって再実行するものではない。プレイブックの移植性を保つためにツールは汎用的にする。cpuprofile と `.json.gz` には DevTools またはトレースパーサー、spindump にはテキストエディタ、heapsnapshot には自分のヒープツール。

1. 形式を特定し、正しいツールで読み込む。大きな成果物はサブエージェントでパースし（**principle-guard-the-context-window** スキル）、絞り込んだ指摘をメインスレッドに保つ。
2. 生の成果物をクエリできる形に変換する。トレースやヒープスナップショットを sqlite にダンプし、サンプル、フレーム、またはノードごとに 1 行にする。読む前にクエリ可能な形に到達する。
3. 原因へ絞り込む。最も時間を占めるフレームをクエリし、呼び出しツリーをたどってホットパスへ進む。リークでは、リークしたオブジェクトから GC ルートまでリテイナーチェーンを追う。spindump では、CPU 上で固まっているかブロックされているスレッドと、その待機理由を見つける。
4. ソースに帰属させる。成果物自身のシンボルを通じて、ホットなフレームをファイル、シンボル、行に対応付ける。ソース対応のないフレームはまだ診断ではない。シンボルを解決するか、成果物がそれを持っていないとはっきり言う。
5. 対になる取得データがあるなら、それと照合して確認する。前後の成果物を diff する。ない場合は、指摘を確認済みの原因ではなく、成果物が支持する最有力の仮説として記す。
6. 引用付きの診断を引き渡す。求められない限り修正はしない。原因が分かったら Bug fix または Perf issue へルーティングする。スループットチェックポイントは 1 行にとどめる: `throughput checkpoint: n/a, read-only forensics`。

**返答:** 成果物と形式、絞り込んだ指摘、ソースの位置、成果物のパス、対になる取得データがそれを確認したかどうか。
