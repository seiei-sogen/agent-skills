### Shipping

**取り込まれるものの責任は自分にある。各 PR を独立に検証し、検証済みの連続部分だけをルートから取り込み、その後はキューに手を出さない。**

これは `playbooks/babysit.md` の後の半分である。

1. **フォージ（forge）、リポジトリの同一性、両方の Git リモートを解決する。** GitHub CLI（`gh`）が既定である。`command -v origin` が成功し、Origin がリポジトリを解決できるなら、PR の表示、監視、編集の操作には `origin pr ...` を使う。マージには、ステップ 5 の expected-head の要件が利用できるときだけ使う。そうでなければ `gh` にとどまり、フォールバックしたことを記録する。フォージが報告したベースリポジトリを正規の `<base-repo>` として記録する。GitHub では、それを `<base-owner>` と `<base-name>` に分割し、すべての `gh pr` コマンドに `--repo "$base_repo"` を渡し、2 つの構成要素を GitHub ウォッチャーに渡す。`<head-remote>` は、ブランチに設定された push リモート、`remote.pushDefault`、ブランチのリモート、唯一の曖昧でないリモートの順で解決する。その push URL が PR のヘッドリポジトリを指していることを確認し、その正確な URL を `<head-url>` として記録する。これにより、取得したリモート状態とガード付きの push が同じリポジトリを対象にする。`<base-remote>` は fetch URL を `<base-repo>` と照合して独立に解決し、トランクに使う前にその URL を確認する。push URL がヘッドリポジトリに一致し、fetch URL がベースリポジトリに一致するなら、同じリモート名が両方の役割を担ってもよい。リモート名が 1 つのリポジトリを特定すると仮定するのではなく、各 URL を役割ごとに比較する。解決した値やフォージが報告した値はすべて直接シェル変数に取得する。コマンド例では `"$branch"` や `"$head_url"` のようなクォートした小文字の変数を使う。それらの値をシェルのソースに貼り付けることは決してしない。フォージ名を Git リモートとして推測したり扱ったりすることは決してせず、Graphite（`gt`）を決して必須にしない。
2. **検証の前にキューを凍結して解除する。** 明示的な下から上への PR リストを凍結する。同一リポジトリのスタックは、そのベースブランチのチェーンと照合して確認する。フォークのヘッドについては、すべての PR がトランクを対象にしフォージのベースはスタックを表現しないので、検証済みのローカルの親の系譜から順序を取る。どの検証器を起動する前にも、凍結されたリストのすべての PR をアクティブなフォージで調べ、既存の merge-when-ready や自動マージのリクエストをすべて解除し、各リクエストが解除済みであることを確認する。GitHub では、各 PR を GraphQL で `id`、`headRefOid`、`baseRefName`、`autoMergeRequest`、`mergeQueueEntry` について照会する。`autoMergeRequest` が非 null のときは `gh pr merge "$pr" --disable-auto --repo "$base_repo"` を実行する。`mergeQueueEntry` が非 null のときは、`gh api graphql -F "id=$pr_node_id" -f query='mutation($id:ID!){dequeuePullRequest(input:{id:$id}){mergeQueueEntry{id}}}'` で `dequeuePullRequest` ミューテーションを呼ぶ。このミューテーションはプルリクエストのノード ID を取る。再照会し、`autoMergeRequest` と `mergeQueueEntry` の両方が null であることを要求する。`autoMergeRequest` が null であるだけでは、プルリクエストが解除済みであることの証明にならない。Origin では、報告されたキャンセル操作を使い、個別に報告されるすべてのキュー状態を調べる。アクティブなフォージがリスト全体の解除を確認できないなら止まる。PR ごとに 1 つのサブエージェント（まとめない）が、それぞれ自身のワークツリーで、その PR の親とヘッドを比べて実際のサーフェスを動かす。最下段の PR のパッチベースはトランクである。各子のパッチベースは直前の PR の正確なヘッドであり、フォークの子がフォージ上でトランクを対象にしている場合も同様である。各サブエージェントは `PASS`、`PASS+NOTES`、または `FAIL` を返し、その判定を自身の PR に投稿する。安全とは、コードを書いていないエージェントからの判定を意味する。CI がグリーンであることは判定ではなく、ボットの承認レビューも判定ではない。下から上へ進み、合格の判定がない最初の PR で止まる。ここで `PASS` と `PASS+NOTES` はどちらも合格である。その上限と、チェーンを壊しているものを報告する。
3. **各判定がまだそのパッチを記述していることを再確認する。** 合格の判定で、`<verdict-sha>`、`<verdict-base-sha>`、および `<verdict-base-sha>..<verdict-sha>` の安定な `<verdict-patch-id>` を記録する。`<landing-sha>` と `<landing-base-sha>` をそのヘッドとベースの値で初期化する。フォークの子のパッチベースをフォージのベースで置き換えない。そのフォージのベースはトランクであり、未マージの親を含むからだ。取り込みの前に、アクティブなフォージを通じて現在の公開済みヘッドを `<current-head>` として読み、ローカルブランチの先端がそれに一致することを要求する。`<landing-base-sha>..<current-head>` の安定なパッチ ID を計算し、`<verdict-patch-id>` と比較する。パッチが変わっていたら再検証する。変わっていなければ、コードの判定を保持し、`<landing-sha>` を `<current-head>` に設定し、そのヘッドでマージ可能性と CI を再実行する。パッチが等価な rebase により `<landing-sha>` が `<verdict-sha>` と異なることがある。両方の値を保持する。一致するコミットメッセージや、古い SHA でのグリーンのチェックを代わりに使うことは決してしない。
4. **最下段の PR だけを準備する。** どのブランチやベースに触れる前にも、現在の最下段とすべての子孫をアクティブなフォージで調べる。GitHub では、ステップ 2 の GraphQL 状態照会を繰り返す。非 null の `autoMergeRequest` をそれぞれ無効化し、非 null の `mergeQueueEntry` をそれぞれデキューし、すべてのプルリクエストで両フィールドが null であることを確認する。Origin では、報告されたキャンセル操作を使い、個別に報告されるすべてのキュー状態を調べる。ステップ 2 の後に別のアクターがプルリクエストを再アームした場合に備え、この解除確認を繰り返す。アクティブなフォージがそのセットのすべての PR を解除して確認できないなら、rebase、force-push、リターゲット、アーム、マージのいずれの前でも止まる。`<base-remote>` 経由で現在のトランクを取得し、その正確な先端を `<trunk-tip>` として記録する。検証済みの最下段のブランチを rebase する前に、その公開済み SHA を `git ls-remote -- "$head_url" "refs/heads/$branch"` で記録し、その `<captured-sha>` がローカルの rebase 前の先端と等しいことを要求する。`git merge-base --is-ancestor "$landing_base_sha" "refs/heads/$branch"` が通ることを要求する。`<landing-base-sha>` が `<trunk-tip>` と異なるときは、`git rebase --onto "$trunk_tip" "$landing_base_sha" -- "$branch"` でこの PR のコミットだけを移動し、次に `<landing-base-sha>` を `<trunk-tip>` に設定する。書き換えた履歴は `git push --force-with-lease="refs/heads/$branch:$captured_sha" -- "$head_url" "HEAD:refs/heads/$branch"` で公開する。値なしのリースや単純な force は決して使わない。`origin pr edit "$pr" --base "$trunk"` または `gh pr edit "$pr" --base "$trunk" --repo "$base_repo"` で、その PR だけをトランクへリターゲットする。リターゲットの後は `baseRefName` を再読し、`<trunk>` と等しいことを要求する。`<trunk>` を、コミット値の `<landing-base-sha>` とは別に、`<landing-base-ref>` として記録する。push やリターゲットの後は、ステップ 3 のパッチ比較と現在のヘッドの確認を繰り返す。子孫のリターゲット、アーム、マージはまだ行わない。
5. **現在の landing SHA とベースに照らして、PR を 1 つずつ取り込む。** マージや自動マージのリクエストの直前に、現在の `headRefOid` と `baseRefName` を読む。`headRefOid` が `<landing-sha>` に等しく、`baseRefName` が `<trunk>`、すなわち記録した `<landing-base-ref>` に等しいことを要求する。この読み取りは事前確認であり、ロックではない。すべてのマージ操作には、サーバー強制の expected-head の前提条件が必要である。GitHub のマージは、一致する事前確認の直後に `gh pr merge "$pr" --squash --match-head-commit "$landing_sha" --repo "$base_repo"` で実行する。GitHub にはサーバー強制の expected-base の前提条件がないので、ガードを発明したり GitHub のフローを無効化したりするのではなく、`baseRefName` を監視し続け、ステップ 8 でマージされたベースを検証する。Origin には文書化された expected-head オプションがない。Origin のマージは、アクティブなサーバーがそのガードを報告するときだけ使う。そうでなければ、それを提供する解決可能なフォージへフォールバックするか、マージの前に止まる。要件がまだ実行中で、ユーザーが merge-when-ready を求めたなら、サーバー側の自動マージは、リポジトリに独立した判定のための必須かつ SHA スコープの検証チェックがあり、それがヘッド更新のたびに未達成になる場合だけ使う。GitHub では、一致する事前確認の直後に `gh pr merge "$pr" --squash --auto --match-head-commit "$landing_sha" --repo "$base_repo"` を実行し、ヘッドまたはベースの変更を観測したらそれを解除する。GitHub がマージする代わりにプルリクエストを必須のマージキューに追加したときは、非 null の `mergeQueueEntry` をアーム済みのリクエストとして扱い、ヘッドとベースの両方を監視し続ける。必須の検証チェックがなければ、サーバー側の自動マージをアームするのではなく、ダイナミックな監視を続け、プルリクエストが準備完了になったときにガード付きの即時マージを実行する。次の PR を準備する前に、その PR がマージされるのを待つ。
6. **GitHub の自動マージやマージキューの状態を、スタックの準備完了として読まない。** `autoMergeRequest` は、1 つのプルリクエストに GitHub の自動マージが要求されたことを示す。`mergeQueueEntry` は、1 つのプルリクエストが GitHub のネイティブなマージキューに入ったことを示す。一方のフィールドが null で他方が非 null になりうる。どちらも、Origin の merge-when-ready がアームされていること、子孫がキューに入っていること、パッチの判定が最新であること、連続したスタックが安全であることの証明にはならない。現在の最下段の PR について、両フィールドとアクティブなフォージの状態を確認する。アクティブなフォージが報告できないなら、状態は不明であると言う。
7. **マージのたびに再計算する。** `<base-remote>` 経由でトランクを取得し、マージされた SHA が存在することを確認し、マージされた PR を凍結された下から上へのリストから除き、新しい最下段の PR のヘッド、`<landing-base-sha>`、チェック、パッチ ID を調べる。新しい最下段は、依然として以前の親の正確な先端を `<landing-base-sha>` として記録している。ステップ 4 が旧親のコミットを落とす前に、その値をフォージのベースで置き換えない。ホストが子を自動的にリターゲットすることもあるが、そうしたと仮定しない。その 1 つの PR についてステップ 3 から 6 を繰り返す。独立した作業はこのチェーンの外に置き、単独で出荷する。
8. **現在のフロンティアがマージまたは失敗するまで監視する。その周囲でキューを変更しない。** Origin では、`origin pr view "$pr" --checks --comments` と `origin pr checks "$pr" --watch` を使い、その後、マージ済みまたはブロックと報告されるまで、現在のバージョンのヘッド SHA、ベースブランチ、自動マージ状態、マージキュー状態、プルリクエストを再読する。GitHub では、インストール済みプラグイン配下で `skills/poteto-mode/scripts/watch-pr/watch-pr --owner "$base_owner" --repo "$base_name" --queued-stack --stack-prs "$bottom"` を、イベントによるウェイクとしてだけ実行する。ウェイクのたびに `gh pr view "$pr" --json headRefOid,baseRefName,state,mergedAt,mergeStateStatus,statusCheckRollup,autoMergeRequest --repo "$base_repo"` でポーリングし、ステップ 2 の GraphQL 状態照会を実行して `mergeQueueEntry` を読む。チェック、キューエントリ、マージを受け入れる前に、`headRefOid` が `<landing-sha>` に等しく、`baseRefName` が `<trunk>`、すなわち記録した `<landing-base-ref>` に等しいことを要求する。ヘッドまたはベースが変わったら、非 null の `autoMergeRequest` を無効化し、非 null の `mergeQueueEntry` をデキューし、現在の監視を止め、ステップ 4 を経てステップ 3 へ戻る。変わったパッチは再検証し、安定なパッチ ID が変わっていなくても CI とマージ可能性を再実行する。それらの確認にもかかわらず PR が別のヘッドで、または別のベースへマージされたなら、安全性の失敗を報告し、スタックを続けない。`autoMergeRequest` と `mergeQueueEntry` の両方が null のまま PR がマージ可能になったら、ステップ 5 へ戻ってマージする。`mergedAt` が非 null になるか `state` が `MERGED` になるまで、ステップ 7 を実行しない。`state` が `CLOSED` で `mergedAt` がないとき、または必須チェックが終端の不合格の結論に達したときは、自動マージやマージキューのエントリが保留中かどうかに関係なく、ハードフェイルする。診断の前に、保留中のリクエストをすべて無効化またはデキューする。`UNSTABLE` はそれ自体では失敗ではない。チェックが保留中の間は監視を続け、完了したチェックは必須かどうかで判断する。`mergeStateStatus` が `DIRTY` のとき、または `BEHIND` が取り込みをブロックするときは、保留中のリクエストをすべて無効化またはデキューし、ステップ 4 のガード付き rebase とステップ 3 の再検証へ戻る。自分で解消できない競合では止まる。チェックがまだ保留中、自動マージがアーム済み、またはマージキューのエントリが存在する間の `BLOCKED` は失敗ではない。ここでは Babysit の queued の `WAITING` や `merge-queue` の停止条件を使わない。監視はダイナミックモードの `/loop` の下で保持する。各マージと新しい上限を報告する。キューが停滞したら、変更する前に診断する。
9. **上限で止まる。** 検証済みの連続部分がマージされたら、何が取り込まれたか、次の未検証の PR は何か、それを検証するには何が必要かを報告する。連続部分を延ばすことは、ステップ 1 からの新しいパスである。

**返答:** 検証済みの連続部分とその上限、各 PR の判定とそれを出した者、何をアームしどう確認したか、何が取り込まれたか、次のギャップに何が必要か。
