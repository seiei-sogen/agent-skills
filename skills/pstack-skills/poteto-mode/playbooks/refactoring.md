### Refactoring

**契約の責任は自分にある。構造は変わる。振る舞いは変わらない。** 振る舞いを追加する Feature や、振る舞いを修正する Bug fix とは別物である。

クリーンアップで欠けている機能や本物のバグが見つかったら、それを切り出し、固定した契約に対して構造変更を先に出荷する。再設計は許されるが、それを明言して Feature へルーティングする。大規模または横断的な構造作業は **figure-it-out** スキルの担当である。このプレイブックは焦点の絞られた中規模までの変更を扱う。

1. まず振る舞いの契約を固定する。影響を受けるサブシステムに対して **how** スキルを実行して契約を学び、次に構造を動かす前に、現在の振る舞いを捕捉する特性テスト、スナップショット、または等価性ハーネスを書く。その領域にカバレッジがないなら、構造に触れる前にピンを書く。型チェックとリントはピンではない。
2. **principle-model-the-domain** に従い、コードに欠けている構造を名指す。形がすでに明快で局所的なら、退屈なコードはそのまま残す。形の変更は分岐や無効な状態を削除しなければならず、間接化を追加してはならない。
3. 目標の形を名指す。今日ビルドするならモジュール配置、型、呼び出しグラフがどうあるべきかを述べる（**principle-foundational-thinking**、**principle-redesign-from-first-principles**）。目標が関数の境界をまたぐなら、移動の前に形の並列設計探索のために **architect** スキルを実行する。
4. 追加する前に引く。新しい形を導入する前に、死んだコードを削除し、呼び出し側が 1 つしかないラッパーを畳み、冗長なバリデータを落とし、孤立した参照を取り除く（**principle-subtract-before-you-add**）。目標の形に到達する最小の変更を出荷する（**principle-laziness-protocol**）。「効くかもしれない」投機的なクリーンアップは戻す。
5. 振る舞いを保つ小さなステップで動かし、各ステップでピンをグリーンに保つ。API の形の変更では、すべての呼び出し側を移行し、同じ波で旧 API を削除する（**principle-migrate-callers-then-delete-legacy-apis**）。互換シムなし、新旧の並行経路なし。すべてのリネームを実際のファイルに対して抜き取り確認する。リネームは文字列、文章、逆参照の中の使用箇所を黙って取り逃す。設定済みの refactoring ディスクリプタ（既定は `grok:grok-4.6@xhigh`）を使い、`isolated-write`、専用のワークツリー、具体的なスコープ（ファイルパス、移動する名前、保つべき振る舞い）でプロバイダディスパッチを通じて機械的な編集を委任する。差分は自分でレビューする。
6. 「コンパイルが通る」ではなく、実際の成果物で振る舞いが変わっていないことを証明する（**principle-prove-it-works**）。大きな形の変更では等価性チェックを実行する。新旧の出力を diff するスクリプト、記録したベースラインを新コードに対して再生するもの、またはドライバースキル（CLI と TUI には `run`、UI には `verify`）を通じた一致するサーフェスでのスモーク実行。検証は自分で担う。委任先の「良さそう」という要約を信用しない。
7. 変更が残す価値のあるものか確認する。成功の尺度は読者の負荷の低減である（**principle-minimize-reader-load**）。差分がどこかで読者の負荷を下げていないなら、戻す。
8. 小さく順序付けたコミットに rebase する。引き算のコミット、次に形の変更、次に後続のクリーンアップ。**sequence-verifiable-units** 原則スキルで形を整え、振る舞いを保つ各スライスが次の前にグリーンのままであるようにする。**Opening a PR** を実行する。

**返答:** 変わった構造、それを照らし合わせたピン、等価性の証明、読者の負荷の差分、出荷したものと戻したもの。新しい振る舞いはない。
