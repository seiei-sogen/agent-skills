### Bug fix

**このタスクの責任は自分にある。計画し、レビューし、検証する。** 調査と修正はサブエージェントに委任し、リードにとどまる。

科学的であること。出荷されるコード行はすべて実行時の証拠にたどれる。「効くかもしれない」念のための二重対策は仮説であり、修正ではない。それは出荷しない。証拠が仮説を否定したら、その仮説が動機となった変更を戻す。証拠が正当化する最小の変更だけを出荷し、それ以上は出荷しない。

1. ドライバースキル（CLI と TUI には `run`、UI には `verify`）を通じて、一致するサーフェスで自分で再現する（必須事項）。再現をユーザーに渡さない。ユーザーに聞くよう指示するデバッグや計装のプロトコルは、これを上書きしない。計装したランタイムを自分で駆動する。ユーザーに聞くのは、制御サーフェスがターゲットに届かない具体的な理由を述べた上で、かつ可能な限り駆動し尽くした後だけにする。直接再現しないなら、強制する。トリガーを合成する、条件を厳しくする、発火するまで計装する。
2. 原因を二分探索する。候補の仮説を立て、1 つが残るまで除外する。影響を受けるサブシステムに対する `how` と、リグレッション履歴のための **why** スキルで仮説の種をまく。各パスで、残る問題空間を最も削る分割を取り、実行時の証拠を得て、除外する。プログラムの状態が不明なら、計装やロギングを追加し、コードが動く中でそれを読む。推測しない。長引く、または手強い探索は Claude Code の `loop` スキルで駆動する。ステップ 3 の architect/interrogate のファンアウトの前に、残った*メカニズム*を実行時の証拠で確認する。
3. 修正を計画する。関数の境界をまたぐなら、まず `architect`。設定済みの bug-fix ディスクリプタ（既定は `codex:gpt-5.6-sol@max`）を使い、`isolated-write`、専用のワークツリー、具体的なスコープでプロバイダディスパッチを通じて実装を委任する。差分をレビューする。
4. 同じサーフェスで検証する。元の再現が今は通る。「結論が出ない」や別サーフェスは合格ではない。その旨を明示する。ユニットテストは分岐の振る舞いを示すものであり、バグの不在を示すものではない。
5. 失敗する再現が修正より前に git 履歴に入るようにコミットを構成する。バグに安価なローカルのテスト経路があるときの、失敗するテストを先に書くリズムについては **tdd** スキルを参照する。テストが高価、統合寄り、または不明確なときは省く。
   これは **sequence-verifiable-units** 原則スキルの典型例であり、失敗するテストが先で、修正がその上に乗る。
6. **Opening a PR** を実行する。

調査は `how` と `why` を並列のサブエージェントとしてファンアウトする。

**返答:** 何が壊れていたか、根本原因、修正、どう検証したか。決定的な失敗出力と成功出力を、アサーションと件数に絞って引用する。
