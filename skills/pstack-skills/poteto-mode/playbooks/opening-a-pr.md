### Opening a PR

他のすべてのプレイブックの最後に呼び出される。

**ワークツリー。** main から切った git ワークツリーで作業する。サブエージェントはそれを引き継ぐ。同じブランチに対する複数の `Agent` 呼び出しは、それぞれ自分のワークツリーを持つ。1 つのブランチを複数のワークツリーで使い回すには、**Shipping** のステップ 1 で `<head-url>` を解決してバリデーションし、`head_url` として保持し、ワークツリー間で `git fetch -- "$head_url" "refs/heads/$branch" && git reset --hard FETCH_HEAD` を実行する。無関係な作業で汚れたブランチは、パッチとして取り出し、新しいワークツリーを作り、適用する。もつれたワークツリーは、main からリセットし、最小限やり直す。

**コミット。** こまめにコミットする。PR を開く前に、小さく順序付けられたコミットに rebase で整える。各コミットは将来の PR である。取り込み可能で、経緯を語る順序に並ぶ。修正が直前のコミットに属するなら amend する。分離できるなら新しいコミットにする。

**PR。** コミット前に差分へ `/deslop` をかける。レビュー前に `/no-comments` を実行する。すべての PR タイトル、PR 説明、コミット本文を `/technical-writing` で書き、次に `/unslop` を適用する。Diátaxis を除くすべての technical-writing の層を適用する。各アクションに 1 語を使い、冠詞を保ち、素の動詞で足りるときは `-ing` を避ける。

**タイトル。** `type(scope): subject` の形の Conventional Commits を使う。type には `feat`、`fix`、`docs`、`refactor`、`test`、`chore`、`perf` のいずれかを使う。scope には `pstack` や `poteto-mode` のような変更した領域を使う。subject は短く命令形に保つ。変更を担う実在のシンボルがあればそれを名指しする。例: `fix(pstack): retarget opening-a-pr babysit trigger`。末尾にピリオドを付けない。

**説明。** PR 本文はブリーフィングであり、実験ノートではない。差分を手にしたレビュアーが、なぜこの変更が存在するのか、何がスコープ外か、変更が動くことをどう証明したかを読み取れなければならない。squash コミットの本文は PR 本文である。

次のセクションをこの順で使う。述べることがないセクションは省く。

- `## Why`。意図と方針を 1 つか 2 つの短い段落で述べる。SHA や rebase の系譜を列挙しない。「main を基にした」という前置きを付けない。
- `## Scope`。実在のシンボルとパスを箇条書きで列挙する。リネームやリターゲットは両側を名指しする。何が含まれ何が含まれないかは、境界が重要なときにだけ述べる。ファイルごとの長文を書かない。
- `## Tradeoffs`。書かなければレビュアーが尋ねてくるであろう、却下した代替案だけを挙げる。実質的な選択がなかったときはこのセクションを省く。
- `## Blast Radius`。1 文から 3 文で、変更が誰または何に触れるか、なぜ安全または危険かを述べる。修正なしで main がレッドのままなら継続的にかかるコストを述べる。
- `## Verification`。実際に実行した各経路とその結果を挙げる。パフォーマンス変更では、主要な数値 1 つを単位付きで `before → after` の形で報告する。残りの証拠は arena または swarm のディレクトリへリンクする。サンプルサイズの方法論、swarm の詳細な羅列、メトリクスの表は含めない。

これらのセクションの後に、主張を証明する動画やスクリーンショットがあれば添付する。完全な SHA、swarm や arena のレーンの羅列、てこの修正についての長文、ファイルごとのチェックリスト、「CLEAN」判定は貼り付けない。これらの詳細はリンク先の成果物に置く。`## Summary` や `## Test plan` の定型文を使わない。コミット本文はその subject を繰り返さない。

**フォージ。** 最初の PR 操作の前にフォージ（forge）を決め、作成、編集、閲覧、監視、マージを通してその選択を維持する。GitHub CLI（`gh`）が既定である。`command -v origin` が成功し、Origin がリポジトリを解決できるなら、`origin pr ...` を優先する。Origin がないか、リポジトリを解決できないなら、`gh` にとどまり、フォールバックしたことを記録する。意図する PR のベースリポジトリを正規の `<base-repo>` として記録し、有効なフォージを通してバリデーションする。チェックアウトの既定リモートから推測しない。シェル変数として保持し、すべての `gh pr` コマンドに `--repo "$base_repo"` を渡す。ヘッドリポジトリがフォークなら、その同一性をバリデーションし、所有者とリポジトリ名を `<fork-owner>` と `<head-name>` として記録する。Graphite（`gt`）を必須にしない。

**サイズとスタック。** 1 つの大きな PR より、5 つの狭い PR を優先する。各子ブランチを親の正確な先端に rebase し、下から上への順序を凍結する。ヘッドリポジトリとベースリポジトリが同じなら、ベースブランチのチェーンを作る。ルート PR はトランクを対象とし、各子 PR は親ブランチを対象とする。同一リポジトリの子は、決めたフォージに応じて `origin pr create --status open --base "$parent_branch"` または `gh pr create --base "$parent_branch" --repo "$base_repo"` で作る。ヘッドリポジトリがフォークなら、スタックされたローカルブランチは親の系譜を保ちつつ、すべての PR はベースリポジトリのトランクを対象とする。フォークの PR はすべて、決めた Origin のコマンドで作る。GitHub では、承認された PR のタイトルと本文を `<title>` と `<body>` として保持し、`gh api --method POST "repos/$base_repo/pulls" -f "title=$title" -f "body=$body" -f "head=$fork_owner:$branch" -f "head_repo=$head_name" -f "base=$trunk" --jq .html_url` を実行する。`-F draft=true` は、準備完了の規則がドラフトを要求するときにだけ加える。フォークにしかない親ブランチは PR のベースになれない。既存の子を rebase、force-push、リターゲットする前に、**Shipping** のステップ 4 の解除して確認する（disarm-and-confirm）規則を、その子とすべての子孫に適用する。同一リポジトリの子は `origin pr edit "$pr" --base "$parent_branch"` または `gh pr edit "$pr" --base "$parent_branch" --repo "$base_repo"` でリターゲットする。フォークの子は、決めた Origin のコマンドまたは `gh pr edit "$pr" --base "$trunk" --repo "$base_repo"` でリターゲットする。トランクから分岐するのは独立した作業だけにする。本格的なスタック作業の前にトランクへ rebase する。

**準備完了。** 各 PR は既定で準備完了（ready）の状態で開く。Origin では `--status open` を渡す。GitHub CLI の create コマンドでは `--draft` を省き、`--repo "$base_repo"` を渡す。上記の GitHub のフォーク API では `draft` フィールドを省く。リポジトリの指示が、名指しされた証拠が揃うまでドラフトを要求するなら、早期の PR はドラフトのままにし、その証拠を記録した後にだけ準備完了にする。GitHub では、CLI の create コマンドに `--draft` を、またはフォーク API に `-F draft=true` を渡し、後で `gh pr ready "$pr" --repo "$base_repo"` を実行する。Origin が有効なときは、Origin が文書化しているドラフトと準備完了の操作を使う。ドラフトの規則が何も当てはまらないのにツールが PR をドラフトで開いた場合は、決めたフォージに応じて `origin pr ready "$pr"` または `gh pr ready "$pr" --repo "$base_repo"` を実行する。PR の状態に言及する前に、`origin pr view "$pr"` または `gh pr view "$pr" --repo "$base_repo"` を実行する。

**Babysit.** PR を開いても、面倒を見る作業は始まらない。URL を投稿し、構築を続ける。フェーズまたはスタックを先に終える。別個に面倒を見るパスを実行するのは、スタック全体が揃った後にユーザーがそれを求めたときだけにし、`babysit.md` に従う。新しい PR ごとに面倒を見ると、構築が停滞し、後のウェーブがやり直すコミットにチェックを費やすことになる。フィードバックが意図からずれたら反論する。

PR を開くサブエージェントは `interrogate`、`/deslop`、`/no-comments` を実行する。URL を返し、面倒は見ない。親に戻る。
