### Orchestrate

**自分が責任を持つのはプログラムであり、コードでは決してない。ブリーフを書き、キューをドレインし、フロンティアをグリーンに保ち、決断する。** 1 つの常設コーディネーターチャットに引き渡されたプロジェクト全体のためのものである。複数日にわたり、多数のスタックされた PR があり、数十から数百のサブエージェントが動き、人間は 5 分ごとではなく 1 日 2 回確認しに来る。1 つのタスクを完了条件まで駒を進めるのは Autonomous run である。特注のワークフローを必要とする 1 回の野心的な実行は figure-it-out である。作業がどの単一エージェントの寿命をも超えるとき、ここにルーティングする。1 つのエージェントがセッションの予算内で終えられる作業はプログラムではない。

手続きの重さはプログラムの規模に合わせなければならない。安価でほぼ同一のユニットでは、各セクションの指示どおりに手続きを畳む。

3 つの規則が残りすべてを支える。

- 完了はキューのイベントであり、割り込みではない。
- すべてのスポーンとすべてのレジュームは、常設命令（standing orders）を原文どおりに携える。
- ブリーフ（brief）が製品である。曖昧なブリーフは静かに失敗する。ワーカーはこちらに質問できないからである。

#### ロールと配置

- **コーディネーター（このチャット）。** 枠組みを定め、ブリーフを書き、インボックスをドレインし、人間向けの報告に責任を持ち、判断を下す。コードを書いたり編集したりは決してしない。競合したマージ、リスタック、コード変更は常にタスクである。検証済みユニットを機械的に取り込むこと（ワーカーのコミットの fast-forward または競合のない cherry-pick と、その後の push）は、ローカル git が安価なリポジトリではコーディネーター自身が行ってよい帳簿作業である。完了した作業を手持ち無沙汰なスタッカーの後ろに並べると、締め切りまでに何も収穫できなくなる。ループは端から端までエージェント的である。エージェントのスポーン、レジューム、ドレインは `Agent` ツールだけを通して行う。状態の読み書きは、ドレインポイントで `orch` CLI を通して行う。コマンド 1 つを入れ、1 行を得る。CLI は何もスポーンせず、待たず、起こさない。
- **サブコーディネーター。** 永続的で、トラックごとに 1 つ、そしてプログラムが 1 つのコーディネーターのドレインで扱える範囲を超えるときにだけ置く。コーディネーター自身がドレインできるトラックには中間層は不要である。入れ子の層が 1 つ増えるごとに、オリエンテーションの前置きを丸ごと払い直すことになり、ブロッキングなサブコーディネーターは、親が手持ち無沙汰の間その子を隠してしまう。自分のトラックのユニットとボードに責任を持ち、配下のワーカーのブリーフを書き、ランタイムがサブエージェントによるスポーンを許す場合は自分のワーカーと検証役を自らスポーンする。許さない場合は、同じレビュー分離を保ったまま、自分のトラックのユニットを直接担当する。ウェーブの境界で集計をロールアップする。子の生の報告を決して転送しない。処理中の子の数は、1 回のドレインで処理できる数、およそ 10 に、ローリングウィンドウとして上限を設ける。ブロッキングなバッチにしてはならない。バッチごとに最も遅い子の分のコストがかかるからである。
- **ワーカー / 検証役（verifier）。** バックグラウンドのサブエージェント（`run_in_background: true`）。Claude Code にはリモートのワーカー環境がないため、分離は書き手ごとのワークツリーまたはブランチであり、別マシンではない。実行時の検証は `run` スキル（CLI と TUI）または `verify` スキル（UI）を通して行う。サブエージェントはこのチャットを決して見ないので、そのブリーフには必要なものをインラインで含めるか、リポジトリとストアのパスを示す。より少なく、より広い範囲を担うワーカーを優先する。ワークツリーまたはブランチごとに書き手は 1 つ（principle-separate-before-serializing-shared-state）。ユニットの検証役は、そのワーカーとは別のモデルファミリーで動かす。

深さはコーディネーター、トラック、ワーカーにとどめる。トラックの分割はプロジェクトごとに決める（ビルド、取り込み、検証はよくある切り方であり、必須の形ではない）。ハードコードしたスウォームツリーは試したうえで、硬直しすぎるとして保留になった。

#### ストアのレイアウト

`~/.claude/orchestrate/<project-slug>/` を、リポジトリの外、セッションの外に作る。ストアはこのチャットより長生きしなければならない。プログラムは何日も走り、セッションの再起動は想定内であり（「生存確認と障害」を参照）、ストアがポストモーテムになるからである。セッションのスクラッチパッドは、いかに便利でも候補にならない。セッションスコープで一時的なので、再起動がプログラムの唯一の状態を道連れにしてしまう。すべてのファイルには書き手がちょうど 1 つある。所有者が事実を公開し、読み手が読み取り時に集計する。帳簿作業にはインストール済みプラグイン配下の `bun skills/poteto-mode/scripts/orch/orch.ts` を使う。以下では `orch` と書く。その正規のプレーン TSV と JSON は、CLI なしでも読める状態を保つ。

- `preferences.md` は常設命令の登録簿である。番号付きの行で、1 行に制約 1 つ（モデルの方針、スタックの形と数、検証の基準、禁止パス、エスカレーションの方針）。すべてのスポーンとすべてのレジュームに原文どおり貼り付ける。指示はレジュームをまたぐと減衰し、抜け落ちた 1 つごとに人間のターンが 1 回失われる。同じ指示を繰り返し述べている自分に気づいたら、行動する前にその行を追記する（principle-encode-lessons-in-structure）。
- `overview.md` は永続的な PR と issue の DB である。追記する。イベントごとに丸ごと書き直してはならない。
- `units.tsv` はユニットごとに 1 行を持つ。id、トラック、状態、ブランチ、PR、ヘッド SHA、ブリーフのパス。行はその場で更新する。
- `frontier.json` は計算されたマージフロンティアである。「スタックの安全」に従う。
- `ledger.tsv` は検証台帳である。「検証」に従う。
- `inbox/` は完了ポインタを保持する。`gates.md` は人間向けのゲートを待機させる（質問、選択肢、無回答時の既定）。
- `decisions.tsv` は show-me-your-work スキルによる決定の記録である。
- `status.md` はドレインごとに `units.tsv` と `ledger.tsv` から導出するもので、手で保守してはならない。イベントを語り込むのではなく、表から再生成する。

#### ブリーフ

エージェントへのプロンプトが唯一の製品であり、ずさんなブリーフはツリー全体にわたるスロップへと膨れ上がる。すべてのスポーンはその全部を携える。埋められないフィールドは、まだスコープを定めていないユニットである。

```
GOAL         一文。成果。チャットにアクセスできない第三者が実行できるもの
SCOPE        このユニットが書いてよいパス。書いてはならないパス。専用のワークツリーまたはブランチ
CONTEXT      ファイルと PR へのポインタ。このユニットが依存する上流の報告は全文を貼り付ける。
             ワーカーは兄弟を見られないためである
ACCEPTANCE   チェック可能な基準。1 行に 1 つ
VERIFY       正確なコマンド、またはドライバースキル（CLI と TUI には `run`、UI には
             `verify`）。加えて既知の落とし穴
TIMEBOX      実行時間のおおまかな上限。期限が来たら、走り続けるのではなく部分的な結果を返して止まる
FORBIDDEN    gt 禁止、rebase 禁止、force-push 禁止、スコープ外の修正禁止。加えてユニット固有の禁止事項
REPORT       状態、ブランチ、ヘッド SHA、PR、判定、実際に実行したこと、逸脱、
             提案する後続作業
STANDING     <preferences.md を原文どおり貼り付ける>
```

ブリーフの大きさはユニットに合わせる。コマンド 1 つのユニットでは、テンプレートを 1 段落に畳むが、それでもゴール、スコープ、検証コマンド、報告の形は名指しする。2 行の編集を囲む 4KB の足場は、書くにも従うにも、その編集より高くつく。スポーンは常設命令ファイルをストアのパスで参照してよい。原文どおりの貼り付けは、すべてのレジュームと、単独で成り立たなければならないブリーフのためのものである。

サブコーディネーターのブリーフには、トラックの境界とユニット一覧、スポーンの予算、ドレインの手順、ロールアップの形式（子ごとに名前、状態、PR、ヘッド SHA、判定を 1 行で。加えてトラックの状態とフロンティアの差分）を追加する。

依存関係はコンテキストの中継であり、順序付けだけではない。宣言されていない上流のコンテキストは、ワーカーに推測を強いる。フィールドの欠落はスポーン拒否の条件である。サブコーディネーターごと、ウェーブごとに、ワーカーのブリーフを 1 つ抽出して監査する。監査は抽出元のウェーブと並行して行い、その前に置くゲートにしてはならない。不合格のブリーフはそのトラックを止め、ワーカーだけでなくサブコーディネーターの指示を直す。実行の後半ではブリーフの品質が落ちるからである。ブリーフをレジュームで連鎖させてはならない。スコープを統合して新規にスポーンし直す。

#### 手順

1. **枠組みを定める。** 完了条件（done predicate）を数えられるものとして述べる（「126 ユニットすべてがマージ済みで、それぞれが台帳で `unit-test-verified` 以上として検証済み」）。スコープを定量化する。ユニット数、おおまかな工数、想定されるスタック、実時間の予算。1 つのエージェントがその予算内で終えられるなら、ここで止まり、代わりに Autonomous run を実行する。畳むことは、別の文書の存在に依存してはならない。畳むとは、このセッションで直接作業を行い、役に立つところでは通常のワーカーを使い、検証はインラインで行い、進めながら取り込み、以下のストア、登録簿、パイロットの仕組みは一切使わないことである。取り込みを予算に合わせて計画する。予算のおよそ 70% に達したら、スポーンを止め、検証済みのものを取り込む。トラックはプロジェクトごとに名付ける。異論のある分割や一方通行の扉は、パイロットの前に arena スキルを通す。枠組みは一度だけ提示する。可逆な準備は待たずに進める。
2. **ランタイムを導入する。** `orch init` を実行する。show-me-your-work スキルで決定の記録を開き、スポーンの前に常設命令を書き、`orch frontier set --repo <repo-dir>` で既存の PR から `frontier.json` を初期化する。
3. **パイロット。** 1 つのユニットを経路の端から端まで通す。ブリーフ、ワーカー、検証、スタックへの登録、台帳の行、マージ。パイロットは、ブリーフのテンプレート、検証レシピ、ユニットの大きさの誤りを、50 エージェントではなく 1 エージェントのコストで暴くために存在する。ファンアウトの前に、パイロットの証拠から契約を直す。パイロットの規模はユニットに合わせる。ほぼ同一の安価なユニットからなるプログラムでは、最初のユニットがパイロットであり、検証コマンドをインラインに持つ通常のユニットとして実行し、それが取り込まれた瞬間にファンアウトを始める。専用のパイロットパイプライン（別個の検証役エージェント、監査ゲート）は高価または新奇なユニットの形のためのものであり、直列化したパイロットに暴くべきものが何もないクローンユニットのためのものではない。
4. **スケールする。** 処理中の上限までワーカーをローリングウィンドウでスポーンし、子が終わるごとに補充する。ブロッキングなバッチは、バッチごとに最も遅い子の分を支払う。トラックのサブコーディネーターは、「ロール」にある 1 ドレインの閾値を超えたときにだけスポーンする。ドレインごとに着手可能な作業を再計算する。上流の報告を下流のブリーフに中継する。兄弟間の通信は上方向のみに保つ。抽出したブリーフの監査は抽出元のウェーブと並行して走り、不合格時には現在の補充ではなく次の補充を止める。
5. **ドレインする。** すべてのドレインポイントで、下のキュー規律を実行する。
6. **取り込む。** 取り込みは継続的であり、最終フェーズでは決してない。統合は最初の検証済みユニットから始まり、残りのウェーブと並行して走る。重いリポジトリでは、スタッカーはウェーブ 1 からの常設ロールであり、ユニットが検証されるごとに統合する。ローカル git が安価なリポジトリでは、「ロール」に従ってコーディネーター自身が検証済みユニットを取り込む。スタック上位の作業の前に、フロンティアをグリーンに保つ。「スタックの安全」が支配する。`frontier.json` を進めるのは、マージ時か、新しいヘッド SHA が報告されたときだけにする。
7. **閉じる。** 最後のインボックスをドレインし、スポーンしたすべてのエージェントを終端の行（done、abandoned、zombie-reconciled）に突き合わせ、実際の成果物で完了条件を確認し、取り込まれたすべての PR に現在のヘッド SHA に対する判定があることを確認し、show-me-your-work に従ってクロスモデルレビューを含めて決定の記録を監査し、繰り返し発生した修正を `preferences.md` またはブリーフのテンプレートに書き込む。ストアはそのまま残す。それがポストモーテムである。

#### キューとドレイン

- 完了通知を受けたら、`orch inbox push <agent> <unit> <status> [--report PATH]` を実行し、していた作業に戻る。インラインで深くレビューしてはならない。レビューが必要な完了は検証役ユニットになる。ドレインの中で差分をレビューしてはならない。
- ドレインは 4 つの時点でまとめて行う。クリティカルセクションの終わり、トラックのロールアップ、フロンティア監視の起床（loop スキルでセットし、長いハートビートをフォールバックにする）、人間向け報告の前。各バッチは `orch inbox drain` で始める。ドレイン中の到着は次のドレインまで待たせる。
- 先に終わらせるクリティカルセクション。ブリーフの作成、スタック操作、競合の判断、ゲートの記入、台帳またはフロンティアの更新。
- 各ドレインでは、すべてのポインタを分類し（landed、needs-verify、failed、zombie、noise）、結果の行を `orch unit add`、`orch unit set`、`orch ledger record` で書き、`orch status` を実行し、そのうえで次のウェーブを 1 つのメッセージでスポーンする。
- スポーンしたすべての子を、そのトラックのロールアップで説明する。到着した、スポーンし直した、またはそのスコープを明示的に吸収した、のいずれかである。行方不明の子の作業を黙ってやり直すと、無駄になった支出と、その結果が埋めるはずだったカバレッジの穴の両方が隠れてしまう。
- ドレインのターンは `orch status` の 3 行で終える。状態ごとの件数、変わったこと、開いているゲート。詳細は `status.md` にある。完全な返答の契約はチェックポイントと終了時に適用する。

#### スタックの安全

- フロンティアは計算されたオブジェクトであり、語りでは決してない。マージとスタック変更のたびに `frontier.json` を `gt` から再計算する。リスタックの途中では GitHub のベース参照がずれる一方、gt の追跡情報が正だからである。内容は、順序付きの PR 一覧、ブランチ名、ヘッド SHA、世代番号、未マージの最下位 PR。gt がスタックを知っている場所、通常はスタッカーのクローンで解決する。gt のメタデータが submit を一度も見ていないチェックアウトは PR を報告せず、コマンドは推測するのではなくエラーになる。
- スタックごとにちょうど 1 つのスタッカーだけが `gt` を実行でき、そのスタック内で直列化する。担当者を常設命令に記録する。この規模でのリスタックは遅く、実行する者をブロックするので、専用のユニットを与え、コーディネーターを関わらせない。
- ワーカーは決して rebase せず、決して `gt` を実行しない。ベビーシッターは `playbooks/babysit.md` に従い、スタックごとに 1 つ、不変のフロンティア世代 1 つにスコープを限る。リスタックするのではなく、競合をスタッカーに報告する。
- PR のクローズとリターゲットはスタッカーだけを通して行う。ベース PR を閉じると、その上のすべてのチェーンが孤立する。マージとスタックの外科手術は、他と同じくブリーフを持つユニットである。
- 事後監視役（retro watcher）1 つが、マージ済み PR について、リバート、マージ後の CI 破損、孤立した後続作業を追う。

#### 検証

検証の規模はユニットに合わせる。VERIFY が安価なコマンド 1 つなら、ワーカーがそれを実行して出力を報告し、コーディネーターがレシートを抜き取り検査する。専用の検証役エージェント（ワーカーとは別のモデルファミリー）は、検証が高価であるか、判断を多く要するか、影響範囲が大きいユニットのためのものである。製品のすべてがコマンド 1 つの再実行になる検証役エージェントは、手続きであって検証ではない。

台帳の行は `orch ledger record` で書く。現在の PR とヘッド SHA は `orch ledger check` で確認する。`ledger.tsv` は判定ごとに 1 行、PR 番号とヘッド SHA をキーとし、値は `live-ui-verified | unit-test-verified | type-check-only | verifier-blocked | verifier-failed`。CI のグリーンは判定への入力であり、判定ではない。挙動に関わる作業には `type-check-only` より上が必要である。`verifier-blocked` は合格ではない。環境が回復したらスポーンし直す。`verifier-failed` には修正ユニットを与える。再検証ではない。ワーカーは自己報告してよい。検証役は同じキーでそれを上書きする。新しいヘッド SHA は行を無効にするので、リスタック後に再検証する。「これは検証されたか」に答えるのは台帳であり、記憶でもトランスクリプトでもない。

ユニットは、その出力が取り込まれた瞬間に外部化されるまで完了ではない。実行の最後にまとめて行ってはならない。ワーカーはブランチを push し、検証役は台帳の行を書き、レシートはストアに収まる。1 台の VM にしか存在しない作業は、その VM が死んだ時点で、そもそも完了していなかったことになる。

#### 生存確認と障害

- 様子を見るためにエージェントをレジュームしてはならない。レジュームは待機中のエージェントを再始動させる。読み取り専用で探る。台帳、`units.tsv`、`gh`、push 済みブランチ、バックグラウンドタスク一覧。トランスクリプトの mtime は生存の証拠ではない。
- 無言の死には、インボックスに合成したポストモーテムの行を作る（ユニット、障害モード、最後の証拠、選択肢）。証拠が届くごとに計画を練り直す。完全な静止を待ってはならない。
- 障害モード別に再試行する。上限到達または OOM なら、スコープを小さくしてスポーンし直す。ネットワーク切断なら、そのまま再試行する。ツールエラーなら、別のモデルで再試行する。不明なら、一度だけ再試行する。再試行 2 回で、そのユニットを放棄し、それを迂回して計画を練り直す。
- 何時間も遅れて戻ってきたゾンビは、何かを受け入れる前に、現在のフロンティアと台帳に突き合わせる。固有の指摘は新規ユニットを通して救い出す。盲目的なマージは決してしない。
- スポーンを続けるとツリー全体にゴミが生まれる状況（上流の出力の不良、受け入れ基準の破損、インフラの停止）では、常設命令の先頭に停止行を書き、処理中の作業を終わらせ、原因を直し、停止行を消す。
- 自分のインフラ再試行にも、子に課すのと同じ上限を課す。ツールの中断が数回続いたら、再試行を止める。永続的な状態に終端の引き渡しを書き（何が完了したか、どこにあるか、再開する正確なコマンド）、実行を終える。
- セッション再起動後は、処理中だったサブエージェントは死んでいるが、push 済みブランチ、開いている PR、ストアは死んでいない。常設命令と `units.tsv` を読み直し、フロンティアを再計算し、処理中だった作業をエージェント ID ではなく PR とブランチで再接続し、トラックごとに 1 つのサブコーディネーターを保存済みブリーフと現在の状態からスポーンし直し、ドレインし、再開する。死んだセッションのストアロックは次の書き込みで自動的に解除される。`orch` は、保持者の pid が消えたロックを置き換える。

#### エスカレーション

人間に届けるもの（項目ごとではなく、ステータスページにまとめて）。不可逆な操作（共有ブランチへの force-push、デプロイ、削除、他人の PR のクローズ）、どんな実験でも決着しない本物のプロダクト上または好みの判断、観測された現実と矛盾する常設命令、計画の練り直しを経ても残ったプログラムレベルの行き詰まり。尋ねる前にそれぞれを `gates.md` の項目として待機させ、作業はそれを迂回してルーティングする。

人間に決して届けないもの。フロンティアの小さな調整、リスタックの機械的作業、再試行、CI の不安定なテストのトリアージ、レビュースレッドのトリアージ、フォーマット修正、ブリーフがすでに禁じているスコープ（拒否して続行する）、「続けてよいか」。迷ったら、行動して記録する。

実行途中の発見では、フロンティアを塞ぐものだけを直す。それ以外はすべて後続作業に待機させる。このファンアウトの規模では、小さなスコープの漏れが、誰も頼んでいない PR へと増殖する。

**返答:** チェックポイントと終了時に。完了条件と、`units.tsv` と `ledger.tsv` から得たそれに対する件数、トラックと各トラックが取り込んだもの、フロンティア（PR 一覧と SHA）、判定の要約、放棄したものとその理由、人間を待つゲート（唯一の依頼事項）、ストアのパス、決定の記録のパス。数字は表から取り、語りにしない。PR のリンクを含める。
