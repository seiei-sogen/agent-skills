# TypeScript ベストプラクティス

まず **type-system-discipline** 原則スキルを適用する。

| 規則 | 要約 |
|------|---------|
| 判別可能ユニオン | ありえない状態を表現できないように、バリアントを `kind` リテラルの判別子でモデル化する。オプショナルフィールドの寄せ集めにしない。 |
| ブランド型 | 混同できないように、プリミティブに `& { readonly __brand: "X" }` でブランドを付ける。境界で一度だけバリデーションする。 |
| 構成的モデリング | 不正な値を構築できないように形を組み立てる。非空には `[T, ...T[]]`、偶数長には `[T, T][]`、範囲には `start` と `duration`。実行時ガードでもなく、篩型（refinement types）への願望でもない。 |
| 最もシンプルな全域型 | それに対するすべての操作が全域である限り `T[]` のままにする。緩い型が `!`、キャスト、または「起こりえないはず」の throw を強いる場所でだけ `NonEmpty<T>` に強める。 |
| `any` より `unknown` | 外部データは `unknown` である。 |
| ガードより先にスキーマ | プロパティごとの型ガードを手書きする前に、リポジトリの実行時スキーマライブラリを使い、`z.infer` のようにスキーマから型を推論する。 |
| `as` キャスト禁止 | すべての `as` は実行時クラッシュの予備軍である。バリデーションの後にだけキャストする。 |
| 絞り込みの階層 | 判別子の switch > `in` 演算子 > `typeof`/`instanceof` > ユーザー定義型ガード > `as`。 |
| 型ガード | 主張を検証しなければならない。嘘をつくガードは `as` より悪い。安全だと言う名前の背後にバグが隠れるからである。`isX` または `hasX` と名付ける。 |
| 網羅性 | 新しいバリアントが追加されたときにコンパイラがエラーを出すように、default 節に `const _exhaustive: never = x;` をインラインで書く。 |
| `as` より `satisfies` | リテラル型を広げずに値をバリデーションする。 |
| 境界バリデーション | データが入ってくる場所で、名前付きのドメイン型へパースする。`Record<string, unknown>`（書き方を問わず）はそのパースで止まる。内部では型を信頼する。**boundary-discipline** 原則スキルを参照。 |
| スキーマ由来の型 | 新しい interface を宣言する前に `Pick`/`Omit`/`Parameters`/`ReturnType`/`Awaited`/`typeof` をまず使う。 |
| オブジェクト引数 | 引数の順序が自己文書化されるように、位置引数ではなくオブジェクトを渡す。ホットパス（フレームごとのレンダリング、トークナイザ、パーサ）では省く。 |
| 本物のテスト | 実行できるものをモックしない。リーク / disposable チェック付きのフレームワークの本物のテストプリミティブを優先し、UI は実行中のビルドで検証する。ローカルで実行できないものだけをモックする。 |
| 構造化テレメトリ | id からデバッグできるだけの文脈を持つ、構造化ロガーの診断情報を優先する。出荷されるコードに `console.log` を置かない。 |
