# TDD によるバグ修正

明確で安価なテストの道筋があるバグを修正するときは、本番コードを変更する前に、壊れた振る舞いを実行可能にする。目標は、修正前に失敗し修正後に通る、焦点の絞られたリグレッションテストである。

現実的でないときにテストを無理に作らない。利用できるテストが広範なハーネスの準備、壊れやすいモック、遅いエンドツーエンドの基盤、本番限定の状態、曖昧な再現手順、または大量の無関係なフィクスチャの変更を必要とするなら、新しいテストの追加は見送り、最も近い有用な検証を代わりに使う。

## ワークフロー

1. **バグを理解する。** 意図された振る舞い、現在の振る舞い、影響を受ける経路、観察可能な最小の再現を特定する。
2. **最も狭い実行可能なチェックを選ぶ。** そのコードパスにすでに使われている、最も近いユニット、コンポーネント、統合、またはリグレッションのテストを優先する。現実的なテストの道筋が明らかでないなら、ワークフローを満たすためだけにゼロから作らない。
3. **まず失敗するテストを書く。** そのバグを捕まえられたはずの、最小で焦点の絞られたテストを追加する。テストは意図された振る舞いを表現するものであり、現在の実装を写し取るものではない。
4. **修正する前に新しいテストを実行する。** 意図した理由で失敗することを確認する。通ってしまう、または無関係な理由で失敗する場合は、実装を編集する前にテストまたは再現を直す。
5. **バグを修正する。** 近隣の契約を保ちつつ、意図された振る舞いを満たす最小の本番コード変更を行う。
6. **リグレッションテストを再実行する。** テストが今度は通ることを確認する。
7. **近隣のバリデーションを実行する。** 変更がより広いリスクを持つときは、関連する隣接テスト、型チェック、リント、またはシナリオチェックを実行する。

## 失敗するテストが現実的でない場合

リグレッションのステップを黙って飛ばしてはならない。修正する前に、失敗するテストが不可能である、またはコストに見合わない理由を明示的に説明し、その後利用できる最も近い実行可能なリグレッションチェックを選ぶ。例としては、対象を絞ったスクリプト、手動の再現コマンド、ブラウザ自動化、スナップショット比較、ログのアサーション、焦点を絞った統合チェックがある。

悪いテストよりも、新しいテストなしを優先する。悪いテストとは、主にモックをテストするもの、現在の実装の詳細を固定するもの、タイミングや無関係なグローバル状態に依存するもの、小さな修正のために高コストな基盤を必要とするもの、または修正を証明した直後に削除されるであろうものである。

## ガードレール

- 誤った実装に合わせるためだけにテストを変更しない。
- 期待される振る舞いが本当に変わっていて、かつその理由が明確である場合を除き、既存のアサーションを弱めない。
- リグレッションテストの焦点をバグに絞る。広範なフィクスチャの変更や無関係なカバレッジの拡大を避ける。
- 現実的なシグナルが弱いときはテストを追加しない。手動またはスクリプトによる検証を使い、その理由を言う。
- バグが不安定（flaky）なら、可能なところではテストを決定的にし、固定しようとしているシグナルを文書化する。
- バグがより広い種類の失敗を露わにしたなら、まず焦点の絞られたリグレッションの経路を取り込み、その後に同類のケースへのカバレッジ追加を検討する。

## 最終返答

結果だけでなく証拠を報告する:

- 修正前に失敗したテストまたは実行可能なチェックと、それが出した失敗を名指しする。
- 修正後に通ったテストの実行と、実施した近隣のバリデーションを名指しする。
- 修正前に失敗する証拠を示せなかった場合は、その理由を述べ、代わりに使った最も近いリグレッションチェックを記述する。
