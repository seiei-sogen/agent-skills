# Recall

**作業を開始または再開する前に、ユーザーの最近の作業コンテキストを再構築し、今どこまで進んでいて次に何をすべきかの引き締まったカプセルを返す。**

引き締めて、話題から外れないようにする。スコープ内のスレッドに必要なものだけを読み、そこで止める。

コンテキストは 2 つの記録に存在する。自分のチャット履歴には、自分が何をし、何を決めたかがある。共有記録には、同じコードの周りで別の名前のもとに起きたすべてがある: ユーザーが繰り返し報告している症状、出荷されてリバートされた修正、本番でまだ発生しているエラー。この 2 つ目の記録こそ、**why** スキルがソース管理、issue トラッカー、チャットと issue のチャンネル、長文ドキュメント、エラートラッキングを横断して検索するものである。長いバグの尾を引く機能は、その物語の大半をそこに残しているので、自分のトランスクリプトだけから再構築しない。

トランスクリプトは `~/.claude/projects/<encoded-cwd>/<uuid>.jsonl` にある。`<encoded-cwd>` はワークスペースのパスから先頭のスラッシュを落とし、各「/」を「-」に変えたものである（つまり `/Users/you/proj` は `-Users-you-proj` になる）。各行が 1 つのチャットメッセージである。

1. 分類してから振り分ける。再開すべき特定の過去チャットが 1 つあるなら、それは `session-pickup` プレイブックであって、これではない。習慣を永続的なスキルにするのは `automate-me` である。人間が読む作業の要約は別のタスクである。Recall は行動する前に、最近の複数チャットにまたがる作業コンテキストを読み込む。ユーザーがすでに完全な状態カプセル（パス、ブランチ、変更内容）を渡しているなら、それを使い、掘り起こしは省く。
2. 検索する前にスコープを固定する。期間（「最近」は実際の範囲であり、デフォルトは過去 7 日間）、名指しされていればトピック、ワークスペース（デフォルトはアクティブなもの。求められずに他のプロジェクトのトランスクリプトを読んではならない）を固定する。スコープを述べ返す。「すべて」を黙って「最近の N 件」に変えてはならない。
3. 自分のチャット履歴にファンアウトする。高速で安価なモデルで並列サブエージェントを起動し、それぞれにコーパスの一部を担当させる。すべてのサブエージェントに、候補を UUID 名ではなく実際の更新時刻（`ls -t`）で並べること、まずトピックを grep してから一致するチャットだけを、それも関連する範囲だけを読むこと、現在のチャットと明らかなノイズ（サブエージェント、評価（eval）、テストのチャット）を飛ばすことを指示する。各サブエージェントは同じスキーマで、チャットごとに 1 ブロックを返す: トピック、ユーザーの目標、決定、未解決のスレッド、苦戦と軌道修正、成果物（PR、チケット、ブランチ）。それぞれにチャットの UUID を引用する。チャットが 1 つか 2 つなら、ファンアウトを省いて直接検索する。生のトランスクリプトはサブエージェントの中に留める。メインスレッドはその発見事項だけを受け取る。
4. トピックが機能、ファイル、サブシステム、領域、バグを名指ししているときは必ず共有記録を掃引する。これはデフォルトであって判断事項ではなく、「X に関する自分の作業」もその例外にはならない。**why** スキルのソース調査役に引き渡すが、その問いを「なぜこう作られたのか」から「現状はどうか、何が試されて定着しなかったか、ユーザーはまだ何を報告しているか」へ向け直す。そのソース別プレイブックを再利用し、調査役をチャット履歴の掘り起こしと並列に走らせ、その姿勢を引き継ぐ: ソースごとに調査役 1 つ、結果なしも発見事項である、利用できない MCP は飛ばしてそう言う。戻ってきたものをブリーフに織り込む。このステップを省くのは、名指しの対象がない純粋な活動の想起（「今週自分は何をしたか」）だけで、そこでは自分の履歴とライブ状態が答えのすべてになる。
5. ライブ状態と照合して検証する。掘り起こしと掃引で浮かび上がった PR、ブランチ、チケットを `git` と `gh` で確認する。答えがエージェントの実際の行動（実行したツール、読んだファイル、遭遇したエラー）にかかっているときは、切り詰められたローカルコピーではなく完全なトランスクリプトを読む。
6. 下の契約に従ってブリーフを書く。スレッドごとにまとめる。名指しされたトピックから外れない。

## 出力契約

カプセルを先頭に、次にスレッドの状況、次に問題、最後に次の一手。それより深い詳細は下に置くか、削る。

- **カプセル。** 最大 5 項目。この作業は何で、全体としてどこまで進んでいるか。
- **スレッド。** 各 1 行、先頭にちょうど 1 つの状態タグを付ける: `[merged #N]`、`[open PR #N]`、`[in flight <branch>]`、`[verified, uncommitted]`、`[reverted #N]`、または `[planned, not started]`。タグのないスレッドはまだ完了していないので、タグを付ける。
- **問題。** 最大 5 つ、繰り返し起きているもの。ユーザーが繰り返し報告している症状と、出荷されてリバートされた修正を含め、次の試みが前回の失敗地点から始められるようにする。
- **次の一手。** 最も有用な次の行動を 1 つ、具体的に。

隣接する機能やチケットは、これをブロックしていない限り含めない。カプセルとスレッドの行が一画面を超えたら、スレッドを削る前に詳細を削る。ブリーフは **unslop** スキルを通して書き、チャットの発見事項は UUID で、共有記録の発見事項はそのソース（PR 番号、チケット ID、チャットのパーマリンク、エラートラッカーの issue）で引用し、公開出力の前に私的なコンテキストを取り除く。

**返答:** 上の契約に従ったブリーフ。
