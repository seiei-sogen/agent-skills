# Test Behavior, Not Implementation

テストはコードをその利用者と同じ方法で呼び出し、利用者が観測する結果または契約をアサートする。内部呼び出しやコピーされた定数についてのアサーションは、その振る舞いを見逃すことがある。

確認方法: テストを残す前に、関連する欠陥を導入し、テストが失敗することを確認する。定義済みの結果が要求される場合、`undefined` を返すことは有用なプローブになりうる。これは、正しい結果が不在であるような否定経路のテストや、関係的な契約のチェックを無効にするものではない。

**理由:** 欠陥に対して失敗できないテストは、CI の時間とレビューの注意を消費し、何も捕まえない。定数の固定は、固定された値が契約の一部でないとき、無害な編集を妨げることがある。

**関連する振る舞いを見逃しうる 5 つの形:**

- **弱いアサーション、またはアサーションなし。** `expect` がない、または契約のごく一部しか確認しないアサーション。`toBeDefined`、`toBeTruthy`、`toBeInstanceOf`、`toBeGreaterThan(0)` は `undefined` では失敗するが、誤った定義済みの結果を受け入れてしまうことがある。
- **モックまたは不在のみ。** モックが呼ばれたことだけを確認すると、誤ったペイロードを見逃すことがある。`not.toThrow`、`not.toHaveBeenCalled`、`toBeUndefined`、`toEqual([])`、`toHaveLength(0)` のような不在のアサーションは、不在が要求される振る舞いであるときには有用である。誤った存在や副作用がテストを失敗させることを確認する。
- **自己参照。** 同じ欠陥のある経路で計算された期待値は欠陥を隠すことがある。`expect(f(a)).toBe(f(a))`。2 つの実装を比較することは、その比較が関連する不一致を検出するなら、要求される関係のテストとして依然として成立する。
- **定数の固定。** 偶発的な定数を書き写すと、振る舞いをテストせずにリファクタリングを妨げることがある。`expect(LIMITS.maxTools).toBe(8)`。本物の契約を強制するプロンプト、設定、テーブルのチェックは残す。
- **フィクスチャがフィクスチャをアサートする。** アサーションがテストの組み立てたデータを読み、対象は一度も実行されない。`beforeEach` で呼び出された対象でも、アサーションがその結果を観測するなら、テストは成立する。

**修正方法:** テスト本体の中で対象を 1 つの具体的な入力で呼び出し、リテラルの出力または観測可能な効果をアサートする。`expect(slugify("Hello, World!")).toBe("hello-world")`。不在については、否定経路を動かし、誤った存在や副作用が失敗することを証明する。別の肯定経路のテストが対比を与えることもある。偶発的な定数については、それを読む仕組みをテストする。モックについては、ペイロードや観測可能な状態が契約であるなら、それをアサートする。テストを書き直すか削除するのは、関連する振る舞いや契約を何も確認していないときだけにする。

テーブルの行にまたがる関係（2 つのテーブルに存在するキー、存在する親）のテストと、`*.test-d.ts` ファイルのコンパイル時チェックは**残す**。
