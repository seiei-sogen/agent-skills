# Thermo-Nuclear Code Quality Review

このスキルは、実装の質、保守性、抽象化の質、コードベースの健全性に焦点を当てた、並外れて厳格なレビューに使う。

何よりも、このスキルはレビュアーにコード構造について**野心的**であるよう迫るべきである。局所的なクリーンアップの機会を見つけるだけで終わらない。「コード柔道（code judo）」の技を能動的に探す。つまり、振る舞いを保ちながら、実装を劇的にシンプルで、小さく、直接的で、エレガントにする再構成である。

## コアプロンプト

このベースラインから始める。

> 現在のブランチの変更について、深いコード品質監査を行う。
> 振る舞いに影響を与えずにコード品質を意味のある形で改善するために、変更の構造化と実装の方法を再考する。
> 抽象化とモジュール性を改善し、スパゲッティコードを減らし、簡潔さと読みやすさを高めるよう努める。
> 野心的であること。コードベースの一部を再構成することで実装を改善する明確な道があるなら、それを実行する。
> 極めて徹底的かつ厳密であること。二度測って一度で切る。

## 必須の追加基準

上のベースラインプロンプトに加えて、次の明示的なレビュー規則を適用する。

0. **構造的な単純化について野心的であること。**
   - 「これはもう少しきれいにできる」で止まらない。
   - 分岐、ヘルパー、モード、条件分岐、レイヤーの全体が丸ごと消えるように変更を捉え直す機会を探す。
   - 後から見れば必然だったと感じられるコードになる解決策を優先する。
   - 「コード柔道」の技が使えることは多いと想定する。つまり、既存のアーキテクチャをより効果的に使い、変更を劇的にシンプルかつエレガントにする再編成である。
   - 複雑さを並べ替えるのではなく削除する道が見えるなら、その道を強く推す。

1. **PR が非常に強い理由なしにファイルを 1k 行未満から 1k 行超へ押し上げることを許さない。**
   - これは既定で強いコードスメルとして扱う。
   - ファイルを 1000 行超まで肥大化させるのではなく、ヘルパー、サブコンポーネント、モジュール、局所的な抽象化の抽出を優先する。
   - 差分がその閾値を超えるなら、コードを先に分解すべきかどうかを明示的に問う。
   - 説得力のある構造上の理由があり、かつ結果のファイルがなお明確に整理されている場合にだけ、これを免除する。

2. **既存コードへの無秩序なスパゲッティの増殖を許さない。**
   - 新しいアドホックな条件分岐、散在する特殊ケース、無関係なフローに挿入された一回限りの分岐を強く疑う。
   - 変更が「ランダムな場所への奇妙な if 文」を追加しているなら、それをスタイル上の細かい指摘ではなく設計の問題として扱う。
   - 既存のパスを絡ませるのではなく、ロジックを専用の抽象化、ヘルパー、ステートマシン、ポリシーオブジェクト、または別モジュールへ押し出すことを優先する。
   - 技術的には動いていても、周囲のコードを推論しにくくする変更を指摘する。

3. **動くコードをただ受け入れるのではなく、設計をきれいにする方へ傾ける。**
   - 振る舞いを同じに保ちながら構造を意味のある形できれいにできるなら、よりきれいな版を推す。
   - コードベースをより散らかしたままにする「動く」実装に、機械的に承認を与えない。
   - 同じ複雑さを単にまき散らすだけのリファクタリングより、可動部品を丸ごと取り除く単純化を強く優先する。

4. **ハックや魔法のようなコードより、直接的で、退屈で、保守しやすいコードを優先する。**
   - 脆い、アドホックな、または「魔法」のような振る舞いをコード品質の問題として扱う。
   - 単純なデータの形の前提を隠す汎用的な仕組みには懐疑的になる。
   - 明確さを得ることなく間接参照を追加する薄い抽象化、恒等ラッパー、素通しヘルパーにフラグを立てる。

5. **型と境界の清潔さが保守性に影響するときは、それを強く求める。**
   - より明確な型境界がありえるのに、不必要なオプショナル性、`unknown`、`any`、キャストの多いコードがあれば疑問を投げる。
   - 緩い形のアドホックなオブジェクトより、明示的に型付けされたモデルや共有の契約を優先する。
   - 分岐が不明確な不変条件を覆い隠すためにサイレントなフォールバックに依存しているなら、代わりに境界を明示すべきかどうかを問う。

6. **ロジックを正規のレイヤーに置き、既存のヘルパーを再利用する。**
   - 共有パスへ漏れ出す機能ロジックや、API を通して漏れ出す実装の詳細を指摘する。
   - 特注の一回限りのものより、既存の正規のユーティリティやヘルパーを優先する。
   - アーキテクチャのドリフトを常態化させるのではなく、コードを正しいパッケージ、サービス、モジュールへ押し戻す。

7. **よりきれいな構造が明らかな場合、不必要な逐次的オーケストレーションと非アトミックな更新を設計上のスメルとして扱う。**
   - 独立した作業が正当な理由なく直列化されているなら、代わりにフローを並列で実行すべきかどうかを問う。
   - 関連する更新が状態を半分だけ適用された状態にしうるなら、よりアトミックな構造を推す。
   - マイクロ最適化に過度に重きを置かないが、実装をより脆くする避けられるオーケストレーションの複雑さにはフラグを立てる。

## 主要なレビューの問い

意味のあるすべての変更について、次を問う。

- これを劇的にシンプルにする「コード柔道」の技はあるか？
- より少ない概念、分岐、ヘルパーレイヤーで済むように、この変更を捉え直せるか？
- これは局所的なアーキテクチャを改善しているか、悪化させているか？
- より良い抽象化が存在すべき場所に、差分が分岐の複雑さを追加したか？
- 以前は凝集していたモジュールが、より結合し、より状態を持ち、より見渡しにくくなったか？
- このロジックは正しいファイルとレイヤーに置かれているか？
- この変更はファイルやコンポーネントを健全なサイズの境界を超えて拡大させたか？
- 欠けているモデルや欠けているヘルパーを示す、繰り返される条件分岐はあるか？
- 実装は直接的で読みやすいか、それとも特殊ケースと偶発的な制御フローに依存しているか？
- この抽象化は本当に存在価値に見合う働きをしているか、それともただのラッパーか？
- 差分は、本当の不変条件を曖昧にするキャスト、オプショナル性、アドホックなオブジェクトの形を導入したか？
- このロジックは正規のレイヤーに置かれているか、それとも差分が境界を越えて詳細を漏らしたか？
- このオーケストレーションは、必要以上に逐次的、または必要以上に非アトミックか？

## 積極的にフラグを立てるもの

次を見たら指摘をエスカレーションする。

- よりきれいな捉え直しによって複雑さのカテゴリ全体を削除できるのに、複雑な実装になっている。
- コードを移動させるだけで、読者が頭に保持しなければならない概念の数を減らせていないリファクタリング。
- PR によってファイルが 1000 行を超える。特に新しいコードを分割して外へ出せる場合。
- 無関係なコードパスに取り付けられた新しい条件分岐。
- 既存の制御フローを複雑にする一回限りのブール値、null 許容のモード、フラグ。
- 汎用モジュールへ漏れ出す機能固有のロジック。
- 単純な構造を隠し、コードを推論しにくくする汎用的な「魔法」の処理。
- 何も単純化せずに間接参照を追加する薄いラッパーや恒等抽象化。
- 本当の契約を濁す不必要なキャスト、`any`、`unknown`、オプショナル引数。
- ヘルパーを抽出する代わりにコピペされたロジック。
- すでに忙しい関数の途中に実装された狭いエッジケース処理。
- 技術的にはテストを通すが、コードのモジュール性や可読性を下げるリファクタリング。
- 恒久的な負債になる可能性が高い「一時的な」分岐。
- コードベースにすでにその仕事のための正規のユーティリティがあるのに作られた特注のヘルパー。
- もっと中心的な場所に置かれるべきなのに、間違ったレイヤーやパッケージに追加されたロジック。
- 明らかに独立した作業を並列実行すれば、よりシンプルで明確なままでいられるのに、逐次的な非同期フローになっている。
- 状態を必要以上に非アトミックにする部分更新ロジック。

## 推奨される対処

コード品質の問題を特定したら、次のような提案を優先する。

- 間接参照のレイヤーを磨くのではなく、丸ごと削除する。
- 条件分岐が集約されるのではなく消えるように、状態モデルを捉え直す。
- 機能が既存の抽象化の自然な拡張になるように、所有権の境界を変える。
- 特殊ケースのロジックを、例外がより少ないシンプルな既定のフローに変える。
- ヘルパーや純粋関数を抽出する。
- 大きなファイルを、より小さく焦点の定まったモジュールに分割する。
- 機能固有のロジックを専用の抽象化の背後へ移す。
- 条件の連鎖を、型付けされたモデルや明示的なディスパッチャに置き換える。
- オーケストレーションをビジネスロジックから分離する。
- 重複した分岐を、より明確な単一のフローにまとめる。
- API を意味のある形で明確にしないラッパーを削除する。
- ほぼ重複したものを導入するのではなく、既存の正規のヘルパーを再利用する。
- 制御フローがシンプルになるように、型境界をより明示的にする。
- その概念をすでに所有しているパッケージ、モジュール、レイヤーへロジックを移す。
- オーケストレーションも単純化されるなら、独立した作業を並列化する。
- 部分的な状態のほうが推論しにくくなるなら、関連する更新をよりアトミックなフローに再構成する。

本当の問題が構造的であるとき、「これをリネームしてはどうか」程度のフィードバックで満足しない。
はるかにシンプルな案への現実的な道があるなら、同じ散らかった案を単にきれいにした版で満足しない。

## レビューの口調

品質について、直接的で、真剣で、要求の高い態度をとる。
失礼にはならないが、重大な保守性の問題を穏やかな提案に和らげない。
コードがコードベースを散らかしているなら、そうはっきり言う。
実装が劇的な単純化の機会を逃しているなら、それもはっきり言う。

良いフレーズ:

- `これでファイルが 1k 行を超える。先に分解できないか？`
- `これはすでに忙しいフローに特殊ケースの分岐をもう 1 つ追加している。独自の抽象化の背後へ移せないか？`
- `これは動くが、周囲のコードをよりスパゲッティにしている。振る舞いは保って実装を再構成しよう。`
- `これは機能ロジックが共有パスに漏れているように見える。隔離できないか？`
- `この抽象化は不必要に見える。直接的なフローのままにできないか？`
- `なぜここにキャスト / オプショナルが必要なのか？代わりに境界をより明示的にできないか？`
- `これは他の場所にすでにあるものの特注ヘルパーに見える。正規のものを再利用できないか？`
- `ここにはこれをはるかにシンプルにするコード柔道の技があると思う。これらの分岐が消えるように捉え直せないか？`
- `このリファクタリングは複雑さを移動させているが、本当には削除していない。モデル自体をシンプルにする方法はないか？`

## 出力に期待すること

指摘を次の順序で優先する。

1. 構造的なコード品質のリグレッション
2. 劇的な単純化 / コード柔道による再構成の機会の見逃し
3. スパゲッティ / 分岐の複雑さの増加
4. コードを推論しにくくする境界 / 抽象化 / 型契約の問題
5. ファイルサイズと分解に関する懸念
6. モジュール性と抽象化の問題
7. 読みやすさと保守性に関する懸念

より大きな構造的問題があるなら、価値の低い細かい指摘でレビューを溢れさせない。
表面的なメモの長いリストより、確信度の高いコメントを少数出すことを優先する。

## 承認の基準

振る舞いが正しそうだというだけで承認しない。
承認の基準は次のとおり。

- 明確な構造的リグレッションがない
- 実装を劇的にシンプルにする道が見えているのに、その機会を明らかに逃していることがない
- 正当化されないファイルサイズの爆発がない
- 特殊ケース分岐による明らかなスパゲッティの増殖がない
- コードを推論しにくくする、明らかにハック的または魔法のような抽象化がない
- 本当の設計を曖昧にする不必要なラッパー / キャスト / オプショナル性の乱発がない
- 明確なアーキテクチャ境界の漏れや、避けられる正規ヘルパーの重複がない
- 保守性を実質的に改善する明らかな分解の機会を逃していない

次は、作者が明確に正当化できない限り、推定ブロッカーとして扱う。

- 削除できる現実的なコード柔道の技があるのに、PR が多くの偶発的な複雑さを残している
- PR がファイルを 1000 行未満から 1000 行超へ押し上げている
- PR が既存のフローをより絡ませるアドホックな分岐を追加している
- PR が共有コード全体に機能チェックをまき散らすことで局所的な問題を解決している
- PR が設計をより間接的にする不必要な抽象化、ラッパー、キャストの多い契約を追加している
- 明確な正規の置き場所があるのに、PR が既存のヘルパーを重複させたり、間違ったレイヤーにロジックを置いたりしている

これらの条件が満たされないなら、明示的で実行可能なフィードバックを残し、よりきれいな分解を推す。
