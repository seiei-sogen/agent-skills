# Blast radius

変更が出荷される前に、別の場所で何を壊すかを見つける。「X の影響範囲」「これは何を壊し得るか」、またはまだ信頼できない小さな差分をレビューするときに使う。

`how` と `why` の相棒である。`how` はコードが何をするかを教える。`why` はなぜその形になっているかを教える。Blast radius は、別の場所で何を壊すかを教える。

呼び出し側を列挙することが仕事ではない。エージェントなら一瞬で grep できる。仕事は、grep では見えない破壊を見つけることである。

## 自分の書いたまとめを信用しない

正しそうに聞こえる影響範囲のまとめは無価値である。真偽に関係なく説得力があるように読める。だからまとめを返してはならない。全体が依存している 1 つか 2 つの事実を見つけ、コードを実行して証明する。

### どれだけ確かか

変更の安全性が依存する事実ごとに、安く済む範囲でこのリストのできるだけ下まで進め、どこで止まったかを言う。

1. 自分がそう言った。それだけでは無価値。
2. 行を指した。実在する `file:line`、またはライブラリ自身のソース。
3. 悪いケースが起こり得ないことを示した。失敗を一歩ずつ辿り、到達しないことを確認した。
4. 実行した。実際のコードを呼び、間違っていれば大きく失敗するスクリプトまたはテスト。
5. 動作中のアプリで再現した。

ステップ 4 まで到達できない安全性の事実は、そう言うこと。確定事項として書いてはならない。ステップ 4 は通常、アプリが出荷しているものと同じライブラリをインポートし、懸念している関数そのものを呼ぶ小さなスクリプト 1 つである。

## 手順

1. 変更を読む。差分、追加・変更・削除されるシンボル、そして今何が違うように動くのか。差分に明示されていない部分も含める。`why` のステップ 2 を使って PR とコミットを取得する。
2. それが安全である根拠となる 1 つの事実を見つける。危険に見える変更の多くは、「この呼び出しはすでに死んでいるキャッシュエントリを落とすだけで他には何もしない」のような、単一の事実によって安全である。その事実を見つける。それが成り立てば、危険なケースの大半が一度に片付く。時間はここに使い、長い「かもしれない」のリストには使わない。
3. grep が止まる場所を見る。呼んでいるライブラリのソースを読み、固定されたバージョンとローカルパッチを確認する。いつ実行されるかを把握する。マイクロタスク、アンマウントとティアダウン、Solid と React の違い。シンボル検索が見逃すものを追う。API が返す JSON、DB のカラム、ワイヤフォーマット、同じバイト列を読む別の言語、フィーチャーフラグ、3 ホップ下流のコード。
4. 各リスクについて正直になる。実際に起こる可能性と、起こった場合の実際のコストを示す。確認できたリスクは残す。確認して問題なしとしたものは別に列挙する。ルールは `why` と同じ。実在する `file:line` を引用し、何も見つからない検索もひとつの答えであり、呼び出し側や API を決してでっち上げない。
5. その 1 つの事実を証明する。実際のコードを実行するスクリプトまたはテストを書き、実行し、起きたことを貼り付ける。安く証明できないなら、未証明とマークする。誇張しない。
6. 大きい変更や広い変更では、`arena` として実行する。複数のモデルに同じ質問をし、答えをマージする。異なるモデルは異なる実バグを捕まえる。

## 返すもの

- **何をするか。** 何が変わったか。明白でない部分も含む。
- **それが安全である根拠となる 1 つの事実。** それを述べ、どのステップまで到達したかを言い、証明を示す。証明できなかった場合は未証明と書く。
- **リスク。** 実在するものだけ。それぞれに、どう壊れるか、`file:line`、可能性と深刻度、確認方法を記す。重要なものには証明を貼り付ける。
- **問題なし。** 何を確認し、なぜ問題ないか。
- **マージ前に。** 実バグを捕まえる最も安いテストまたは再現。自分が書いたスクリプトを含む。

`unslop` を通して書き、実在するコードを引用し、公開される前に私的な情報をすべて取り除く。

**返答:** 上記のまとめ。安全性の 1 つの事実は、証明済みか未証明のいずれかとマークする。
