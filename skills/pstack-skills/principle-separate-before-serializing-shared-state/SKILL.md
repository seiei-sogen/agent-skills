# Separate Before Serializing Shared State

並行するアクターが可変な状態を共有する可能性があるときは、まず、それらが同じ可変オブジェクトを必要としているのかを問う。必要でなければ、共有をなくす。共有が本物であるときは、直列化を構造的に強制する。ロックファイル、順次実行するフェーズ、排他的な所有権である。指示や慣習は並行性制御ではない。

**理由:** 共有状態への並行書き込みは、間欠的で、再現しにくく、デバッグに費用がかかる競合状態を生む。

**パターン:**
1. **共有された可変状態を特定する**（両者が読み書きするファイル、両者が push するブランチ、両者が定義し利用する API）。
2. **既定: 共有された書き込み先をなくす。** 問う。これらのアクターは 1 つの正準なオブジェクトを必要としているのか、それとも独立した事実を公開しているだけなのか。各アクターに自分が所有するファイル、キー、ブランチ、または状態ディレクトリを与え、読み取り／報告の境界でだけマージする。2 つのワーカーがそれぞれ自分の `lastX` フィールドを 1 つの `state.json` に書き込むのは、依然として共有された変更である。`indexer-state.json` + `metrics-state.json` はそうではない。
3. **共有された単一の書き込み先が本物の不変条件である場合にだけ、アクセスを構造的に直列化する**（ロックファイル、順次実行するフェーズ、単一の書き手アクター、またはアトミックな compare-and-swap）。「ロックが必要だ」は既定の答えではなく、確認すべき設計上の臭いとして扱う。
