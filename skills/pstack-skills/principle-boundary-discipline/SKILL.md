# Boundary Discipline

バリデーション、型の絞り込み、エラー処理をシステム境界に置く。内部コードは無条件に信頼する。ビジネスロジックは純粋関数に置く。シェルは薄く機械的にする。

**理由:** 散在したバリデーションはノイズが多く、冗長で、誤った安心感を与える。ロジックをフレームワークの配線から切り離し、フレームワークなしでテストできるようにする。

**パターン:**
- **境界では**（CLI 引数、設定ファイル、外部 API、ネットワークプロトコル）: バリデーションし、エラーを返し、防御的に処理する。
- **システムの内側では:** 型付きデータ、エラーの伝播、再バリデーションなし。型を信頼する。
- **境界をまたぐとき。** 境界の内部表現ではなく、ドメインの概念を公開する。汎用的な仕組みは内側に、特定目的のポリシーは端に置く。

**適用例:**

バリデーションとエラー処理:
- 設定はビジネスロジックの内側ではなく、パース時（境界）にバリデーションする
- 生データは境界でドメイン型にパースする
- トランスポート、ストレージ、フレームワーク、ワイヤの型を公開サーフェスから再エクスポートしない
- 境界ですでにバリデーションしているなら、呼び出し連鎖の深部で冗長な nil チェックをしない

コードの構成:
- ビジネスロジックはフレームワーク依存のない純粋関数に置く
- パース関数: 生バイト列から型付き状態への純粋な変換
- プロンプト構築: 構造化された状態を入力し、文字列を出力する
- スコアリングと評価: 状態から結果への純粋な変換

**判定方法:**
- 「このデータは今まさにシステム境界を越えているか?」そうでなければ、バリデーションは冗長である。
- 「これはシェルが単に呼び出すだけの純粋関数にできるか?」できるなら、抽出する。
