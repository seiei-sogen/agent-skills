# Automate me

ユーザーの作業上の慣習を、エージェントが従うスキルへ変換するためのガイド付きフロー。出力はそのユーザーに合わせた 1 つの `-mode` スキル（例: `jay-mode`、`priya-mode`）である。

このスキルは他の 3 つを統括する。インラインのマイニングパス（ステップ 1 を参照）、`plugin-dev:skill-development` スキル（執筆）、**unslop** スキル（文章の規律）である。このスキルはそれらを順序付けるだけで、置き換えるものではない。

**プラットフォームに関する注記。** Codex やその他の非 Claude ランタイムでは、以下に挙げる Claude のツール名、`claude-*` スラッグ、Claude 組み込みスキル（`plugin-dev:skill-development` を含む）は Claude の既定値である。[`codex-tools.md`](../poteto-mode/references/codex-tools.md) を通じて解決すること。

## フロー

### 0. 既存スキルの確認

ユーザーのハンドルに一致する `.claude/skills/**/*-mode/SKILL.md` と `~/.claude/skills/*-mode/SKILL.md` を再帰的に探す。モードスキルはトップレベルだけでなく、個人用カテゴリディレクトリ（`.claude/skills/<handle>/`）にも置かれることがある。存在する場合は、`AskUserQuestion` で意図を確認する（ユーザーがすでに「自分のスキルを更新して」などと言っている場合を除く）。

- 既存スキルを更新する（繰り返し実行時の既定）
- 最初から作り直す（まれ。実行前に理由を尋ねる）

更新モードでは、以降のフローが次のように変わる。
- ステップ 1 では、スキルが最後に編集された時点以降の履歴だけをマイニングする（`git log -1 --format=%cI <path>`）。
- ステップ 2 では、ゼロから何を捕捉するかではなく、何が変わったか、何が足りないかを尋ねる。
- ステップ 4 では、既存ファイルをその場で編集する。ユーザーが否定していないセクションは保つ。新しい証拠のあるセクションは改訂する。新しいセクションは、本当に新しいルールに対してだけ追加する。

### 1. 履歴をマイニングする

ファンアウトする前に、アクティブなワークスペースのトランスクリプトの場所を特定する。Claude Code はそれらを `~/.claude/projects/<encoded-cwd>/*.jsonl` に保存しており、`<encoded-cwd>` はワークスペースの作業ディレクトリの `/` を `-` に置き換えたものである。そのパスだけを使う。`~/.claude/projects/` 全体を glob してはならない。それはワークスペースの境界を越え、無関係なプロジェクトの私的なチャットを読むことになる。

そのスコープ内で最近のエージェントとの会話を調査し、繰り返し現れるパターンを探す。履歴のスライスごとに複数のサブエージェントを並列で実行する（例: 直近 2〜4 週間を、それぞれに十分な材料があるように 3 スライスに分ける）。各スライスのマイニングを行うサブエージェントは、親が提供するワークスペーススコープのパスからトランスクリプトを読み、以下のシグナルを探し、見つけたパターンの短い構造化リストを証拠ポインタ付きで返す。追うべき既定のシグナルは次のとおり。

- 返答の好み（長さ、トーン、形式、「もっと簡単に言って」という訂正）
- 委任の習慣（サブエージェント、モデル、専門化されたワークフロー、並列性）
- 検証の姿勢（「完了」の意味、ユニットテストか実環境での再現か、レビュアー）
- コードと文章の規律（スタイル、引用される原則、リント／フォーマットツール）
- プロセスの慣習（ワークツリー、コミット、PR、レビュー／マージのツール）
- メタな好み（タスク途中でのスキル修正、新しいスキルの提案）

シグナルを格上げする前に、スライス間で相互に確認する。2 つ以上のスライスで見られたパターンは確信度が高い。単独のシグナルは弱く、通常は捨てられる。

### 2. ユーザーに直接尋ねる

マイニングでは、まだ話題に出ていない意図を取りこぼす。ユーザーにゼロから入力させるのではなく、`AskUserQuestion` ツール（構造化された多肢選択）を使う。

形式: 各 4〜6 個の選択肢を持つ 1〜2 問で、カテゴリを問う質問には `allow_multiple: true` を付ける。広く始め（「どの領域が最も重要か」）、選ばれた領域について具体的な選択肢で追加質問する。構造化されたラウンドの後、自由回答のチャット質問を 1 つ設け、選択肢で拾えなかったものを捕捉する。

20 個の質問を一気に投げてはならない。

### 3. 発見事項をクラスタリングする

集めたシグナルをセクションにまとめる。よくあるセクション（該当するものだけを使う）:

- **返答スタイル**: 長さ、トーン、形式。
- **自律性**: 尋ねずにどこまで進めるか、MCP ツールの使用。
- **まず理解する**: 変更のスコープ決めや調査のときにどのスキルを使うか。
- **サブエージェント**: 既定、並列性、タスクごとのモデル、専門化されたワークフロー。
- **文章／コードの規律**: 原則、リントツール、スタイルガイド。
- **レビューと検証**: 再現の姿勢、検証スキル、実環境テストのツール。
- **プロセス**: git ワークツリー、コミット、PR、レビュー／マージのツール。
- **スキル**: スキル執筆の習慣、まずスキルを直す、新しいスキルの提案。

**poteto-mode** スキルがその形を示している。粒度を知るために読むこと。内容をコピーしてはならない。ユーザーのルールは poteto-mode のルールと同じではない。

### 4. スキルを起草する

**plugin-dev:skill-development** スキルを使ってスキルを執筆する。配置:

- パス: 既存のモードスキルのカテゴリを保つ。新しいモードでは、リポジトリにそのハンドル用の確立された個人カテゴリがある場合、`.claude/skills/<handle>/<handle>-mode/SKILL.md` を使う。それ以外はプロジェクト内の `.claude/skills/<handle>-mode/SKILL.md` を既定とする（ユーザーが個人用スキルを望む場合は `~/.claude/skills/<handle>-mode/`）。
- ハンドル: ユーザーのファーストネーム、または選んだ識別子。
- Frontmatter の `description`: 「コードを書く」や「PR をレビューする」のような汎用キーワードではなく、ユーザーの名前 + `/<handle>-mode` + 「本人のスタイルで作業する」でトリガーする。
- Frontmatter の書式: `plugin-dev:skill-development` の YAML ルールに従う。`description` は 1 つの YAML スカラーに保つ。句読点や折り返しが必要な場合は、引用符で囲むか、`description: >-` とインデントした継続行を使う。
- Frontmatter の `disable-model-invocation: true` を既定とする。ユーザーが自分のモードを毎ターン適用したいと明示した場合だけ外す。

### 5. 文章を反復改善する

**unslop** スキルと `plugin-dev:skill-development` の執筆ガイドラインをすべての行に適用する。

ドラフトをユーザーに見せてフィードバックを受ける。複数回の反復を想定する。容赦なく削る。モードスキルはマニュアルではない。

### 6. 取り込む

main から切ったワークツリーで作業する。コミットして PR を開く。main へ直接 push してはならない。

## ガードレール

- **1 つの会話に過剰適合しない。** 一度述べられ、別のときに否定された好みはノイズである。規則化する前に複数の事例を要求する。
- **賢く振る舞おうとしない。** 他のスキルの内容を言い換える、比喩を発明する、エージェント読者向けに「詩的な」文章を書くことは、利益のないコストである。運用的な記述に保つ。
- **参照する。インライン化しない。** ユーザーが頼っている他のスキルは、貼り付けた抜粋ではなくパス参照として載せる。ユーザーが別の場所で管理している原則ドキュメントも同様。
- **セクションは最小限に保つ。** ユーザーがそこに具体的で既定ではないルールを持っている場合だけセクションを追加する。「明確に伝える」はセクションではない。「短い段落。選択肢を比較するときは表。項目が本当に並列のときだけ箇条書き。」はセクションである。
- **呼称は汎用にする。** 命令文では著者のファーストネームではなく「ユーザー」または「人間」を使う。
- **対称性を強いない。** 書き留める価値のあるプロセスルールをユーザーが持っていないなら、プロセスのセクションを丸ごと省く。

## 評価

`-mode` スキルは主観的な出力である。`plugin-dev:skill-development` 流のテスト／反復ベンチマークループはここでは役に立たない。ユーザーと感触を確認する。本人らしく読めるか。何か見落としていないか。それから出荷する。

description の最適化ループは、スキルのトリガー精度が実際に問題になった場合だけ実行する。

## 使わないとき

- ユーザーがタスク固有のスキル（作業上の慣習ではない）を望んでいる: `plugin-dev:skill-development` だけで足り、マイニングは不要。
- ユーザーが 1 つの狭いワークフロー（例: 「コミットメッセージの書き方」）を捕捉したい。それは通常のスキルであり、モードスキルではない。
