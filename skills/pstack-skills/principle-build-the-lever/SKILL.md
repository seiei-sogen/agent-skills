# Build the Lever

作業が自明でないときは、手作業で行うのではなく、それを実行するツールを作る。

**理由:** 2 つの見返りがある。スループット: codemod、ジェネレータ、スクリプトは毎回同じやり方で作業を行い、追加コストなしに再実行できる。確信度: ツールは、レビュアーが作業を確認するために読んで再実行できる 1 つの成果物である。手作業の変更は、やり直すことでしか再検証できない。決定的なスクリプトは「信じてほしい」を「これを実行せよ」に変える。

**パターン:** てこを作ることを既定にする。省くのはタスクが自明なとき、つまり一目で分かる 2、3 の明らかな編集だけのときに限る。

- 最初の 1 単位は手作業で行ってレシピを学び、それからツールを作る。その単位でツールを再実行し、手作業版との差分を取って証明する。てこは安全に再実行できるようにする。
- 編集には codemod かスクリプト、繰り返しの多いファイルにはジェネレータ、分析には sqlite へダンプしてクエリ、検証には再実行可能なチェック。
- 決定的なてこはファンアウトに勝る。ツールが 1 回のパスですべての単位を処理できるなら、自分で実行する。スクリプトでできることを手作業で適用させるために、委任先をファンアウトしない。
- 作業をサブエージェントにファンアウトするときは、てこを全員が読むスキルとして書く。レシピ、検証の契約、触ってはならない柵を 1 つの成果物にまとめる。委任先が契約を密かに編集できないように、委任先の書き込み範囲の外に置く。
- この原則を適用するとファイルが生まれる。この原則を引用したのに、差分に codemod、スクリプト、ジェネレータ、委任先向けスキルのどれもないなら、適用していない。
- 作業がセッションより長く残るなら、てこをコミットする。

**バランス:** 基準は自明さであり、繰り返しではない。てこが作業を確認可能にするものであるなら、一回限りの作業でもてこに値する。[Laziness Protocol](../principle-laziness-protocol/SKILL.md) に従い、仕事を実行または証明する最小のスクリプトを作る。フレームワークは決して作らない。

[Encode Lessons in Structure](../principle-encode-lessons-in-structure/SKILL.md) とは異なる。あちらは繰り返される指示を永続的なガードレールにする。こちらは目の前の作業のスループットとレビュー可能性である。検証そのものをスクリプト化することについては [Prove It Works](../principle-prove-it-works/SKILL.md) を参照。
