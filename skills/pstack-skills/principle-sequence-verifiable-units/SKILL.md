# Sequence work into verifiable units

作業を、それぞれが確認できる状態で終わる小さな単位の連なりとして並べ、現在の単位がグリーンになるまで先に進まない。

**理由:** 原因となった単位で捕まえた破損は、位置を特定するのが安い。バッチの後で捕まえた破損は埋もれており、そのときにはすでに壊れたベースの上に積み上げてしまっている。同じ単位を、レビュアーが再生できるデリバリーの形に並べることで、「信じてほしい」が「赤になってから緑になるのを見てほしい」に変わる。

**実行。** 一括修正、移行、または似た編集の連続では、次に着手する前に各変更を検証する。各単位は前後を括る 1 組である。既知の正常な状態、1 つの変更、チェックの実行、それから次へ進む。まずクリーンなトランクに rebase し、すべてのチェックが本当のベースラインに対して測られるようにする。てこが編集を行う場合、単位ごとのチェックはほぼ無料である。それでも実行する。

**デリバリー。** 作業を証明する順序でコミットと PR をスタックする。正準な形は、失敗するテストが先、その上に修正である。他の筋立てとしては、形を変える前の引き算、処置の前のベースライン取得、機能の前の足場がある。各コミットは単独で取り込まれ、その並びは論証として読める。

**パターン:**
- チェックで終わる最小の単位を選ぶ。編集とそのテスト、または単独で成立するコミット。
- 先に進む前に検証する。単位ごとに赤から緑へ。最後のバッチに先送りしない。
- 実行中の自分にとっても、スタックを読むレビュアーにとっても、その並びが自ら確信を積み上げるように単位の順序を決める。

これは、各チェックを本物に保つ **prove-it-works** 原則スキルと、単位ごとのチェックを安くする **build-the-lever** 原則スキルを、順序付けの面から補完するものである。
