# Encode Lessons in Structure

繰り返される修正は、文章による指示ではなく仕組み（ツール、コード、メタデータ、自動化）にエンコードする。あらゆるエラー、人間による訂正、予期しない結果は学習の信号である。捕捉し、ルーティングし、ループを閉じる。

**理由:** 文章による指示は見逃しやすい。読者が気づき、覚え、従うことを要求する。構造的な仕組み（リント規則、メタデータフラグ、実行時チェック、自動化スクリプト）は、協力なしに規則を強制する。

**パターン:**
同じ指示を 2 回目に書いていると気づいたら:
1. 問う: これはリント規則、メタデータフラグ、実行時チェック、またはスクリプトにできるか?
2. できるなら、エンコードする。指示を削除する
3. できないなら（判断を要するなら）、指示をより目立たせ、失敗モードの例を追加する

**最も強い仕組みを選ぶ。** 複数の仕組みが機能するときは、状況が許す最も強いものを選ぶ（コンパイルできない表現不可能な状態、次に CI を失敗させるリントや禁止 API、次に正規のヘルパー、次に実行時チェック）。エージェントは周囲のコードがすでにしていることをそのまま模倣するので、弱いガードが次のテンプレートになるからである。

**帰結:** 修正が構造的なら、構造的な修正だけを使う。指示は症状である。

**フィードバックループ:**
- **すべての訂正を捕捉する。** 人間が介入したりテストが失敗したりしたら、一回限りかパターンかを判断する。
- **正しい層にルーティングする。** 一回限り -> brain ノート。繰り返される修正 -> スキルまたはリント規則。系統的な問題 -> 原則。
- **ループを閉じる。** 記録するだけで終わらない。今すぐ適用するか、具体的な TODO を作る。

**アンチパターン:**
- 記録せずに了解する（「覚えておく」は持続しない）
- ルーティングせずに記録する（存在すべきリント規則についての brain ノートは、そのリント規則が実装されなければ無駄になる）
- 一般化せずに修正する（繰り返されるパターンを残したまま 1 つの事例だけを修正する）
