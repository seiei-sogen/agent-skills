# Make PR Easy to Review

レビュアーが意図、重要なファイル、リスクをすばやく理解できるように PR を整える。デフォルトの目標は、振る舞いを変えずにレビューしやすくすることである。

## ワークフロー

1. ユーザーが指定した URL または現在のブランチから対象の PR を特定する。
2. コミット、差分の大きさ、変更されたパス、生成ファイル、PR 説明文を調べる。
3. レビューしやすさの問題を見つける: ノイズの多いコミット、古くなった説明文、無関係な変更、機械的な変更とロジック変更の混在、テストの欠如、レビュアーの入り口の不明確さ。
4. 履歴を書き換えたり force-push したりする前に計画を提案する。
5. 安全な改善を適用し、その後ツリーまたは差分が意図したコードと一致したままであることを検証する。

## 履歴の整理

履歴の書き換えは、ユーザーが求めた場合、または計画に同意した場合のみ行う。書き換える前に:

```bash
gh pr view <PR> --json title,headRefName,baseRefName,state,commits
git fetch origin <headRefName> <baseRefName>
ORIGINAL_TREE=$(git rev-parse origin/<headRefName>^{tree})
```

良いコミットのまとめ方は、通常は依存関係の順序に従う:

1. スキーマ / ストレージ、または生成された API 定義。
2. コアロジック。
3. 配線と統合。
4. UI またはサーフェスの振る舞い。
5. テスト。

書き換えた後、内容が同一であることを検証する:

```bash
echo "Original tree: $ORIGINAL_TREE"
echo "Current tree:  $(git rev-parse HEAD^{tree})"
git diff origin/<headRefName> --stat
```

ツリーが意図せず変わっていたら push しない。

## レビュアー向けガイダンス

コードの振る舞いに手を付けるべきでないときは、PR 説明文とレビューノートを優先する:

- 実際の差分と一致する TL;DR を追加する。
- コアのファイルを、生成されたファイルや機械的なファイルから分離する。
- リスクのある振る舞いの変更、マイグレーションの順序、ロールアウト計画、テストカバレッジを明示する。
- issue トラッカー、ダッシュボード、設計ドキュメントが意図を説明しているなら、それらへリンクする。

## ガードレール

- 意味のある振る舞いの変更を「整理」の中に隠してはならない。
- ユーザーが明示的に求めない限り、フックをバイパスしない。
- PR が大きすぎてノートではレビュー可能にできない場合は、問題の周りを磨くのではなく分割を推奨する。
