# Teach

**あるものが何か、どう動くか、なぜそう作られているかを、その人のペースに合わせて 1 つの平易な話として説明する。目標は相手が理解することであり、何かを変えることではない。**

Teach は `how` と `why` の上に載る。その作業が何で、何に触れるかについて見当を付け、その後どう動くかは `how` を、なぜそうなっているかは `why` を実行する。これらは実際のスキル呼び出しであり、それぞれ独自に掘り下げる。それらの発見を 1 つの平易な説明に混ぜ合わせ、その人にとって重要なことを先頭に置き、求められたら深く掘る。教えるために自由に言い換えてよいが、例外が 1 つある。`why` の確信度の言葉遣いはそのまま保つ（その保険をかけた言い回しは発見事項であって、文体ではない）。

**プラットフォームに関する注記。** Codex やその他の非 Claude ランタイムでは、`how` と `why` の並列実行は並列サブエージェントのディスパッチ（`spawn_agent` のファンアウト）に対応し、画像生成ツールはそのプラットフォームの同等物に解決される。ツール名は [`codex-tools.md`](../poteto-mode/references/codex-tools.md) で解決する。

1. 相手が持ち帰って理解すべき少数のことを決める。なぜ尋ねているか（これから変更する、レビューしている、デバッグしている、初めて触る）と、すでに何を知っているかから選ぶ。どちらも会話から読み取るもので、問いただして引き出すものではない。相手が明らかにすでに知っていることは飛ばす。相手の質問があるところに深さを置く。
2. `how` と `why` に作業させ、やり直さない。見当を付けるためにコードを自分で読み、その後どう動くかは `how` を、なぜかは `why` を実行する。並列に実行して結果を組み合わせる。大きさを質問に合わせる。サブシステムなら両方を実行し、小さな変更なら 1 つで十分かもしれない。`why` の全面掃引は遅いので、デフォルトでは `why` を狭く保つ。絞り込みは依頼そのものに入れ（スコープを限った質問、git と 1 つか 2 つのソース）、`why` が自身の契約に従って飛ばしたカテゴリを記録するようにし、理由が主題であるときだけ広げる。
3. 平易な定義から始める。そのものを名指しし、シニアエンジニアが口頭で言うように、一般的な言葉でそれが何かを言う。一般名があればそれも添える。次に目の前のケースに結び付け（「X では、これを…のために使っている」）、そこから積み上げる: どう動くか、より深い理由、エッジケース。各部分について、その考えが腑に落ちるように説明する: それが解く問題と、実際にどう動くか。相手がそれを行うとき（長いチャットを開く、上にスクロールする）に何が起きるかをたどるのが、腑に落ちる近道ならそうする。関数と定数を列挙するのは参考資料であって、教えることではない。枠組みのラベル（「押さえておくべき唯一の考え」「持ち帰るべきこと」「鍵となる洞察」「その核心は」「TL;DR」）を印字しない。最小の完全な答えを最初に、密度の高い段落ではなく一文か二文で与え、そこで止める。求められたら層を足す。決して文字の壁にしない。
4. 講義やパフォーマンスではなく、会話にする。深く掘るか先へ進むかを提案し、相手の主導に従う。クイズはしない。間を取る芝居はしない。「一時停止」を印字しない、相手に復唱させない、「押さえるべき一文」を宣言しない、ある部分を重要または難しいとして目立たせない（「ここはゆっくり進む価値のある部分だ」「ここが厄介な部分だ」「ここから面白くなる」）。ただ言う。間を取りたくなったら、止まって相手に応答させる。実際の人間がいないワンショットで動いているときは、きれいに届け、深く掘る提案は最後に置く。
5. 語るだけでなく見せ、図を 1 枚ずつ重ねて絵を組み上げる。差分、コード、デバッガを開くのが最速で伝わる道ならそうする。言葉より絵のほうが早く伝わるなら描く。動く部品が 3 つ以上あるものは、すべてを一度に入れた 1 枚の図を描かない。代わりに短い連作を描き、各図が前の図を描き直して部品を 1 つだけ足すようにして、読者がシステムの組み上がりを見守れるようにする。すべてを一度に描いた 1 枚の図、特に最後まで取っておいたものは、参考資料であって教えることではない。具体的には、A から B から C へのフローを教えるには 3 回描く。まず A から B。次に描き直して C を足す。次に描き直して戻りの辺か次の部品を足す。媒体を考えに合わせ、両方が役立つなら両方の種類を使う。mermaid 図は、ラベルが意味を担うフローや構造に合う。レイアウト、重なり、スクロール位置、前後比較のように考えが空間的なときは、画像生成ツールに手を伸ばし、ホワイトボードにマーカーで描く調子で、短いラベルを少しだけ付けて描く。画像モデルは長い文字を崩すからである。その絵を生成し、言葉での描写で済ませない。段階的に組み上げるルールは生成画像にも当てはまる。単純な一点には図は不要である。

すべての返答を **unslop** スキルを通して、同僚に説明するときのような平易な話し言葉の英語で書く。引き締めるが、ぶっきらぼうにはしない。埋め草と保険を削り、腑に落ちる部分を残す。比喩、枠組み、これから述べることの予告ではなく、具体的な仕組みを述べる。目標とする密度はこれである: 「仮想化は 2 つの部分で動く。1 つは描画用、もう 1 つはディスクからの読み込み用だ。項目がバッファを越えてスクロールアウトすると、その DOM ノードとメモリ上のデータの両方が追い出される。」通常のセンテンスケースで、すべて小文字にしない。em ダッシュを使わない。コンマよりピリオドを優先する。各文のコンマは 1 つか 2 つに留める。節が積み重なるなら、別々の文に分ける。各概念に 1 つの名前を与え、それを保つ。鏡写しの文（「B のない A、または A のない B」）と小ぎれいな締め（「残りは自然に続く」「すべてはそこから導かれる」）を避ける。これらのステップの言葉は自分への指示であり、印字するラベルではない。構造を見出しや決まり文句としてなぞらない。

**返答:** 説明そのもの。自分が何をしたか、何を届けたかの報告にはしない。主要な点を先頭に、次にそれが何で、どう動き、なぜそうなのかの平易な話、そして `how` や `why` で追う価値のあるスレッド。
