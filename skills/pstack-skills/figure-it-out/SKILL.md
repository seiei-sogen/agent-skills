# Figure it out

タスクがどのプレイブックにも当てはまらないときは、プレイブックを設計する。コードより前の成果物はワークフローそのものである。すなわち、厳密さをタスクに合わせて調整し、科学的方法を実行し、人間が離席後に監査できる決定の記録を残す一連のフェーズである。厳密さを高める方向に寄せる。間違ったものを作るコストは、慎重であるコストをはるかに上回る。

## 開始

最初の項目が **poteto-mode** スキルの Principles セクションを読むことである TODO リストを開く。次に、以下のフェーズを TODO として追加する。

## Phase A: 枠組みを決める

まず現状を把握し、それから決める。次を述べられるようになるまで実行を始めてはならない。

- 反証可能な述語としての完了の定義（**prove-it-works** 原則スキル）。
- 定量化したスコープ。おおよその単位とエフォート、加えて現状把握で浮かび上がったブロッカー。
- 厳密さのレベル。高めに寄せる。一方通行の扉と大きな影響範囲にはより多く。可逆で低リスクなステップにはより少なく。厳密さとはゲートと成果物であり、「もっと頑張る」ではない。

長い実行に踏み切る前に、枠組みとトレードオフを提示する。可逆な作業は進めてよい（**never-block-on-the-human** 原則スキル）が、数時間の実行には 1 回のチェックポイントが必要である。

## Phase B: ワークフローを設計する

アトミックで、独立して取り込める単位に分解する。最もリスクの高い未知を最初に並べる。足場と検証は機能より先に来る（**foundational-thinking** 原則スキル）。

- 作業の前に検証ハーネスを構築し、変更前の状態からベースラインを取得しておく。これでチェックが「旧値 vs 新値」として読める。
- 一方通行の扉となる設計上の決定には、**architect** スキルを実行する（これは **arena** を実行する）。形がすでに具体的な機械的作業ではスキップする。決着した設計に 2 回目の arena をかけるのは過剰設計である（**laziness-protocol** 原則スキル）。
- 何をファンアウトするかを決める。並列化は継ぎ目で分割できる場合に限り、各ワーカーに自分のワークツリーまたはブランチを与える（**separate-before-serializing-shared-state** 原則スキル）。ファンアウトし過ぎない。
- 設計したフェーズのリストを書き出す。そのリストが人間のレビュー対象である。

それから設計を実行する。そのステップを具体的な項目として TODO リストに追加する。Phase C のエントリの後、Phase D の前に置く。各ステップを Phase C のループ規律のもとで実行し、Phase D のログをそれらに織り込む。記録全体を最後まで取っておくのではなく、各ステップが完了するごとに 1 行を追加する。

## Phase C: ループを実行する

各単位は実験である。仮説を述べ、最小の変更を行い、実際の成果物に対して述語で測定し、前進したなら残し、しなかったなら戻す。
**sequence-verifiable-units** 原則スキルを適用し、最後にチェックをまとめるのではなく、次に着手する前に各単位を検証する。

- 成果物を検査して検証する。自己申告を根拠にしてはならない。あまりにも簡単に通るものがあれば、システムより先に観測方法を疑う。
- 委任した作業にはジャッジを組み合わせ、委任先の成果物を信頼する前に自分で監査する。ワーカーがゲートをすり抜ける小細工をしたら、リセットして契約を固くする。ゲート自体が間違っているなら、回避するのではなく、ゲートを独立した変更で直す。
- 判定は VERIFIED、NOT VERIFIED、INCONCLUSIVE のいずれかである。Inconclusive は合格ではない。否定的な結果を隠さない。

## Phase D: 監査の記録を残す

**show-me-your-work** スキルで実行を記録する。決定ごと、単位ごとに 1 行を持つ正規の TSV を 1 つ作り、証拠はリンクとする。figure-it-out の作業は通常、レビュアーが PR で読めるように記録をコミットするに足るほど野心的である。確信度を示す必要があるときはコミットする。コミットされたスクリプトが生成した証拠を優先する。記録と差分が、人間が戻ってきて作業を信頼できるようにするものである。

## Phase E: 検証して返す

ハーネスだけでなく、実際の製品に対して Phase A の述語で全体を確認する。繰り返し発生する修正は、ゲート、リントルール、チェック、スクリプトのいずれかとしてエンコードする（**encode-lessons-in-structure** 原則スキル）。

**返答:** 設計したプレイブック、厳密さのレベルとその理由、決定の記録のパス、述語に対して何が検証済みか、何がまだ未解決か。
