# Notes 検証マップ

このディレクトリは、Notes のユーザー向けの動作を検証するために保守されるソースである。アプリを操作する前にインデックスを読み、次に該当する機能ファイルをレシピとして使う。

## 基本の前提条件

- 使い捨てのデータディレクトリを使って、Notes を `http://127.0.0.1:4173` で起動する。
- 並行する実行が状態を共有しないように、`NOTES_DATA_DIR=/tmp/notes-verify-$RUN_ID` を設定する。
- `Quarterly plan` と `Grocery list` というタイトルのノートをシードする。
- `control-notes` と `notes` CLI を `PATH` に置く。
- `control-notes doctor` を実行し、期待する URL、データディレクトリ、ビルドリビジョンであることを必須とする。
- この検証実行が起動していないインスタンスは決して操作しない。

## 操作の規約

- 前提条件に別の指定がなければ、すべてのレシピを基本状態から始める。
- CSS セレクタや DOM の位置より、ARIA ロールとアクセシブルネームを優先する。
- すべてのコマンドを字句どおりに扱う。引用符で囲まれた名前とフラグは変えない。
- ブラウザ操作は `control-notes browser` を通して実行する。
- ターミナル操作は `control-notes cli -- <command>` を通して実行する。
- 変更の後はシードデータを復元する。クリーンアップ中に証明の成果物を削除しない。

## 証明とスキップの報告

- 最終画面だけでなく、ユーザーの操作とその結果の状態を取得する。
- UI の証明には、ARIA スナップショットと、アプリの識別情報が見えるスクリーンショットを含める。
- CLI の証明には、コマンド、stdout、stderr、終了コードを含める。
- 変更の証明には、保存された値の読み取り専用の 2 回目の表示を含める。
- すべての成果物に、使用した機能 ID と入口を記録する。
- 到達できない経路は、試したコマンドと満たされなかった前提条件とともに報告する。
- スキップした入口を、別の経路で検証済みとして報告しない。

## 機能エントリの契約

各機能ファイルは、H1 のタイトルと、ユーザーに見える動作を説明する 1 段落で始まる。その後、次の順序でちょうど 4 つの H2 セクションを使う。

1. `Sub-features` は短い ID を列挙し、動作ごとに 1 行を書く。
2. `How to get to it (user POV)` はユーザーの入口をすべて列挙する。
3. `Driving it with <harness>` は `Preconditions:` で始まり、ラベル付きの箇条書きで各ユーザー操作に正確なコマンドと観察可能な結果を対にする。
4. `Gotchas` は検証実行を無駄にしたり無効にしたりしうる罠を列挙する。

実装の詳細はマップに入れない。ユーザーの経路、安定したハンドル、必要な状態、コマンド、観察可能な証明だけを記す。

## 機能

- [ノートを作成する](./create-note.md) は、ブラウザと CLI での作成、キャンセル、永続化、クリーンアップを扱う。
- [ノートを検索する](./search.md) は、ツールバー、キーボード、CLI からの検索を、一致、空、クリアの各状態とともに扱う。
