# 検証スキルを作る

本格的なプロジェクトには、実際のアプリを操作して動作を証明するスクリプト化された手段が必ず必要になる。アプリを起動し、ユーザーがするように機能を実行し、証拠を取得する。このスキルはそれをリポジトリに合わせたプロジェクトローカルなスキル（`.claude/skills/verify-<app>/`）として生成する。この生成器の出力は人間ではなく次のエージェントに向けて書く。それはアプリを一度も見たことのないエージェントが、タスクの途中で前知識なしに読むものだ。

**プラットフォームに関する注記。** 生成されたスキルは Claude Code では `.claude/skills/verify-<app>/` 配下に置かれる。Codex や他のランタイムでは、代わりにそのランタイムのプロジェクトスキルの置き場所に書く。アプリを操作するハーネス（ブラウザ/CDP、PTY/tmux、HTTP）はプラットフォームに依存しない。ツール名は [`codex-tools.md`](../poteto-mode/references/codex-tools.md) で解決する。

## 1. ユーザーではなくリポジトリに聞き取りをする

次の問いにコードベースから答え、観察できないことだけをユーザーに聞く。

- **サーフェス:** ユーザーが実際に触るものは何か。Web UI、CLI/TUI、デスクトップアプリ、API、モバイルアプリ、ライブラリのどれか。リポジトリが複数を持つこともある。主要なものを 1 つ選び、残りは記録する。
- **実行:** アプリはローカルでどう起動するか。リポジトリ自身が文書化している開発用コマンド（パッケージスクリプト、Makefile、README のクイックスタート）を優先する。ポート、環境変数、シードデータ、認証を記録する。
- **操作:** エージェントはどうやってプログラムから対話できるか。まず既存のハーネスを探す。Playwright/Cypress のスペック、expect スクリプト、PTY ヘルパー、curl で叩けるエンドポイント、デバッグポート。その後ではじめて汎用のレシピを選ぶ。Web と Electron にはブラウザ/CDP、CLI/TUI には tmux/PTY ハーネス、サービスには素の HTTP。
- **観察:** どんな証拠を取得できるか。スクリーンショット、ターミナルのトランスクリプト、レスポンスボディ、ログ、終了コード、DB の状態。
- **分離:** 2 つのインスタンスを並べて実行できるか（ポート、データディレクトリ、プロファイル）。できないなら生成するスキルにそう書く。共有インスタンスを二重に操作することを拒むほうが、ユーザーのセッションを壊すよりよい。

チェックアウトがそのままではビルドや起動できないなら、生成の前にまずそれを直す（または正確に報告する）。壊れたベースに対して書いたスキルは間違った手順を教える。無関係な欠落アセット（API が決して配信しない静的ディレクトリ、サンプル設定）が起動を妨げる場合、生成するスキルがそれを作成してもよいが、検証用の足場であると明示し、クリーンアップで削除する。

## 2. スキルを生成する

`.claude/skills/verify-<app>/SKILL.md` を書く。YAML フロントマター（`name: verify-<app>` と、アプリ、サーフェス、いつ使うかを記した `description`。フロントマターがないとスキルは決して登録されない）と次のセクションを含め、各セクションは聞き取りで実際に見つかった内容に根拠を置く（プレースホルダを残さない）。

- **Launch:** 検証用にアプリを起動する正確なコマンドと、準備完了をどう判断するか（ログ行、応答するポート、プロンプト）。ティアダウンも含める。短命な CLI や TUI には維持し続けるサーバーがない。この場合の起動とは、バイナリのビルド（または依存関係のインストール）を一度行い、その後は各操作をそれぞれ分離された PTY または tmux セッションで開始することを意味する。
- **Doctor:** 「このインスタンスは操作する価値があるか」に答える読み取り専用のチェックを 1 つ。プロセスが起動している、正しいバージョン/ビルドである、ポートを自分が所有している、認証が有効である。何かおかしく見えたら、エージェントはまずこれを実行する。
- **Drive:** このリポジトリの実際のセレクタ/コマンドを使ったハーネスのレシピ。例ではなく実物を書く。座標やタブ順ではなく、安定したハンドル（ARIA ラベル、data 属性、プロンプト文字列、ルートパス）を優先する。
- **Evidence:** 証明のために何を取得し、どこに置くか。証明の基準を明記する。内部のセッターやテスト専用エンドポイントではなく、実際のユーザー経路を実行する。最終画面だけでなく、操作とその結果の状態を取得する。見えるものと合わせて副作用（書かれたファイル、挿入された行、送信されたメッセージ）を検証する。モックは本番の境界がすでに外部システムを分離している場所に限る。安全な経路がドライランやテストモードの場合、その名前を信用するのではなく、観察（ファイル、ネットワーク、git の ref）によって実際に何をスキップしているかを検証する。ドライランの中にはネットワークに触れたりブラウザを開いたりするものもある。
- **Cleanup:** 実行が作成したインスタンスをどうティアダウンするか。プロセス名で kill してはならない。自分が起動したものを kill する。クリーンアップはインスタンスとスクラッチ状態を削除するが、証拠は決して削除しない。証明の成果物はティアダウン後も、スキルが名指しした場所に残る。
- **Helpers:** スキルに同梱するスクリプトはすべて実行可能で、その呼び出し方をスキル本文に示す。読者がリバースエンジニアリングしなければならないヘルパーはヘルパーではない。

## 3. 機能マップの種をまく

`.claude/skills/verify-<app>/features/README.md` と、識別できるユーザー向け機能ごとに 1 ファイルを作る（ルート、コマンド、メニュー、ドキュメントから、まずは上位 3〜5 個を目指す）。[`references/feature-map-example/`](references/feature-map-example/) の形に従い、README のインデックスと機能ごとに 1 ファイルとする。各ファイルはユーザーの視点から次に答える。その機能は何か、どう到達するか、ハーネスでどう操作するか、どの観察可能な終了状態が動作を証明するか。4 つの H2 は `Sub-features`、`How to get to it (user POV)`、`Driving it with <harness>`、`Gotchas` とする。このマップはリポジトリで保守される検証のソースである。マップが他の入口を挙げているのに、都合のよい入口 1 つだけを操作した証明は不完全である。

## 4. 引き渡す前に生成したスキルを証明する

自身の指示を一度、端から端まで実行する。起動、doctor、マップにある機能を 1 つだけ操作（1 つで十分。マップがあるのは後の実行で残りをカバーするためだ）、証拠の取得、クリーンアップ。クリーンアップ後、証拠が名指しした場所にまだ存在することを確認する。証明を食ってしまうクリーンアップはこのステップで不合格になる。失敗したものを直し、失敗した反復のたびにも生成したクリーンアップを実行して、壊れた試行がプロセスやポートを放置しないようにする。一度も実行されていない生成スキルは草稿であり、成果物ではない。

## 5. 保守ループを提案する

アプリの変化に合わせてマップを正直な状態に保つために、ユーザーに `/maintain-verification-skill` を示す。頻度の提案は、ユーザーが求めた場合に限る。
