# レビュールーブリック

関連するレンズを通してレビューする。すべてのレンズがすべての変更に当てはまるわけではない。判断力を働かせる。

## 正確性

コードは意図が言うとおりのことを実際にしているか。

- エッジケース: 空の入力、nil/undefined、境界値、並行アクセス
- エラー処理: エラーは捕捉されているか、伝播されているか、それとも黙って握りつぶされているか
- オフバイワン、型の強制変換、整数オーバーフロー、文字列エンコーディング
- 状態管理: レース条件、古いクロージャ、ダングリング参照
- ハッピーパスは動くか。サッドパスは動くか。
- 冪等性: この操作が 2 回実行されたら、または前回の実行が途中でクラッシュしていたら何が起きるか。答えが「残された状態に依存する」なら、状態を整合させるステップが欠けている。
- 並行性: 複数のアクターが同じ可変状態（ファイル、ブランチ、共有データ）に触れられるなら、アクセスは構造的に直列化されているか（ロック、逐次フェーズ、排他的所有）、それとも守られない慣習によってか。

潜在的なバグを見つけたら、実行パスを追う。「これは nil になりうる」と指摘するだけにしない。それを nil にする呼び出しチェーンを示す。

## 根本原因と症状

コードは実際の問題を直しているか、それとも症状を糊塗しているか。

これに答えるには、変更されたファイルの外を見る必要があることが多い。周辺のコード（呼び出し側、呼び出される側、型定義、兄弟モジュール）を読み、変更が置かれるアーキテクチャを理解する。利用できるツール（Read、Grep、Glob）を使って探索する。呼び出しチェーンを追う。型を読む。変更が正しいレイヤーに対処しているかを判断する前に、そのコードがなぜ存在するかを理解する。

- より深い不変条件の違反を覆い隠すガード節
- 壊れた契約を隠すリトライロジック
- モデリングの誤りを黙らせる型キャスト
- 回避策を見たら問う。なぜその回避策が必要なのか。適切な修正はどのような形になるか。
- 本当はモジュール B の契約の修正であるべき、モジュール A での修正
- 構造のほうが良いところに指示がある場合: 修正が「X をしないこと」というコメントや、誰かが覚えておかなければならない慣習なら、代わりに型制約、リントルール、または誤ったことを不可能にする実行時チェックにできないかを問う

## 構造的な整合性

コードはそれが属するシステムにうまく収まっているか。

- 境界の規律: バリデーションはシステム境界にあるか、それともビジネスロジックのあちこちに散っているか。データはシステムに入る場所で一度バリデーションし、内部ではそれを信頼する。
- 抽象化のレベル: コードは高レベルのオーケストレーションと低レベルの詳細を混ぜていないか。
- 結合: この変更は将来の変更を難しくする依存関係を持ち込んでいないか。
- データモデルの適合: データ構造は実際のアクセスパターンに合っているか。正しい構造は下流のコードを自明にする。誤った構造は事あるごとに抵抗する。
- 後付けか統合か: 変更は既存の設計に貼り付けられたのか、それとも設計が最初からそれを織り込んでいたかのように読めるか。新しい要件が最初から分かっていたら、コードはこのような形になっていたか。
- レガシーの二重パス: 変更は古い API を生かしたまま新しい API を導入していないか。外部の利用者がいないなら、同じ一回の変更で呼び出し側を移行し、古いパスを削除する。恒久化してしまう互換レイヤーを残さない。

抽象化がないことで単純なコードを減点しない。早すぎる抽象化は重複より悪い。

## 検証

このコードが動くことを、読んで分かるか。

- テストはあるか。テストは振る舞いをテストしているか、実装の詳細をテストしているか。
- リグレッションを捕まえるアサーション／不変条件はあるか。
- これがバグ修正なら、そのバグに対するテストはあるか。
- これが統合境界に触れるなら、パス全体がテストされているか。
- 代替指標ではなく実物を確認する。コードが実際の値を読む代わりにファイルの mtime やキャッシュされた状態で生存確認をしているなら、それは検証の穴である。
- 委任した作業や非同期の作業について、コードは実際の出力成果物を検証しているか、それとも自己報告と要約を信頼しているか。

## 複雑さの予算

複雑さはコードが達成することによって正当化されているか。

- 正確性や明快さを失わずにもっと単純にできるコード
- 呼び出し箇所が 1 つしかない抽象化
- まだ存在しないケースのための設定やパラメータ化
- デッドコード、未使用のインポート、痕跡的なパラメータ
- 過剰設計: 現在の呼び出し側がいない「念のため」のコードパス
- もう必要のない移行期の安定性のために生かされている、時代遅れの互換パス。移行が完了しているなら足場を削除する
- ユーザー体験は複雑さを正当化しているか。すべての機能、コントロール、オプションはその居場所を自ら獲得すべきである。半端に完成した機能は、ない機能より悪い。

単純なほうが誤りでない限り、単純なほうが良い。3 行の重複は早すぎる抽象化に勝る。

## セキュリティ

コードを通じて実際に追跡できるセキュリティ問題だけを指摘する。入力パスを示さない「これはインジェクションの経路になりうる」は有用ではない。

- サニタイズなしに危険なシンク（SQL、シェル、eval、innerHTML）へ流れるユーザー入力
- 新しいエンドポイントの認証／認可の穴
- コード、ログ、エラーメッセージ内のシークレット
- セキュリティ上重要なパスにおける TOCTOU（time-of-check-time-of-use）
