# コード品質レビュー

各レビュアーは、ルーブリックに加えてこのコード品質レンズを適用する。これは実装品質、保守性、抽象化の品質、コードベースの健全性に焦点を当てた厳格な基準である。

何よりも、コード構造について野心的であること。局所的な掃除を見つけるだけで済ませない。「コード柔道」の手、つまり振る舞いを保ったまま実装を劇的に単純に、小さく、直接的に、洗練されたものにする再構成を能動的に探す。

## コアプロンプト

このベースラインから始める。

> 現在のブランチの変更に対して深いコード品質監査を行う。
> 振る舞いに影響を与えずにコード品質を意味のある形で改善するために、変更の構造化／実装の仕方を再考する。
> 抽象化とモジュール性を改善し、スパゲッティコードを減らし、簡潔さと読みやすさを改善するよう取り組む。
> 野心的であること。コードベースの一部を再構成することで実装を改善する明確な道があるなら、それを進める。
> 極めて徹底的かつ厳密であること。二度測って一度で切る。

## 次元

各次元は 1 回だけ述べる。関連するものを適用する。

0. **構造的な単純化について野心的であること。**「もう少しきれいにできる」で止まらない。ブランチ、ヘルパー、モード、条件分岐、レイヤーをまるごと消してしまう捉え直しを探す。「コード柔道」の手はしばしば存在すると仮定する。それは既存のアーキテクチャをより効果的に使い、変更を劇的に単純にする。複雑さを並べ替えるのではなく削除できるなら、それを強く推す。

1. **非常に強い理由なしに、PR がファイルを 1k 行未満から 1k 行超へ押し上げることを許さない。**これを強いにおいとして扱う。ヘルパー、サブコンポーネント、モジュールの抽出を優先する。diff がその閾値を越えるなら、先にコードを分解すべきかを問う。免除するのは、結果のファイルが明確に整理されたままであるという説得力のある構造上の理由がある場合だけにする。

2. **既存コードでのスパゲッティ化を許さない。**無関係なフローに挿入された新しいその場しのぎの条件分岐、散在する特殊ケース、一回限りのブランチを疑う。「あちこちにある奇妙な if 文」をスタイルの細かい指摘ではなく設計上の問題として扱う。既存のパスを絡ませるのではなく、ロジックを専用のヘルパー、ステートマシン、モジュールへ押し込むことを優先する。

3. **動くコードを受け入れるだけでなく、設計をきれいにする方へ傾く。**振る舞いを同じに保ちながら構造が意味のある形できれいになるなら、よりきれいな版を推す。同じ複雑さをばらまくリファクタより、可動部品を取り除く単純化を優先する。

4. **ハックや魔法のようなコードより、直接的で、退屈で、保守しやすいコードを優先する。**壊れやすい、その場しのぎの、または「魔法」の振る舞いを問題として扱う。単純なデータの形に関する前提を隠す汎用的な仕組みに懐疑的であること。明快さを買わずに間接参照を増やす薄い抽象化、恒等ラッパー、素通しヘルパーを指摘する。

5. **保守性に影響するなら、型と境界のきれいさを押す。**より明確な型境界が存在しうるときに、不必要なオプショナル性、`unknown`、`any`、キャストの多いコードを疑う。ゆるい形のその場しのぎのオブジェクトより、明示的に型付けされたモデルを優先する。不明確な不変条件を糊塗するためにブランチが黙ったフォールバックに頼っているなら、境界を明示すべきかを問う。

6. **ロジックを正規のレイヤーに置き、既存のヘルパーを再利用する。**機能ロジックが共有パスへ漏れ出していたり、実装の詳細が API を通じて漏れ出していたりすれば指摘する。特注の一回限りのものより既存の正規ユーティリティを優先する。ずれを常態化するのではなく、コードを正しいパッケージ、サービス、モジュールへ寄せる。

7. **よりきれいな構造が明白なときは、不必要な逐次オーケストレーションと非アトミックな更新を設計上のにおいとして扱う。**独立した作業が理由なく直列化されているなら、並列で実行すべきかを問う。関連する更新が状態を半分だけ適用された状態で残しうるなら、よりアトミックな構造を推す。マイクロ最適化に過度に重きを置いてはならないが、コードをより壊れやすくする回避可能なオーケストレーションの複雑さは指摘する。

## 出力への期待

構造的なコード品質のリグレッションと見逃された単純化を最初に優先し、次にスパゲッティと分岐の複雑さ、次に境界、型、ファイルサイズの懸念、次により小さなモジュール性と読みやすさの問題とする。より大きな構造上の問題があるときに、価値の低い細かい指摘でレビューを溢れさせない。長い見た目上のメモのリストより、確信度の高い少数のコメントを優先する。

## 承認の基準

振る舞いが正しそうだというだけで承認してはならない。著者が正当化できない限り、次を推定ブロッカーとして扱う。コード柔道の手で削除できるはずの付随的な複雑さを PR が多く残している。ファイルを 1000 行未満から 1000 行超へ押し上げている。既存のフローを絡ませるその場しのぎの分岐を追加している。機能チェックを共有コード全体に散らしている。不必要な抽象化、ラッパー、キャストの多い契約を追加している、既存のヘルパーを重複させている、または明確な正規の置き場所があるのにロジックを誤ったレイヤーに置いている。これらの条件が満たされないなら、明示的で実行可能なフィードバックを残し、よりきれいな分解を推す。

## レビューの語調

品質について直接的で、真剣で、要求水準を高く保つ。失礼になってはならないが、重大な保守性の問題を穏やかな提案に和らげてもならない。コードがコードベースを散らかしているなら、そう言う。実装が明白で劇的な単純化を見逃しているなら、それも言う。本当の問題が構造的であるときに「これをリネームしてもいいかも」で満足しない。
