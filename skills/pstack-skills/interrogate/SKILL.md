# Interrogate

設定されたモデルごとにレビュアーを 1 つ起動し、コード変更を敵対的にレビューする。各モデルには同じプロンプトとルーブリックを渡す。敵対的なシグナルは、割り当てたペルソナではなくモデルの多様性から生まれる。

成果物は統合された判定である。変更を自動で適用してはならない。

**ディスパッチ契約。** レビュアーを起動する前に [`provider-dispatch.md`](../poteto-mode/references/provider-dispatch.md) を読む。設定されたエントリはプロバイダ修飾付きのディスクリプタであり、親がネイティブと外部の読み取り専用レーンを直接起動する。Codex 上では、残りの Claude ツール名を [`codex-tools.md`](../poteto-mode/references/codex-tools.md) で解決する。

## ステップ 1、スコープを決める

コンテキストからレビュー対象を特定する。

- ユーザーが特定のファイルや diff を指しているなら、それを使う
- フィーチャーブランチ上にいるなら、`git diff main...HEAD`（または適切なベースブランチ）を実行して変更セット全体を取得する
- ユーザーのメッセージが最近の作業を参照しているなら、関連ファイルを集める

diff（またはファイル内容）に加えて、レビュアーがコードを理解するために必要な周辺のコンテキストファイルをまとめる。

## ステップ 2、意図を明示する

レビュアーを起動する前に、意図を明示的に述べる。次から導く。

- ユーザーのメッセージ
- コミットメッセージ
- PR の説明（存在する場合）
- コードそのもの

明確な段落を 1 つ書く。意図に確信が持てないなら、先へ進む前にユーザーに尋ねる。

## ステップ 3、レビュアーを起動する

すべてのレビュアーを 1 回のファンアウトフェーズで起動する。現在のハーネスの pstack モデルシートに `interrogate reviewers` があればそれを使い、エントリごとにレビュアーを 1 つ割り当て、下記のレビュアー A/B/C/D のラベルを設定されたエントリ数に合わせて増減する。なければ表のデフォルトを使う。ネイティブのレビュアーは親のサブエージェントプリミティブを使う。外部のレビュアーはランチャーを直接使い、モデル検証済みの完全なレシートを返さなければならない。

| サブエージェント | デフォルトモデル |
|----------|---------------|
| レビュアー A | `claude:fable@max` |
| レビュアー B | `codex:gpt-5.6-sol@max` |
| レビュアー C | `grok:grok-4.6@xhigh` |
| レビュアー D | `claude:opus@xhigh` |

各レビュアーについて、設定されたディスクリプタを `read-only` アクセスと一意の出力／レシートパス付きでルーティングする。ディスクリプタが `inherit-parent` または `auto` なら、モデルの上書きなしで親のサブエージェントプリミティブを使う。プロバイダ、ログイン、またはモデルが利用できないなら、ドロップアウトを記録し、完了したレビュアーで続行する。最も近いモデルを選んだり黙ってフォールバックしたりしてはならない。それはプロバイダ横断の合意の意味を壊す。

`references/reviewer-prompt.md` を読み、テンプレートに次を埋める。
1. 明示した意図
2. diff またはファイル内容
3. `references/rubric.md` のレビュールーブリック
4. `references/code-quality-review.md` のコード品質レンズ

埋めた同じテンプレートをすべてのレビュアーに渡すので、すべてのモデルがコード品質レンズを適用する。

## ステップ 4、統合する

結果が返ってきたら、統一された全体像を組み立てる。

1. レビュアーからの**すべての指摘をパースする**
2. **合意を特定する**。2 つ以上のモデルが独立に挙げた指摘が最も強いシグナルである。
3. **単独モデルの指摘を特定する**。読む価値はあるが、それに応じて重みを付ける。
4. **重複を除く**。異なるモデルが同じ問題を異なる言い方で記述することがある。これらを統合し、どのモデルが挙げたかを記す。
5. **不一致を記す**。あるモデルが何かを指摘し、別のモデルが明示的にその逆を述べているなら、それは判定に役立つコンテキストである。

## ステップ 5、リードの判断

自分はリードレビュアーであり、実利主義のシニアエンジニアであって、中立な集約者ではない。

完全なフレームワークは `references/lead-judgment.md` を読む。

すべての指摘を次のバケットで分類する。

- **対応する**。実際の目標に照らして、正確性、セキュリティ、または保守性に影響する本物の問題。実際の PR ならブロックするもの。
- **検討する**。正当な指摘だが、今それに対応するコストを上回るかどうか確信がないもの。ユーザーの注意に値する。
- **記録のみ**。技術的には正しいが、対応の対象にはならないもの。コンテキスト依存、早すぎる最適化、または現在の段階では影響が小さいもの。
- **却下**。誤り、些末、またはコンテキストを欠いているもの。理由を簡潔に説明する。

各指摘について次を含める。
- どのモデルが挙げたか
- カテゴリ（対応する／検討する／記録のみ／却下）
- 分類の 1 行の根拠説明

## 出力形式

判定を次の構造で提示する。

### 意図
> [ステップ 2 で明示した意図の段落]

### レビュアー
- レビュアー [ラベル]: [モデル名]、[N 件の指摘]（レビュアーごとに 1 項目）

### 対応する
[対応すべき指摘。各項目に、説明、どのモデルが挙げたか、なぜ重要か。]

### 検討する
[検討に値する指摘。各項目に、説明、どのモデルが挙げたか、関係するトレードオフ。]

### 記録のみ
[正しいが優先度の低いもの。簡潔なリスト。]

### 却下
[却下した指摘と簡潔な根拠説明。]

### 合意マップ
[モデルはどこで一致し、どこで分かれたか。一致と不一致のパターンは何を示しているか。]
