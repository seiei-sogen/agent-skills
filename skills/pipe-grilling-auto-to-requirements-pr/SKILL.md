# 要件ドラフトを自動壁打ちして PR にする

指定された要件定義書の下書きを事前調査し、その JSON を根拠に自動で詰め、品質を上げたうえで、その変更を説明する GitHub PR を作成する。ソースコードの実装や PR の merge は行わない。

## 子スキルと優先順位

開始時に次のスキルを利用できることを確認し、それぞれを実行する段階で `SKILL.md` を最後まで読む。

- `pre-investigation-report`
- `grilling-jp`
- `quality-gated-review-improve`
- `asciidoc-to-colorful-html`
- `pr-update-gh`

指示が衝突する場合は、現在のユーザー指示、この親スキルの段階固有の指示、子スキルの通常指示の順に優先する。子スキルが見つからなければ、同等手順で代替せず、見つからないスキル名を報告して停止する。

この親スキルが上書きするのは、`grilling-jp` の「意思決定ごとにユーザー回答を待つ」という規則だけである。自動壁打ち中は各推奨回答をユーザー回答として採用する。それ以外の子スキルの制約と停止条件は維持する。

## 入力と開始状態を確定する

`$ARGUMENTS` は、初期の要件定義書下書き1件のローカルファイルパスとする。

1. パスを解決し、既存の通常ファイルで、内容が空ではないことを確認する。
2. `git rev-parse --show-toplevel` で現在の Git リポジトリを特定し、入力ファイルがその配下にあることを確認する。
3. 入力ファイルの現在内容、形式、文字コード、見出し構造を確認する。この内容を壁打ちの原本として扱う。
4. 現在のブランチ、remote、upstream、GitHub CLI の認証状態、作業ツリーを確認し、開始時点の変更一覧を記録する。

パスがない、複数ある、ディレクトリである、リポジトリ外にある、または空ファイルである場合は、ファイルを変更せず停止する。detached HEAD、GitHub CLI の未認証、または push 先を一意に確定できない状態でも、ファイルを変更する前に停止する。入力ファイルに未コミット変更があっても、その現在内容をユーザーが指定した下書きとして扱う。入力ファイル以外の既存変更は変更、stage、commit しない。

## Phase 1: 事前調査レポートを生成する

入力ファイル名から拡張子と先頭の `req-` または `requirements-` を除き、小文字の英数字とハイフンへ正規化した値を `<requirements-slug>` とする。連続するハイフンを1つにまとめ、前後のハイフンを除く。空になる場合は `requirements` を使う。issue ID がファイル名に含まれる場合は slug に残す。

調査レポートは入力ファイルと同じディレクトリへ、次の名前で保存する。

```text
pre-investigation-report-<requirements-slug>.json
```

たとえば `req-issue244-backend-refactor-unify-db-connection-pool.adoc` の調査レポートは、`pre-investigation-report-issue244-backend-refactor-unify-db-connection-pool.json` とする。

同名ファイルがある場合は、有効な JSON で、`related_files` などから同じ入力ファイルの調査成果物だと確認できた場合だけ再生成する。別対象のファイル、または判定できないファイルは上書きせず停止する。

入力ファイルを調査入力、上記 JSON を保存先として `pre-investigation-report` を実行する。要件を具体化するために必要な関係ファイル、現状の責務、制約、既存パターン、未確定事項、推奨探索起点を根拠付きで調査させる。この Phase では、調査レポート以外のファイルを変更しない。

生成後、JSON として parse でき、子スキルの必須フィールドを持ち、`related_files`、`constraints`、`existing_patterns` に根拠パスがあり、未確定事項が `open_questions` に分離されていることを確認する。調査レポート以外へ予期しない変更があれば、その変更を巻き戻さず、対象を報告して停止する。検証済みの保存先を以後「調査レポート」とする。

## Phase 2: 推奨回答を自動採用して要件を確定する

入力ファイルを検討対象、調査レポートを読み取り専用の根拠として `grilling-jp` を実行する。この Phase に限り、同スキルの質問待ちを次の自動モードへ置き換える。

1. 下書きと調査レポートを読み、目的、想定利用者、対象範囲、制約、既知の事実を把握する。
2. 事実は調査レポートの根拠パスで確認し、`open_questions` と意思決定を区別する。調査レポートにない事実を推測したり、同じコード探索をやり直したりしない。
3. 残る論点を依存順に並べる。
4. 論点ごとに質問、選択肢、推奨回答、根拠、影響、不確実性を内部で整理する。
5. 推奨回答をユーザー回答として自動採用し、依存する次の論点へ進む。
6. 主要論点と、回答から派生した論点が尽きるまで繰り返す。

確認できない事実を推奨回答で作らない。安全に確定できない事項は、実装を妨げないなら要件内へ「要確認」と確認方法を残す。セキュリティ、法令、データ損失、不可逆操作、外部契約に関わり、安全な推奨を置けない場合は、入力ファイルを上書きせず停止して判断が必要な論点を報告する。

採用した判断を統合し、元の意図、調査レポートで確認した事実、文書形式を保った完成版を作る。少なくとも、目的、対象と対象外、観測可能な受け入れ条件、正常系、境界条件、失敗時挙動、前提と制約、採用した判断と理由、未確定事項を実装者が追える状態にする。調査レポートを根拠にした重要な制約や既存パターンは、要件内でも参照元が追えるようにする。

完成版だけを入力ファイルへ上書きする。別名の要件定義書は作らない。上書き後に再読し、採用した推奨回答が反映され、元の意図と確認済みの事実が失われていないことを確認する。

## Phase 3: 調査レポートを根拠に品質ゲートを通す

入力ファイルを唯一の改善対象、調査レポートを読み取り専用の根拠として `quality-gated-review-improve` を実行し、最良版を同じ入力ファイルへ反映させる。呼び出し時に両ファイルの役割を明示し、調査レポート自体は変更しない。要件定義書として、特に次を採点と改善の対象に含める。

- 目的、読者、対象範囲、対象外が一意に読める。
- 要件と受け入れ条件が具体的で検証可能である。
- 境界条件、失敗時挙動、互換性、運用上の制約に漏れがない。
- 採用した判断の理由と、未確定事項の確認方法が追える。
- 調査レポートの `constraints`、`existing_patterns`、`open_questions` と矛盾せず、重要な根拠の反映漏れがない。
- 入力にない事実を断定せず、元の意図を保持している。

子スキルの既定どおり80点以上を最低合格、90点以上を合格目標とし、到達可能なら100点を目指す。最終点が80点未満なら、HTML 生成、commit、push、PR 作成へ進まず、終了理由と残課題を報告する。

最終版を再読し、Markdown または AsciiDoc の構造が壊れていないこと、調査レポートが変更されていないこと、対象成果物以外を変更していないことを確認する。子スキルが調査レポートまたは対象成果物以外へ予期しない変更を加えた場合は、その変更を巻き戻さず、対象を報告して Git 操作前に停止する。

## Phase 4: 要件定義書を単体 HTML にする

入力ファイルが AsciiDoc（`.adoc`、`.asciidoc`、`.asc`）の場合、品質ゲートを通過した最終版を入力として `asciidoc-to-colorful-html` を実行し、同じディレクトリへ拡張子だけを `.html` に替えた単体 HTML を生成する。入力ファイル自体は変更しない。

同名 HTML が既にある場合は、このパイプラインが生成した HTML だと確認できたときだけ `-force` で再生成し、確認できない場合は上書きせず対象を報告して停止する。変換に失敗した場合、または子スキルの出力契約を満たさない場合は、壊れた HTML を成果物として扱わず、Git 操作前に停止する。変換警告から include、画像、xref などの文書不備が判明した場合は、Phase 3 に戻って AsciiDoc を修正・再評価してから HTML を作り直す。

生成後に HTML を再確認し、空でないこと、`<style>` があり `<link rel="stylesheet">` がないこと、文書タイトルと主要な見出しが最終版と一致することを確かめる。検証済みの HTML を以後「要件 HTML」とする。

入力ファイルが AsciiDoc でない場合はこの Phase を省略し、省略した理由を最終報告に記載する。以後の Phase では要件 HTML を対象成果物から除く。

## Phase 5: 対象成果物だけを commit・push する

Git と GitHub の状態を再取得し、リポジトリの既定ブランチを base とする。現在のブランチが既定ブランチなら、リポジトリの命名規則に従って要件更新用の作業ブランチを作る。規則がなければ、入力ファイル名から安全な slug を作り、`docs/<slug>-requirements` とする。既存の同名ブランチを推測で再利用しない。

既定ブランチから作業ブランチを作る場合は、既定ブランチと upstream が同じ commit を指すことを確認する。先行、遅延、分岐がある場合は、pull、rebase、reset を行わず停止する。入力ファイルまたは調査レポートに秘密鍵、認証情報、`.env` の実値など公開すべきでない情報が含まれる可能性が高い場合も、値を伏せて該当箇所を報告し、commit 前に停止する。

現在のブランチにオープンな PR がある場合は、その PR を後続で再利用する。PR がなく、base との差分に対象成果物と無関係な既存 commit が含まれる場合は、意図しない変更を PR に混ぜず、commit 前に対象を報告して停止する。

1. `git add -- <入力ファイル> <調査レポート> <要件 HTML>` で対象成果物だけを stage する。要件 HTML がない場合は前2件だけを stage する。
2. `git diff --cached` と `git status --short` を確認し、対象が入力ファイル、調査レポート、要件 HTML だけであることを確かめる。
3. リポジトリの規約に従う短い件名で1回 commit する。
4. upstream があれば通常の `git push`、なければ `origin` へ `git push --set-upstream origin <現在のブランチ>` を1回実行する。

stage する差分がなく、再利用できる PR もない場合は、PR を作成せず「PR にする差分がない」と報告する。commit hook または push が失敗した場合は回避せず、force push、rebase、pull、追加 commit へ進まず、現在の状態を報告する。

## Phase 6: PR を作成して平易な本文へ更新する

push 後、現在のブランチに紐づくオープンな PR を再確認する。PR がなければ、既定ブランチを base、現在のブランチを head として `gh pr create` で1件作成する。タイトルは「どの要件をどう具体化したか」が初見で分かる短い日本語にする。初期本文には少なくとも、変更対象、調査で判明した主要な制約、決めたこと、品質ゲートの結果、確認してほしいことを記載する。

PR が存在する状態になってから `pr-update-gh` を実行する。同スキルへ次の品質要求を追加する。

- リポジトリや機能の前提知識がない読者でも「何を決め、何が変わるか」を理解できる。
- 専門用語や略語は最初に短く説明する。
- 一文一義を基本にし、並列情報は箇条書きにする。
- 「改善」「対応」だけで済ませず、受け入れ条件や対象外を具体的に書く。
- 調査レポートの役割と、要件へ反映した主要な制約・既存パターン・未確定事項を説明する。
- 品質点、検証結果、影響は確認できた事実だけを書く。

更新後は PR の URL、title、body、base、head、state を再取得し、現在のブランチのオープンな PR であることと、本文に変更対象と内容が平易に記載されていることを確認する。PR 作成または更新に失敗した場合は、別の PR を選んだり同じ外部変更を無制限に繰り返したりせず、作成済み commit と push 状態を含めて報告する。

## 実行権限と完了条件

このスキルの全工程を依頼されたことは、調査レポートの生成、指定ファイルの上書き、要件 HTML の生成、必要な作業ブランチの作成、対象成果物だけの commit・push、PR の作成・本文更新を進める根拠になる。環境が個別承認を要求する操作では、その場で承認を求める。PR の merge、ソースコードの実装、対象成果物以外の stage は行わない。

再実行時は、既存 commit、upstream、オープンな PR を確認し、同じ commit や PR を重複して作らない。

次をすべて満たしたときだけ完了とする。

- 調査レポートが有効な JSON で、事実、制約、既存パターン、未確定事項を根拠付きで含む。
- 入力ファイルが調査レポートを参照して自動採用した推奨回答と、品質改善後の最良版を含む。
- 品質点が80点以上で、終了理由が記録されている。
- 入力ファイルが AsciiDoc の場合、その最終版から生成した要件 HTML が存在し、出力契約を満たす。
- 対象 commit が remote に存在する。
- 現在のブランチに紐づくオープンな PR の本文を再取得して確認している。
- 対象成果物以外の既存変更を commit していない。

最後に、更新した要件定義書、生成した調査レポート、要件 HTML のパス（省略した場合はその理由）、調査で判明した主要事項、採用した主要判断、最終品質点と終了理由、検証結果、ブランチ、commit hash、PR URL、残課題を簡潔に報告する。
