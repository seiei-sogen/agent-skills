# トリアージ

プロジェクトの課題トラッカー上で、トリアージ役割の小さな状態機械を通じて課題を移動させます。

もしこのリポジトリが外部プルリクエストをリクエストサーフェスとして扱う場合（イシュートラッカーの設定を参照）、トリアージはそれらもカバーします：**PRはコードが添付された問題です**。同じロール、同じステート、同じマシンを使用し、一部の差分が下記の「PR用」としてマークされています。トラッカーの設定に従って、裸の`#42`を問題またはPRに解決してください。

トリアージ中に課題トラッカーに投稿されるすべてのコメントや問題には、**必ず**次の免責事項を先頭に付ける必要があります:

```
> *This was generated by AI during triage.*
```

## 参照ドキュメント

- [AGENT-BRIEF.md](AGENT-BRIEF.md): 耐久性のあるエージェントブリーフの書き方
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md): `.out-of-scope/` 知識ベースの仕組み

## 役割

二つの**カテゴリ**役割:

- `bug`: 何かが壊れている
- `enhancement`: 新機能または改善

五つの**状態**役割:

- `needs-triage`: メンテナーが評価する必要があります
- `needs-info`: 追加情報のために報告者を待っています
- `ready-for-agent`: 完全に指定済みで、AFKエージェントの準備ができています
- `ready-for-human`: 人間による実装が必要です
- `wontfix`: 処理されません

PRの場合、添付されたコードに対して同じステートが次のように読まれます：`ready-for-agent` は概要が添付されており、エージェントが差分に対して次のステップを踏むべきことを意味します；`ready-for-human` は人間がマージする準備ができていることを意味します。

すべてのトリアージ済みの問題には、正確に1つのカテゴリーロールと1つのステートロールを持たせる必要があります。ステートロールが競合する場合は、何もする前にそれをフラグとしてマネージャーに確認してください。

これらは標準的な役割名です。実際に課題トラッカーで使用されるラベル文字列は異なる場合があります。マッピングは提供されているはずです。もし提供されていない場合は、ユーザーに`/setup-matt-pocock-skills-matt-ryu`を実行するよう伝えてください。

状態遷移: ラベルのない問題は通常、最初に`needs-triage`に行きます。そこから`needs-info`、`ready-for-agent`、`ready-for-human`、または`wontfix`に移動します。`needs-info`は、報告者が返信すると`needs-triage`に戻ります。メンテナーはいつでも上書きできます; 異常に見える遷移にはフラグを立て、進める前に確認してください。

## 呼び出し

メンテナーは`/triage-matt-ryu`を呼び出し、自然言語で望むことを説明します。リクエストを解釈して行動してください。例：

- 「注意が必要なものをすべて見せて」
- 「#42を見てみましょう」（Issue または PR）
- 「#42を ready-for-agent に移動」
- 「エージェントが取り掛かる準備ができているのは何？」

## 注意が必要なものを表示してください

Issue トラッカーをクエリして、3つのバケットに並べて表示してください。古いものから順に：

1. **未ラベル**: 一度もトリアージされていないもの。
2. **`needs-triage`**: 評価中。
3. **`needs-info`（前回のトリアージメモ以降のレポーター活動あり）**: 再評価が必要。

PR が対象範囲にある場合、これらのバケットに外部 PR を含め、各行に `[PR]` または `[issue]` とタグを付けます。ディスカバリーは *外部* PR のみを表面化します（トラッカーの設定で誰が外部としてカウントされるかが定義されます）、つまり協力者の進行中の PR はトリアージ作業ではありません。このフィルターはディスカバリー専用です。明示的に指定された PR は、作成者に関係なく常にトリアージされます。

各アイテムごとの件数と一行の概要を表示します。メンテナーに選んでもらいます。

## 特定のイシューまたはPRをトリアージします

1. **文脈を集める。** 問題やPRの全文（本文、コメント、ラベル、作成者、日付；PRの場合は差分も）を読む。以前のトリアージノートを解析して、すでに解決された質問を再度尋ねないようにする。プロジェクトのドメイン用語集を使ってコードベースを探索し、その領域のADRを尊重する。コードベースに対して2つのチェックを実行する: (a) **冗長性**: ドメイン概念による要求された動作の既存の実装を検索（要求の文言だけでなく）し、どこを調べたか報告する。見つかった場合、それはすでに実装されている`wontfix`（ステップ5）である。 (b) **以前の却下**: `.out-of-scope/*.md`を読み、この要求に似ているものを洗い出す。

2. **推奨。** メンテナーに自分のカテゴリを伝え、理由付きで推奨事項を述べ、要求に関連する簡単なコードベースの概要（すでに実装されているかどうかも含む）を添えてください。指示を待ちます。

3. **主張を検証する。** 壁打ちを始める前に、その主張が正しいか確認してください。バグの場合は、報告者の手順から再現します。PRの場合は、差分が主張通りのことをしているか確認してください：チェックアウトし、関連するテストやコマンドを実行します。結果を報告します：確認済み（コードパス付き）、失敗、または詳細不足（強い`needs-info`信号）。確認済みの検証は、はるかに強力なエージェントブリーフを作ります。

4. **必要に応じてグリルする。** 要求内容を具体化する必要がある場合は、Skillツールを2回呼び出し、`grilling-matt-ryu`と`domain-modeling-matt-ryu`を行い、質問ごとに形を整え、ドメイン用語を洗練させ、意思決定が決まったら`CONTEXT.md`/ADRをインラインで更新する。

5. **結果を適用する:**
   - `ready-for-agent`: エージェント向けの簡単なコメントを投稿する（[AGENT-BRIEF.md](AGENT-BRIEF.md))）。
   - `ready-for-human`: エージェントブリーフと同じ構造ですが、なぜ委任できないのかを記録してください（判断が必要な作業、外部アクセス、設計判断、手動テストなど）。
   - `needs-info`: トリアージ後のメモ（以下のテンプレート）。
   - `wontfix`の場合は、理由に応じてコメントを付けて課題をクローズしてください。
     - **実装済み**: 変更はすでにコードベースにある。実装箇所を示す。`.out-of-scope/`には書かない（そこは*却下した*要望の記録であり、実装済みのものは対象外）。
     - **却下（バグ報告）**: 丁寧に理由を説明してからクローズする。
     - **却下（機能改善）**: `.out-of-scope/`に記録し、コメントからリンクしてクローズする（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`: 役割を適用します。部分的な進捗がある場合はコメントは任意です。

## 状態の上書きをすぐに行う

メンテナーが「#42をready-for-agentに移動」と言った場合は、彼らを信頼し、役割を直接適用してください。行うこと（役割の変更、コメント、クローズ）を確認してから実行してください。突っ込んだ質問は省略してください。もし`ready-for-agent`に移動する場合で壁打ちセッションがない場合は、エージェントブリーフを書きたいかどうかを尋ねてください。

## Needs-infoテンプレート

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

壁打ち中に解決されたすべてのことを「これまでに確立されたもの」の下に記録して、作業が失われないようにしてください。質問は具体的で実行可能なものである必要があり、「詳細情報を提供してください」のようなものではいけません。

## 前回のセッションを再開する

もし問題やプルリクエストに以前のトリアージノートが存在する場合、それを読み、報告者が未解決の質問に答えているか確認し、続行する前に最新の状況を示してください。解決済みの質問を再度尋ねないでください。
