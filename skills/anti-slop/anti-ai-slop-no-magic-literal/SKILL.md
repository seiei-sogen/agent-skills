# マジックリテラルを整理する

意味を持つリテラルの用途や取りうる集合を、名前と定義から読み取れる形にする。定数化によって、同じ概念の値が複数箇所で食い違うことを防ぐ。

## 1. 対象と使用言語を確認する

依頼されたファイルまたは差分を対象にする。次の資料を対象ファイルの言語に応じて読み、依存関係、既存の定数・列挙・スキーマ、呼び出し元を確認する。

- TypeScript は [typescript.md](references/typescript.md) を読む。
- Ruby は [ruby.md](references/ruby.md) を読む。
- ほかの言語は共通手順に従い、その言語の標準機能とプロジェクトの規約を使う。

複数言語の変更では、ファイルごとに対応する資料を使う。言語固有の列挙機能や命名を、ほかの言語へそのまま当てはめない。

## 2. 候補を検出し、修正対象を選ぶ

次の箇所を候補として列挙する。リテラルがあるという理由だけで修正しない。

- 状態・種別・ロールなどを、リテラルと直接比較する箇所。
- 分岐の選択肢や集合への所属判定に、値を直接列挙する箇所。
- ドメイン上の値を、引数、キー、添字として直接指定する箇所。
- 同じ概念を表すリテラルが、複数箇所で繰り返される箇所。
- 上限、期間、サイズなど、数値だけでは意味や単位が分からない箇所。

次は原則として対象外にする。

- 1箇所だけで使い、意味が自明なファイル名など。
- ログやエラーメッセージの本文。
- テストの固定値や期待値。検証対象の定義へ合わせて独立した根拠を失わせない。
- 外部仕様で固定された、1回だけ使うキー。
- 値が1つだけで、列挙にしても理解が深まらないもの。

判断基準は、読み手が値の用途や取りうる集合を知る必要があるか、同じ概念の値を一緒に変更すべきかとする。同じ値でも、意味が異なるものはまとめない。

## 3. 値の定義を1箇所にまとめる

候補ごとに、同じ値と意味を持つ既存の定数・列挙・スキーマを探して再利用する。定義がなければ、プロジェクトで採用済みの機構か、その言語の標準機能で表す。単純な定数化のために依存関係を追加しない。

- 値の集合は1箇所で定義し、必要な型や一覧は、利用できる導出機能でそこから得る。
- 数値には意味が分かる名前を付け、期間やサイズは単位も名前に含める。
- 元の値、型、単位、評価のタイミングを保つ。リテラルが毎回作られていた場合は、定数化による共有や凍結で挙動が変わらないかも確認する。DB・API・設定ファイルの値を内部都合で変えない。
- 命名は言語とプロジェクトの規約に従う。
- 定義はそのドメインのモジュールに置く。1箇所でしか使わないなら、利用側のファイル内に置く。
- 無関係な値を巨大な共通定数ファイルに集めない。

対象とした同じ概念の参照をすべて更新する。分岐がある場合は、必要な選択肢と不正値の扱いが保たれていることを、言語が提供する網羅性チェックや関連テストで確認する。

公開 API や保存形式の変更が必要な置換は自動で進めず、影響と互換性を保つ代案を報告する。

## 4. 検証して報告する

差分と参照元を確認し、同じ値の二重定義、置換漏れ、過剰な定数化がないことを確かめる。利用できる関連テスト、型チェック、構文チェック、lint を実行する。検索や lint の指摘は発見の補助として使い、修正対象かどうかは手順2の基準で判断する。

修正した箇所と定義先、見送った箇所と理由、互換性の判断が必要な箇所、実行した確認を簡潔に報告する。実行できなかった確認は、その理由も伝える。
