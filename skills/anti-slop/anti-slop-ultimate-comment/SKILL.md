# コメントを残余に絞る

現在の差分のコメントを、挙動を変えずに「未来の変更者が誤らないために必要な残余」だけにする。理論の根拠は [sanko.md](sanko.md) にあり、判定に迷ったときだけ読む。

判定の基本は一行である。

```text
このコメントが消えたとき、未来の変更者が誤る確率は上がるか。
上がらないなら書かない。上がるなら、その人が自分で再導出できる前提の形で書く。
```

コードに書けないもの（残余）は次の 6 種類だけである。残すコメントは、手順 2 の How の例外を除き、このどれかに該当する。

| 残余 | 例 |
| --- | --- |
| 記述のもとでの意図 | 「3 回リトライ」ではなく「不安定なネットワークをやり過ごす」 |
| 様相（必然か偶然か） | この順序・この定数・この名前のどれが荷重を支えているか |
| 反実仮想（Why not） | 却下した代替案と、変えたら何が壊れるか |
| 非局所的な制約 | 「ここを変えるならあのファイルも」 |
| 外部世界への参照 | 法律、仕様書の節、論文、ハードウェアの errata、業務上の決定 |
| 規則の意図された延長 | 新しいケースをどう扱うべきかの理論 |

## 1. 対象を確定する

ユーザーが対象範囲を指定している場合は、その範囲を優先する。指定がなければ、現在のブランチの変更を対象にする。

1. ベースブランチとの差分と staged、unstaged、untracked の変更を確認する。
2. 変更行を含むコメントをすべて列挙する。変更されていない行のコメントは、変更行と同じ関数またはブロック内にあるものだけ加える。
3. 変更されたコードのうち、読み手の期待を裏切る箇所を列挙する。慣用句からの逸脱、値が荷重を支える定数、入れ替えると壊れる順序、リトライ・タイムアウト・sleep、無効化したチェック、回避策、別ファイルとの暗黙の結合がこれにあたる。
4. 各候補について、呼び出し元、関連する型・テスト、`git log` と `git blame`、リンクされた issue や PR を読み、前提の出どころを集める。

次のものは対象から外し、そのまま維持する。ライセンス表記、shebang、ツール向け指示（`eslint-disable`、`@ts-expect-error`、`# noqa`、`pragma` など）、docstring と TSDoc（宛先が呼び出し側なので別ジャンルに属する）。

列挙した既存コメントと驚きの箇所のそれぞれに、前提の出どころが「分かった」か「分からない」かを付けられたら、この手順は完了である。

## 2. 既存コメントを判定する

候補ごとに、最初に該当する判定を採用する。

1. **コードと食い違う**。前提が分かるなら手順 3 の形式で書き直す。分からないなら原文を残し、「要確認」として報告する。
2. **形式媒体が明瞭になれない領域の How**（数値計算、ビット演算、並行制御、プロトコルの癖）。How のままで残す。手順 3 の形式検査だけ行う。
3. **コードの言い換え**（How や What をなぞるだけ）。名前、型、構造、assert、テストで同じことを真にできるなら、そちらへ移してコメントを削除する。移せないなら削除する。
4. **残余に該当しない**（上の 6 種類のどれでもない）。削除する。
5. **残余に該当する**。残す。手順 3 の形式検査へ回す。

言い換えを形式媒体へ移す変更は、リネーム、型の絞り込み、assert の追加、テストケースの追加に限る。業務上の挙動、公開 API、永続化形式は変えない。

すべての既存コメントに「削除」「形式媒体へ移して削除」「残す」のどれかが付いたら、この手順は完了である。

## 3. 残すコメントの形式を検査する

残すコメントと手順 4 で追加するコメントに、次の 4 つの検査を順に適用し、通らないものは書き直す。

1. **結論ではなく前提**。「ここを消すな」「X を使うな」は、その指令が導かれる前提に置き換える。読み手が現在の条件で推論をやり直せる形にする。
2. **検証可能な事実に固定**。「新しい方の」「現在は」「最近」のような直示表現を、バージョン、日付、チケット番号、仕様書の節番号で固定する。「X は Y のとき deadlock する（#123）」のように反証可能にする。`TODO` や `FIXME` も同じ扱いで、固定子を付けられないものは削除する。
3. **失効条件**。前提が消えたときにコメントも消せるよう、何が変わったら不要になるかを書く。前提に失効条件が含まれているなら重ねて書かない。
4. **位置**。判断が行われるその行、誘惑が生じるその行に置く。関数の先頭やファイル末尾にまとめない。コミットログや設計書に書いてある前提でも、消えたら誤るものはその行に要約を置き、出どころを固定子として添える。

言語と記法は、同じファイルの既存コメントに合わせる。

書き直しの例を示す。

```text
書き直し前:
  // 消すな
  sleep(100)

書き直し後:
  // 上流 API は 10 rps 制限（docs/limits.md v3）。制限が撤廃されたら sleep も消す。
  sleep(100)
```

前提、固定子、失効条件のどれかが手順 1 で「分からない」になった場合は、推測で作らない。原文を残し、「要確認」として報告する。

残すコメントのすべてが 4 つの検査を通ったら、この手順は完了である。

## 4. 欠けているコメントを補う

手順 1 で列挙した驚きの箇所のうち、コメントがないものを扱う。候補ごとに、最初に該当する対応を採用する。

1. 名前、型、構造、assert、テストで驚きを消せるなら、そちらで消す。コメントは書かない。
2. 前提が分かっていて残余に該当するなら、手順 3 の形式でコメントを書く。
3. 前提が分からないなら書かない。「要確認」として報告する。

コメントの密度は驚きの大きさに比例させる。慣用句どおりの箇所には書かない。却下した代替案は、読み手がいま手を伸ばしそうな別案に限って書く。

驚きの箇所のすべてに「形式媒体で解消」「コメント追加」「要確認」のどれかが付いたら、この手順は完了である。

## 5. 検証して報告する

1. 差分を再確認し、変更がコメントと手順 2・4 の形式媒体への移行（リネーム、型、assert、テスト）だけであることを確かめる。
2. 利用できる formatter、lint、型チェック、構文チェック、関連テストを実行する。
3. 形式媒体への移行が原因で失敗した場合は、修正を 2 回まで試す。それでも通らなければその移行を戻し、元のコメントを手順 3 の形式で残す。

削除したコメント、形式媒体へ移した箇所、書き直したコメント、追加したコメント、要確認として残した箇所、実行した確認を簡潔に報告する。実行できなかった確認は、その理由も伝える。対象がなければ、その旨を報告して終了する。
