# AI Slop を取り除く

現在の差分を、契約と挙動を変えずに小さくし、処理を追いやすくする。対象言語の標準機能とプロジェクトの規約を使う。

基本とするデータフローは次のとおりである。

```text
信頼できない入力 -> 境界で必要な検証 -> 契約を確認した内部値 -> 直接的な業務処理
```

## 1. レビュー対象を確定する

ユーザーが対象範囲を指定している場合は、その範囲を優先する。指定がなければ、現在のブランチの変更を対象にする。

1. リポジトリの指示を読み、ベースブランチとの差分と staged、unstaged、untracked の変更を確認する。
2. 変更されたコードとテストのファイルを、言語ごとに列挙する。
3. 変更された関数、その呼び出し元、入力を定義する型・契約・スキーマを読む。
4. 入力を、信頼できない境界値または契約を確認済みの内部値に分類する。

変更箇所の入力と、追加されたガード、ヘルパー、フォールバック、変換、抽象化をすべて分類できたら、この手順は完了である。

## 2. 該当するルールだけを読む

差分に該当する共通資料と、対象言語の資料を読む。複数言語の変更なら、ファイルごとに対応する資料を使う。他のスキルにも、手順1で確定した対象を渡す。

- 型、入力検証、ガード、型変換、欠損状態、外部データを変更している場合は、[types-and-boundaries.md](references/types-and-boundaries.md) を読む。
- ヘルパー、ラッパー、データ表現、レイヤー、クラス、非同期処理を変更している場合は、[abstractions.md](references/abstractions.md) を読む。
- 分岐、フォールバック、例外処理、ログを変更している場合は、[control-flow-and-errors.md](references/control-flow-and-errors.md) を読む。
- TypeScript または JavaScript の変更では、[typescript.md](references/typescript.md) を読む。TypeScript 固有の型構文は TypeScript にだけ適用する。
- Ruby の変更では、[ruby.md](references/ruby.md) を読む。
- ほかの言語では、共通資料と、その言語の標準機能・プロジェクト規約を使う。
- 手書きの型判定、入力・フォーム検証、3つ以上の判定を含む条件を変更している場合は、[anti-ai-slop-type-check-condition-fixer](../anti-ai-slop-type-check-condition-fixer/SKILL.md) も適用する。

## 3. 優先順位に従って簡潔にする

候補ごとに、最初に該当する修正を採用する。

1. 入力元の契約や型を正すか、実際の信頼境界で必要な検証を行う。
2. 既存のスキーマ、プラットフォーム機能、標準ライブラリ、プロジェクト内の仕組みを再利用する。
3. 重複したチェック、フォールバック、変換、レイヤー、データ表現を削除する。
4. 単純で1か所からしか使われないヘルパーや、処理をそのまま渡すだけのラッパーをインライン化する。
5. 広すぎる汎用処理を、具体的なドメイン処理へ置き換える。
6. 実際に起こり得る状態を扱う防御処理は残す。

不確かな値は、呼び出し先を修正する前に入力元までたどる。利用できる型の仕組みで契約を表現し、確認済みの内部値を各利用箇所で検証し直さない。

挙動を保ち、次のコストのどれかを、ほかのコストを増やさずに減らせる場合だけ修正する。

- 読み手が理解する必要のある概念の数。
- 通過するレイヤーやデータ表現の数。
- 分岐と可変状態の数。
- 契約を表現するために必要なコード量。

## 4. 本当に必要な境界処理を守る

不正な外部入力、外部 API の失敗、対象データの不在、永続化された欠損状態、解析失敗、認可、セキュリティ検査、外部ライブラリの仕様として存在する不確実性に対する検証とエラー処理は残す。

業務上の挙動、公開 API、イベント名、永続化形式、正当な欠損状態、エラーの意味を変えない。

## 5. 簡潔にした差分を確認する

1. 手順1で挙げたすべての候補について判断済みであることを確認する。
2. 必要な境界検証が残り、内部値が確認した契約を保つことを確かめる。
3. 削除した抽象化の呼び出し元が残っていないことを確認する。
4. 差分が簡潔になり、無関係な修正を含まないことを確認する。

## 6. マジックリテラルをレビュー・修正する

[anti-ai-slop-no-magic-literal](../anti-ai-slop-no-magic-literal/SKILL.md) を読み、適用する。対象の差分にある意味を持つリテラルと列挙値をレビューし、同スキルの基準に従って修正する。

## 7. コメントをレビュー・修正する

[anti-slop-ultimate-comment](../anti-slop-ultimate-comment/SKILL.md) を読み、適用する。対象の差分のコメントをレビューし、同スキルの基準に従って削除、書き直し、追加する。docstring と TSDoc は同スキルの対象外なので、ここでは扱わない。

## 8. テストと関連実装をレビュー・修正する

[anti-slop-tdd-matt-p](../anti-slop-tdd-matt-p/SKILL.md) を読み、適用する。コメントの対象がなくても、この手順へ進む。対象のテストと関連実装をレビューし、問題がある箇所だけ修正する。

問題がない場合や、対象のテスト・テストが必要な振る舞いの変更がない場合は、同スキルの基準に従って変更せず、その旨を報告する。

## 9. 最終差分を検証して報告する

手順6〜8の変更を含む最終差分を確認する。手順8で追加・変更したテストのコメントも、手順7の基準で確認する。利用できる formatter、lint、型チェック、構文チェック、関連テストを実行する。すでに通過した確認は、以後の変更が影響する場合だけ再実行する。

簡潔にした箇所、残した防御処理、マジックリテラルとコメントの修正、テストレビューの判定と修正内容、実行した確認を簡潔に報告する。実行できなかった確認は、その理由も伝える。
