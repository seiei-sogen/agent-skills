# Ruby の AI Slop

Ruby の変更に適用する。既存のオブジェクトの契約とフレームワークの規約を確認し、採用済みの型定義・型検査があればそれも使う。TypeScript の構文を Ruby へ持ち込まない。

## 入力の契約を確認する

Gemfile、ロックファイル、既存コードから、採用済みの検証機構を確認する。dry-schema、dry-validation、ActiveModel validations などを、同じ契約と用途に合う場合だけ再利用する。

`is_a?` と `respond_to?` は、クラスへの所属とオブジェクトの能力という異なる契約を調べる。内部値の契約を把握してから冗長な判定を減らし、クラス名による判定へ機械的に統一しない。

`to_s`、`to_i`、`to_f` などの変換は入力検証ではない。不正値や nil を、空文字列や数値の0へ変えて成功扱いにしない。文字列とシンボルのキー、欠損キー、nil の違いは、受理する入力と既存の通知方法に合わせる。

手書きの検証や条件を変更する場合は、[Ruby の型判定と条件式](../../anti-ai-slop-type-check-condition-fixer/references/ruby.md) の基準を使う。Ruby では0と空文字列も真であり、Rails の `present?`・`blank?` は通常の真偽判定とは異なる。

## 動的な呼び出しとフレームワークの契約を保つ

Rails などの callback、validation、scope、シリアライズ、autoload に使われる定義は、直接の呼び出し元が見えなくても契約の一部になり得る。DSL、設定、動的な呼び出しも確認してから削除・インライン化する。

モデルの保存時検証を入力用スキーマへ移したり、認可・transaction・lock を担うサービスやラッパーを、薄いという理由だけで削除したりしない。

## 例外・ブロック・共有状態の意味を保つ

`rescue` や `ensure` の変更では、例外の通知、回復、リソース解放のタイミングを保つ。ブロックを別のメソッドや Proc に移す場合は、`return`・`break`・`next` の対象と引数の扱いを確認する。

文字列、Array、Hash の複製や `freeze` は、呼び出し先の変更と所有権を確認してから整理する。共有した値の変更が別の呼び出しへ漏れる場合は、必要な複製を残す。

コメントは採用済みの規約に従う。Ruby へ TSDoc を適用しない。RSpec または Minitest、構文チェック、採用済みの RuboCop などで確認し、テスト品質のレビューは本体の手順7で行う。
