# 制御フローとエラー

分岐、フォールバック、例外処理、ログを変更する場合に読む。

## 主な処理経路を見やすくする

無効な状態や例外的な状態を先に返すことでネストが減る場合は、早期リターンを使う。可変フラグを段階的に設定するより、読みやすい範囲で条件を直接表現する。ネストした条件式は、その言語の分岐構文で意図を明確にする。

中間変数にはドメイン上の判断を表す名前を付ける。別のローカル変数に名前を付け直すだけの変数は削除する。3つ以上の判定を含む条件は、[anti-ai-slop-type-check-condition-fixer](../../anti-ai-slop-type-check-condition-fixer/SKILL.md) の基準に従い、意味が分かる名前を付ける。

短絡評価、評価順序、評価回数、副作用、結果の値を保つ。真偽判定や欠損の扱いは言語ごとに異なるため、見た目が似た演算子や便利メソッドへ機械的に置き換えない。

## 失敗時の意味を明確にする

空の値が契約の一部である場合だけフォールバックを残す。必須の状態が欠ける場合は、プロジェクトで定められたエラーまたは結果の表現を使う。

現在の境界で回復する場合、ドメインエラーへ変換する場合、ほかでは得られない情報を追加する場合、リソースを解放する場合に、例外を捕捉する。再送出するだけ、ログを出して再送出するだけ、失敗を隠すだけの捕捉は削除候補にする。削除時は後始末や例外の通知方法を保つ。

エラーの文脈は、失敗した処理を所有する境界で一度だけ追加する。レイヤー名を重ねて元のメッセージを分かりにくくしない。

## 運用に役立つ情報だけを残す

意味のある運用上のイベントを、責任を持つ1つの境界でログに記録する。内部処理を順番に説明するログや、呼び出し元でも記録される同じ失敗のログは削除する。

## 完了条件

変更した失敗経路をすべて呼び出し元までたどる。各分岐の結果、エラーの通知、回復・後始末が意図どおりであり、失敗が暗黙に成功へ変換されていなければ完了である。
