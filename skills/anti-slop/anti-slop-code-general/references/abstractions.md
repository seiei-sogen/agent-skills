# 抽象化

ヘルパー、ラッパー、データ表現、汎用処理、レイヤー、クラス、非同期処理を追加・変更する場合に読む。

## 隠す複雑さと導入コストを比べる

抽象化は、導入する複雑さより多くの複雑さを隠す必要がある。読み手が覚える名前、ファイル、型、呼び出し階層、データ表現を数える。

呼び出し元が1か所しかなく、次のいずれかしか行わない抽象化は、インライン化または削除を検討する。

- フィールドへアクセスする。
- 同じ引数をそのまま渡す。
- 単純な文字列整形や、確認済みの値の再判定を行う。
- 防御的なデフォルト値を返す。
- 標準ライブラリの処理に別名を付ける。
- 実質的に同じデータ構造を相互変換する。

名前が実際のドメインルールを表す場合、不変条件を1か所へ集約する場合、意味のある複数の呼び出し元がある場合は、小さなヘルパーでも残す。

呼び出し元の数は、静的な参照だけで判断しない。公開 API、設定、登録処理、フレームワークや動的な呼び出しから使われる入口も確認する。

## 処理をそのまま渡す構造を畳む

ポリシー、マッピング、キャッシュ、認可、トランザクション境界、所有権、エラー変換を担わないラッパーは削除候補にする。

次の構造も、数や名前だけではなく、隠す複雑さと契約で判断する。

- 処理を渡すだけのレイヤーの連鎖。
- 意味が同じ入力・モデル・出力の派生表現と相互変換。
- 実装が1つしかないインターフェース。
- 直接構築できるオブジェクトのためだけの構築機構。
- 選択肢が固定されている場合の汎用的な登録・解決・ディスパッチ機構。

固定された分岐には、その言語の分岐構文を使う。呼び出し側の契約を単純にする境界や、外部から必要とされる差し替え点は残す。

## 具体的なコードを優先する

再利用が仮定にすぎない汎用的な変換・抽出・正規化や、コールバックを介した間接処理は、具体的なドメイン処理へ置き換える。

共有する概念がないまま抽象化するより、小さな重複を明示的に残す。概念と呼び出し元が安定してから抽出する。プラットフォームと標準ライブラリの処理へ名前を付ける場合も、ドメイン上の意味が必要である。

## 不要な委譲と複製を削除する

非同期処理を同じ結果へ包み直す処理、1つの関数を呼ぶだけのコールバック、所有権や変更理由のない複製は削除候補にする。入力、エラー、評価のタイミング、所有権、呼び出し方の契約を保てる場合だけ削除する。

状態を持たない処理には、その言語で単純な表現を使う。状態、ライフサイクル、多態的な振る舞いによって明確になる場合は、クラスなどの構造を使う。コードを追うための移動を増やすだけの小さなメソッドはインライン化する。

契約やデータフローを修正した後は、不要になったヘルパー、型、ファイルを、すべての呼び出し元を確認して削除する。

## 完了条件

追加された抽象化ごとに、隠す具体的な複雑さと、意味のある呼び出し元を説明する。説明できない抽象化は契約を保って削除またはインライン化し、すべての呼び出し元を確認したら完了である。
