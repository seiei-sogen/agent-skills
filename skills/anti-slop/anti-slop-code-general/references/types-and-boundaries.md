# 型・契約と境界

型、入力検証、ガード、変換、欠損状態、外部データの処理を変更する場合に読む。構文やライブラリの選び方は、対象言語の資料に従う。

## 信頼境界から確認する

HTTP リクエスト、Webhook、キューメッセージ、外部 API、環境変数、ユーザー入力、解析前のデータ、契約が未確認のデータベース結果は、信頼できない値として扱う。既存の検証機構を使って境界で契約を確認し、内部へ渡す。

内部コードが生成した値でも、外部データ由来の不確実性が残るなら必要な検証を保つ。契約を確認済みの値は、各利用箇所で同じ検証を繰り返さない。言語が対応する場合は、その契約を具体的な型でも表現する。

## 次の置き換えを検討する

| 兆候 | 優先する実装 | 元の実装を残す条件 |
| --- | --- | --- |
| 内部まで持ち込まれた広い型や曖昧な構造 | 境界で確認したドメインの型・契約 | その関数が解析境界である、または複数の構造を扱う契約である |
| 同じ型・構造の判定の繰り返し | 境界での検証、または入力元の型・契約の修正 | 入力が実際に複数の形を取り得る |
| 既知の構造を取り出すだけのヘルパー | 契約を確認した値への直接アクセス | 再利用されるドメイン上の不変条件を表す |
| 必要以上に広い部分更新の表現 | 実際に受け入れる項目だけの表現 | すべての項目の部分更新を受け入れる契約である |
| 意味が重複する欠損状態 | 契約に必要な欠損状態 | 各状態に異なる観測可能な意味がある |
| 防御目的で追加された任意項目 | ドメイン上必須なら必須項目 | 欠損が実際にサポートされる状態である |
| 既知のイベントと曖昧なペイロード | イベントごとに契約が定まる表現 | イベントが動的に登録される |
| 重複する入力・モデル・出力の構造 | 意味を共有する1つの構造 | 契約、公開範囲、ライフサイクルが異なる |

## 検証と変換を分ける

型変換や文字列整形だけでは、入力の正しさを検証したことにならない。不正な入力が変換によって正常な値に見えないか確認する。契約で受け入れる変換と正規化だけを行う。

空の値へのフォールバックは、サポートされるドメイン状態を表す場合だけ使う。必須データがない場合は空の値を作らず、プロジェクトで定められた失敗として扱う。

## 検証機構は実装全体で比較する

採用済みのスキーマやフレームワークの検証機能を再利用する。型を導出できる言語・ライブラリでは、同じ契約から導出する。

依存関係、重複する定義、エラー変換まで含めて比較する。契約を確認済みの内部コードを長くするためだけの検証は追加しない。

## 永続化の契約を確認する

データベースのスキーマと、アプリケーションが扱う型・契約を一致させる。保存形式が保証されるなら、その形式で必要な操作を直接行う。複数形式が混在するデータ、移行中のデータ、欠損を許すデータ、外部から投入されるデータには、必要な実行時チェックを残す。

## 完了条件

変更経路の曖昧な型・構造をすべて、アプリケーションへ入る地点までたどる。境界で契約を確認しているか、確認を保留する理由が明確であり、内部処理がその契約を保っていれば完了である。
