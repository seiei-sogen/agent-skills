# TDD の基準でレビュー・修正する

`tdd-matt-p` を使ってレビューし、問題がある箇所だけを修正する。問題がなければ、そのまま終了する。

## レビュー対象と基準を読む

ユーザーが指定した範囲を対象にする。指定がなければ、現在の Git ブランチとベースブランチの差分に加え、staged、unstaged、untracked の変更を対象にする。

対象のテストと関連実装、公開インターフェース、既存のテスト構成を読む。`CONTEXT.md` があれば読み、対象に関係する ADR と仕様を確認する。

[tdd-matt-p](../../matt/engineering/tdd-matt-p/SKILL.md) と、その `tests.md`、`mocking.md` を読み、レビューと修正に適用する。相対パスが使えない環境では、インストール済みの `tdd-matt-p` とその参照ファイルを読む。

## テストと関連実装をレビューする

`tdd-matt-p` の「良いテストとは何か」「シーム」「アンチパターン」を基準に、次の点を確認する。

- 公開インターフェースから、ユーザーや呼び出し元が関心を持つ振る舞いを検証しているか。
- 振る舞いを保った内部リファクタリングで壊れるテスト、プライベートメソッドへの依存、内部の呼び出し回数や順序の検証がないか。
- モックが外部 API、時間などのシステム境界に置かれ、内部のクラスやモジュールを置き換えていないか。
- 期待値が仕様に基づいて決まり、実装と同じ計算を繰り返していないか。
- テスト名とアサーションが具体的な振る舞いを表し、形だけの成功判定や同じ振る舞いの不要な重複がないか。
- 変更した振る舞いを検証できているか。仕様上必要な失敗条件や、修正したバグを検出するテストが欠けていないか。

テストと関連実装を照合し、問題ごとに対象箇所と理由を特定する。差分からテストと実装を書いた順序が分からないことだけを理由に、不合格にはしない。

## 問題がある場合だけ修正する

問題がなければファイルを変更せず、関連テストの結果とともに `OK` と報告する。対象のテストやテストが必要な振る舞いの変更がなければ、その旨を報告して終了する。

問題がある場合は、次の方針で必要な箇所だけを修正する。

- テスト品質の問題は、意図した振る舞いと有効な検証を保ち、公開インターフェースを使うテストに直す。
- 実装の不具合は、まずその不具合を再現するテストを1件書き、期待した理由で失敗することを確認する。そのテストを通す最小の実装修正を行い、次の問題へ進む。
- 既に正しく動いている振る舞いのテストが不足している場合は、その振る舞いを検証するテストを追加する。

赤から緑へのサイクルは `tdd-matt-p` の「ループのルール」に従う。問題の修正に関係しない機能追加やリファクタリングは行わない。

修正後は関連テストと、変更に必要な型チェック・lint を実行し、差分を再レビューする。問題を隠すためにテストを削除したり、アサーションを弱めたりしない。

最後に、判定、見つけた問題、修正内容、実行した検証と結果を簡潔に報告する。検証できなかった場合は理由を明記し、`OK` と断定しない。
