# 型チェックと複合条件を簡潔にする

現在のブランチの変更を対象に、元の契約と評価の挙動を保ちながら修正する。

## 1. 対象と使用言語を確認する

1. ベースブランチとの差分に加え、staged、unstaged、untracked の変更を確認する。
2. 差分内の型判定、型ガード、入力・フォーム検証、分岐の条件を列挙する。
3. 対象箇所の呼び出し元、入力の契約、既存の検証処理、依存関係、関連テストを読む。
4. 対象ファイルの言語に応じて、次の資料を読む。複数言語の変更なら、ファイルごとに対応する資料を使う。

- TypeScript は [typescript.md](references/typescript.md) を読む。
- Ruby は [ruby.md](references/ruby.md) を読む。
- ほかの言語は共通手順に従い、その言語の標準機能とプロジェクトの規約を使う。

対象箇所と入力の契約を把握できたら、修正へ進む。

## 2. 手書きの検証を既存の仕組みへ置き換える

対象ごとに、既存のスキーマ、フレームワークの検証機能、標準ライブラリを使うほうが短く明確になるかを判断する。重複、依存関係、型の表現、エラー処理まで含めて実装全体が簡単になる場合だけ置き換える。

- 同じ契約を表すスキーマや検証処理があれば、再利用または合成する。
- 実行時検証と型定義の両方が必要なら、同じ契約を重複して定義せず、言語が対応する導出機能を使う。
- 受理・拒否条件、型変換、既定値、エラーの内容と通知方法、検証のタイミングを保つ。
- 外部入力に必要な検証は残し、保証済みの内部値に新しい検証を足さない。
- 単純な判定を置き換えるためだけに依存関係を追加しない。新規導入が必要な案は、コストも含めて比較する。

すべての対象について置換するか残すかを判断し、簡単になる箇所だけ修正したら、この手順を完了する。

## 3. 残った複合条件に名前を付ける

手順2で置き換えなかった条件のうち、1つの式に3つ以上の判定が論理演算子で結合されているものを確認する。比較、真偽判定、述語呼び出しをそれぞれ1つの判定として数え、呼び出した関数の内部までは数えない。条件式全体を、意図が分かる変数または述語関数へ抽出する。

- 真偽値の名前と述語関数の書き方は、言語別資料とプロジェクトの規約に従う。
- 元の短絡評価、評価順序、評価回数、副作用、結果の値、分岐の挙動を保つ。
- 元と同じタイミングで評価される位置へ抽出する。ループ外への移動や先行評価で挙動を変えない。
- 条件が2つ以下の式や、抽出しても読みやすさが変わらない式はそのままにする。

該当する式をすべて確認し、意図が読み取りやすくなる抽出だけを行ったら、この手順を完了する。

## 4. 検証して報告する

差分を再確認し、対象の見落としと無関係な変更がないことを確かめる。変更箇所の受理・拒否条件、エラー、短絡評価を関連テストで確認し、利用できる型チェック、構文チェック、lint を実行する。

検証機構へ置き換えた箇所、名前を付けた条件、残した対象と理由、実行した確認を簡潔に報告する。実行できなかった確認は、その理由も伝える。
