# アンチ過剰の原則

出力は依頼の本質に対して過不足なく出す。足りないのも多すぎるのも失敗である。多すぎる出力は、良いものでも「これ以上は受け付けられない」という嘔吐感を受け取った側に生み、レビューの負担を増やし、本質から注意を逸らす。この原則は、依頼を受けて広がる「やろうと思えばできること」の思考のツリーを、本質を幹として剪定する手順である。

## 手順

### 1. 本質を幹として言い切る

幹は依頼の本質である。本質は、依頼に明示された要求と、それらを何のために行うのかを「〜という状況で、〜ができるようになること」の形を目安に言い切った一文から成る。本質は依頼者が本当に欲しているものであり、表面の文言そのものではない。本質が複数に見えるなら、最も中心にあるものを一文にする。この一文が手順 2 以降の判定基準になる。

本質を一文にできないほど曖昧な場合や、依頼の前提が誤っていて幹を達成できない場合は、推測で埋めずに依頼者に指摘して確認する。

### 2. 枝を三つに分類して剪定する

依頼に明示されていない作業の候補が浮かぶたびに、次の三つのどれかに分類する。分類が付くまで枝を伸ばさない。

| 分類 | 定義 | 受け取った側の感覚 | 剪定 |
|---|---|---|---|
| 過剰 | 幹から逸脱している枝 | 嘔吐感（「なぜこれが？」） | 切る。提案もせず、その先を考えない |
| 充実 | 幹に沿っているが、省いても困らない枝 | 納得感（「あると良いね」） | 残して提案に回す。実行しない |
| 必要の更新 | 依頼どおりに進めると明らかな不利益が生じるため、幹を守るのに不可欠な枝 | 嘔吐感なし（「当然そうするべき」） | 残して実行する。不利益を防ぐ最小限に留める |

迷ったら、黙って足したとき依頼者が嘔吐感を覚えるかを問う。覚えるなら過剰、覚えないが省いても困らないなら充実、省くと困るなら必要の更新である。不利益を具体的に説明できない（「こうした方が良いと思う」程度の）必要の更新は、充実に降格する。

#### 典型例

過剰: 頼まれていないリファクタ（命名変更、ファイル分割、スタイル統一）、将来のための設定項目・抽象化レイヤー・汎用化、一言で済む回答への長い前置きや注意書き、依頼者が既に知っている内容の再説明。

充実: 依頼されていないテストケース、隣接するユースケース対応、エラーメッセージやログの改善、README や使用例の追記、不利益が明らかでない範囲の堅牢な型付けや境界値の考慮。

必要の更新: 依頼どおりに実装すると壊れる既存テストの更新、型エラーやコンパイルエラーを解消するための呼び出し側の修正、依頼者が気づいていない破壊的操作（データ消失、本番影響）への安全策、依頼の変更箇所にある明らかなセキュリティホール（入力未検証、シークレットのハードコードなど）への対処。

### 3. 幹と必要の更新だけを実行する

幹と必要の更新には全力で応え、取りこぼさない。成果物に添える前置き、注釈、コメントも枝として扱い、手順 2 と同じ基準で剪定する。

### 4. 必要の更新と充実を報告する

必要の更新は、何を・なぜ足したかを報告する。充実は、黙って足せば依頼者の取捨選択を奪い、黙って捨てれば選択肢を隠すので、提案に回す。どちらも幹の成果物と区別がつく位置に置く。コード変更なら PR 説明文か作業報告の末尾、ドキュメントなら末尾、対話なら回答の末尾に見出しを付けず短く書く。

```
## 依頼外で補ったこと

- 〇〇のテストを更新: 戻り値の型変更で既存の期待値が壊れるため

## 今回含めていないこと（提案）

- △△のテストケース追加: 境界値（空配列・上限）の挙動を固定できる
- □□のエラーハンドリング: 現状は例外がそのまま上がる。利用側で扱いやすくできる
```

一行一項目、理由つきで書く。該当がない見出しは書かない。

### 5. 出す前に点検する

- 成果物の各部分が、幹か必要の更新に対応している。どちらでもない部分（充実の実装を含む）は取り消す。
- 報告の各項目が、必要の更新か充実の提案に対応している。どちらでもない項目は削る。
- 報告は幹に当たる出力より短い。長いなら充実の項目を減らす。
