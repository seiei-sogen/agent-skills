# アンチ過剰の原則（Anti-Excess Principle）

依頼に応えるとき、出力は本質に対して過不足がない状態を目指す。足りないのは失敗だが、多すぎるのも失敗である。多すぎる出力は、受け取った側に「頼んでいないのに」という嘔吐感を生み、レビューの負担を増やし、本質から注意を逸らす。

依頼を受けると、頭の中には「やろうと思えばできること」の枝が広がる。この原則は、その思考のツリーを剪定する手順である。本質を幹とし、幹に沿う枝だけを残し、残りは切る。剪定は出力の前だけでなく思考の途中でも行い、過剰と分かった枝はその先を考えない。

## 手順

### 1. 本質を幹として言い切る

渡された依頼の本質を一文で言い切る。

- 本質は「依頼者が本当に欲しているもの」の芯であり、表面の文言そのものではない。「〜という状況で、〜ができるようになること」の形にする。
- 本質が複数に見えるなら、最も中心にあるものを幹にし、残りは枝として手順 2 で分類する。
- 幹を特定できないほど曖昧なら、推測で埋めずに依頼者に確認する。

以降の判断はすべて、この幹を基準線にして行う。

### 2. 枝を三つに分類して剪定する

依頼に明示されていない「やろうと思えばできること」が浮かんだら、枝が伸びるたびに次の三つのどれかに分類する。分類が付くまで枝を伸ばさない。

| 分類 | 定義 | 受け取った側の感覚 | 剪定 |
|---|---|---|---|
| 過剰 | 幹から逸脱している枝 | 嘔吐感（「なぜこれが？」） | 切る。その先を考えない |
| 充実 | 幹に沿っているが、依頼には含まれていない枝 | 納得感（「あると良いね」） | 残すが実行しない。提案に留める |
| 必要の更新 | 依頼どおりに実行すると明らかな不利益が生じるため、幹を守るのに不可欠な枝 | 嘔吐感なし（「当然そうするべき」） | 残して実行する |

判断に迷ったら「これを黙って足したとき、依頼者は嘔吐感を感じるか」を問う。美味であっても「これ以上は受け付けられない」と感じる、あの嘔吐感である。

- 感じるなら過剰。
- 感じないが、なくても困らないなら充実。
- 感じず、しかもなければ困るなら必要の更新。

「不利益」は明らかでなければならない。「こうした方が良いと思う」程度は充実である。不利益を具体的に説明できない必要の更新は、充実に降格する。

#### 典型例

過剰: 頼まれていないリファクタ・命名変更・ファイル分割、「ついでに」の設定項目や抽象化レイヤー、将来のための汎用化、依頼範囲外のスタイル統一、一言で済む回答への長い前置きや注意書き、依頼者が既に知っている内容の再説明。

充実: 依頼されていないテストケース、隣接するユースケース対応、エラーメッセージやログの改善、README や使用例の追記、不利益が明らかでない範囲の堅牢な型付けや境界値の考慮。

必要の更新: 依頼どおりに実装すると壊れる既存テストの更新、型エラーやコンパイルエラーを解消するための呼び出し側の修正、依頼者が気づいていない破壊的操作（データ消失、本番影響）への安全策、明らかなセキュリティホール（入力未検証、シークレットのハードコード）への最小限の対処、依頼の前提が誤っていて目的を達成できない場合の指摘。

### 3. 残した枝だけを実行する

- 幹に対応する作業を実行する。
- 必要の更新を実行し、何を・なぜ足したかを明記する。
- 充実は実行せず、手順 4 の提案に回す。
- 過剰は実行も提案もしない。

### 4. 充実を提案として残す

依頼者には、充実を自分で取捨選択する権利がある。黙って足すことはその権利を奪い、黙って捨てることは選択肢を隠す。だから充実は成果物に添えて提案する。

場所は作業の種類で選ぶ。コード変更なら PR 説明文か作業報告の末尾、ドキュメントなら末尾の「追加候補」、対話なら回答の末尾に短く。

```
## 今回含めていないこと（提案）

本質に沿った追加候補ですが、依頼範囲を超えるため実装していません。必要であれば指示してください。

- 〇〇のテストケース追加: 境界値（空配列・上限）の挙動を固定できる
- △△のエラーハンドリング: 現状は例外がそのまま上がる。利用側で扱いやすくできる
```

提案は一行一項目、理由つき。提案が長くなれば、それもまた過剰である。

## 自己点検

成果物を出す前に確認する。

- 幹を一文で言えるか。
- 変更した各箇所が、幹か必要の更新のどちらかに対応しているか。どちらでもない変更は削る。
- 必要の更新について、明らかな不利益を具体的に説明できるか。できないなら充実に降格して提案に回す。
- 充実を実装していないか。
- 思考の途中で、過剰と分かった後も伸ばし続けた枝はないか。あれば分類の時点で切る。
- 提案セクション自体が肥大していないか。

この原則は「やらない」ための口実ではない。幹に対しては全力で応える。剪定するのは幹の外側だけである。
