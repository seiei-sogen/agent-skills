# Handoff

現在の会話を、次の作業者が会話履歴を読まなくても作業を再開できる引き継ぎメモへ変換する。
引数は出力先ディレクトリのパス 1 つとする。

## 1. 出力ファイルを用意する

1. 引数がない場合は、出力先ディレクトリのパスをユーザーに確認する。
2. 相対パスは現在の作業ディレクトリを基準に解決する。指定ディレクトリがなければ作成する。指定パスが既存の通常ファイルなら、その事実を報告して終了する。
3. 現在の Git ブランチ名から issue 番号を確認する。ブランチ名から一意に判断できない場合だけ、現在の作業ディレクトリのベース名も確認する。`issue211`、`issue-211` のような表記、またはプロジェクトで確認できる命名規則がある場合だけ番号を採用し、それ以外は省略する。
4. 会話の主題を、英小文字と数字による 2〜4 語程度の短い kebab-case で表す。たとえば、バックエンドの修正なら `backend-fix` とする。
5. 現在時刻を日本標準時（`Asia/Tokyo`）の `YYYYMMDD-HHMMSS` 形式で取得し、次の規則でファイル名を作る。
   - issue 番号が分かる場合: `handoff-issue<番号>-<主題>-YYYYMMDD-HHMMSS.adoc`
   - issue 番号が分からない場合: `handoff-<主題>-YYYYMMDD-HHMMSS.adoc`
   - 例: `handoff-issue211-backend-fix-20260828-092037.adoc`
   - 例: `handoff-backend-fix-20260828-092037.adoc`
6. 同名ファイルがある場合は拡張子の直前へ `-2`、`-3` のような連番を付け、既存ファイルを保持する。
7. 確定したパスに空の新規ファイルを作り、続く手順で内容を書き込む。

## 2. 会話から引き継ぐ事実を整理する

次の項目を、会話と確認済みの作業結果から拾う。

- ユーザーの目的と、依頼されたこと
- ユーザーが指定した要件、制約、優先順位
- 会話中に決まったことと、その理由
- agent が置いた仮定と、まだ確認できていないこと
- 完了した作業、その結果、変更したファイル
- 実行した確認と、その成否
- 残作業、問題、作業を止めている要因
- 次の作業者が最初に行う具体的な操作

事実、仮定、未確認事項を区別する。
作業再開に必要なパス、コマンド、エラー文は正確に記す。
秘密情報は値を伏せ、存在と必要な扱いだけを記す。

## 3. 平易な AsciiDoc を書く

次の構成を基本にする。

```asciidoc
= 引き継ぎメモ

== 30秒で分かる要約

== 依頼されたこと

== 決まったこと

== 終わったこと

== 変更したファイル

== 確認結果

== 残っていること

== 注意点

== 次にやること
```

初めて読む人を想定し、次の基準で書く。

- 短い文と箇条書きを中心にし、1 文には 1 つの事実または操作を書く。
- 専門用語には、最初の登場時にかっこ書きで意味を添える。
- 「これ」「それ」「対応する」のような指す先が曖昧な表現は、具体的な対象名へ置き換える。
- 完了事項には結果を、未完了事項には次の一手を添える。
- 情報がない節には `なし` と書き、記載漏れと区別する。
- 会話を時系列に丸写しせず、次の作業判断に必要な内容へまとめる。

## 4. 完了を確認する

次をすべて満たしたら完了とする。

- 指定ディレクトリ配下に、新規の `.adoc` ファイルが 1 つ存在する。
- ファイル名が「出力ファイルを用意する」の命名規則に一致する。
- ファイルは空ではなく、先頭に AsciiDoc の文書タイトルがある。
- ユーザーの目的、現在の状態、残作業、次の一手を、会話履歴なしで理解できる。
- 既存ファイルを変更していない。
- ユーザーへ生成ファイルのパスを報告する。
