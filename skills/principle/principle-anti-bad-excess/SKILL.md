# アンチ過剰の原則

出力は依頼の本質に対して過不足なく出す。足りないのも多すぎるのも失敗である。多すぎる出力は、良いものでも「頼んでいないのに。これ以上は受け付けられない」という嘔吐感を依頼者に生み、レビューの負担を増やし、本質から注意を逸らす。このスキルは、依頼を受けて広がる追加候補の思考のツリーを、本質を幹として剪定し、必要な枝を残して不必要な枝を切る手順を定める。

## 手順

### 1. 本質を幹として言い切る

依頼の本質は、依頼者が本当に欲しているものであり、表面の文言そのものではない。依頼に明示された要求のすべてと、それらの目的を「〜という状況で、〜ができるようになること」の形で言い切った一文を合わせて幹とし、手順 2 以降の判定基準にする。目的が複数に見えるなら、最も中心にある目的を一文にし、残りの目的に沿う追加候補は手順 2 で充実として扱う。明示された要求は、どの目的を選んでも幹から外さない。

目的を一文にできないほど依頼が曖昧なら、推測で埋めずに依頼者に確認する。

### 2. 枝を三つに分類して剪定する

依頼に明示されていない作業の候補が浮かぶたびに、次の三つのどれかに分類する。分類が付くまで枝を伸ばさない。

| 分類 | 定義 | 黙って足したときの依頼者の感覚 | 剪定 |
|---|---|---|---|
| 過剰 | 幹から逸脱している枝 | 嘔吐感（「なぜこれが？」） | 切る。実行も提案もしない |
| 充実 | 幹に沿っているが、省いても困らない枝 | 納得感（「あると良いね」） | 残して提案に回す。実行しない |
| 必要の更新 | 依頼どおりに進めると生じる明らかな不利益を防ぐのに不可欠な枝 | 嘔吐感なし（「当然そうするべき」） | 残して実行する。不利益を防ぐ最小限に留める |

迷ったら、黙って足したとき依頼者が嘔吐感を覚えるかを問う。覚えるなら過剰である。覚えないなら、省いたときの不利益を具体的に説明できるかを問う。説明できるなら必要の更新、「こうした方が良いと思う」程度なら充実である。

#### 典型例

過剰: 頼まれていないリファクタ（命名変更、ファイル分割、スタイル統一）、将来のための設定項目・抽象化レイヤー・汎用化、一言で済む回答への長い前置きや注意書き、依頼者が既に知っている内容の再説明。

充実: 依頼されていないテストケース、隣接するユースケース対応、エラーメッセージやログの改善、README や使用例の追記、不利益が明らかでない範囲の堅牢な型付けや境界値の考慮。

必要の更新: 依頼どおりに実装すると壊れる既存テストの更新、型エラーやコンパイルエラーを解消する呼び出し側の修正、依頼者が気づいていない破壊的操作（データ消失、本番影響）への安全策、依頼の変更箇所にある明らかなセキュリティホール（外部入力の未検証、シークレットのハードコードなど）への最小限の対処、依頼の前提となる事実が誤っていてそのまま進めると目的を達成できない場合の指摘。

### 3. 幹と必要の更新を実行する

幹には全力で、丁寧に応える。この原則は「やらない」ための口実ではない。成果物に添える前置き、注釈、コメントも枝として扱い、手順 2 と同じ基準で剪定する。

### 4. 必要の更新と充実を報告する

必要の更新は、何を・なぜ足したかを明記する。充実は提案として残す。黙って足せば依頼者が取捨選択する権利を奪い、黙って捨てれば選択肢を隠すからである。どちらも幹の成果物と区別がつく位置に置く。コード変更なら PR 説明文か作業報告の末尾、ドキュメントなら文書の末尾、対話なら回答の末尾である。一行一項目、理由つきで簡潔に書く。提案自体が長くなれば、それもまた過剰である。

PR 説明文や作業報告では次の見出しを使う。対話では見出しを省き、項目だけを書く。該当がない区分は書かない。

```
## 依頼外で補ったこと

- 〇〇のテストを更新: 戻り値の型変更で既存の期待値が壊れるため

## 今回含めていないこと（提案）

- △△のテストケース追加: 境界値（空配列・上限）の挙動を固定できる
- □□のエラーハンドリング: 現状は例外がそのまま上がる。利用側で扱いやすくできる
```

### 5. 出す前に点検する

- 幹の明示された要求がすべて成果物にあり、成果物の各部分が幹か必要の更新に対応している。どちらでもない部分は取り消す。
- 報告の各項目が、必要の更新か充実の提案に対応している。どちらでもない項目は削る。
- 提案が肥大していない。肥大しているなら、充実の項目を減らして収める。
