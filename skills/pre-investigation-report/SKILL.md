# 事前調査レポートの生成

## 目的と運用想定

- 与えられた問題について、コードベースを調査し、後続の作業者（上位モデルまたは人間）が **追加の探索なしで** 作業に着手できる JSON レポートを作る。
- このスキルは下位モデル（Claude Sonnet など）での実行を想定する。後続の上位モデルはこのレポートだけを読み、ファイル探索・grep・試し読みを繰り返さない。
- したがってレポートは「調査の代替物」であり、調査ログではない。後続の判断を変えない情報は載せない。

## 入力

引数として次のいずれか（複数可）を受け取る。

- ファイルパスまたはディレクトリパス
- エラーメッセージ、スタックトレース、ログの抜粋
- 問題や変更要望の説明文

入力から調査対象の問題を特定できない場合は、調査を始めずに不足している情報を指摘して終了する（対話中なら質問してよい）。推測で問題を決めて調査しない。

## 調査の進め方

1. 入力から問題の主題とスコープを 1〜2 文で言語化する（レポートの `problem` になる）。
2. 入力に含まれるパス・シンボル名・エラー文言を起点に、Grep / Glob / 部分 Read で関係ファイルを特定する。
3. 各関係ファイルについて、現状の責務・主要シンボル・依存関係を把握する。ファイル全体を読む必要がない場合は、シンボル定義の周辺だけを読む。
4. 制約を集める。技術的制約（型、依存ライブラリのバージョン、API 契約）、リポジトリの規約（lint 設定、CLAUDE.md や AGENTS.md、既存コメント）、ビジネス的制約（コメントやドキュメントに明記されたもの）を対象にする。
5. 既存パターンを集める。同種の処理が既にどう書かれているか、命名規則、エラーハンドリングやテストの流儀など、後続作業が従うべき前例を、実例のパス付きで記録する。
6. 調査は読み取り専用とする。レポートの保存先として指定されたファイルへの書き込みを唯一の例外とし、それ以外のファイルの作成・変更・削除、ビルド、テスト実行を行わない。

## トークン節約のルール

- 事実は必ず `パス` または `パス:行番号` で裏づける。コード本体は貼らず、必要ならシンボル名とシグネチャだけを載せる。
- 推測で埋めない。確認できなかったことは `open_questions` に回す。
- `related_files` は関連度順に並べ、原則 20 件以内に絞る。閾値を超えた分は件数と概要だけを `meta.omitted` に記す。
- 同じ情報を複数フィールドに重複させない。
- 値はすべて簡潔な文にする。箇条書きの連結や省略記号の多用で意味を欠落させない。

## 出力フォーマット

出力は次のスキーマに従う **単一の妥当な JSON** とする。前後に説明文を付けない。保存先ファイルの指定があれば、コードブロックで囲まない生の JSON をそこへ書き、回答では保存先パスだけを報告する。指定がなければ、回答に JSON コードブロック 1 個だけを出力する。

```json
{
  "meta": {
    "subject": "調査対象の一言表現",
    "generated_at": "ISO 8601 日時",
    "repo_root": "リポジトリルートの絶対パス（git リポジトリ外なら調査基点ディレクトリの絶対パス）",
    "git_ref": "調査時点のブランチ名とコミットハッシュ（git リポジトリ外なら null）",
    "omitted": "関連度が低く省略した情報の件数と概要（なければ null）"
  },
  "problem": {
    "summary": "問題の 1〜2 文の要約",
    "scope": "調査対象に含めた範囲と、意図的に外した範囲"
  },
  "related_files": [
    {
      "path": "repo_root からの相対パス",
      "relevance": "high | medium | low",
      "role": "このファイルが問題に対して持つ役割",
      "key_symbols": [
        { "name": "シンボル名", "kind": "function | class | type | const | config など", "location": "パス:行番号", "note": "シグネチャや責務の一言説明" }
      ]
    }
  ],
  "responsibilities": [
    {
      "component": "コンポーネント・モジュール名",
      "path": "代表パス",
      "responsibility": "現状の責務の説明",
      "collaborators": ["連携するコンポーネントやパス"]
    }
  ],
  "constraints": [
    {
      "type": "technical | convention | business | dependency",
      "description": "制約の内容",
      "evidence": "根拠のパス:行番号（設定ファイル、ドキュメント、コメントなど）"
    }
  ],
  "existing_patterns": [
    {
      "name": "パターンの短い名前",
      "description": "何をどう書くのが既存の流儀か",
      "examples": ["実例のパス:行番号"],
      "applies_to": "後続作業のどの部分がこのパターンに従うべきか"
    }
  ],
  "open_questions": [
    "調査で確定できず、後続の作業者が判断または確認すべき事項"
  ],
  "suggested_entry_points": [
    { "path": "パス:行番号", "reason": "後続作業をここから始めるべき理由" }
  ]
}
```

- 該当がないフィールドは省略せず、空配列または `null` を入れる（スキーマを一定に保ち、後続の機械処理を可能にする）。
- `relevance` は「後続の作業者がそのファイルを開く必要性」で判定する。変更が及ぶ可能性が高いものが `high`、読む必要はあるが変更しないものが `medium`、参考程度が `low`。

## 完了条件

次のすべてを満たした場合だけ完了とする。

- 出力が単一の妥当な JSON で、スキーマの全フィールドを持つ。
- `related_files`・`constraints`・`existing_patterns` の各項目に根拠パスがある。
- 推測で書いた項目がなく、未確定事項はすべて `open_questions` にある。
- 調査中にファイルを変更していない。
