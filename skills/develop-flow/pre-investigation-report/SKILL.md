# 事前調査レポートの生成

## 目的と運用想定

- 後続の作業者（上位モデルまたは人間）が、追加の探索を節約できる JSON レポートを作る。目的は、特に上位モデルのトークン消費を減らすこと。
- 下位モデル（Claude Sonnet, gpt-5.6-luna など）での実行を想定する。確認済みの事実と未解決の問いを分け、後続作業者が同じ探索を繰り返さず、必要な箇所だけを確認できるようにする。
- 調査ログではなく、作業判断に必要な要約を残す。追加探索が不要だとは保証せず、判断を変えない情報は載せない。

## 子スキル

入力から必要な調査を選び、選んだスキルの `SKILL.md` と、その手順で必要な参照ファイルを読んで実行する。

| 要件から解くべき問い | 使うスキル | レポートに残す内容 |
| --- | --- | --- |
| どう動くか、どこが責務を持つか、どこへ変更を入れるか | `pstack:how` | 主要概念、起点から結果までの処理・データの流れ、分岐、責務境界、注意点 |
| なぜこの形か、制約や閾値の根拠は何か、回帰や過去の判断をどう扱うか | `pstack:why` | 設計理由、トレードオフ、確度別の証拠、競合する説明、未解決事項、調査範囲 |
| 仕組みと経緯の両方が変更判断に必要 | 両方 | `how` のパス・シンボルを `why` の調査起点に渡し、同じコード探索を繰り返さない |

現状把握が目的なら `how` を選び、設計理由が後続の判断に関係する場合に `why` を使う。選択理由は `meta.investigations` に残す。選んだスキルが見つからない場合は、その名前を報告して停止する。

子スキルには対象の問い、既知の根拠、読み取り専用の制約、以下の JSON 出力契約を渡す。このスキル経由では、子スキルの説明用 Markdown・図・原文提示の指定を JSON への統合に置き換える。確度の区別や根拠は保持する。

モデルをユーザーが指定している場合はその指定を優先する。指定がなければ、子スキルの役割ごとの既定モデルを今回の調査担当モデルに合わせ、整形・統合のためだけに上位モデルを起動しない。委譲方法は子スキルの provider dispatch に従い、永続的なモデル設定は変更しない。必須の委譲が実行できなければ、理由を報告して停止する。情報源へのアクセス不足は `why.sources_consulted` に記録し、参照できる情報源の調査を進める。

## 入力

引数として次のいずれか（複数可）を受け取る。

- ファイルパスまたはディレクトリパス
- エラーメッセージ、スタックトレース、ログの抜粋
- 問題や変更要望の説明文

入力から調査対象の問題を特定できない場合は、調査を始めずに不足している情報を指摘して終了する（対話中なら質問してよい）。推測で問題を決めて調査しない。

## 調査の進め方

1. 入力から問題の主題とスコープを 1〜2 文で言語化する（レポートの `problem` になる）。
2. 引数の `file` と issue ID を受け取ったら、`file` と同じディレクトリに `pre-investigation-issue{issue ID}-report.json` を `{}` で初期化する。調査中はこのファイルを出力先として扱う。
3. 入力に含まれるパス・シンボル名・エラー文言を起点に、Grep / Glob / 部分 Read で関係ファイルを特定する。
3. 選んだ子スキルで問いを調べる。`how` では入口から結果までを追い、呼び出し先、データの変化、重要な分岐を記録する。配置や責務だけが対象なら、該当する構造を説明する。`why` では対象コードに加えて履歴・PR・文書などを確認し、理由が明記された証拠と解釈を分ける。コードの挙動だけから作者の意図を断定しない。
4. 制約を集める。技術的制約（型、依存ライブラリのバージョン、API 契約）、リポジトリの規約（lint 設定、CLAUDE.md や AGENTS.md、既存コメント）、ビジネス的制約（コメントやドキュメントに明記されたもの）を対象にする。
6. 既存パターンを集める。同種の処理が既にどう書かれているか、命名規則、エラーハンドリングやテストの流儀など、後続作業が従うべき前例を、実例のパス付きで記録する。
6. 調査結果を JSON に統合する。`why` の結果が変更作業に関係する場合は、維持すべきこと・変更可能なこと・避けるべきこと・リスクを `change_guidance` にまとめる。未解決の問いには、判断への影響と次の確認先を記す。

対象の問いに根拠付きで答えられ、残る不明点の影響と確認先を示せたら調査を終える。`why` を選んだ場合は情報源の網羅確認も完了させる。隣接領域の網羅を目的に探索を広げない。調査結果は、作成した `pre-investigation-issue{issue ID}-report.json` に valid な JSON として書き込む。

調査は子スキルを含めて読み取り専用とする。指定されたレポート保存先への書き込みだけを例外とし、それ以外のファイルの作成・変更・削除、ビルド、テスト実行、外部サービスへの書き込みは行わない。

## トークン節約のルール

- 挙動の根拠は `パス:行番号`、履歴の根拠はコミットハッシュとパス、外部情報は PR・issue・文書・発言などの URL で特定する。証拠には何が確認できたかを短く添え、リンクだけの一覧にしない。コード本体は貼らず、必要なシンボル名とシグネチャを載せる。
- `why.findings` は `direct | supported | inferred | speculative` を区別する。`direct` は理由を明記した一次資料、`supported` は複数の間接証拠が一致する判断、`inferred` は解釈、`speculative` は証拠の薄い仮説とする。解釈には推論の筋道を添える。結論が出ない問いは `open_questions` に残し、仮説で空欄を埋めない。
- `related_files` は関連度順に並べ、目安を 20 件とする。判断に必要なファイルは件数を超えても残し、参考程度の情報を省く。省いた件数と範囲は `meta.omitted` に記す。
- `related_files` は場所、`responsibilities` は責務、`how.flows` は処理順序、`why.findings` は理由を担当する。同じ説明を重複させず、根拠や項目の参照でつなぐ。
- `why.sources_consulted` には子スキルの 7 情報源カテゴリを記録する。利用可否や検索結果が異なる情報源は、同じカテゴリでも別項目にする。検索済みで結果なし・利用不可・対象外を区別し、検索語・対象・期間と結果または未検索理由を残す。`irrelevant` は対象外と判断できる具体的な根拠がある場合だけ使う。個々のツール呼び出しログは載せない。
- 値はすべて簡潔な文にする。箇条書きの連結や省略記号の多用で意味を欠落させない。

## 出力フォーマット

出力は次の構造に従う **単一の妥当な JSON** とする。保存先の指定があれば、生の JSON をそこへ書き、回答では保存先パスだけを報告する。指定がなければ、回答に JSON コードブロック 1 個だけを出力する。

以下はフィールド説明用のひな形であり、JSON Schema ではない。説明文は調査結果に置き換え、` | ` で示した選択肢は一つの値を選ぶ。配列の要素数は調査結果に合わせる。

```json
{
  "meta": {
    "schema_version": 2,
    "subject": "調査対象の一言表現",
    "generated_at": "ISO 8601 日時",
    "repo_root": "リポジトリルートの絶対パス（git リポジトリ外なら調査基点ディレクトリの絶対パス）",
    "git_ref": "調査時点のブランチ名とコミットハッシュ（git リポジトリ外なら null）",
    "investigations": [
      { "skill": "pstack:how | pstack:why", "question": "このスキルで解く問いと選択理由" }
    ],
    "omitted": "関連度が低く省略した情報の件数と概要（なければ null）"
  },
  "problem": {
    "summary": "問題の 1〜2 文の要約",
    "scope": "調査対象に含めた範囲と、意図的に外した範囲"
  },
  "related_files": [
    {
      "path": "repo_root からの相対パス",
      "relevance": "high | medium | low",
      "role": "このファイルが問題に対して持つ役割",
      "key_symbols": [
        { "name": "シンボル名", "kind": "function | class | type | const | config など", "location": "パス:行番号", "note": "シグネチャや責務の一言説明" }
      ]
    }
  ],
  "responsibilities": [
    {
      "component": "コンポーネント・モジュール名",
      "path": "代表パス",
      "responsibility": "現状の責務の説明",
      "collaborators": ["連携するコンポーネントやパス"]
    }
  ],
  "how": {
    "overview": "対象の役割と全体像。詳細は以下の項目で説明する",
    "key_concepts": [
      { "name": "主要な型・用語", "meaning": "この処理を理解するための定義", "evidence": "パス:行番号" }
    ],
    "flows": [
      {
        "trigger": "処理の起点となる入力やイベント",
        "steps": [
          { "location": "パス:行番号", "symbol": "シンボル名", "action": "入力から出力への変化、次の呼び出し先や重要な分岐条件" }
        ],
        "result": "呼び出し元に返す値、永続化、通知などの結果"
      }
    ],
    "gotchas": [
      { "description": "後続の変更で見落としやすい挙動や境界", "evidence": ["パス:行番号"] }
    ]
  },
  "why": {
    "findings": [
      {
        "id": "why-1",
        "decision": "調べた設計判断や閾値",
        "rationale": "根拠の確度に合った表現で示す理由やトレードオフ",
        "confidence": "direct | supported | inferred | speculative",
        "evidence": [
          { "source": "パス:行番号、コミットハッシュとパス、または URL", "supports": "この資料が実際に示すこと" }
        ],
        "reasoning": "間接証拠から理由を導いた筋道。直接の明記があれば null",
        "alternatives": [
          { "explanation": "競合する説明", "evidence_for": ["根拠とその内容"], "evidence_against_or_missing": ["反証または不足する証拠"] }
        ]
      }
    ],
    "sources_consulted": [
      {
        "category": "source_control | issue_tracker | documents | team_chat | observability | error_tracking | analytics",
        "source": "利用したツールまたは情報源。利用不可なら null",
        "status": "searched | no_results | unavailable | irrelevant",
        "scope": "検索語、対象パス・PR・チャンネル・期間など。未検索なら null",
        "result_or_reason": "得られた根拠の要約、結果なしの範囲、または未検索の理由"
      }
    ],
    "confidence_summary": "どこまで確かで、どこから判断に留保が必要か"
  },
  "constraints": [
    {
      "type": "technical | convention | business | dependency",
      "description": "制約の内容",
      "evidence": "根拠のパス:行番号。外部資料に基づく制約は、適用先のパス:行番号と資料の URL を併記"
    }
  ],
  "existing_patterns": [
    {
      "name": "パターンの短い名前",
      "description": "何をどう書くのが既存の流儀か",
      "examples": ["実例のパス:行番号"],
      "applies_to": "後続作業のどの部分がこのパターンに従うべきか"
    }
  ],
  "change_guidance": [
    {
      "action": "preserve | change | avoid | risk",
      "description": "調査結果から導く変更時の判断材料。実装済み・承認済みの計画ではない",
      "basis": ["why-1 または根拠のパス:行番号・URL"],
      "confidence": "direct | supported | inferred | speculative"
    }
  ],
  "open_questions": [
    "未解決の問い。後続判断への影響、調査済みの範囲と結果、次の具体的な確認先。why.sources_consulted に記録済みならその情報源を参照"
  ],
  "suggested_entry_points": [
    { "path": "パス:行番号", "reason": "後続作業をここから始めるべき理由" }
  ]
}
```

- 該当がない配列は `[]`、値を確定できない単一のフィールドは `null` とし、キーは省略しない。
- 未実行の `how` または `why` はオブジェクト全体を `null` にする。実行した場合は配下の全フィールドを持たせ、該当のない配列は空にする。`meta.investigations` は実行したスキルだけを列挙する。
- `how.flows[].steps` は実行順に並べる。`why.findings[].id` はレポート内で一意にし、`change_guidance[].basis` から参照できるようにする。`change_guidance` の確度は根拠より強くしない。
- 既存キーの名前と型を維持する。特に `open_questions` は文字列配列のままにし、既存の後続スキルからも読めるようにする。
- `relevance` は「後続の作業者がそのファイルを開く必要性」で判定する。変更が及ぶ可能性が高いものが `high`、読む必要はあるが変更しないものが `medium`、参考程度が `low`。

## 完了条件

次のすべてを満たした場合だけ完了とする。

- JSON をパースでき、ひな形の全キーと型、選択肢、項目参照が正しい。未実行の調査は指定どおり `null` になっている。
- `related_files`・`constraints`・`existing_patterns` の各項目に根拠または適用先のパスがある。外部資料に基づく制約には資料の URL もある。
- `how` を使った場合は対象の仕組みや責務を根拠付きで説明でき、後続が読むべき場所を特定できる。処理フローを調べた場合は入口・処理順序・結果を追える。
- `why` を使った場合は結論の確度と証拠が対応し、7 情報源カテゴリの検索結果または未検索理由がある。証拠の矛盾や競合する説明を隠していない。
- 未確定事項は `open_questions` にあり、後続判断への影響と次の確認先が分かる。推論や仮説を確定した制約として扱っていない。
- `file` と同じディレクトリに `pre-investigation-issue{issue ID}-report.json` が存在し、調査結果がそのファイルへ valid な JSON として書き込まれている。`{}` による初期化から結果の書き込みまでを完了している。
- 保存した JSON をパーサーで検証できる。
- 指定されたレポート保存先以外のファイルや外部サービスを変更していない。
