# 人に聞くのを、人にしか決められない判断だけに絞る

対象は、今の作業で人に聞こうとしている問いのすべてです。引数で渡された一覧、PR 本文や課題本文の確認事項、設計レビューの質問表、まだ書いていないが聞くつもりの問いを含みます。

## 手順

1. 問いを判断一覧に書き出す。1行に1つの判断を書く。1つの問いに判断が2つ以上入っていれば、行を分ける（例：「ここで直すか」と「元の課題を閉じるか」）。本番での実行（流す時期・承認）は、何をするかとは別の行にする。
2. 問いごとに、答えを導ける材料を次の順に当たる。
   - ソースコードと今の挙動
   - 仕様の正本（脳、docs）
   - 上流の決定（分割元の課題の設計、ほかの課題でもらった回答など、この作業の外で人が決めたもの）
   - 要求（REQ）

   導けたら「決めたこと」にし、根拠を `パス:行` か URL で書く。根拠は、その問いの答えを直接書いている箇所に限る。同じ項目の別の性質や、似た問いへの答えは、根拠に数えない。根拠を書けなければ、導けていない。
3. 導けなかった問いは、下の「人にしか決められない区分」に当たるかを見る。当たれば「要確認」にし、区分の名前と、当たったが答えが無かった材料を書く。当たらなければ「決めたこと」にする。区分に当たるかで迷ったら「要確認」にする。
4. 採用案（要確認では推奨案）は、次の優先順で選ぶ：安全 → 仕様の正本と今の挙動に合う → 範囲が最小 → 戻せる → 推奨案。選ばなかった案は「代替案」に書く。要確認の答えしだいで変わる決めたことは、根拠の欄にその要確認の番号を書く。
5. 判断でファイルを変えるときは、1つの判断を1つのコミットにし、判断一覧にコミットの SHA を書く。決めたことは、あとでそのコミットを revert すれば戻せる。
6. 人への確認のお願い（PR 本文の確認事項、課題のコメント、チャット）には「要確認」だけを載せる。要確認の問いは推奨案を添えて、「はい／いいえ」で答えられる形にする。同じ問いをほかの課題や PR ですでに聞いているときは、そのリンクを載せ、回答をそちらにまとめる。「決めたこと」は判断一覧に残すだけにし、「念のためご確認ください」の形でも確認のお願いには載せない。

完了の条件：判断一覧のすべての問いに「要確認」か「決めたこと」が付いている。決めたことには根拠（`パス:行`・URL）か、優先順のどの段で選んだかが書かれている。要確認には区分の名前と、当たった材料が書かれている。

## 人にしか決められない区分

導けない問いのうち、次のどれかに当たるものだけを「要確認」にします。

- 顧客への約束：データの廃棄について、顧客に何と説明するか
- お金・契約・法務：契約を解除したあとも、請求の台帳を残すか
- 本番を触ること・戻せないこと：本番でスクリプトを流す時期、本番データの削除
- 優先度・期限・チケットの分け方：環境単位の削除を、別のチケットにするか

## 判断一覧の形

「要確認」を先頭に並べます。作業の決まりで置き場所が決まっていればそこに、無ければ返信に書きます。
