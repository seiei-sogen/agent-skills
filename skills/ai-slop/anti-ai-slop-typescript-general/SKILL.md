# TypeScript 全般の AI Slop を取り除く

現在の TypeScript または JavaScript の差分を、契約を変えずに小さくし、処理を追いやすくする。

基本とするデータフローは次のとおりである。

```text
信頼できない入力 -> 境界で一度だけ検証 -> 正確な型 -> 直接的なビジネスロジック
```

## 1. レビュー対象を確定する

1. リポジトリの指示と現在の差分全体を読む。
2. 変更された `.ts`、`.tsx`、`.js`、`.jsx` ファイルをすべて列挙する。
3. 変更された関数、その呼び出し元、入力を定義する型やスキーマを読む。
4. 変更箇所が受け取る入力を、信頼できない境界値または型付け済みの内部データに分類する。

変更箇所の入力と、追加されたガード、ヘルパー、フォールバック、型アサーション、抽象化をすべて分類できたら、この手順は完了である。

## 2. 該当するルールだけを読む

差分に該当する分岐のリファレンスをすべて読む。該当しないリファレンスは読まない。

- 型注釈、`unknown`、`any`、`Record`、`Partial`、型アサーション、実行時ガード、バリデーション、型変換、オプショナルな値、キューのペイロード、HTTP 入力、データベースのドキュメントを変更している場合は、[types-and-boundaries.md](references/types-and-boundaries.md) を読む。
- ヘルパー、ラッパー、DTO、マッパー、インターフェース、レイヤー、ジェネリクス、ファクトリー、コールバック、Promise のラッパー、クラス、共通ユーティリティを変更している場合は、[abstractions.md](references/abstractions.md) を読む。
- 真偽値の分岐、ネストした条件、三項演算子、中間変数、`try/catch`、エラーのラップ、ログ、コメント、暗黙のフォールバックを変更している場合は、[control-flow-and-errors.md](references/control-flow-and-errors.md) を読む。
- 手書きの型チェック、型ガード、フォームバリデーション、3つ以上の判定を含む `if` 条件を変更している場合は、[ai-slop-type-check-condition-fixer](../ai-slop-type-check-condition-fixer/SKILL.md) も適用する。

## 3. 優先順位に従って簡潔にする

候補ごとに、最初に該当する修正を採用する。

1. 入力元の型を正すか、実際の信頼境界で一度だけ検証する。
2. 既存のスキーマ、プラットフォーム機能、標準ライブラリ、プロジェクト内の仕組みを再利用する。
3. 重複したチェック、フォールバック、変換、レイヤー、データ表現を削除する。
4. 単純で1か所からしか使われないヘルパーや、処理をそのまま渡すだけのラッパーをインライン化する。
5. 広すぎる汎用処理を、具体的なドメイン処理へ置き換える。
6. 実際に起こり得る状態を扱う防御処理は残す。

型が広すぎる値や不確かな値は、呼び出し先を修正する前に入力元までたどる。各呼び出し先へガードを追加するより、原因を1か所で直す。

挙動を保ち、次のコストのどれかを、ほかのコストを増やさずに減らせる場合だけ修正する。

- 読み手が理解する必要のある概念の数。
- 通過するレイヤーやデータ表現の数。
- 分岐と可変状態の数。
- 契約を表現するために必要なコード量。

## 4. 本当に必要な境界処理を守る

不正な外部入力、外部 API の失敗、データベース上の対象不在、永続化された nullable フィールド、キューや JSON の解析失敗、認可、セキュリティ検査、外部ライブラリの仕様として存在する不確実性に対する検証とエラー処理は残す。

業務上の挙動、公開 API、イベント名、永続化形式、正当な null 許容性、エラーの意味を変えない。

## 5. 結果を検証する

1. 差分全体を読み直し、手順1で挙げたすべての候補について判断済みであることを確認する。
2. リポジトリで利用できる formatter、lint、型チェック、関連テストを実行する。
3. 信頼できないデータが一度だけ検証され、内部値が正確な型を保ち、削除した抽象化の呼び出し元が残っていないことを確認する。
4. 最終差分が作業開始時より簡潔で、無関係な修正を含まないことを確認する。

簡潔にした箇所、意図的に残した防御処理、実行した検証コマンドとその結果を報告する。
