# 概要

`origin/main` を現在のブランチにマージして、GitHub の PR で発生している競合を解消する。

## 手順

### 1. フェッチし、`zdiff3` 形式でマージする

```sh
git fetch origin main
git -c merge.conflictstyle=zdiff3 merge origin/main
```

### 2. 競合がある場合は、未解消のままコミットする

マージで競合が発生した場合は、**先に競合を解消せず、競合マーカーをそのままコミットする**。
これにより、解消前の競合状態が、解消内容とは別の専用コミットに記録される。

```sh
git add -A
git commit -m "merge origin/main (conflicts unresolved)"
```

### 3. 競合を解消する

未解消の状態をコミットした後、次を行う。

1. 競合した各ファイルを読み、競合の両側の内容を理解する。
2. **コードファイル**の競合を解消する（競合マーカーを削除し、正しいコードを選ぶ）。
3. **生成ファイル**（ゴールデンフィクスチャ、生成されたパーサーなど）で競合が発生した場合は、ジェネレーターを再実行して**再生成**し、新たな出力をコミットする。
   競合マーカーを手作業で解消したり、対応を先送りしたりしない（後述の「生成ファイル」を参照）。
4. 解消結果をステージし、コミットする。

```sh
git add -A
git commit -m "resolve merge conflicts"
```

### 4. 簡易確認として `mise run test` を実行する

CI では clippy とフォーマットが適用されるため、ここでは簡易確認で十分である。

## 重要事項

- 競合マーカーにマージベースを表示し、`zdiff3` によってノイズを減らすため、必ず `-c merge.conflictstyle=zdiff3` を使う。
- 必ず未解消の競合を先にコミットし、その後、解消結果を別のコミットにする。
  これにより、競合時の状態と解消内容を明確に記録できる。
- この2つのコミットを `squash` して1つにまとめてはならない。

## 生成ファイル

- **ゴールデンファイルまたは生成ファイルで競合が発生した場合は、必ず再生成してコミットする。**
  ジェネレーターを再実行し（競合マーカーを手作業で解消しない）、その出力をコミットする。
  競合したファイルをスキップしたり、`on-task-done` や CI に先送りしたりしない。
- **競合がない場合は、タスクの明示的な指示に従って再生成の要否を判断する。**
  再生成が常に必要とは限らない。
  「常に再生成する」「CI が処理する」といった一般的な方針を、依頼内容より優先してはならない。
- **生成結果を黙って破棄してはならない**（例：作業ツリーをクリーンにしたり、フックの警告を消したりするために `git restore` を実行すること）。
  コミットするか、ユーザーに確認する。
  ユーザーに確認せず生成結果を破棄することは、常に誤りである。
